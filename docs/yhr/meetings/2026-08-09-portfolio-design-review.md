## 무엇을 만드나

여러 증권사 계좌를 한데 모아 **6개 화면**으로 보여준다.

| 화면 | 답하는 질문 |
|---|---|
| 요약 | 지금 내 자산 상태는? |
| 종목별 | 뭘 얼마나 갖고, 각각 얼마 벌었나? |
| 비중 분석 | 내 돈이 어디에 쏠려 있나? |
| 계좌별 | 어느 기관·계좌유형에 뭐가 있나? |
| 실현손익 | 이번 달·올해 확정한 손익은? |
| 자산 변화 | 는 게 벌어서인가, 넣어서인가? |

EOD 일배치 + 수동 새로고침. 실시간이 아니다.

# 합의 안건 8건

각 항목은 독립적으로 읽을 수 있게 썼다. 설계 스펙을 읽지 않아도 판단할 수 있다.

## 1. 현금흐름에서 매매대금을 걸러낼 수 있는가 `데이터`

**배경.** 자산 변화 화면은 "자산이 는 게 벌어서인가 넣어서인가"에 답한다. 계산은 자산 증감에서 내가 넣고 뺀 돈을 걷어내는 방식이다.

그런데 증권사 입출금내역 API는 **매수대금 출금과 매도대금 입금을 같은 응답에 담아 준다.** 이게 그대로 "입금"으로 들어오면 이런 일이 생긴다.

```
1,000만원어치 매도  →  주식 −1,000만, 예수금 +1,000만  →  자산 증감 ≈ 0
계산: 0 − (입금 1,000만) = −1,000만원 손실
```

**한 번 팔았다는 이유만으로 1,000만원 손실이 표시된다.**

**결정할 것.** 매매대금·예수금 내부이동(RP·CMA 자동매수/환매)·환전·매매수수료를 제외한 현금흐름만 제공할 수 있는가.

**판단 기준.** 기관별 응답에 매매대금을 식별할 필드가 있는가. 없다면 체결내역과 대조해 걸러낼 수 있는가. 기관마다 응답이 다른 것을 흡수하는 작업이므로 데이터 쪽에서 처리하는 것이 경계에 맞는다.

**제안.** 데이터가 배제한 결과만 제공한다. 응답 필드로 식별이 안 되면 체결내역과 대조해 제거한다.

**트레이드오프.** 기관을 추가할 때마다 배제 규칙을 다시 검증해야 하고, 그 부담이 전부 데이터 쪽에 쌓인다. 더 아픈 건 대조 방식일 때다 — 체결내역이 없는 계좌는 대조할 대상이 없어 배제가 불완전해지는데, **하필 그 계좌가 자산 변화 화면이 가장 필요한 계좌**다. 백엔드가 배제하는 대안을 포기하는 대신 기관별 분기가 백엔드로 들어오지 않지만, 배제 누락을 백엔드가 발견해도 고치는 건 데이터 쪽이라 왕복이 생긴다.

**막히면.** 자산 변화 화면이 통째로 무의미해진다. 이 화면은 거래내역 조회가 막힌 연금계좌에서 손익을 알 수 있는 유일한 경로라 대체재가 없다.

## 2. "기업행위 없음"과 "데이터 못 구함"을 구분할 수 있는가 `데이터`

**배경.** 실현손익을 계산하려면 액면분할 같은 기업행위를 반영해야 한다.

```
10주를 100원에 매수  →  2:1 분할  →  실제로는 20주 50원
거래내역에는 "매수 10주 @100"만 남음  →  보정 없으면 손익이 부호까지 틀어짐
```

문제는 기업행위 테이블에 **행이 없을 때** 그게 "이 종목엔 기업행위가 없었다"인지 "데이터를 못 구했다"인지 알 방법이 없다는 것이다.

**결정할 것.** 커버리지를 별도로 제공할 수 있는가 — 어느 기간·어느 시장의 기업행위를 확보했는지. ETF 구성종목도 같은 문제라 함께 필요하다.

```
ca_coverage   (시장 또는 종목, 커버 시작일, 커버 종료일)
etf_coverage  (ETF, 확보 | 미확보, 기준일)
```

**판단 기준.** 수집 파이프라인이 "무엇을 수집했는지"를 기록하는가. 기록만 노출하면 되는 일인지, 새로 만들어야 하는 일인지.

**제안.** 두 커버리지 테이블을 데이터가 제공한다.

**트레이드오프.** 수집 파이프라인이 "무엇을 수집했는지"를 별도로 기록해야 한다 — 지금 없다면 신규 작업이다. 그리고 **경고의 정확도는 커버리지의 정밀도까지만** 올라간다. 시장 단위로 주면 개별 종목의 예외를 못 잡는다. 커버리지를 아예 두지 않는 선택지도 있는데, 그러면 기업행위 경고 기능 자체를 포기하고 사용자가 틀린 손익을 그대로 믿게 된다.

**막히면.** 원천이 미확보일 때 모든 종목이 "기업행위 없음"으로 보여 경고가 **하나도 뜨지 않는다.** 틀린 실현손익이 "신뢰" 배지를 달고 나간다. 조용히 틀리는 것이 가장 나쁘다.

## 3. ETF 구성비중을 한 겹으로 펼쳐 줄 수 있는가 `데이터`

**배경.** ETF를 구성종목으로 풀어 "실제로 어떤 종목에 얼마나 노출됐나"를 계산한다. 이 작업에는 세 가지가 들어간다.

- ETF가 다른 ETF를 담고 있으면 **재귀로 풀기** (순환 참조 차단 포함)
- 국내 6자리 코드와 미국 티커를 **같은 종목으로 매칭**
- 운용사 파일 포맷이 바뀌면 **따라가기**

셋 다 무겁고 자주 바뀐다.

**결정할 것.** `ETF → 최종 종목 → 최종 비중` 한 겹 표로 제공할 수 있는가. 중첩·순환·매칭이 이미 처리된 상태로.

**판단 기준.** 구성종목 수집과 종목 마스터를 이미 데이터 쪽이 소유한다. 매칭 실패가 늘어나면 고치는 것도 데이터 쪽이라, 백엔드가 처리하면 발견과 수정이 팀을 건너다닌다. 반대로 데이터 쪽 부담이 얼마나 늘어나는지가 반대편 근거다.

**제안.** 데이터가 평탄화까지 처리해 한 겹으로 준다.

**트레이드오프.** 재귀·순환 차단·종목 매칭 로직이 전부 데이터 쪽으로 들어간다. 그리고 백엔드가 "왜 이 종목이 안 나오지"를 조사할 때 **자기 코드에 답이 없어 데이터 쪽 로직을 봐야 한다.** 백엔드가 평탄화 결과를 검증할 수단은 총합 보존 하나뿐이라, 비중이 잘못 배분돼도 합계만 맞으면 통과한다.

**막히면.** 백엔드가 재귀와 매칭을 떠안고, 원천 포맷이 바뀔 때마다 백엔드 배포가 필요해진다.

## 4. 체결 식별자가 재수집해도 같은 값인가 `데이터`

**배경.** 실현손익은 **매도 체결 1건마다 한 행**을 만든다. 기업행위가 늦게 도착하거나 과거 체결이 뒤늦게 들어오면 다시 계산하는데, 같은 체결이 같은 키를 가져야 덮어쓰기가 된다.

**결정할 것.** `trade_id`가 재수집·재처리에도 같은 체결에 같은 값을 갖는가.

**판단 기준.** 원천이 체결 고유 ID를 주는가. 안 준다면 무엇으로 합성하는가. `(계좌, 종목, 체결일시, 수량, 가격)` 해시는 위험하다 — 같은 조건의 분할 체결이 하나로 뭉치거나, 정정 체결에서 값이 갈린다. 합성한다면 규칙을 문서로 고정해야 한다.

**제안.** 원천 고유 ID를 우선 쓰고, 없으면 데이터가 합성 규칙을 문서로 고정한다.

**트레이드오프.** 규칙을 고정하면 나중에 개선하기 어렵다 — 정정 체결 처리를 바꾸는 순간 키가 달라져 **과거 실현손익이 전부 재생성**된다. 백엔드가 자체 키를 만드는 대안을 포기하는데, 그건 데이터가 재수집했을 때 같은 체결을 알아볼 방법이 없어서다.

**막히면.** 재수집마다 새 행이 생겨 **실현손익이 중복 합산된다.** 사용자가 알아채기 어려운 종류의 오류다.

## 5. 정규화 테이블 네 개의 컬럼을 확정할 수 있는가 `데이터`

**배경.** 백엔드는 기관별 응답 차이가 흡수된 공통 테이블을 읽어 도메인 계산(평단·손익·등급 판정)을 한다.

```
cln_balance    잔고 — 종목·수량·평단·평가금액·통화
cln_deposit    예수금 — 계좌·통화·금액
cln_trade      체결 — 매수/매도·수량·가격·수수료·세금·체결일시
cln_cashflow   입출금 — 유형·금액·일시   (안건 1의 배제 규칙 적용)
```

**결정할 것.** 네 테이블의 컬럼. 그리고 **조회 기간 한계**를 함께 알려줄 것.

**판단 기준.** 조회 기간 한계는 단순 참고가 아니라 계산에 직접 들어간다 — "거래내역이 언제부터 있는가"가 그 종목의 실현손익을 믿을 수 있는지를 결정한다(안건 2와 연결).

**제안.** 최소 필드로 확정하고 이후 추가는 마이그레이션으로 처리한다.

**트레이드오프.** 나중에 필요한 필드가 드러나면 데이터와 백엔드가 **같이 배포해야 한다.** 반대로 넉넉하게 잡으면 쓰지 않는 컬럼이 남아 스키마가 무엇을 보장하는지 흐려진다. 확정을 미루는 선택지는 사실상 없다 — 백엔드 첫 단계가 이 테이블을 읽는다.

**막히면.** 백엔드가 첫 단계(스냅샷 생성)를 시작할 수 없다.

## 6. 수집과 계산의 순서를 테이블 하나로 맞출 수 있는가 `데이터`

**배경.** 증권사 호출은 데이터가 하고, 그 결과로 스냅샷을 만드는 것은 백엔드가 한다. 두 가지가 필요하다.

- 백엔드는 수집이 **끝난 뒤에** 돌아야 하는데 끝났는지 알 방법
- 사용자가 새로고침을 누르면 백엔드가 **수집을 요청**할 방법

**결정할 것.** 테이블 하나로 양방향을 처리하는 데 동의하는가.

```
백엔드가 요청 행 삽입  →  데이터 잡이 집어감  →  완료 기록  →  백엔드가 읽고 다음 단계
```

**판단 기준.** 큐 인프라를 도입할지, 테이블 하나로 끝낼지. 계좌 단위 독립 실행, 부분 실패, 재시도가 표현돼야 한다. 3인 팀 규모에서 큐 운영 부담이 값어치를 하는지가 판단점이다.

**제안.** 테이블 하나로 처리하고 큐는 도입하지 않는다.

**트레이드오프.** 큐가 공짜로 주는 것들을 직접 만들어야 한다 — 재시도, 타임아웃, 죽은 잡이 남긴 요청 행 정리. 그리고 **폴링 주기만큼 지연이 생겨** 수동 새로고침이 즉시 시작되지 않을 수 있다. 대신 운영할 인프라가 하나 늘지 않고, 상태를 SQL로 바로 조회할 수 있다.

**막히면.** 수집과 계산의 순서가 시간 기반 추정("데이터 배치가 16시에 끝나니 백엔드는 16시 30분")이 되어 실패에 취약해진다.

## 7. 자격증명을 시크릿 매니저에 둘 수 있는가 `인프라`

**배경.** KIS는 사용자 앱키로, CODEF는 Connected ID로 계좌에 접근한다. 이 값들의 소유는 백엔드다 — 계좌 연동 화면이 백엔드 소관이라 등록도 백엔드가 받는다. 그런데 **실제로 증권사를 호출하는 건 데이터 잡**이다.

**결정할 것.** 자격증명을 시크릿 매니저에 두고 테이블에는 참조만 저장하는 데 동의하는가. 데이터 잡은 수집 요청에 실린 단기 참조로 접근한다.

**판단 기준.** 대안은 데이터 잡이 백엔드 소유 테이블을 직접 읽는 것이다. 그러면 팀 경계가 흐려지고 접근 범위가 넓어진다. 반대로 시크릿 매니저를 도입하면 운영 요소가 하나 늘어난다.

**제안.** 시크릿 매니저에 보관하고 수집 요청에 단기 참조를 실어 전달한다.

**트레이드오프.** 운영 요소가 하나 늘고 권한 설정·로테이션이 따라온다. **시크릿 매니저가 죽으면 수집 전체가 멈춘다.** 로컬 개발에서도 붙여야 해서 개발 편의가 떨어진다. 테이블 직접 접근이라는 단순한 길을 포기하는 대신, 자격증명 접근 범위를 좁게 유지한다.

**막히면.** 자격증명 접근 경로가 구현 시점에 임의로 정해진다. 민감정보라 나중에 되돌리기 비싸다.

## 8. 국내 ETF 구성종목을 확보할 것인가 `팀 공통`

**배경.** ETF 분해는 비중 분석 화면의 핵심이다. 미국 ETF는 운용사가 구성종목 파일을 정적 URL로 공개해 수집이 된다.

**국내는 막혀 있다.** KRX가 자바스크립트 기반 봇차단을 걸어 순수 코드 수집이 통과하지 못하고, 약관상 자동 호출도 제한된다. 브라우저로는 되지만 코드로는 안 된다.

**현재 설계 스펙은 확보를 전제로 썼다.** 이 안건이 다른 것과 성격이 다른 이유다 — 나머지는 방법의 문제지만 이건 **기능 하나가 성립하느냐**의 문제다.

**결정할 것.** 넷 중 하나.

| 선택 | 감수하는 것 |
|---|---|
| 헤드리스 브라우저 수집 | UI 변경에 취약, 약관 위험 잔존 |
| 운용사 파일 직접 파싱 | 운용사마다 포맷이 달라 유지보수 부담 |
| 유료 벤더 | 비용 |
| **범위 축소** — 미국 ETF만 분해 | 국내 ETF 보유자에게 비중 분석이 반쪽 |

**판단 기준.** 실질적으로는 **사용자의 국내 ETF 비중이 얼마나 되는가**가 근거다. 국내 ETF를 거의 안 들고 있으면 범위 축소가 합리적이고, 상당 부분이면 수집 방법을 감수할 값어치가 있다.

**제안.** **1차는 미국 ETF만 분해하고 국내는 미분해로 표시한다.** 운용사 파일 파싱은 후속으로 검토한다.

헤드리스는 유지보수 부채가 크고 약관 위험이 상업화 시점에 발효된다. 반면 미분해 경로는 **이미 설계에 있다** — 미확보 ETF는 전개하지 않고 그대로 두면서 "이만큼은 분해되지 않았다"를 금액과 함께 알린다. 1차 목적(설계 검증·개인 사용)에는 그 정보로 충분하다.

**트레이드오프.** 국내 상장 ETF를 들고 있으면 그만큼 섹터·시장 비중이 비어 보인다. `TIGER 미국나스닥100` 같은 종목은 국내로만 잡히고 실제 미국 익스포저가 안 드러난다. **"실제로 어디에 노출됐나"라는 기능의 절반이 국내에서 동작하지 않는다.** 국내 ETF 비중이 큰 사용자에게는 비중 분석의 값어치가 크게 떨어진다.

**막히면.** 미분해 경로가 이미 설계에 있어 동작은 하지만, 스펙이 "확보 전제"로 쓰인 문구를 미분해 중심으로 고쳐야 한다.

# 배경 — 핵심 설계 6가지

안건을 이해하는 데 필요하지 않다. 설계 방향을 알고 싶을 때 읽으면 된다.

## 1. 저장은 한 종류, 화면은 묶는 기준만 바꾼다

```
position_line  ── 한 행 = (날짜, 계좌, 종목)
```

이 행 집합 하나에서 묶는 기준을 바꾸면 화면이 나온다. 종목으로 묶으면 종목별, 섹터로 묶으면 비중 분석, 안 묶으면 요약.

축을 늘리는 일이 **컬럼 이름 한 줄**이라, "레버리지 비중"처럼 나중에 붙는 요구가 싸게 들어온다.

## 2. 금액만 저장하고 비율은 나중에 계산한다

수익률·비중 컬럼을 **스키마에 만들지 않는다.** 비율은 더할 수 없어서 저장해두면 묶는 기준이 바뀔 때마다 틀린다. 자리가 없으면 잘못 더할 방법도 없다.

## 3. 원장을 셋으로 나눈다 — 리스크 격리

| 원장 | 확보 | 쓰는 화면 |
|---|---|---|
| 보유 스냅샷 | **항상** — 잔고가 진실 | 요약 · 종목별 · 비중 · 계좌별 |
| 현금흐름 | 대체로 | 자산 변화 |
| 거래내역 | **구간별로 불완전** | 실현손익 |

**6개 중 4개가 항상 믿을 수 있는 데이터만 쓴다.** 최대 약점인 "거래내역이 불완전하다"가 제품 전체로 번지지 않고 실현손익 한 화면에 갇힌다.

## 4. 자산 변화 뷰는 거래내역 없이도 정확하다

```
투자손익 = 자산 증감 − 넣은 돈 − 배당 + 수수료
```

우변에 거래내역이 없다. 체결내역 조회가 막힌 연금계좌도 "얼마 벌었나"에 정확히 답한다.

이 화면의 존재 이유는 **자산은 늘었는데 손실인 상황**이다. 다른 화면으로는 드러나지 않는다.

> 자산이 200만원 늘었지만 350만원을 넣고 150만원을 잃었어요

## 5. 신뢰도를 감이 아니라 계산으로 판정한다

```
opening_qty = 잔고 수량 − 확보구간 매수 + 확보구간 매도
```

0이면 그 구간이 포지션 전체라 실현손익을 믿을 수 있다. 0보다 크면 앞부분이 없어 추정값이며 "추정" 배지를 단다. 조회 기간 한계 때문에 상당수 계좌가 여기 해당할 것이라, 숨기지 않고 표시하되 구분한다.

## 6. 동기화가 실패해도 그날 데이터를 만든다

직전 성공분을 이월하고 "07-26 기준입니다"라고 알린다. 빼면 총자산이 급락해 손실처럼 보이므로, 포함하되 낡았다고 말하는 쪽이 안전하다.

## 곁가지 — ETF 분해의 한계

분해하면 **평단과 수익률은 정의가 성립하지 않는다.** ETF를 산 시점의 구성비중을 알 수 없고 보유 중에도 계속 바뀌기 때문이다. 분해 화면에는 평가금액·비중·환산수량만 남는다.

# 역할 분담

경계는 **"기관 고유성이 사라지는 지점"**이다. 기관마다 다른 응답을 공통 모양으로 만드는 것까지가 데이터, 거기에 도메인 규칙을 얹는 것이 백엔드.

| 영역 | 데이터 | 백엔드 |
|---|---|---|
| 수집 | 잔고·거래·입출금·구성종목·환율 | — |
| 마스터 | 종목 마스터, ETF 구성비중 평탄화 | 조인만 |
| 도메인 계산 | — | 평단·기업행위 보정·등급 판정·실현손익 |
| 조회 | — | ETF 분해 · 집계 · 응답 조립 |
| 연동 | — | 계좌 연동·재인증·동기화 오케스트레이션 |

ETF 분해는 두 팀에 걸친다. **중첩을 펼쳐 한 겹으로 만드는 것까지가 데이터**, 그 비중으로 사용자 보유분을 나누는 것이 백엔드다.

### 소유 테이블

| 데이터 | 백엔드 |
|---|---|
| `raw_*` · `cln_balance` · `cln_deposit` · `cln_trade` · `cln_cashflow` | `account` |
| `instrument` · `etf_constituent` · `fx_rate` · `corporate_action` | `position_line` |
| `ca_coverage` · `etf_coverage` · `collection_run` | `position_basis` · `realized_pnl_line` · `sync_run` |

# 검증되지 않은 가정 3가지

설계가 "데이터가 이렇게 준다"를 전제하는데 아직 실측이 없다. 구현 초기에 깨질 수 있어 미리 공유한다.

| 가정 | 깨지면 |
|---|---|
| 신뢰도 역산이 실제 KIS 체결내역으로 동작 | 등급 판정 방식 재설계 |
| CODEF 입출금내역에서 매매대금 식별 가능 | 안건 1이 성립하지 않아 자산 변화 화면 재설계 |
| 잔고 평단의 수수료 포함 여부가 증권사마다 다름 | 미실현·실현 원가를 나눈 근거가 약해짐 |
