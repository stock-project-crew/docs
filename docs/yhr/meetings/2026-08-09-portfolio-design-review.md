## 무엇을 만드나

여러 증권사 계좌를 한데 모아 **6개 화면**으로 보여준다.

| 화면 | 답하는 질문 |
|---|---|
| 요약 | 지금 내 자산 상태는? |
| 종목별 | 뭘 얼마나 갖고, 각각 얼마 벌었나? |
| 비중 분석 | 내 돈이 어디에 쏠려 있나? |
| 계좌별 | 어느 기관·계좌유형에 뭐가 있나? |
| 실현손익 | 이번 달·올해 확정한 손익은? |
| 자산 변화 | 는 게 벌어서인가, 넣어서인가? |

EOD 일배치 + 수동 새로고침. 실시간이 아니다.

## 핵심 설계 6가지

### 1. 저장은 한 종류, 화면은 묶는 기준만 바꾼다

```
position_line  ── 한 행 = (날짜, 계좌, 종목)
```

이 행 집합 하나에서 묶는 기준을 바꾸면 화면이 나온다. 종목으로 묶으면 종목별, 섹터로 묶으면 비중 분석, 안 묶으면 요약.

축을 늘리는 일이 **컬럼 이름 한 줄**이라, "레버리지 비중"처럼 나중에 붙는 요구가 싸게 들어온다.

### 2. 금액만 저장하고 비율은 나중에 계산한다

수익률·비중 컬럼을 **스키마에 만들지 않는다.** 비율은 더할 수 없어서, 저장해두면 묶는 기준이 바뀔 때마다 틀린다. 자리가 없으면 잘못 더할 방법도 없다.

### 3. 원장을 셋으로 나눈다 — 리스크 격리

| 원장 | 확보 | 쓰는 화면 |
|---|---|---|
| 보유 스냅샷 | **항상** — 잔고가 진실 | 요약 · 종목별 · 비중 · 계좌별 |
| 현금흐름 | 대체로 | 자산 변화 |
| 거래내역 | **구간별로 불완전** | 실현손익 |

**6개 중 4개가 항상 믿을 수 있는 데이터만 쓴다.** 이 프로젝트 최대 약점인 "거래내역이 불완전하다"가 제품 전체로 번지지 않고 실현손익 한 화면에 갇힌다.

### 4. 자산 변화 뷰는 거래내역 없이도 정확하다

```
투자손익 = 자산 증감 − 넣은 돈 − 배당 + 수수료
```

우변에 거래내역이 없다. **체결내역 조회가 막힌 연금계좌도 "얼마 벌었나"에 정확히 답한다.** 거래내역은 그걸 실현/미실현으로 쪼갤 때만 필요하다.

이 화면의 존재 이유는 **자산은 늘었는데 손실인 상황**이다. 다른 화면으로는 드러나지 않는다.

> 자산이 200만원 늘었지만 350만원을 넣고 150만원을 잃었어요

### 5. 신뢰도를 감이 아니라 계산으로 판정한다

```
opening_qty = 잔고 수량 − 확보구간 매수 + 확보구간 매도
```

0이면 그 구간이 포지션 전체라 실현손익을 믿을 수 있다. 0보다 크면 앞부분이 없어 추정값이며 "추정" 배지를 단다.

조회 기간 한계 때문에 **상당수 계좌가 추정에 해당할 것**이라, 숨기지 않고 표시하되 구분한다.

### 6. 동기화가 실패해도 그날 데이터를 만든다

직전 성공분을 이월하고 "07-26 기준입니다"라고 알린다. 빼면 총자산이 급락해 손실처럼 보이므로, **포함하되 낡았다고 말하는 쪽**이 안전하다.

### 곁가지 — ETF 분해

ETF를 구성종목으로 풀어 실제 익스포저를 본다. 다만 **평단과 수익률은 분해하면 정의가 성립하지 않는다** — ETF를 산 시점의 구성비중을 알 수 없고 보유 중에도 계속 바뀌기 때문이다. 분해 화면에는 평가금액·비중·환산수량만 남는다.

## 역할 분담

경계는 **"기관 고유성이 사라지는 지점"**이다. 기관마다 다른 응답을 공통 모양으로 만드는 것까지가 데이터, 거기에 도메인 규칙을 얹는 것이 백엔드.

| 영역 | 데이터 | 백엔드 |
|---|---|---|
| 수집 | 잔고·거래·입출금·구성종목·환율 | — |
| 마스터 | 종목 마스터, ETF 구성비중 평탄화 | 조인만 |
| 도메인 계산 | — | 평단·기업행위 보정·등급 판정·실현손익 |
| 조회 | — | 분해 · 집계 · 응답 조립 |
| 연동 | — | 계좌 연동·재인증·동기화 오케스트레이션 |

ETF 분해는 두 팀에 걸친다. **중첩 ETF를 펼쳐 한 겹으로 만드는 것까지가 데이터**, 그 비중으로 사용자 보유분을 나누는 것이 백엔드다.

### 소유 테이블

| 데이터 | 백엔드 |
|---|---|
| `raw_*` · `cln_balance` · `cln_deposit` · `cln_trade` · `cln_cashflow` | `account` |
| `instrument` · `etf_constituent` · `fx_rate` · `corporate_action` | `position_line` |
| `ca_coverage` · `etf_coverage` · `collection_run` | `position_basis` · `realized_pnl_line` · `sync_run` |

## 합의 요청 상세

### 전대홍 (데이터)

**① 현금흐름 배제** — 증권사 입출금내역은 매수대금 출금·매도대금 입금을 같은 응답에 담아 준다. 이게 그대로 들어오면 1,000만원어치 매도 한 번에 1,000만원 손실이 표시된다. 매매대금·예수금 내부이동(RP·CMA)·환전·매매수수료를 걸러낸 결과만 필요하다.

**② 커버리지 2종** — 행이 없다는 사실만으로는 "기업행위가 없었다"인지 "데이터를 못 구했다"인지 알 수 없다. 구분 못 하면 원천 미확보 시 경고가 하나도 안 뜨고 틀린 손익이 그대로 나간다.

```
ca_coverage   (시장 또는 종목, 커버 시작, 커버 끝)
etf_coverage  (ETF, COVERED | UNAVAILABLE, 기준일)
```

**③ ETF 구성비중 평탄화** — `ETF → 최종 종목 → 최종 비중` 한 겹으로. 중첩 ETF 재귀·순환 차단·종목번호 매칭까지 포함. 그러면 백엔드는 곱셈 한 번으로 끝난다.

**④ `trade_id` 안정성** — 같은 체결은 재수집·재처리해도 같은 값이어야 한다. 원천이 고유 ID를 안 주면 합성 규칙을 문서화하고 고정. 보장이 없으면 재수집마다 새 행이 생겨 실현손익이 중복된다.

**⑤ `cln_*` 스키마** — 네 테이블의 컬럼 확정. 조회 기간 한계도 함께 알려주면 신뢰도 등급 판정에 반영한다.

**⑥ `collection_run`** — 수집 트리거와 완료 신호를 한 테이블로. 백엔드가 요청 행을 넣으면 데이터 잡이 집어가고, 완료를 기록하면 백엔드가 읽어 다음 단계를 돈다. 큐 없이 양방향이 된다.

### 황해정 (인프라)

**⑦ 시크릿 매니저** — KIS 앱키와 CODEF Connected ID를 시크릿 매니저에 두고 테이블에는 참조만 저장. 데이터 잡이 수집할 때 단기 참조를 넘겨받는 구조. 지금 설계는 데이터 잡이 백엔드 테이블을 직접 읽지 않는 것을 전제한다.

### 팀 공통

**⑧ 국내 ETF 구성종목** — 현재 스펙은 **확보를 전제로** 설계했다. 미확보 시 비중 분석의 분해 기능이 국내 ETF에 대해 동작하지 않는다. 헤드리스 수집 / 운용사 파일 파싱 / 유료 벤더 중 무엇을 감수할지, 아니면 미국 ETF만 지원할지 결정이 필요하다.

## 검증되지 않은 가정 3가지

설계가 "데이터가 이렇게 준다"를 전제하는데 아직 실측이 없다. 구현 초기에 깨질 수 있어 미리 공유한다.

| 가정 | 깨지면 |
|---|---|
| 신뢰도 역산이 실제 KIS 체결내역으로 동작 | 등급 판정 방식 재설계 |
| CODEF 입출금내역에서 매매대금 식별 가능 | 자산 변화 뷰의 정확성 전제가 무너짐 |
| 잔고 평단의 수수료 포함 여부가 증권사마다 다름 | 미실현·실현 원가를 나눈 근거가 약해짐 |
