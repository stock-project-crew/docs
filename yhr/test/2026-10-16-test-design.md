## 1. 방법

통합테스트는 두 기능의 모든 기능과 분기를 한 번 이상 지난다. 시나리오가 경로를 덮고, 케이스가 분기를 덮는다.

| 출처 | 뽑는 것 | 전수 기준 |
|---|---|---|
| 와이어플로우 두 개 · 앱 정보 구조 §2 ~ §5 · 화면 · API 설계 | **시나리오** — 화면 사이의 경로 | 모든 화면과 모든 전이(§2)를 시나리오가 한 번 이상 지난다. 화면 상태(포트폴리오 §10 · 알림 §15)는 그 화면을 지나는 시나리오의 변형으로 붙는다 |
| 시나리오의 단계 · 상태 변형, 스펙의 나열(§4) | **케이스** — 분기 | 시나리오의 단계 · 상태 변형마다 한 건 이상. 스펙에 나열된 값 · 조건마다 한 건 |

- 화면 이동으로 생기지 않는 분기(이월 · 지연 · 다시 울리기 등)는 상태를 만들어 도는 시나리오로 둔다
- **훑기**: 케이스는 시나리오에서 뽑고, 스펙의 나열(§4)을 훑어 시나리오가 지나지 않는 분기를 찾는다. 사용자가 화면에서 겪는 분기면 시나리오에 단계를 더한다. 화면 조작으로 생기지 않는 분기(권한 우회 · 동시 요청 · 서버 안의 판정 경계)는 시나리오 밖 케이스로 둔다. 케이스가 없는 전이 · 상태가 있으면 케이스가 빠진 것이다
- 화면 이름과 버튼 문구는 현재 front-end 코드를 따른다. 코드가 아직 없는 화면은 스펙 · 앱 정보 구조를 따른다
- 화면 설계 문서가 있는 화면은 그 문서의 상태 표를 화면 상태로 쓴다. 구현이나 근거 문서가 없는 것은 기록만 한다(§2.4)
- 뒤로 가기(`‹`)는 모든 스택 화면에 있어 전이로 세지 않는다(포트폴리오 §10 · 알림 §15). 돌아가는 자리가 정해진 것(푸시로 연 울린 알림 상세, 새 알림 닫기, 입출금에서 자산 변화)만 전이로 센다

**실행 수단** — 화면 조작은 Claude Code가 크롬으로 앱의 웹 실행(`expo start --web`)을 조작해 한다. 기대값은 API 응답과 DB 질의로 대조한다. 웹에서 돌지 않는 것만 사람이 실기기로 한다.

| 수단 | 하는 것 | 쓰는 곳 |
|---|---|---|
| `크롬` | Claude Code가 웹 실행을 조작하고 화면 문구를 읽는다 | 화면 경로 · 화면 상태 |
| `API` | 응답 본문 · 상태 코드를 대조한다 | 숫자 · notice · 오류 코드 |
| `DB` | 읽기 질의로 행과 상태를 대조한다. 관측 조회를 포함한다 | 저장 결과 · 평가 · 발송 상태 |
| `실기기` | 사람이 iOS · Android에서 조작한다 | 푸시(웹 실행은 푸시를 등록 · 수신하지 않는다), 앱 뒤 · 앱 꺼짐 상태, 1등급 경로의 네이티브 확인 |
| `사람` | 자격증명을 입력하고, 앱 밖의 화면과 대조한다 | KIS 앱키 · 시크릿 · 계좌번호 입력, KIS 앱 잔고 · 체결내역 |
| `단위 테스트` | 기존 테스트(§5) | 분기 · 계산 |

- 크롬은 접근성 라벨과 화면 문구로 요소를 찾는다. 그래서 단계는 화면에 보이는 문구로 쓴다
- 실제 자격증명은 Claude Code가 입력하거나 읽지 않는다. 그 칸은 사람이 채우고, 형식 오류처럼 가짜 값으로 되는 변형만 `크롬`으로 한다
- 웹에서 통과한 것은 네이티브 통과의 증거가 아니다. 날짜 입력 · 시트처럼 웹과 네이티브가 다르게 그리는 곳이 있다. 1등급 경로는 실기기로 한 번 더 지난다

## 3. 시나리오

### 3.1 전제

**전제 구현** — 아래가 테스트 전에 배포된다는 전제로 시나리오를 짠다. 배포되지 않은 것에 걸리는 시나리오 단계는 유보로 돌린다(§8).

| 구현 | 근거 자료 | 걸리는 시나리오 |
|---|---|---|
| 수동 동기화의 화면 — 계좌별의 `지금 동기화`와 동기화 카드 | 계좌 연동 · 동기화 화면 설계 §2.2 · §3.5. `POST /sync` · `GET /sync/{run_id}`는 있다 | PF3 |
| `position_basis` · `realized_pnl_line` 생성 | 포트폴리오 §3.6 1.5 · 1.6단계 | PF9 |
| 앱 로그아웃 | 없음(§2.4) | X2 |
| 클러스터 백엔드의 웹 출처 허용 | 백엔드 `WebOriginCorsConfig` — 허용 출처를 `APP_WEB_ORIGINS`로 받는다. 클러스터 백엔드에 `http://localhost:8081`을 넣어 배포한다 | `연계` 환경에서 `크롬`으로 도는 단계 |

**환경**

| 항목 | 값 |
|---|---|
| 사용자 | `로컬`: 본인 1명(`yhr@a.com`) · 격리 확인용 2명(`hhj@a.com` · `jdh@a.com`). `연계`: 테스트 전용 계정(`it1@a.com` 본인 역 · `it2@a.com` 격리 확인용). 운영테스트 계정(`yhr` · `hhj` · `jdh`)으로는 `연계`를 돌리지 않는다 |
| 계좌 | KIS 모의계좌. 팀원마다 하나씩 있다. 국내 주식 · ETF 1개 · 미국 종목 1개를 담는다 |
| 기기 | iOS 2대 · Android 1대. `실기기` 수단에 쓴다 |
| 웹 실행 | 개발 머신의 `expo start --web`(`http://localhost:8081`) + `local` 프로파일 백엔드. `local` 프로파일은 데이터 테이블 미러를 함께 적용하므로 로컬 DB에서 돈다. 화면 상태를 만드는 데이터는 로컬 DB에 넣는다 |
| 앱 → API | 개발 머신에서 SSM 터널과 `kubectl port-forward --address 0.0.0.0`으로 잇는다. 공개 Ingress가 없다 |
| 클러스터 | `연계` 실행은 클러스터 DB에서 테스트 계정으로 돈다. 클러스터 DB는 운영테스트와 같이 쓴다(3주 계획 §3.1). 장중 · 종가 시각에 실데이터로 도는 시나리오는 그 시각에 클러스터가 켜져 있어야 한다(3주 계획 "가동 시간") |

**표기**

| 표기 | 뜻 |
|---|---|
| 실 | 실계좌 · 실데이터로 돈다 |
| 주입 | 로컬 DB에서 주입 · 재생이 필요하다(§7) |
| 유보 | 구현이 없어 못 돈다. 이유를 함께 적는다 |
| 관측 조회 | 3주 계획 §3.6의 관측 수단 |

#### PF3. 계좌를 수동으로 동기화한다

| | |
|---|---|
| 전제 | `CONNECTED` 계좌 |
| 경로 | E05 → E06 |
| 단계와 기대 | ① `POST /sync`(전 계좌 · 단일 계좌) → 즉시 `202`, `run_id`와 `다음 수집(MM-dd(요일) HH:mm)에 반영됩니다` ② 뷰마다 `SYNC_IN_PROGRESS` notice. 앱은 계좌별의 동기화 카드에만 그리고 다른 화면에는 그리지 않는다 ③ `GET /sync/{run_id}`의 계좌 행이 `RUNNING` → 다음 수집 뒤 `DONE`, 뷰 값이 새 라인과 같다 ④ 그날이 이미 확정이면 응답 문장이 `{as_of} 값은 이미 확정되어 바뀌지 않습니다 …`이고 뷰에 `ALREADY_FINAL` ⑤ 다시 보내도 오류가 없고, 같은 날 같은 계좌를 두 번 수집하지 않는다 ⑥ 해제한 계좌 지정 `409 ACCOUNT_DISCONNECTED` · 계좌 없이 전체 `409 NO_ACCOUNTS` · 남의 계좌 `403 FORBIDDEN_ACCOUNT` · 남의 실행 조회 `403 FORBIDDEN_SYNC_RUN` ⑦ 시한까지 수집되지 않으면 실행이 닫히고 그 계좌는 `FAILED` · `PICKUP_TIMEOUT` ⑧ 계좌별에서 `지금 동기화`를 누르면 동기화 카드에 다음 수집 예정이 보이고, 수집 뒤 계좌 탭에 다시 오면 카드에 결과(완료 · 부분 실패 · 전체 실패)가, 계좌별 · 요약에 새 값이 보인다. 앱을 다시 켜도 결과가 남고 `닫기`로 지운다 |
| 상태 변형 | 동기화 진행 중 · 부분 실패(실패 계좌도 총자산에 포함하고 이월로 표시) · 전체 실패 · 완료 |

## 5. 기존 테스트 매핑

백엔드에 테스트 파일 110개와 6뷰 골든 파일이, 프론트에 테스트 파일 42개가 있다. 매핑 결과는 케이스의 `자동화` 항목에 적는다.

- 이미 덮는 테스트가 있으면 `자동-기존`과 테스트 이름
- 없으면 `자동-신규`(테스트를 쓴다) 또는 `수동`(사람이 돈다)
- 사람의 시간은 수동으로만 되는 것에 쓴다 — 실기기 푸시, 실계좌 연동, 체감 속도, 화면이 이해되는지

구조 강제 테스트는 그대로 둔다 — `ArchitectureRulesTest` · `MigrationLintTest` · `SchemaContractTest` · `CatalogInvariantTest` · `PositionLineInvariantsTest` · `UserScopeIsolationTest`.

## 6. 실행 환경과 등급

### 6.1 실행 환경 — 케이스는 하나, 실행은 셋

| 값 | 어디서 | 어떤 케이스 |
|---|---|---|
| `로컬` | 로컬 + CI | 결함 주입 · 재생이 필요한 것 — 가짜 휴장일, 이력 자르기, 20일 연속, 보정 누락 |
| `연계` | 클러스터 DB · 테스트 계정 | 파이프라인이 있어야만 되는 것 — 도착 타이밍, 5분 주기 준수, 미러 스키마 실물, `data` 읽기 권한 |
| `둘 다` | 양쪽 | 1등급 핵심. 로컬에서 분기를 만들어 확인하고, 연계에서 같은 기대값으로 한 번 더 |

`크롬` 수단은 `로컬`에서 돈다(§3.1 웹 실행). `연계`에서는 클러스터 백엔드에 웹 출처 허용이 배포되면 돈다(§3.1 전제 구현). 그 전까지 `연계` 케이스의 화면 확인은 `실기기`로 한다.

파이프라인 연계 테스트를 별도 케이스로 두지 않는다. 기대값과 근거 절이 같고 입력을 누가 주느냐만 다르다. 기대값이 하나이므로 `둘 다`의 결과가 갈리면 그게 결함이다.

### 6.2 등급

| 등급 | 기준 | 목표 |
|---|---|---|
| **1등급** | 틀리면 사용자가 잘못된 숫자를 믿거나 알림을 못 받는다 | 100% 실행 |
| **2등급** | 틀리면 화면이 이상하지만 판단을 망치지 않는다 | 90% 이상 |
| **3등급** | 극단 경계값, 동시성, 비정상 입력 | 기록만. 시간 남으면 |

1등급의 예 — 신뢰도 등급 판정, 가산성(금액 합산), 사용자 스코프, 자격증명 비노출, 엣지 발화 1회, 허용 지연 초과 시 미평가, 결측 시 미발화 대신 확인 불가 표시.

등급은 위 피해 기준으로만 정한다. 에이전트가 1등급 후보를 근거와 함께 제안하고, 사람이 정한다.

## 7. 결함 주입과 재생

테스트 기간에 자연히 관측되지 않는 분기를 만드는 수단이다. 왜 필요한지는 3주 계획 §6에 있다.

### 7.1 수단

각 항목에 되돌리기를 함께 만든다. 되돌릴 수 없는 주입은 쓰지 않는다.

- 특정 시장 · 종류의 완료 신호를 늦추거나 빼기 → `DATA_MISSING` · `MARKET_DATA_DELAYED`(AL7)
- 특정 종목의 일봉 이력을 잘라내기 → `INSUFFICIENT_HISTORY`
- 장중 스냅샷의 시각을 과거로 밀기 → 허용 지연 초과(국내 10분 / 미국 20분)
- 캘린더에 가짜 휴장일 심기 → `NO_TRADE` · 연속 조건 끊김 · 개장 지연 판정
- 과거 일봉 구간을 재생해 평가기에 먹이기 → 20일 연속, 보정 누락, 박스권 돌파(AL6)
- 수집을 일부만 성공시키기 → 포트폴리오 부분 실패 표시 정책(PF3 · PF11)
- `collection_run`을 `REAUTH_REQUIRED`로 끝내기 → 재인증 요구(PF4)
- 평가기를 며칠 멈췄다 켜기 → 따라잡기(AL7)
- 만료된 토큰으로 바꿔 넣기 → `401`(C2 · X2)
- 자격증명 저장소 호출을 실패시키기 → `CREDENTIAL_STORE_UNAVAILABLE`(PF1)

### 7.2 안전장치

- 주입 수단은 환경 플래그 뒤에 둔다. 클러스터 DB를 가리키는 설정에서는 동작하지 않는다
- 주입 전 상태를 기록하고, 테스트 후 되돌린 것을 확인한다
- 주입은 로컬에서만 돈다. 클러스터 DB는 운영테스트와 같이 쓰므로, 데이터 테이블 · 평가 상태를 바꾸는 주입이 걸리면 모든 사용자의 알림이 틀어진다

## 8. 범위 제외 · 유보

덮을 수 없는 것이다. 결함이 아니라 미구현 · 데이터 한계이므로 분리해 기록한다.

| 항목 | 상태 | 영향 |
|---|---|---|
| CODEF 경로(포트폴리오 §7.1) | 범위 제외 | 구현 계획이 없다(등록 API 설계 §1 · 계좌 연동 · 동기화 화면 설계 §1). 기관 선택 · 인증 입력 · 추가 인증 화면과 계좌 연동의 추가 인증 요구 상태 |
| 수동 동기화의 화면 | 유보 | 구현이 없다. PF3 ⑧ |
| 종목 상세(포트폴리오 §2.10) | 유보 | 구현이 없다. PF10, X1 ② |
| 로그아웃 | 유보 | 스펙 · 앱 정보 구조에 자리가 없다. X2 로그아웃 변형 |
| KIS 계좌의 재인증 CTA | 유보 | 여는 곳을 정한 문서가 없다. PF4 ④ |
| 알림 스펙 §17이 미룬 것 | 범위 제외 | OR 트리 · 혼합 평가 시점 · 백테스트 · 알림 공유 |
| 재인증 실발생 | 주입만 | KIS 계좌는 데이터 워커가 `REAUTH_REQUIRED`를 내지 않는다(PF4) |
| 배당 현금흐름 실데이터 | 주입만 | 모의 환경은 권리 · 배당 조회를 하지 않는다(PF9) |

| 전제 구현(§3.1) | 구현 중 | 배포되지 않은 것에 걸리는 시나리오 단계는 유보로 돌린다 |

## 9. 데이터 품질 검사 항목

클러스터 DB를 읽기 전용으로 매일 검사한다. 일정·산출물·실패 처리는 3주 계획 §5에 있다.

**종목 마스터**
- 행 수와 시장별 분포. 국내 전 상장 · 미국 NYSE·NASDAQ이 들어왔나
- `name` · `symbol` · `market` · `currency`의 null 비율
- 보유 종목과 `alert_watchlist` 종목이 빠짐없이 있나
- 이름·종목코드 부분 일치 검색이 되나

**수정주가 일봉**
- 종목별 이력 길이 ≥ 300거래일
- 거래일 중 빈 날 — 캘린더와 대조
- OHLC 불변식 — `low ≤ open, close ≤ high`, `volume ≥ 0`
- 보정 계열인가 — 과거 분할 종목의 분할 전후가 연속인지
- 키가 `instrument_id`인가

**투자자별 순매수**
- 이력 길이 ≥ 30거래일
- 금액 단위가 원인가. 순매도가 음수로 오나
- 확정치인가 — 같은 날짜를 하루 뒤 다시 읽어 값이 변하지 않는지

**장중 스냅샷**
- 스냅샷 간격 ≤ 5분. 결손 구간의 길이와 횟수
- `price > 0`, `cum_volume`이 당일 안에서 단조 증가
- 대상이 `alert_watchlist`와 일치하나
- 보관이 당일분 이상인가 — 미국은 현지 거래일 기준

**`market_data_run`**
- `DONE` 시각의 분포. 약속한 도착 시점을 지키나
- `DONE`인데 종목이 누락된 경우가 없나 — 일부만 적재된 `DONE`은 빠진 종목을 `NO_TRADE`로 오판시킨다
- `FAILED` 발생률

**영업일 캘린더**
- `is_trading_day`가 실제와 맞나
- `prev_trading_day` · `next_trading_day` 연결이 끊긴 날이 없나
- `open_at` · `close_at`이 채워져 있나

**포트폴리오 쪽**
- `cln_*` 중복 행
- `trade_id` 안정성 — 재수집 후 같은 체결이 같은 값인가
- `fx_rate` 결측과 폴백 길이
- `etf_constituent` 비중 합과 `as_of` 최고령
- `ca_coverage` · `etf_coverage`로 "없음"과 "미확보"가 구분되나
- `collection_run` — 계좌별 EOD 행이 KR 영업일마다 생기나, `silver_synced_at`이 찍히나

`data`에 아직 없는 표는 질의만 두고 "비었음"으로 보고되게 한다.
