- **작성일**: 2026-10-16
- **일정·준비·운영·결함 관리·종료 조건**: [통합테스트 · 운영테스트 3주 계획](../plan/2026-10-11-integration-and-operation-test-plan.md)
- **근거 스펙**: [포트폴리오 스펙](../specs/portfolio-management/2026-07-28-portfolio-management-spec.md) · [알림 스펙](../specs/buy-sell-timing-alert/2026-07-12-buy-sell-timing-alert-spec.md) · [데이터 요구사항](../specs/data-requirements.md) · [앱 정보 구조](../specs/app-information-architecture.md)

- **스펙 수정 금지**: 이 문서는 스펙을 인용만 한다. 스펙이 틀렸다고 판단되면 멈추고 보고한다

## 1. 두 층

- **시나리오** — 사용자 여정 단위. **운영테스트가 이 층을 돈다**
- **케이스** — 분기 단위. 수백 건. **통합테스트가 이 층을 돈다**

시나리오는 **이야기가 끊기지 않는지**를, 케이스는 **분기가 빠지지 않았는지**를 본다.

**설계는 위에서 아래로 간다.** 시나리오를 확정하고 케이스를 뽑는다. 시나리오가 지나는 분기가 1등급 후보가 되고, 지나지 않는 분기는 등급이 내려간다.

## 2. 시나리오

### 2.1 전제

**전제 구현** — 아래 넷이 테스트 시작 전에 배포된다는 전제로 시나리오를 짠다. 넷 모두 구현 중이다. 배포되지 않은 것에 걸리는 시나리오 단계는 유보로 돌린다(§7).

| 구현 | 걸리는 시나리오 |
|---|---|
| 계좌 연동 API · 수동 동기화(`POST /sync`) · 계좌 연동 화면 | P2 · P4 · P7 |
| `position_basis` · `realized_pnl_line` 생성 (포트폴리오 스펙 §3.6 1.5 · 1.6단계) | P6 |
| ETF 안분 (§3.6 2단계) | P5 |
| 앱 로그아웃 | A8 |

**운영 환경**

| 항목 | 값 |
|---|---|
| 사용자 | 본인 1명(`yhr@a.com`) · 격리 확인용 2명(`hhj@a.com` · `jdh@a.com`) |
| 계좌 | KIS 모의계좌. 국내 주식 · ETF 1개 · 미국 종목 1개를 담는다. 같은 사용자의 두 번째 모의계좌는 확보 여부 미정 |
| 기기 | iOS 2대 · Android 1대 |
| 앱 → 운영 API | 개발 머신에서 SSM 터널과 `kubectl port-forward --address 0.0.0.0`으로 잇는다. 공개 Ingress가 없다 |
| 클러스터 | 테스트 기간 상시 가동이 필요하다. 가동 시간은 팀 협의 중이다 |

**운영 규칙** — 테스트 기간 동안 테스트 계좌에 입출금을 하지 않는다. 입출금 입력 기능이 없어(§7) 입출금이 생기면 자산 변화 뷰의 투자손익에 그 금액이 섞인다(포트폴리오 스펙 §2.9 · §4.6).

**표기**

| 표기 | 뜻 |
|---|---|
| 실 | 실계좌·실데이터로 돈다 |
| 주입 | 클러스터 테스트 DB에서 주입·재생이 필요하다(§6) |
| 유보 | 구현이 없어 못 돈다. 이유를 함께 적는다 |
| 관측 조회 | 3주 계획 §3.6의 관측 수단 |

### 2.2 각 시나리오에 적는 것

| 항목 | 내용 |
|---|---|
| 전제 | 사용자 · 계좌 · 보유 · 알림 · 데이터 |
| 단계와 기대 | 조작을 순서대로, 각 단계에서 보여야 할 것 |
| 근거 절 | 스펙 위치 |
| 관측 | 화면 / API / DB / 푸시 / 관측 조회 |
| 실데이터 | 실 / 주입 / 유보 |
| 판정 | 무엇을 보면 통과인가. 애매하면 시나리오가 덜 설계된 것이다 |
| 소요 | 한 번에 걸리는 시간과 주기 |

각 시나리오를 돌 때 **"사용자가 되어 본 느낌"**을 한 줄 남긴다. 운영 일지의 "느낌" 줄과 같은 것이다.

### 2.3 포트폴리오

#### P1. 계좌 없는 사용자가 처음 로그인한다

| 근거 절 | 포트폴리오 §8.8 · §10 · 앱 정보 구조 §5 · 알림 §12.7 |
| 관측 | 화면 |
| 실데이터 | 실 |
| 판정 | 빈 화면마다 정해진 문구가 나오고, 무한 로딩·오류 화면이 없다 |
| 소요 | 1회 10분 |

| | |
|---|---|

| 단계와 기대 | ① 요약 총자산 = 종목별 평가금액 합 = 비중 분석 축별 합 = 계좌별 합 ② 종목별 수량·평단 = KIS 모의 앱 잔고 ③ 예수금 행이 있고 원가·손익은 `—` ④ 환율 표기(`FX_APPLIED`) ⑤ 미국 종목은 현지 통화 병기, `PRICE_LAG_MARKET` |
| 다계좌 변형 | 같은 종목 두 계좌 합산과 수량가중 평단 · 계좌 비중 · 계좌 필터 · 계좌별 행 → 종목별(계좌 필터). 두 번째 계좌가 없으면 주입 |

| 판정 | 네 합계가 원 단위까지 같고, KIS 앱과 수량·평단이 같다 |
| 소요 | 매일 10분 |

|---|---|

### 2.4 알림

#### A1. 프리셋으로 알림을 만든다

| | |
|---|---|
| 전제 | 알림이 없는 사용자. OS 알림 권한 미정 |
| 단계와 기대 | ① `＋ 새 알림` → 종목 선택: 보유 종목 구역 가나다순. 검색 정렬은 종목코드 완전 일치 → 이름 시작 → 이름 포함. 미국 종목은 영문 이름 + 티커 ② 조건 선택: 미국 종목의 수급 프리셋은 `국내 종목만`으로 비활성. 보유하지 않은 종목의 수익률 도달은 `보유 종목만` ③ 가격 도달: 직전 종가로 미리 채움, `M/D 종가 기준` ④ 공통 설정: 충족 중이면 경고 ⑤ 첫 저장 → 권한 안내 시트 → 허용 → `push_device` 1행 ⑥ 저장 → 알림 상세 |
| 근거 절 | 알림 §6.3 · §9.2 · §11.1 · §12.5.1 ~ §12.5.5 · §12.7 · 앱 정보 구조 §2.4 |
| 관측 | 화면 · DB(`alert` · `alert_state` · `alert_watchlist` · `push_device`) |
| 실데이터 | 실 |
| 판정 | 행이 생기고, 카드 문구가 서버의 짧은 형과 같다 |
| 소요 | 1회 15분 |

#### A2. 조립형으로 다지표 AND 알림을 만든다

| | |
|---|---|

| 실데이터 | 실 |
| 판정 | 문장 상자가 고른 조건과 같은 뜻이고, 저장된 spec에 `lag`가 없다 |

#### A3. 종가 알림이 울리고 푸시를 받는다

| | |

## 4. 기존 테스트 매핑

백엔드에 테스트 파일 70개와 6뷰 골든 파일이, 프론트에 테스트 파일 31개가 있다.

## 5. 실행 환경과 등급

### 5.1 실행 환경 — 케이스 표는 하나, 실행은 셋

| 값 | 어디서 | 어떤 케이스 |
|---|---|---|
| `로컬` | 로컬 + CI | 결함 주입·재생이 필요한 것 — 가짜 휴장일, 이력 자르기, 20일 연속, 보정 누락 |
| `연계` | 클러스터 테스트 DB | 파이프라인이 있어야만 되는 것 — 도착 타이밍, 5분 주기 준수, 미러 스키마 실물, `data` 읽기 권한 |
| `둘 다` | 양쪽 | 1등급 핵심. 로컬에서 분기를 만들어 확인하고, 연계에서 같은 기대값으로 한 번 더 |

파이프라인 연계 테스트를 별도 표로 두지 않는다. 기대값과 근거 절이 같고 입력을 누가 주느냐만 다르다. 기대값이 하나이므로 `둘 다`의 결과가 갈리면 그게 결함이다.

### 5.2 등급

| 등급 | 기준 | 목표 |
|---|---|---|
| **1등급** | 틀리면 사용자가 잘못된 숫자를 믿거나 알림을 못 받는다 | 100% 실행 |
| **2등급** | 틀리면 화면이 이상하지만 판단을 망치지 않는다 | 90% 이상 |
| **3등급** | 극단 경계값, 동시성, 비정상 입력 | 기록만. 시간 남으면 |

1등급의 예 — 신뢰도 등급 판정, 가산성(금액 합산), 사용자 스코프, 엣지 발화 1회, 허용 지연 초과 시 미평가, 결측 시 미발화 대신 확인 불가 표시.

등급은 에이전트가 1등급 후보를 근거와 함께 제안하고, 사람이 정한다.

## 6. 결함 주입과 재생

3주 창에서 자연히 관측되지 않는 분기를 만드는 수단이다. 왜 필요한지는 3주 계획 §6에 있다.

### 6.1 수단

각 항목에 되돌리기를 함께 만든다. 되돌릴 수 없는 주입은 쓰지 않는다.

- 특정 시장·종류의 완료 신호를 늦추거나 빼기 → `DATA_MISSING` · `MARKET_DATA_DELAYED`
- 특정 종목의 일봉 이력을 잘라내기 → `INSUFFICIENT_HISTORY`
- 장중 스냅샷의 시각을 과거로 밀기 → 허용 지연 초과(국내 10분 / 미국 20분)
- 캘린더에 가짜 휴장일 심기 → `NO_TRADE` · 연속 조건 끊김 · 개장 지연 판정
- 과거 일봉 구간을 재생해 평가기에 먹이기 → 20일 연속, 보정 누락, 박스권 돌파
- 수집을 일부만 성공시키기 → 포트폴리오 부분 실패 표시 정책(포트폴리오 §7.5)
- `collection_run`을 `REAUTH_REQUIRED`로 끝내기 → 재인증 요구(P7 ⑤)
- 평가기를 며칠 멈췄다 켜기 → 따라잡기(알림 §3.3 · §8.3)

### 6.2 안전장치

- 주입 수단은 환경 플래그 뒤에 둔다. 운영 DB를 가리키는 설정에서는 동작하지 않는다
- 주입 전 상태를 기록하고, 테스트 후 되돌린 것을 확인한다
- 3주차 월요일의 주입은 클러스터 테스트 DB에서 돈다. 운영 DB의 알림 가동을 건드리지 않는다

| 입출금 입력(포트폴리오 §4.6) | 범위 제외 | 테이블·읽기 경로는 있고 입력 화면·`POST`가 없다. "투자손익 = 잔차"는 테스트 DB에 직접 넣어 계산과 화면까지 확인한다. 입력 화면·`POST`는 검증하지 않는다 |
| 종목 상세 화면(포트폴리오 §2.10) | 범위 제외 | 계좌별 분해·종목 거래내역 화면과 종목 상세 `알림 걸기` 진입이 없다(X2) |
| 알림 스펙 §17이 미룬 것 | 범위 제외 | OR 트리 · 혼합 평가 시점 · 백테스트 · 알림 공유 |
| 재인증 실발생 | 주입만 | KIS 계좌는 데이터 워커가 `REAUTH_REQUIRED`를 내지 않는다(P7 ⑤) |
| 배당 현금흐름 실데이터 | 주입만 | 모의 환경은 권리·배당 조회를 하지 않는다(P6) |
| 실계좌 운영 | 범위 축소 | 운영테스트는 KIS 모의계좌로 돈다 |
| 같은 사용자의 다계좌 실데이터 | 미정 | 두 번째 계좌가 없으면 다계좌 분기는 주입으로만 덮는다(P2) |
| 계좌유형 소계(일반·연금) | 주입만 | 모의계좌는 일반계좌뿐이다 |
| 전제 구현 4건(§2.1) | 구현 중 | 배포되지 않은 것에 걸리는 시나리오 단계는 유보로 돌린다 |

## 8. 2주차 월요일에 심을 알림

관측 가능성을 보고 고른다. 가동 후 열흘 안에 각 분기가 적어도 한 번 열려야 한다.

- **반드시 울릴 것** — 기준값을 현재가에 바싹 붙인 가격 알림. 국내 1건 · 미국 1건
- **며칠 걸리는 것** — `streak(3거래일)` 종가 조건
- **장중에만 도는 것** — `persist_min` 지속 조건
- **안 울리는 게 정상인 것** — 기준값을 멀리 둔 알림. 오발화를 잡는다
- **발화 방식 3종** — `EDGE_REARM` · `ONE_SHOT` · `COOLDOWN` 각 1건
- **프리셋 1건** · **조립형 다지표 AND 1건**
- **수급 조건 1건** — 확정치 도착 시점이 맞는지
- **보유 종목 수익률 도달 1건** — 보유 스냅샷 평가(X1)

## 9. 데이터 품질 검사 항목

클러스터 운영 DB를 읽기 전용으로 매일 검사한다. 일정·산출물·실패 처리는 3주 계획 §5에 있다.

**종목 마스터**
- 행 수와 시장별 분포. 국내 전 상장 · 미국 NYSE·NASDAQ이 들어왔나
- `name` · `symbol` · `market` · `currency`의 null 비율
- 보유 종목과 `alert_watchlist` 종목이 빠짐없이 있나
- 이름·종목코드 부분 일치 검색이 되나

**수정주가 일봉**
- 종목별 이력 길이 ≥ 300거래일
- 거래일 중 빈 날 — 캘린더와 대조
- OHLC 불변식 — `low ≤ open, close ≤ high`, `volume ≥ 0`
- 보정 계열인가 — 과거 분할 종목의 분할 전후가 연속인지
- 키가 `instrument_id`인가

**투자자별 순매수**
- 이력 길이 ≥ 30거래일
- 금액 단위가 원인가. 순매도가 음수로 오나
- 확정치인가 — 같은 날짜를 하루 뒤 다시 읽어 값이 변하지 않는지

**장중 스냅샷**
- 스냅샷 간격 ≤ 5분. 결손 구간의 길이와 횟수
- `price > 0`, `cum_volume`이 당일 안에서 단조 증가
- 대상이 `alert_watchlist`와 일치하나
- 보관이 당일분 이상인가 — 미국은 현지 거래일 기준

**`market_data_run`**
- `DONE` 시각의 분포. 약속한 도착 시점을 지키나
- `DONE`인데 종목이 누락된 경우가 없나 — 일부만 적재된 `DONE`은 빠진 종목을 `NO_TRADE`로 오판시킨다
- `FAILED` 발생률

**영업일 캘린더**
- `is_trading_day`가 실제와 맞나
- `prev_trading_day` · `next_trading_day` 연결이 끊긴 날이 없나
- `open_at` · `close_at`이 채워져 있나

**포트폴리오 쪽**
- `cln_*` 중복 행
- `trade_id` 안정성 — 재수집 후 같은 체결이 같은 값인가
- `fx_rate` 결측과 폴백 길이
- `etf_constituent` 비중 합과 `as_of` 최고령
- `ca_coverage` · `etf_coverage`로 "없음"과 "미확보"가 구분되나
- `collection_run` — 계좌별 EOD 행이 KR 영업일마다 생기나, `silver_synced_at`이 찍히나

`data`에 아직 없는 표는 질의만 두고 "비었음"으로 보고되게 한다.
