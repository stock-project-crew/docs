# 실습 노트 F: 마이그레이션 호환 검사

- 날짜: 2026-11-15
- 계획서: `yhr/review/upgrade-plan.md`의 F절
- back-end: `practice/F`(기준 `e1b913b`). 로컬 커밋만 했고, 원격 푸시와 main 반영은 하지 않았다. 커밋은 아래 "진행"의 단계마다 적었다.
- 환경: 로컬 Docker 컨테이너 `pf-f`(Postgres 16.15, 포트 5506), Spring Boot 3.4.5, Flyway 10.20.1. 운영 DB와 클러스터는 쓰지 않았다.

## 1. 배경

### 왜 했나

main에 푸시하면 곧 운영에 배포된다. CI가 이미지를 만들고 매니페스트의 태그를 바꾸면, ArgoCD가 그 커밋을 보고 클러스터에 반영한다. Flyway는 앱이 기동할 때 마이그레이션을 적용한다.

앱 파드는 두 개(`replicas: 2`)이고, 하나씩 교체된다(롤링). 그래서 배포 중에는 이런 순간이 반드시 생긴다.

1. 새 파드가 뜨면서 새 마이그레이션을 적용한다. DB는 이제 새 스키마다.
2. 옛 파드는 아직 살아서 요청을 받는다. 옛 파드의 SQL은 옛 스키마를 기준으로 쓰였다.
3. 즉, "옛 코드 + 새 스키마" 조합이 잠깐 돈다. 롤백할 때도 같은 조합이 생긴다.

이때 옛 코드를 깨는 마이그레이션을 막는 장치가 없었다. CI는 새 코드의 테스트만 돌리고, 그것도 main에 들어간 뒤에 돈다.

사례로 V19가 있었다. V19는 `push_device`에 `session_id NOT NULL` 열을 더한다. 옛 코드의 기기 등록 INSERT는 이 열을 채우지 않는다. 그래서 롤링 중 옛 파드로 간 기기 등록은 실패할 것으로 봤다.

이 실습에서 메우려는 역량은 무중단 배포 중의 스키마 호환이다. 확장-축소(expand/contract) 마이그레이션과, 롤링 중 두 판이 공존하는 문제가 여기에 든다.

### 출발한 가설 (계획서 F절)

정적 검사(마이그레이션 SQL의 위험한 문형을 찾는다):

1. V19를 잡는다(DEFAULT 없는 NOT NULL 추가).
2. 문형이 같아도 안전한 경우를 가르지 못해 허용 목록이 늘어난다.
3. CHECK 축소(V15)는 옛 CHECK와 견줘야 알 수 있어서, 한 파일만 보는 검사로는 못 잡는다.

옛 코드 테스트(새 스키마에서 옛 코드의 테스트를 돌린다):

4. V19에서 기기 등록 테스트가 NOT NULL 위반으로 실패해 잡힌다.
5. V15는 옛 테스트가 축소된 값을 넣는 경우에만 잡힌다.
6. 지금 테스트 시간만큼 한 번 더 걸린다. 마이그레이션이 바뀐 커밋에서만 돌리면 평소 비용은 0이다.

공통:

7. 둘 다 못 잡는 유형은 컬럼의 의미가 바뀌는 경우다. 이것은 리뷰 몫으로 남는다.

함께 볼 것: 옛 코드가 자기가 모르는 더 높은 버전이 적용된 DB에서 기동하면 Flyway가 어떻게 동작하는가.

## 2. 진행

### 0단계: 준비

- back-end `origin/main`(`e1b913b`)에서 worktree `.worktrees/be-practice-F`, 브랜치 `practice/F`를 만들었다.
- `pf-f` 컨테이너를 띄웠다.
- 계획서의 코드 위치(`275cb26` 기준)를 지금 main에서 다시 찾았다. V19의 위치는 그대로였다. CI 테스트 단계는 `build-and-push.yml:50-51`으로 옮겨 있었다.

조사 중에 계획서에 없던 사실 두 가지를 알게 됐다.

- **운영과 테스트가 적용하는 마이그레이션이 다르다.** 운영은 `db/migration`만 적용한다. 테스트와 로컬은 데이터팀 소유 표의 사본(`db/external`, 이하 "미러")까지 함께 적용한다.
- **V15 직전 코드가 축소된 값을 실제로 쓴다.** `PositionWriteMapper`가 `link_state = 'REAUTH_REQUIRED'`로 UPDATE한다. V15는 이 값을 CHECK에서 뺀다.

### 원리: 확장-축소 마이그레이션

롤링 중 두 판이 같이 돌아도 깨지지 않게 하려면, 스키마 변경을 여러 배포로 나눈다.

| 배포 | 스키마 | 코드 |
|---|---|---|
| 1. 확장 | 열을 NULL 허용으로 더한다. CHECK에는 새 값을 더하기만 한다 | 새 열을 채우기 시작한다 |
| 2. 이전 | 옛 행을 채운다 | 새 열만 읽는다 |
| 3. 축소 | NOT NULL을 걸고, 옛 열과 옛 CHECK 값을 뺀다 | (옛 값을 이미 안 쓴다) |

한 줄로 줄이면 이렇다. **한 배포의 마이그레이션은 바로 앞 판의 코드가 깨지지 않는 변경만 한다.**

V19는 1번과 3번을 한 번에 했다. V15도 CHECK 축소(3번)를 코드 변경과 같은 배포에 넣었다.

이 규칙을 사람 대신 검사가 지키게 하는 방법으로 두 가지를 만들어 비교했다.

- 정적 검사: SQL 문장의 모양만 본다. 빠르지만 문맥을 모른다. 옛 코드가 그 열을 쓰는지, CHECK를 넓히는지 줄이는지 알지 못한다.
- 옛 코드 테스트: 새 스키마에서 옛 코드를 실제로 돌려 본다. 옛 코드가 실제로 쓰는 경로만 잡는다. 대신 옛 테스트가 그 경로를 지나가야 잡고, 테스트를 한 번 더 돌리는 만큼 시간이 든다.

### 1단계: Flyway가 미래 버전을 만나면

옛 파드가 롤링 중에 재시작하면, 자기가 모르는 높은 버전이 이미 적용된 DB에서 기동하게 된다. 이때 Flyway가 기동을 막는지부터 확인했다.

방법:

1. 빈 DB `f_future`에 지금 main의 마이그레이션을 전부 적용했다. 운영 마이그레이션은 V25, 미러는 V26까지다.
2. 옛 커밋을 따로 체크아웃해 Flyway를 켠 채 그 DB에 붙여 기동했다.

| 옛 코드 | 결과 |
|---|---|
| V24 시점(`0046624^`), `R__app_column_comments.sql`이 있음 | 기동했다. 경고 한 줄만 남겼다: `Schema "app" has a version (26) that is newer than the latest available migration (24) !` |
| V18 시점(`47155af^`), `R__` 파일이 없음 | 기동하지 못했다. `Validate failed: Detected applied migration not resolved locally: app column comments` |

해석:

- 미래의 V 버전은 무시된다. Flyway의 기본 설정(`ignoreMigrationPatterns=*:future`)이 그렇게 되어 있다. 그래서 Flyway 단계에서는 옛 파드가 막히지 않는다. 옛 코드가 실제로 깨지는지는 SQL을 실행할 때 드러난다.
- 반복 마이그레이션(`R__`, 버전 번호 없이 내용이 바뀔 때마다 다시 적용되는 파일)은 "미래 버전"이 아니라 "사라진 마이그레이션"으로 취급된다. 옛 코드에 그 파일이 없으면 검증에서 실패한다.
- `R__app_column_comments.sql`은 `0dd4498`에서 처음 생겼다. 그래서 이 커밋보다 앞선 판으로 롤백하면 그 파드는 기동하지 못할 것으로 본다. 로컬에서 재현한 결과이고, 운영에서는 확인하지 않았다.

이 결과로 옛 코드 테스트는 계획서대로 Flyway를 끄고 돌려야 한다는 것이 분명해졌다. Flyway를 켜 두면 `R__` 같은 이유로 기동이 먼저 실패해서, 정작 보려던 SQL 호환성을 볼 수 없다.

### 2단계: 정적 검사 (`7719bb9`)

검출기를 만들었다(`MigrationCompatRules`). SQL에서 주석과 문자열 값을 지운 뒤 `;`로 문장을 나누고, 공백을 한 칸으로 줄여서 본다. 그래서 줄을 넘겨 쓴 문장도 한 줄처럼 검사된다. ALTER TABLE 한 문장에 절이 여러 개면, 괄호 밖의 쉼표로 나눠 절마다 본다.

규칙은 계획서의 네 개에 두 개를 더했다.

| 규칙 | 출처 | 왜 위험한가 |
|---|---|---|
| DROP COLUMN, RENAME, DROP TABLE | 계획서 | 옛 코드가 옛 이름·옛 열·옛 표를 쓴다 |
| ADD COLUMN … NOT NULL(DEFAULT 없음) | 계획서 | 옛 INSERT가 새 열을 채우지 않는다 |
| ALTER COLUMN … SET NOT NULL | 실습 중 추가 | 효과가 위와 같다. "열 추가 → 채우기 → NOT NULL"을 한 파일에 쓰면 위 규칙을 빠져나간다(V13이 그렇다) |
| DROP CONSTRAINT …_check | 실습 중 추가 | CHECK 교체. V15 같은 축소를 잡을 수 있는지 보려고 더했다 |

처음에는 허용 목록을 비우고 모든 V 파일에 돌려, 무엇이 걸리는지 먼저 봤다.

| 파일 | 규칙 | 판단 |
|---|---|---|
| V13 | SET_NOT_NULL | 위험(옛 INSERT가 새 열을 비운다) |
| V15 | CHECK_REPLACED ×3 | 위험(허용 값을 줄인다) |
| V19 | ADD_NOT_NULL_NO_DEFAULT | 위험 |
| V22, V25 | CHECK_REPLACED | 안전. 허용 값을 더하기만 한다. 앞선 정의(V8)와 값 집합을 비교해 확인했다. 빠진 값이 없고, V22는 `ERROR`, V25는 `DEPOSIT_CURRENCY_MISSING`을 하나씩 더했다 |

DROP COLUMN, RENAME, DROP TABLE은 지금까지 한 번도 쓰인 적이 없었다.

게이트 테스트(`MigrationCompatLintTest`)는 운영에 적용되는 `db/migration`의 V 파일만 본다. 이미 운영에 적용된 파일은 허용 목록에 이유와 함께 넣었다. 그러면 새로 들어오는 파일만 기본으로 검사된다. 허용 목록에 있는데 실제로 걸리지 않는 항목이 있으면 테스트가 실패하게 해서, 목록이 실제 파일과 어긋나지 않게 했다.

규칙 단위 테스트(`MigrationCompatRulesTest`) 7개로 경계를 확인했다. 줄을 넘긴 NOT NULL, 주석과 문자열 안의 키워드, `ADD CONSTRAINT … IS NOT NULL`, 새 표의 NOT NULL 등을 본다.

### 3단계: 옛 코드 테스트 (`225d9f1`)

스크립트 `scripts/compat/old-code-test.sh <옛 커밋>`를 만들었다. 하는 일은 이렇다.

1. 옛 커밋을 별도 worktree로 꺼낸다.
2. 새 코드의 테스트 하나(`SchemaSmokeTest`)를 돌려 Flyway가 빈 DB에 새 스키마를 적용하게 한다.
3. 같은 DB에서 Flyway를 끈 채(`SPRING_FLYWAY_ENABLED=false`) 옛 커밋의 테스트를 전부 돌린다.

몇 가지를 정해야 했다.

- **스키마 자체를 단정하는 테스트는 뺐다.** `SchemaSmokeTest`, `AlertSchemaTest`, `SchemaContractTest`가 그렇다. 이 테스트들은 옛 스키마를 기대하므로, 호환 여부와 상관없이 새 스키마에서는 실패한다. 옛 커밋의 `build.gradle.kts`를 고치지 않으려고 Gradle init 스크립트(`-I`)로 뺐다.
- **`test --rerun`을 붙였다.** Gradle은 환경 변수를 입력으로 보지 않는다. 그래서 DB 주소만 바꿔 돌리면 "이미 끝난 작업"으로 보고 건너뛸 수 있다.
- **테스트끼리 데이터를 지우는 방식이 Flyway에 기대지 않는지 확인했다.** 테스트는 TRUNCATE·DELETE로 직접 지운다.

### 4단계: 판정용 재현

측정 전에 다른 세션의 테스트가 돌고 있었다. 다른 worktree의 Gradle 테스트와 front-end의 jest였다. 그래서 다른 테스트가 3분 연속 없고 1분 평균 부하가 4 미만이 될 때까지 기다렸다가 돌렸다. 조합마다 한 번씩 돌렸다.

| 조합 | 결과 |
|---|---|
| 1. 직전 운영판 `d0dbf86` 코드 + main 스키마 | **실패 30건**(예상은 통과) |
| 2. V18 시점 `3f1f6f0` 코드 + V19 스키마(`47155af`) | 1154개 중 30개 실패 |
| 3. V14 시점 `236f6e8` 코드 + V15 스키마(`4123c10`) | 970개 중 361개 실패 |
| 4. main 전체 테스트(기준 시간) | 통과, 114초 |

실패한 테스트마다 맨 아래 SQL 오류를 뽑아 원인별로 묶었다.

**1번: 처음엔 통과할 줄 알았는데, 방법이 만든 거짓 양성이었다.** 실패 30건이 모두 데이터팀 미러 V26에서 왔다. V26은 `cln_trade_coverage`에 `market NOT NULL`을 더하고, 기본키를 `(account_ref)`에서 `(account_ref, market)`으로 바꿨다. 깨진 곳은 옛 **테스트 fixture**가 이 표에 INSERT하는 부분이었다. `ON CONFLICT (account_ref)`가 더는 맞는 키를 찾지 못했고, `market`을 채우지 않았다.

옛 앱 코드는 이 표를 읽기만 하고 쓰지 않는다(코드에서 INSERT·UPDATE·DELETE를 찾아 확인했다). 그리고 운영에서 배포가 바꾸는 것은 `db/migration`뿐이다. 데이터팀 표는 데이터팀이 따로 바꾼다. 그래서 스크립트를 고쳤다. 새 스키마를 "새 코드의 `db/migration` + 옛 커밋의 `db/external`" 조합으로 만든다. 다시 돌린 1번은 **통과**했다(옛 테스트 109초).

2번과 3번은 두 커밋 사이에 미러가 바뀌지 않아서 다시 돌리지 않았다(`git diff`로 확인했다).

**2번(V19): 깨끗하게 잡혔다.** 30건 모두 `null value in column "session_id" of relation "push_device"`였다. 기기 등록·발송·영수증 확인 테스트들이다.

**3번(V15): 잡혔지만 잡음에 묻혔다.**

- 355건은 `account_source_check` 위반이었다. 옛 fixture가 `source='CODEF'` 계좌를 넣다가 막힌 것이다. 옛 앱 코드는 계좌를 넣을 때 언제나 `'KIS'`를 쓴다(`AccountLinkMapper`). 그래서 이것은 운영과 상관없는 잡음이다.
- 진짜 신호는 몇 건뿐이었다. `RunProcessor`가 `link_state='REAUTH_REQUIRED'`로 바꾸려다 CHECK에 막혔고, `SyncCloser`가 `final_state='REAUTH_REQUIRED'`를 쓰려다 막혔다(sqlstate 23514). 둘 다 옛 앱 코드의 경로다.
- 두 코드는 예외를 잡아 경고 로그만 남긴다. 그래서 테스트에는 예외가 아니라 "값이 기대와 다르다"는 단정 실패로 나타났다.
- 이 경로가 KIS만 쓰는 지금 운영에서 실제로 실행되는지는 확인하지 않았다. `REAUTH_REQUIRED`는 CODEF 수집의 종료 상태다.

### 결정 지점: 채택할 검사 방식

선택지:

| | 얻는 것 | 잃는 것 |
|---|---|---|
| A. 정적 검사만 | V19·V15를 모두 잡는다(CHECK 교체 규칙 포함). 0.04초. 실패 메시지가 문장을 가리킨다 | CHECK를 넓힐 때마다 허용 목록에 넣어야 한다. 옛 코드가 실제로 쓰는지 모른다 |
| B. 옛 코드 테스트만 | 실제 경로만 잡는다. 안전한 넓히기(V25)는 통과한다 | 테스트 단계가 약 2배. 잡음 분류는 사람 몫. CI에 옛 커밋 체크아웃이 필요하다 |
| C. 둘 다(옛 코드 테스트는 마이그레이션이 바뀐 커밋에서만) | 서로의 빈틈을 메운다. 평소 비용은 0 | 구현과 유지가 가장 많다 |

처음에는 C를 추천했다. 이유는 이랬다. CHECK 교체 규칙은 넓힐 때마다 울려서 허용 목록에 넣는 습관이 들기 쉽다. 그런데 옛 코드 테스트는 넓히기는 통과시키고 축소는 실제 경로에서 잡았다.

그러자 사용자가 "클러스터가 꺼져 있다"는 조건을 짚었다. 이 조건을 넣으니 판단이 바뀌었다.

- 클러스터가 꺼져 있어도 CI는 푸시마다 매니페스트 태그를 올린다. 그래서 "매니페스트의 직전 태그"는 실제로 돌았던 옛 판이 아니다. 옛 코드 테스트가 엉뚱한 판과 비교하게 된다.
- 꺼져 있는 동안 푸시가 여러 번 쌓이면, 켤 때 그 마이그레이션이 한꺼번에 적용된다. 푸시마다 확장 → 축소를 지켰어도, 한 번에 축소까지 가서 옛 파드가 깨질 수 있다. 이 경우는 푸시 단위로 보는 검사로는 A든 B든 못 잡는다.
- 꺼져 있는 동안에는 사용자 요청이 없다. 켤 때의 짧은 롤링 구간만 위험하다.

**고른 것: A.** 정적 검사를 CI에 붙인다. 규칙은 계획서의 4개 + SET_NOT_NULL + CHECK_REPLACED다. 옛 코드 테스트가 없으니 CHECK 축소는 거칠게라도 정적 검사가 맡는다.

옛 코드 테스트는 CI에 붙이지 않고, 클러스터를 켜기 전에 손으로 돌리는 도구로 남긴다. 그때 옛 판은 "끄기 전 마지막으로 돌던 판"을 쓴다.

### 5단계: CI 연결 (`3b13ec2`)

정적 검사는 JUnit 테스트라 CI의 `./gradlew test`에서 이미 돈다. 그래서 워크플로는 테스트 단계에 그 사실을 적는 주석만 더했다. 옛 코드 테스트 스크립트에는 손으로 돌리는 도구이고, 옛 커밋은 운영에서 마지막으로 돌던 판이어야 한다고 적었다.

### 6단계: 클러스터 재가동 전 확인

클러스터는 토요일(11/14) 01:00에 꺼졌다. 끈 시각은 git에 남지 않아서 사용자에게 물었다.

- 그 직전 마지막 태그 커밋은 `732cb39`(11/13 00:38)이고, 이미지는 `6e782b3`이다. 끄기 약 24시간 전이라 ArgoCD가 동기화를 마쳤을 것으로 본다. 그 사이 클러스터가 켜져 있었는지는 확인하지 않았다.
- 그 뒤 main에 쌓인 운영 마이그레이션은 V22~V25와 `R__app_column_comments`다. 정적 검사 기준으로는 모두 안전하다(V22·V25는 CHECK 넓히기, V23·V24는 NULL 허용 열 추가).

옛 코드 테스트로도 확인했다. `6e782b3` 코드 + `60048b1`(당시 main) 스키마 조합이 **통과**했다(새 스키마 적용 10초, 옛 테스트 104초).

## 4. 배운 점

### 원리

- 롤링 배포에서는 "옛 코드 + 새 스키마"가 반드시 생긴다. 그래서 마이그레이션은 바로 앞 판의 코드가 깨지지 않는 변경만 해야 한다. 깨는 변경(NOT NULL 추가, CHECK 축소, 열 삭제)은 확장 → 이전 → 축소로 나눠 배포한다.
- Flyway는 미래 V 버전을 기본으로 무시한다. 그래서 호환 문제는 기동 때가 아니라 SQL을 실행할 때 드러난다. 반대로 반복 마이그레이션(`R__`)은 옛 코드에 없으면 기동 자체를 막는다.
- 정적 검사는 "모양"을 보고, 옛 코드 테스트는 "실제 사용"을 본다. 모양만으로는 CHECK를 넓히는지 줄이는지 알 수 없다. 반대로 실제 사용은 테스트가 그 경로를 지나가야만 보인다.
- 검사가 비교하는 "옛 판"은 실제로 운영에서 돌던 판이어야 의미가 있다. 매니페스트의 직전 태그가 늘 그 판인 것은 아니다.

### 예상과 달랐던 것

- 직전 운영판 조합은 통과할 줄 알았는데 30건이 실패했다. 원인은 데이터팀 미러였다. 테스트 환경은 운영과 달리 데이터팀 표까지 같은 Flyway로 만든다. 그래서 "배포가 바꾸는 것"만 새 판으로 두도록 방법을 고쳐야 했다.
- V15의 진짜 신호는 361건 가운데 몇 건뿐이었다. 옛 테스트 fixture는 옛 앱 코드가 더는 쓰지 않는 값(`CODEF`)도 넣는다. 그래서 옛 코드 테스트의 실패는 "앱 코드에서 났는가, fixture에서 났는가"를 사람이 갈라야 한다.
- 옛 코드가 예외를 잡아 삼키는 곳에서는, 호환 문제가 예외가 아니라 단정 실패로만 드러났다.
- `R__`가 롤백을 막는다는 것은 계획서에 없었다. 1단계에서 처음 알았다.
- 처음 추천(C)은 클러스터가 꺼져 있다는 운영 조건을 빼고 낸 것이었다. 그 조건을 넣자 옛 코드 테스트의 전제(직전 태그 = 실제로 돌던 판)가 무너졌다.

### 다시 한다면

- 옛 코드 테스트의 첫 실행 전에, 두 커밋 사이에서 `db/external`이 바뀌었는지 먼저 보겠다. 미러 차이는 미리 걸러낼 수 있었다.
- 실패를 원인별로 묶는 스크립트를 처음부터 스크립트에 넣겠다. 이번에는 스크래치 스크립트로 따로 돌렸다.
- 추천을 내기 전에 클러스터 가동 방식(계속 켜 두는지, 자주 끄는지)부터 확인하겠다.
