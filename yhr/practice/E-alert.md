## 1. 배경

### 출발한 문제

E-base가 지표 노출 기반과 이름 목록을 만들었다. 그래도 주기 작업이 제대로 도는지 알려 주는 숫자는 아직 LOST 계수기 하나뿐이었다. 확정이 멈춰도, 푸시가 쌓여도, 실행 처리가 계속 실패해도 신호는 warn 로그였다. 한 계좌 때문에 전 사용자의 확정이 멈춘 결함(O1)도 그랬다.

이 단위가 채우는 것은 두 가지다.

- 지표: 사용자 피해로 이어지는 상태를 숫자로 낸다.
- 경보: 그 숫자가 이상하면 사람이 로그를 열지 않아도 알게 한다.

경보는 만들기만 해서는 믿을 수 없다. 그래서 장애를 일부러 넣어 울리는지 보고, 정상 운영에서 울리지 않는지도 본다.

### 계획서의 가설

1. DB를 집계하는 Gauge를 수집 주기(15~30초)마다 돌려도, 쿼리 몇 개라 부하가 작다.
   - 예외로 본 것: 처리 대기 실행 수 count는 collection_run 크기에 비례한다. 그래서 100배에서는 주기를 늘려야 할 수 있다.
2. 다섯 경보 모두, 해당 장애를 넣은 뒤 "경보 지속 시간 + 수집 주기" 안에 울린다.
3. 정상 하루를 돌렸을 때 거짓 경보가 나올 수 있는 곳이 둘(확정 멈춤, 발송 적체) 있다. 정의를 좁히면 0건이 된다.

## 2. 진행

### 2.0 개념

결정에 앞서 다음 개념을 먼저 잡았다.

- **경보 규칙의 평가**: Prometheus는 평가 주기(여기서는 15초)마다 식을 계산한다. 식이 참이면 경보가 pending이 되고, `for` 동안 계속 참이면 firing이 된다. 중간에 한 번이라도 거짓이면 처음부터 다시 센다. 값이 아예 없으면 참이 아니다.
- **증상 경보와 원인 경보**: 사용자 피해 자체(확정이 멈춤, 푸시가 안 나감)를 보는 경보는 원인이 무엇이든 울린다. 그래서 등급을 "즉시"로 둔다. 원인 쪽(실행 처리 실패, 평가 느림, 연결 풀 대기)은 "당일 확인"으로 둔다.
- **Gauge(DB)와 파드별 지표**: DB 상태를 세는 Gauge는 두 복제본이 같은 값을 낸다. 그래서 `max`로 본다. 파드마다 세는 Counter·Timer는 `sum`이나 `by (instance)`로 본다.
- **히스토그램 버킷과 백분위**: 버킷이 30초와 +Inf 둘뿐이면, `histogram_quantile`은 30초 넘는 값을 30으로 잘라 낸다. 이것은 Prometheus 문서에서 읽은 것이고, 직접 재지는 않았다. 그래서 p95 대신 "30초를 넘은 주기의 비율"로 식을 썼다.
- **트랜잭션과 계수**: 재시도되는 트랜잭션 안에서 세면 같은 결과를 두 번 센다. 그래서 커밋된 뒤에 센다.

### 2.1 구현

| 지표 | 자리 | 요점 |
|---|---|---|
| `portfolio.snapshot.stage` Timer | `SnapshotJobs.stage` | 단계 5개 × 결과 2개 조합을 미리 만들어 0으로 낸다 |

처음 주입 1·3은 경보가 울리지 않았다. 원인은 준비 단계에 있었다.

- 정상 경로를 미리 확인하면서 넣은 11/13 실행이, 대상이 모두 정리돼 마감 전에 확정됐다.

### 2.6 대시보드

경보 범위를 마친 뒤 대시보드가 범위에 더해졌다. 목적은 경보를 받은 사람이 처음 여는 화면이다. 클러스터에는 Grafana가 이미 있어서, JSON을 E-cluster에서 운영 Grafana에 가져와 확인한다.

#### 개념

- Grafana는 데이터를 갖지 않는다. 패널마다 PromQL을 Prometheus에 보내 그린다. 경보 식을 그대로 패널에 넣으면 "경보가 보는 숫자"를 그대로 본다.
- 데이터소스 uid를 JSON에 박으면, 다른 Grafana에서는 그 uid가 없어 패널이 비어 나온다. 그래서 데이터소스·job·파드를 대시보드 변수로 두었다.
- 프로비저닝: Grafana가 기동할 때 데이터소스와 대시보드를 파일에서 읽는다. 파일이 원본이고, 화면에서 고친 것은 저장되지 않는다.

#### 배치

위에서 아래로 "사용자 영향 → 어느 단계 → 어느 자원" 순서다.

| 행 | 패널 |
|---|---|
| 경보 조건(6) | 확정 멈춤 · 확정 지연 / 발송 적체 · 가장 오래 기다린 발송 / 수집 끊김 · 수집 성공(up) / 실행 처리 실패 · 가장 오래된 실패 / 평가 주기 느림 · 30초 넘은 주기 비율 / 연결 풀 대기 · 연결을 기다리는 요청 |
| 단계(8) | 스냅샷 단계별 평균 소요 / 스냅샷 오류(분당) / 처리 대기 · 실패 실행 수 / 평가 주기 소요(파드별) / 평가 대상 · 시점 수(파드별) / LOST 비율 / 발송 적체 수 / 발송 결과(분당) |
| 자원(7) | HTTP 요청률(초당) / HTTP 5xx 비율 / HTTP 지연(파드별) / DB 연결 풀(파드별) / JVM 힙(파드별) / GC 멈춤 시간 비율(파드별) / 수집 소요(파드별) |

- 경보 조건 행은 경보 식에서 비교 앞부분을 그대로 그리고, 문턱을 빨간 선으로 겹친다. 선 위쪽은 옅은 빨강으로 칠한다.
- 처음에는 문턱 위아래를 모두 칠했다. 그런데 확정 멈춤처럼 문턱이 0에 가까운 패널은 화면 전체가 빨갛게 돼 읽을 수 없었다. 그래서 문턱 위쪽만 칠하고, 문턱이 보이도록 축의 최댓값을 문턱의 두 배쯤으로 잡았다(값이 크면 축이 따라 늘어난다).
- 런북의 확인 단계는 지표 이름 대신 「패널 이름」을 가리킨다.

#### 결정

사용자가 추천을 골랐고, 완성 뒤 같은 데이터로 고르지 않은 선택지를 그려 비교했다(캡처는 `yhr/practice/E-alert-img/`).

| 11 | 경보 패널 수 | A. 다섯(수집 끊김은 자원 행으로) / B. 여섯 | B | 수집이 끊기면 다른 경보 패널이 비거나 남은 파드 값만 보인다. 그 이유가 같은 행에 있어야 한다 |

## 4. 배운 점

### 원리

- 경보를 믿으려면 일부러 깨 봐야 한다. 이번 주입 6개 가운데 하나(연결 풀 대기)는 설계대로라면 울려야 했지만 울리지 않았다. 규칙 문법이나 promtool 테스트로는 잡을 수 없는 종류다. 지표를 내는 경로 자체가 장애에 휘말렸기 때문이다.
- 지표가 재려는 자원을 지표 수집이 같이 쓰면, 그 자원이 바닥나는 장애에서 지표가 사라진다. "값이 없음"은 경보에서 거짓이다. 그래서 `up == 0` 같은 바깥쪽 경보가 꼭 있어야 한다.
- "기다린 시간"을 지표로 내면 문턱이 곧 지속 시간이다. 개수를 지표로 내고 `for`를 거는 방식보다, 한 번 비었다가 다시 차는 흔들림에 덜 흔들린다.
- Timer는 일이 끝나야 기록한다. 느려지는 장애는 늦게 보이고, 끝나지 않는 장애(멈춤)는 아예 보이지 않는다. 멈춤은 횟수가 오르지 않는 것으로 따로 봐야 한다.
- 지표의 조건은 업무 쿼리와 같은 문자열을 공유하게 했다(`PENDING`, `DUE`). 정의가 따로 놀면 "지표는 0인데 실제로는 밀려 있음"이 생긴다.

- 대시보드의 문턱 표시와 경보 띠는 정상 화면이 아니라 장애 화면에서 읽히는지를 봐야 한다. 정상일 때는 깔끔했던 설정이, 여러 경보가 함께 울리자 읽을 수 없게 됐다.

### 예상과 달랐던 것

- 처음에는 장애 주입의 준비가 맞다고 봤다. 그런데 정상 경로를 확인하면서 넣은 데이터가 확정 상태를 바꿔 주입 두 개가 무효가 됐다. 이 과정에서 "늦게 도착한 과거 날짜 실행이 조용히 무시된다"는 것을 알게 됐다.
- 연결 풀 대기 경보는 부분 대기에는 울리지만, 완전히 바닥났을 때는 울리지 않는다. 결정 전에 예측은 했지만, 수집이 10초 제한에 걸려 6분 30초 동안 한 번도 성공하지 못한 것은 실측으로 처음 봤다.
- 평가 주기 느림의 도달 시간은 `for`보다 "느린 주기 하나의 길이"에 더 좌우됐다(2분).
- Expo 장애는 발송 적체로 잡히지 않는다. 이것은 코드 읽기로 낸 결론이고, 주입하지는 않았다. 실패하면 `next_attempt_at`이 뒤로 밀려 "지금 집을 수 있는 행"에서 빠진다. 다섯 번 실패하면 FAILED로 끝난다. `results{failed}`도 그때에야 오른다. 정상 회차에서 재시도된 연결 실패 한 건이 failed로 세지 않은 것과 맞는다.
- 처리 대기 실행 수 쿼리는 가설의 예외대로 100배에서 0.6초를 넘었다. 그런데 같은 조건에 `reason = 'ERROR'`를 더한 실패 실행 수는 20ms였다. 조건 하나가 계획을 바꾼다.

### 다시 한다면 바꿀 것

- 장애 주입마다 시작 상태를 스크립트로 되돌린 뒤 넣는다. 정상 경로 확인은 주입과 다른 날짜로 한다.
- 상태 감시 스크립트만 믿지 않고, 처음부터 `ALERTS` 시계열로 시각을 확인한다.
- 가짜 외부 서버는 실제 클라이언트로 먼저 한 번 보내 본다. 이번에는 chunked 본문을 읽지 못해 첫 발송이 실패했다.

## 5. 남은 것

### 이 단위에서 하지 않은 것

- 실시간 24시간 정상 회차. 압축 회차의 조건은 다음과 같다.
  - 마감을 02:25로 옮겼다.
  - 계좌 2개만 썼다.
  - 장중 시세가 없어 평가 시점 0이었다.
  - Expo는 가짜 서버였다.
- Expo 장애 주입(가짜 서버가 실패를 돌려주게 하기)
- 평가가 끝나지 않는 멈춤의 주입. 지금 식으로는 비율이 NaN이라 울리지 않는다. 런북에 `rate(..._count[5m]) == 0`을 적어 두었다

### 다른 단위로 넘긴 것

- E-cluster: 대시보드 JSON을 운영 Grafana에 가져와 확인한다. 운영 Grafana 버전과 schemaVersion 41 호환, 운영 Prometheus의 job 라벨(변수가 고른다)을 본다.

- E-cluster
  - 운영 Prometheus의 수집 대상과 경보 수신처를 확인한다.
  - 전송 실패율 경보(`rate(results{failed}) > rate(results{sent})`)를 정한다. Expo 장애를 잡기 위해서다.
  - 평가 멈춤 경보를 정한다.
- B(부하) 또는 E-cluster: DB Gauge를 별도 스레드가 계산해 두고 수집은 읽기만 하는 구조(결정 10의 B). 연결 풀 대기 경보가 완전히 바닥난 상태에서도 울리게 된다. 계산이 멈췄을 때 값이 낡는 것을 막을 "마지막 계산 뒤 지난 시간" 지표가 함께 필요하다.
- A-batch(A2): 처리 대기 실행 조건이 100배에서 0.6~0.8초다. 생성기의 `pending()`도 같은 조건이라 회차마다 같은 비용이 든다. 인덱스나 조건을 바꾸면 Gauge도 같이 빨라진다.
- B: 연결 풀 대기 문턱(임시값)을 대기가 생기기 시작하는 VU로 다시 정한다.
- 미정(경보 없음): 뒤 날짜가 확정된 뒤 도착한 과거 날짜 실행은 `FINAL_EXISTS`·`OLDER_THAN_EXISTING`으로 조용히 건너뛰어진다. 이것이 정상 흐름인지, 알아야 할 일인지는 정하지 않았다.
