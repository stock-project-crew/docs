- **작성일**: 2026-10-11
- **기간**: 2026-10-12(월) ~ 2026-11-01(일). 영업일 15일
- **대상**: `back-end/` · `front-end/` · `dataeng/` 연계 전체
- **근거 스펙**: [포트폴리오 스펙](../specs/portfolio-management/2026-07-28-portfolio-management-spec.md) · [알림 스펙](../specs/buy-sell-timing-alert/2026-07-12-buy-sell-timing-alert-spec.md) · [데이터 요구사항](../specs/data-requirements.md) · [앱 정보 구조](../specs/app-information-architecture.md)

**Goal:** 3주 끝에 두 가지를 손에 쥔다 — ① 두 기능의 기능과 분기를 훑은 **케이스 결과표**, ② 실계좌·실데이터로 영업일 10일 이상 끊기지 않고 돌아간 **운영 기록**. 그 과정에서 찾은 결함은 등급별로 정리되고 S1·S2는 닫힌다.

## 1. 두 테스트의 역할

| | 통합테스트 | 운영테스트 |
|---|---|---|
| 목적 | 기능과 분기를 **전수로 훑는다** | 사용자가 되어 **실제로 쓸 수 있는지 본다** |
| 데이터 | 시드·픽스처. 값을 내가 정한다 | 실계좌·실데이터. 값을 내가 못 정한다 |
| 시간 | 언제든 돌린다. 반복 가능 | 장이 열리고 날이 흘러야 관측된다 |
| 자동화 | 대부분 가능 | 불가능. 사람이 본다 |
| 찾는 것 | 분기 누락, 경계값, 오류 처리 | 설계가 놓친 현실, 체감 문제, 운영 사고 |
| 판정 | 기대값과 일치하는가 | 쓸 만한가. 믿을 수 있는가 |

둘은 대체 관계가 아니다. 통합테스트는 `DATA_MISSING`이 뜨는 것을 확인하고, 운영테스트는 **그게 실제로 얼마나 자주 뜨는지**를 알려준다.

여기에 성격이 또 다른 하나가 붙는다 — **데이터 품질·계약 검사**(§5). 분기가 아니라 **데이터 자체**가 약속한 모양인지 보는 일이고, 1회성이 아니라 매일 돈다.

## 2. 3주 일정

### 일정이 이렇게 된 이유

**운영테스트는 시간을 먹는다.** 일봉은 거래일 1회, 장중 스냅샷은 장중에만 온다. `streak(3거래일 연속)`은 가동 후 3영업일이 지나야 처음 관측되고, `EDGE_REARM` 재발화는 조건이 참→거짓→참을 거쳐야 한다. 미국 장은 한국 시간 밤에 열린다.

그래서 **가동과 관찰을 분리한다.**

| | 언제부터 | 왜 |
|---|---|---|
| 포트폴리오 스냅샷 | **1주차 화 (10/13)** — 계좌를 붙이는 날 | `position_line`이 하루 한 벌 쌓인다. 3주차에 자산 변화·일간 변화를 볼 이력이 그때부터 만들어진다 |
| 알림 평가기 | **2주차 월 (10/19)** | 가동일부터 10/30까지 영업일 10일을 확보한다. 3주차에 켜면 5영업일뿐이고 연속·재발화 조건을 못 본다 |
| 집중 관찰 | **3주차 (10/26~)** | 쌓인 기록을 해석하고, 자연히 안 생기는 분기를 인위적으로 만든다 |

즉 3주차는 "가동 개시"가 아니라 **"집중 관찰 + 인위적 분기 생성"** 주차다. 가동은 그 전에 켜둔다. 켜두는 것 자체는 사람 손이 안 간다.

관측 가능성을 보고 고른다. 가동 후 열흘 안에 각 분기가 적어도 한 번 열려야 한다.

- **반드시 울릴 것** — 기준값을 현재가에 바싹 붙인 가격 알림. 국내 1건 · 미국 1건
- **며칠 걸리는 것** — `streak(3거래일)` 종가 조건
- **장중에만 도는 것** — `persist_min` 지속 조건
- **안 울리는 게 정상인 것** — 기준값을 멀리 둔 알림. **오발화를 잡는다**
- **발화 방식 3종** — `EDGE_REARM` · `ONE_SHOT` · `COOLDOWN` 각 1건
- **프리셋 1건** · **조립형 다지표 AND 1건**
- **수급 조건 1건** — 확정치 도착 시점이 맞는지

## 3. 준비

준비가 테스트의 절반이다. 여기서 막히면 3주가 1주가 된다. 각 항목에 **막히면 어떻게 하나**를 함께 적는다.

### 3.1 테스트 환경 — 세 갈래

| 어디 | 무엇을 | 파이프라인 | 쓰기 |
|---|---|---|---|
| **로컬 + CI** | 분기 전수. 결함 주입·재생 | 없음 — **의도된 것** | 자유 |
| **클러스터 테스트 DB** | 실제 배포 형상이 필요한 케이스 | 없음. 필요하면 운영 쪽에서 읽어 복사 | 자유 |
| **클러스터 운영 DB** | 알림 연속 가동 · 포트폴리오 실계좌 | 꽂힘 | **사용자 행위만** |

- [ ] 클러스터 안에 **테스트용 데이터베이스를 따로 둔다.** 같은 Postgres 인스턴스, 다른 database. 파이프라인은 운영 쪽에만 꽂는다.
- [ ] 통합테스트가 운영 DB에 쓰지 않는지 확인한다. 실수로 섞이는 사고가 가장 흔하다.

**통합테스트가 운영 DB에 쓰지 않는 이유** — 그 DB가 실사용자를 가졌기 때문이 아니다. **그 DB에서 운영테스트가 영업일 10일간 연속 가동되기 때문**이다.

1. 쌓이는 발화 이력·평가 상태·일지가 산출물인데, 테스트 데이터가 섞이면 "이 발화가 실제냐 테스트냐"를 못 가린다.
2. 결함 주입(가짜 휴장일, 완료 신호 삭제, 스냅샷 시각 밀기)이 운영 DB에 걸리면 실제 알림이 오발화하거나 안 울린다. 종료 조건의 "오발화 0건"을 판정할 수 없게 된다.
3. 통합테스트는 같은 입력에 같은 결과가 나와야 하는데 운영 DB는 매일 변한다. 골든 비교가 성립하지 않는다.
4. 백엔드 CI는 매 푸시마다 실제 Postgres로 테스트를 돌린다. 그게 운영이면 배포 파이프라인이 운영 데이터를 건드리는 구조가 된다.

**읽기는 반대로 권한다.** 운영 DB를 읽어 통합테스트 시드로 복사하면 픽스처보다 데이터 모양이 정확하다. 쓰기만 막는다.

### 3.2 테스트 사용자

회원가입 경로가 없다(포트폴리오 스펙 §12). 사용자 행은 마이그레이션이 심는다.

- [ ] **운영테스트용 1명** — 본인. 실계좌를 붙인다
- [ ] **스코프 격리 확인용 1명** — 계좌를 붙이거나, 남의 계좌만 있는 상태로 둔다
- [ ] 생성 절차를 문서로 남긴다 — BCrypt 해시 생성, INSERT, 롤백
- [ ] 비밀번호·해시를 저장소에 커밋하지 않는다

`UserScopeIsolationTest`가 이미 격리를 검증하지만, **배포 환경에서 실제로 남의 데이터가 안 보이는지는 사람이 한 번 봐야 한다.**

### 3.3 계좌 연동

**이날부터 포트폴리오 스냅샷이 쌓인다.** 늦추면 3주차에 볼 자산 변화 이력이 그만큼 짧아진다.

- [ ] **계좌를 2개 이상 확보한다.** 멀티계좌 합산이 이 기능의 존재 이유이므로 1개로는 핵심이 검증되지 않는다
  - 막히면: 1개로 돌리고 합산·계좌별 뷰·계좌 필터는 시드로만 덮는다. **범위 제외로 기록한다**
- [ ] `account.source` 두 갈래(`KIS` · `CODEF`) 중 어디까지 붙는지 확인한다
- [ ] 자격증명은 시크릿 매니저에만 둔다. DB에는 `credential_ref`만 들어간다
- [ ] `link_state` 4상태(`CONNECTING` · `CONNECTED` · `REAUTH_REQUIRED` · `DISCONNECTED`)를 **한 번씩 실제로 만든다.** 연동 → 해제 → 재연동 → 자격증명 무효화
- [ ] 보유 종목이 **국내·미국 양쪽에 있는지** 확인한다. 한쪽만이면 `PRICE_LAG_MARKET`·환율·통화 병기 분기가 안 열린다
  - 막히면: `alert_watchlist`에만 미국 종목을 올려 알림 쪽만 덮는다

### 3.4 데이터 실연계 확인

**운영테스트의 유일한 블로커다. 10/12 월요일 첫 일로 확인한다.**

[데이터 요구사항](../specs/data-requirements.md)의 테이블별로 흐르는지 본다. 품질까지 보는 건 §5이고, 여기선 **오느냐 안 오느냐**만 본다.

- [ ] 종목 마스터 — 채워져 있고 검색이 되나
- [ ] 수정주가 일봉 — 국내 300거래일이 있나. 미국은 어느 종목까지 오나
- [ ] 투자자별 순매수 — 확정치가 다음 영업일 개장 전에 오나
- [ ] 장중 스냅샷 — `alert_watchlist` 기반으로 5분마다 오나. 앱 DB `data` 스키마에 직접 들어오나
- [ ] `market_data_run` — `DONE`이 찍히나
- [ ] 영업일 캘린더 — `open_at` · `close_at`이 있나
- [ ] 포트폴리오 쪽 — `cln_*` · `collection_run` · `fx_rate` · `etf_constituent` · 커버리지
- [ ] 백엔드 역할이 `data` 스키마를 읽을 권한이 있나

**막히면:** 어느 테이블까지 되는지 선을 긋고, 안 되는 것에 의존하는 기능은 시드로만 덮는다. 운영테스트 범위를 줄이되 **가동일을 미루지 않는다** — 되는 것부터 켠다.

### 3.5 실기기와 푸시

알림 스펙 §9.6이 v1 플랫폼을 제약한다. **마지막 주에 확인하면 늦는다.**

- [ ] iOS 실기기에 Expo Go로 앱이 올라가나 — **Expo Go SDK 상한 54.** 그보다 최신 SDK면 실기기가 거부한다
- [ ] 수신 권한을 허용하면 `push_device`에 토큰이 등록되나
- [ ] **실제로 푸시 한 건이 기기에 도착하나** — 앱이 떠 있을 때 / 백그라운드 / 완전히 꺼져 있을 때 각각
- [ ] 푸시를 탭하면 의도한 화면이 열리나
- [ ] Android는 앱 안 알림만인 제약이 화면에서 어떻게 보이나
- [ ] 로그아웃 시 기기가 지워지고 `DeviceNotRegistered` 영수증이 처리되나

**막히면:** 발송 대기열(`alert_delivery`)까지 쌓이는 것으로 판정하고 실기기 수신은 **범위 제외로 기록**한다. 다만 기능의 마지막 한 칸이라 가능하면 끝까지 붙잡는다.

### 3.6 관측 수단 — 운영테스트의 전제

**관측이 없으면 운영테스트 결과를 해석할 수 없다.** 알림이 안 울렸을 때 조건이 거짓이어서인지, 데이터가 안 와서인지, 평가기가 죽어서인지 구분이 안 되면 그날의 관찰은 기록할 값이 없다.

대시보드는 필요 없다. 조회 수단 하나면 된다.

- [ ] 마지막 `market_data_run` 수신 시각 — 시장 · 종류별
- [ ] 직전 평가 사이클 — 평가 건수 / 발화 건수 / 건너뛴 건수와 사유 / 소요 시간
- [ ] `alert_delivery` 상태별 건수와 마지막 실패 사유
- [ ] 알림별 마지막 평가 시점과 결과 — 참 / 거짓 / 확인 불가 + 사유
- [ ] 포트폴리오 — 마지막 `collection_run` · `sync_run` 상태, 계좌별 `source_as_of`, 캐리포워드 여부

운영자 조회 API 하나 또는 psql 질의 묶음으로 충분하다. **에이전트에 맡길 수 있다.**

### 3.7 CI 보강

- [ ] **프론트엔드 CI가 없다.** 테스트 18개가 있는데 아무것도 자동으로 안 돈다. 워크플로 하나로 테스트·린트·타입체크를 게이트로 만든다
- [ ] 백엔드 CI는 이미 실제 Postgres로 테스트를 돌리고 통과하지 못한 이미지를 올리지 않는다. 그대로 쓴다
- [ ] 새로 쓰는 통합테스트가 CI에서 돌아가는지 확인한다. 로컬에서만 도는 테스트는 2주 뒤에 썩는다

### 3.8 DB 백업 — 보험

운영 DB가 클러스터 안의 단일 파드다(`back-end/k8s/postgres.yaml`). 3주간 쌓는 운영 기록이 산출물이므로 중간에 날아가면 메울 수 없다.

- [ ] `pg_dump` CronJob을 걸고 산출물을 클러스터 밖에 둔다
- [ ] **복구를 한 번 실제로 해본다.** 해보지 않은 백업은 백업이 아니다

## 4. 테스트 설계

### 4.1 두 층으로 나눈다

- **시나리오** — 사용자 여정 단위. "처음 로그인해서 계좌를 붙여 알림을 걸고 받기까지". **운영테스트가 이 층을 돈다**
- **케이스** — 분기 단위. "장중 스냅샷이 11분 늦었을 때 평가하지 않고 배너를 띄운다". 수백 건. **통합테스트가 이 층을 돈다**

시나리오는 **이야기가 끊기지 않는지**를, 케이스는 **분기가 빠지지 않았는지**를 본다.

**설계는 위에서 아래로 간다 — 시나리오를 먼저 확정하고 케이스를 뽑는다.** 시나리오가 지나는 길에 걸리는 분기가 1등급이 되고, 지나지 않는 분기는 등급이 내려간다. 케이스를 먼저 뽑으면 수백 건이 전부 같은 무게로 쌓여 무엇이 중요한지 가릴 기준이 없다.

### 4.2 시나리오 — 운영테스트가 도는 길

**이것이 테스트 설계의 출발점이다.** 아래 목록은 **제목이지 설계가 아니다.** 그대로 쓰지 말고 검토하고 다시 설계한다.

#### 초안

- [ ] S1 가입된 사용자가 **처음 로그인**해 계좌를 붙이고 6개 뷰를 둘러본다
- [ ] S2 계좌가 2개일 때 합산과 계좌별이 **서로 맞는다**
- [ ] S3 **다음 날** 다시 들어와 일간 변화와 자산 변화를 본다
- [ ] S4 ETF를 분해해 보고(렌즈), 분해 불가 표시를 이해한다
- [ ] S5 실현손익을 기간별로 본다
- [ ] S6 **알림을 조립형으로 만든다** — 지표 · 변형 · 연산자 · 기준값
- [ ] S7 **알림을 프리셋으로 만든다**
- [ ] S8 종가 알림이 **실제로 울리고 푸시를 받는다**
- [ ] S9 장중 알림이 **장중에 울린다**
- [ ] S10 미국 종목 알림이 **밤에 울린다**
- [ ] S11 울린 알림을 **재무장**하고 다시 울린다
- [ ] S12 데이터가 늦은 날 **배너를 보고 상황을 이해한다**
- [ ] S13 알림을 수정·삭제하고 중복 경고를 본다
- [ ] S14 계좌 재인증을 요구받고 복구한다
- [ ] S15 **두 기능을 번갈아 쓰며** 길을 잃지 않는다 — [앱 정보 구조](../specs/app-information-architecture.md)대로

#### 각 시나리오에 적을 것

| 항목 | 내용 |
|---|---|
| 전제 | 어떤 상태에서 시작하나 — 사용자 · 계좌 · 보유 · 알림 · 데이터 |
| 단계 | 사용자가 하는 조작을 순서대로. **화면 이름은 [앱 정보 구조](../specs/app-information-architecture.md) §6을 쓴다** |
| 단계별 기대 | 각 단계에서 무엇이 보여야 하나 |
| 근거 절 | 스펙 어디에 그렇게 적혀 있나 |
| 관측 수단 | 무엇으로 확인하나 — 화면 / API 응답 / DB / 푸시 / 관측 조회(§3.6) |
| 실데이터 가능 여부 | 실데이터로 되나, 주입·재생이 필요하나(§6) |
| 판정 | 무엇을 보면 통과인가. **애매한 판정은 시나리오가 덜 설계된 것이다** |
| 소요 | 한 번 도는 데 얼마나 걸리나. 3주차에 매일 돌 수 있는 분량인가 |

#### 검토 지침

- **전수성을 따진다.** 초안이 두 기능의 주요 여정을 다 덮는지 본다. 초안에 없어 보이는 것 —
  알림 일시중지·재개, 울린 알림 읽음 처리와 배지, 기기 등록·해제, 로그아웃과 재로그인,
  종목 검색, 빈 상태(계좌가 없는 사용자 · 보유가 없는 계좌 · 알림이 없는 사용자)
- **돌 수 없는 것은 지우지 않고 유보로 둔다.** 구현이 없어 못 도는 시나리오는 "왜 못 도는지"와 함께
  남긴다. 공백이 메워지면 되살린다(§4.7)
- **중복과 과잉을 걷어낸다.** 두 시나리오가 같은 길을 지나면 하나로 합친다. 개수를 채우려고 쪼개지 않는다
- **승인을 받고 케이스로 넘어간다.** 시나리오가 확정되지 않은 상태에서 뽑은 케이스는 등급을 매길 기준이 없다

각 시나리오에 **"사용자가 되어 본 느낌"**을 한 줄 남긴다. 이게 운영테스트의 고유 산출물이다. 통합테스트는 "맞다/틀리다"만 알려주고 "쓸 만한가"는 말해주지 않는다.

### 4.3 케이스는 스펙에서 추출한다

두 스펙이 이미 "이럴 때 이렇게 동작한다"를 전수로 적어놨다. 케이스 목록은 그걸 옮기는 작업이고, 새로 생각할 것이 아니다.

| 출처 | 추출되는 케이스 |
|---|---|
| 포트폴리오 §10 화면 상태 전수 | 6뷰 × 화면 상태 |
| 포트폴리오 §8.2 응답 봉투 | notice 16종 × 발생 조건 |
| 포트폴리오 §8.6 오류와 빈 상태 | `empty_reason` 5종 |
| 포트폴리오 §4.4 · §4.5 | 신뢰도 4등급 + `ca_unknown` + SEEDED 표시 정책 |
| 포트폴리오 §3.4 렌즈 | `lens_safe` 3값 × 뷰 |
| 포트폴리오 §3.3 · §3.7 | 축·필터 조합, 통화 병기 가능·불가 |
| 포트폴리오 §7.2 · §7.3 · §7.5 | 계좌 4상태, 캐리포워드, 부분 실패 표시 정책 |
| 포트폴리오 §9 검증 규칙 | 런타임 불변식 위반 시 거절 |
| 포트폴리오 §3.8 | 사용자 스코프 — 남의 데이터 · 남의 `as_of` |
| 알림 §15 화면 상태 전수 | 알림 화면 × 상태 |
| 알림 §6.1 ~ §6.9 | 3값 평가 · 발화 3방식 · 첫 평가 · 재무장 · 조건 변경 · 중복 경고 · 삭제 · 발화 문구 |
| 알림 §7.1 ~ §7.4 | 완료 신호 · 확인 불가 사유 전종 · 보정 의심 · 사용자 표시 |
| 알림 §3.1 ~ §3.3 | 두 평가 시점 · 시장별 지원 · 중단 후 따라잡기 |
| 알림 §5.1 ~ §5.3 | 지표 × 변형 × 연산자 × 프리셋 |
| 알림 §8.3 · §8.4 · §14.4 | 재시작 · 되돌리기 · 런타임 불변식 |
| 알림 §9.3 ~ §9.6 | 발송 · 영수증 · 권한 거부 · 기기 없음 · 플랫폼 제약 |
| 알림 §11.4 | API 오류 전종 |
| 데이터 요구사항 "충족 안 될 때" | 테이블별 미충족 시 동작 |

- [ ] 위를 돌며 케이스를 **하나의 표로** 뽑는다. 열: `ID · 기능 · 분기 · 전제 · 조작 · 기대 · 근거 절 · 시나리오 · 실행 환경 · 등급 · 수단 · 결과`
- [ ] **"시나리오" 열에 그 케이스가 지나는 승인된 시나리오를 적는다.** 등급 판단의 근거가 된다. 어느 시나리오도 지나지 않는 케이스는 3등급 후보다
- [ ] **"근거 절"을 반드시 채운다.** 근거 없는 케이스는 내가 상상한 기대값이고, 그게 스펙과 다르면 멀쩡한 코드를 고치게 된다

### 4.4 이미 있는 테스트와 겹치는 것을 먼저 걷어낸다

**이 단계를 건너뛰면 2주차를 중복 작업에 쓴다.** 백엔드에 테스트 파일 52개와 6뷰 골든 파일이 있고 프론트에 18개가 있다.

- [ ] 케이스마다 **이미 덮는 테스트가 있는지** 표시한다. 있으면 `자동-기존`
- [ ] 없으면 `자동-신규`(테스트를 쓴다) 또는 `수동`(사람이 돈다)으로 나눈다
- [ ] 자동으로 되는 건 자동으로 돌린다. **사람의 시간은 수동으로만 되는 것에 쓴다** — 실기기 푸시, 실계좌 연동, 체감 속도, 화면이 이해되는지

이미 있는 구조 강제 테스트는 그대로 둔다 — `ArchitectureRulesTest` · `MigrationLintTest` · `SchemaContractTest` · `CatalogInvariantTest` · `PositionLineInvariantsTest` · `UserScopeIsolationTest`.

### 4.5 실행 환경 — 케이스 표는 하나, 실행은 셋

파이프라인 연계 테스트를 **별도 표로 두지 않는다.** 기대값과 근거 절이 통합테스트와 같고, 다른 건 입력을 누가 주느냐뿐이다. 표를 나누면 둘을 대조할 수 없다.

| 값 | 어디서 | 어떤 케이스 |
|---|---|---|
| `로컬` | 로컬 + CI | 결함 주입·재생이 필요한 것 — 가짜 휴장일, 이력 자르기, 20일 연속, 보정 누락 |
| `연계` | 클러스터 테스트 DB | 파이프라인이 있어야만 되는 것 — 도착 타이밍, 5분 주기 준수, 미러 스키마 실물, `data` 읽기 권한 |
| `둘 다` | 양쪽 | **1등급 핵심.** 로컬에서 분기를 만들어 확인하고, 연계에서 같은 기대값으로 한 번 더 |

`둘 다`가 이 설계의 핵심이다. 로컬에서 "지연 11분이면 평가하지 않는다"를 주입으로 확인하고, 연계에서 실제 지연이 났을 때 같은 일이 벌어지는지 본다. **기대값이 하나이므로 결과가 갈리면 그게 바로 결함이다.**

### 4.6 등급 — 전수를 다 돌 수 없다는 것을 인정한다

| 등급 | 기준 | 목표 |
|---|---|---|
| **1등급** | 틀리면 사용자가 **잘못된 숫자를 믿거나 알림을 못 받는다** | 100% 실행 |
| **2등급** | 틀리면 화면이 이상하지만 판단을 망치지 않는다 | 90% 이상 |
| **3등급** | 극단 경계값, 동시성, 비정상 입력 | 기록만. 시간 남으면 |

1등급의 예 — 신뢰도 등급 판정, 가산성(금액 합산), 사용자 스코프, 엣지 발화 1회, 허용 지연 초과 시 미평가, 결측 시 미발화 대신 확인 불가 표시.

### 4.7 범위 제외 — 지금 못 덮는 것

덮을 수 없는 이유가 **구현이 없기 때문**인 것들. 결함이 아니라 미구현이므로 분리해 기록한다.

- **입출금 입력** — 테이블·매퍼·읽기 경로는 있으나 POST 엔드포인트와 입력 화면이 없다. 자산 변화 뷰의 "투자손익 = 잔차" 정의가 입출금 입력을 전제하므로 **설계의 핵심 주장 하나가 화면에서 검증되지 않는다.** 통합테스트는 DB에 직접 넣어 계산만 검증한다
- **종목 상세 화면**(포트폴리오 스펙 §2.10) — 화면이 없다
- 알림 스펙 §17이 의도적으로 미룬 것들 — OR 트리 · 혼합 timeframe · 백테스트 · 알림 공유

## 5. 데이터 품질·계약 검사

데이터 요구사항이 약속한 모양대로 왔는지 **데이터 자체를 검사**한다. 통합테스트와 성격이 다르다 — 기능 분기와 무관하고, 1회성이 아니라 **매일 돈다.** 어제 맞았던 데이터가 오늘 틀릴 수 있다.

- **어디서**: 클러스터 운영 DB를 **읽기 전용**으로
- **언제부터**: 2주차 수(10/21)부터 3주차 끝까지 매일
- **산출물**: 검사 질의 묶음 + 매일의 결과 한 줄

### 검사 항목

**종목 마스터**
- [ ] 행 수와 시장별 분포. 국내 전 상장 · 미국 NYSE·NASDAQ이 들어왔나
- [ ] `name` · `symbol` · `market` · `currency`의 null 비율
- [ ] 보유 종목과 `alert_watchlist` 종목이 **빠짐없이 있나**
- [ ] 이름·종목코드 부분 일치 검색이 되나

**수정주가 일봉**
- [ ] 종목별 이력 길이 **≥ 300거래일**
- [ ] 거래일 중 빈 날 — 캘린더와 대조
- [ ] OHLC 불변식 — `low ≤ open, close ≤ high`, `volume ≥ 0`
- [ ] **보정 계열인가** — 과거 분할 종목의 분할 전후가 연속인지
- [ ] 키가 `instrument_id`인가

**투자자별 순매수**
- [ ] 이력 길이 **≥ 30거래일**
- [ ] 금액 단위가 원인가. 순매도가 음수로 오나
- [ ] **확정치인가** — 같은 날짜를 하루 뒤 다시 읽어 값이 변하지 않는지

**장중 스냅샷**
- [ ] 스냅샷 간격 **≤ 5분**. 결손 구간의 길이와 횟수
- [ ] `price > 0`, `cum_volume`이 당일 안에서 단조 증가
- [ ] 대상이 `alert_watchlist`와 일치하나
- [ ] 보관이 당일분 이상인가 — 미국은 현지 거래일 기준

**`market_data_run`**
- [ ] `DONE` 시각의 분포. 약속한 도착 시점을 지키나
- [ ] **`DONE`인데 종목이 누락된 경우가 없나** — 일부만 적재된 `DONE`은 빠진 종목을 `NO_TRADE`로 오판시킨다
- [ ] `FAILED` 발생률

**영업일 캘린더**
- [ ] `is_trading_day`가 실제와 맞나
- [ ] `prev_trading_day` · `next_trading_day` 연결이 끊긴 날이 없나
- [ ] `open_at` · `close_at`이 채워져 있나

**포트폴리오 쪽**
- [ ] `cln_*` 중복 행
- [ ] **`trade_id` 안정성** — 재수집 후 같은 체결이 같은 값인가
- [ ] `fx_rate` 결측과 폴백 길이
- [ ] `etf_constituent` 비중 합과 `as_of` 최고령
- [ ] `ca_coverage` · `etf_coverage`로 "없음"과 "미확보"가 구분되나

### 검사가 실패하면

**데이터팀에 전달할 결함으로 분리해 기록한다.** 우리 코드 결함과 같은 목록에 섞지 않는다 — 고치는 주체가 다르고, 고쳐지기까지 우리가 할 수 있는 건 기능이 그 상황을 견디는지 확인하는 것뿐이다. 그 확인은 §6의 주입으로 한다.

## 6. 결함 주입과 재생

### 왜 필요한가 — 3주 창에서 자연 관측이 안 되는 것

| 분기 | 왜 안 되나 | 어떻게 하나 |
|---|---|---|
| 국내 휴장일 | 10/12~10/30에 주말 외 휴장일이 없다(캘린더로 확인할 것) | 캘린더 주입 |
| 20거래일 연속 조건 | 가동 기간이 영업일 10일이다 | 과거 데이터 재생 |
| 데이터 결측·지연 | 데이터팀이 정상 운영하면 안 생긴다 | 신호·시각 주입 |
| 기업행위 보정 누락 | 해당 종목에 기업행위가 있어야 한다 | 과거 분할 종목 재생 |
| 계좌 재인증 요구 | 증권사 사정이다 | 자격증명 무효화 |
| 수집 부분 실패 | 드물게 생긴다 | 일부만 성공시키기 |

**이 수단을 만들지 않으면 스펙의 "충족 안 될 때" 분기를 3주가 지나도 한 번도 못 본다.** 그리고 이 수단이 그대로 통합테스트의 절반이다 — 재생이 있으면 "3일 연속 순매수"를 3일 기다리지 않고 검증할 수 있다.

### 수단

각 항목에 **되돌리기**를 함께 만든다. 되돌릴 수 없는 주입은 쓰지 않는다.

- [ ] 특정 시장·종류의 완료 신호를 **늦추거나 빼기** → `DATA_MISSING` · `MARKET_DATA_DELAYED`
- [ ] 특정 종목의 일봉 이력을 **잘라내기** → `INSUFFICIENT_HISTORY`
- [ ] 장중 스냅샷의 시각을 **과거로 밀기** → 허용 지연 초과(국내 10분 / 미국 20분)
- [ ] 캘린더에 **가짜 휴장일 심기** → `NO_TRADE` · 연속 조건 끊김 · 개장 지연 판정
- [ ] 과거 일봉 구간을 **재생**해 평가기에 먹이기 → 20일 연속, 보정 누락, 박스권 돌파
- [ ] 수집을 **일부만 성공**시키기 → 포트폴리오 부분 실패 표시 정책(스펙 §7.5)
- [ ] 평가기를 **며칠 멈췄다 켜기** → 따라잡기(알림 스펙 §3.3 · §8.3)

### 안전장치

- [ ] 주입 수단은 **환경 플래그 뒤에** 둔다. 운영 DB를 가리키는 설정에서는 동작하지 않는다
- [ ] 주입 전 상태를 기록하고, 테스트 후 **되돌린 것을 확인한다**
- [ ] 3주차 월요일에 쓰는 주입은 클러스터 테스트 DB에서 돈다. 운영 DB의 알림 가동을 건드리지 않는다

## 7. 운영테스트 운영 방식

10/19 가동일부터 3주차 끝까지 **하루 30분~1시간.** 루틴을 고정한다. 2주차에는 통합테스트와 병행하므로 짧게, 3주차에는 길게 본다.

### 아침 — 장 전, 09:00 이전

- [ ] 관측 조회 — 간밤 미국 일봉·수급 확정치가 왔나. `market_data_run`에 `DONE`이 찍혔나
- [ ] 미국 알림이 울렸나. 울렸으면 푸시가 왔나. **안 울렸으면 왜 안 울렸는지 관측으로 구분한다** — 조건 거짓인가, 확인 불가인가, 평가기가 안 돌았나
- [ ] 데이터 품질 검사 결과 확인(§5)
- [ ] 앱을 열어 6개 뷰를 본다. 어제와 숫자가 이어지나. 배너가 떴으면 내용이 이해되나

### 장중 — 1회

- [ ] 장중 스냅샷이 5분 주기로 오나. 허용 지연을 넘지 않나
- [ ] 장중 알림이 평가되고 있나. 사이클 소요 시간이 주기보다 짧나

### 저녁 — 장 마감 후

- [ ] 국내 일봉이 당일 중에 왔나. 종가 알림이 평가됐나
- [ ] `alert_delivery`에 실패가 쌓이지 않았나
- [ ] 그날의 포트폴리오 스냅샷이 생겼나. 캐리포워드면 왜인가

### 일지

`docs/yhr/operations/2026-10-operation-log.md` 한 파일에 날짜순으로 쌓는다.

```
## 10/22 (목)
- 데이터: KR 일봉 18:40 DONE · US 일봉 07:10 DONE · 수급 08:20 DONE · 장중 결측 2회(10:35, 14:05)
- 품질검사: 통과. 단 미국 일봉 3종목 이력 280일 (< 300) → DT-003
- 알림: 평가 7건 / 발화 1건(삼성전자 가격) / 확인 불가 2건(INSUFFICIENT_HISTORY)
- 푸시: 1건 발송 · 1건 수신 확인(iOS, 백그라운드, 지연 4초)
- 포트폴리오: 정상. 계좌 2개 모두 source_as_of 당일
- 이상: 장중 결측 2회 동안 배너가 안 떴다 → D-012
- 느낌: 발화 문구에 기준일이 없어 "언제 기준인지" 헷갈렸다 → D-013
```

**"느낌" 줄을 반드시 쓴다.** 통합테스트가 절대 찾아주지 않는 결함이 거기서 나온다.

## 8. 결함 관리

### 두 목록을 따로 둔다

| 목록 | 무엇 | 고치는 주체 |
|---|---|---|
| **D-** 결함 | 우리 코드가 설계대로 동작하지 않는다 | 백엔드 · 앱 |
| **DT-** 데이터 결함 | 데이터가 요구사항대로 오지 않는다 | 데이터 |

섞으면 "우리가 고칠 수 있는 게 몇 개인가"가 안 보인다. DT-는 전달하고, 고쳐지기 전까지 **그 상황을 기능이 견디는지**를 §6 주입으로 확인한다.

### 등급과 처리

| 등급 | 뜻 | 처리 |
|---|---|---|
| **S1** | 못 쓴다. 틀린 숫자를 믿게 되거나 알림이 안 온다 | 즉시. 동결 후에도 고친다 |
| **S2** | 기능이 깨졌지만 우회로가 있다 | 동결 전까지 |
| **S3** | 표시·문구 문제 | 시간 남으면 |
| **S4** | 사소함 | 기록만 |

### 기록

열: `ID · 발견일 · 발견 경로(통합/연계/운영/품질) · 등급 · 현상 · 기대 · 근거 절 · 상태 · 수정 커밋`

- **결함마다 근거 절을 적는다.** 적을 근거가 없으면 결함이 아니라 **스펙 공백**이다. 별도 목록으로 분리하고 코드를 고치기 전에 보고한다
- **S1 · S2를 고칠 때는 자동 테스트를 함께 남긴다.** 안 남기면 같은 게 돌아온다
- **10/28 동결 후에는 S1만 고친다.** 그 외는 목록에 적고 넘긴다

## 11. 사람과 에이전트

| 에이전트 | 사람 |
|---|---|
| **시나리오 설계(§4.2)** — 초안 검토 · 재설계 · 전수성 점검 | **시나리오 승인** — 어느 길을 반드시 돌 것인지 결정 |
| 케이스 추출(§4.3) — 스펙에서 표로 옮기기 | 등급 부여 — 무엇이 치명적인지 판단 |
| 기존 테스트 매핑(§4.4) | 계좌 연동 · 실기기 조작 |
| 자동-신규 테스트 작성 | 운영테스트 — 사용자가 되어 보기 |
| 관측 수단 구현(§3.6) | 일지의 "느낌" 줄 |
| 데이터 품질 검사 질의(§5) | 품질 결과 해석 — 전달할 것과 견딜 것 구분 |
| 결함 주입·재생 수단(§6) | 스펙 공백 판정 — 결함인지 설계 누락인지 |
| 프론트 CI · 백업 CronJob | 동결 판단 · 종료 조건 판정 |
| 런북 초안 | 런북 검증 — 실제로 그 순서로 되나 |

케이스 추출과 테스트 작성은 분량이 크고 기계적이라 맡기는 편이 낫다. 다만 **등급과 종료 판정은 맡기지 않는다** — 무엇이 치명적인지는 이 서비스를 쓸 사람이 정한다.
