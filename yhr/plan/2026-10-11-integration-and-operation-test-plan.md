# 통합테스트 · 운영테스트 3주 계획

- **작성일**: 2026-10-11
- **기간**: 2026-10-12(월) ~ 2026-11-01(일). 영업일 15일
- **대상**: `back-end/` · `front-end/` · `dataeng/` 연계 전체
- **근거 스펙**: [포트폴리오 스펙](../specs/portfolio-management/2026-07-28-portfolio-management-spec.md) · [알림 스펙](../specs/buy-sell-timing-alert/2026-07-12-buy-sell-timing-alert-spec.md) · [데이터 요구사항](../specs/data-requirements.md) · [앱 정보 구조](../specs/app-information-architecture.md)
- **통합테스트 설계**: 화면 · 전이 목록 · 시나리오 · 케이스 추출 기준 · 실행 환경 · 등급 · 범위 제외 · 주입 수단 · 품질 검사 항목은 [통합테스트 설계](../test/2026-10-16-test-design.md)에 둔다. 이 문서는 일정 · 준비 · 운영 · 결함 관리 · 종료 조건을 다룬다
- **스펙 수정 금지**: 이 계획은 스펙을 인용만 한다. 테스트가 스펙과 다른 동작을 찾으면 코드를 고치고, 스펙이 틀렸다고 판단되면 멈춰서 보고한다.

**Goal:** 3주 끝에 두 가지를 손에 쥔다 — ① 두 기능의 기능과 분기를 훑은 **케이스 결과표**, ② 실계좌·실데이터로 영업일 10일 이상 끊기지 않고 돌아간 **운영 기록**. 그 과정에서 찾은 결함은 등급별로 정리되고 S1·S2는 닫힌다.

## 1. 두 테스트의 역할

| | 통합테스트 | 운영테스트 |
|---|---|---|
| 목적 | 기능과 분기를 **전수로 훑는다** | 사용자가 되어 **실제로 쓸 수 있는지 본다** |
| 데이터 | 시드·픽스처. 값을 내가 정한다 | 실계좌·실데이터. 값을 내가 못 정한다 |
| 시간 | 언제든 돌린다. 반복 가능 | 장이 열리고 날이 흘러야 관측된다 |
| 자동화 | 대부분 가능 | 불가능. 사람이 본다 |
| 찾는 것 | 분기 누락, 경계값, 오류 처리 | 설계가 놓친 현실, 체감 문제, 운영 사고 |
| 판정 | 기대값과 일치하는가 | 쓸 만한가. 믿을 수 있는가 |

둘은 대체 관계가 아니다. 통합테스트는 `DATA_MISSING`이 뜨는 것을 확인하고, 운영테스트는 **그게 실제로 얼마나 자주 뜨는지**를 알려준다.

여기에 성격이 또 다른 하나가 붙는다 — **데이터 품질·계약 검사**(§5). 분기가 아니라 **데이터 자체**가 약속한 모양인지 보는 일이고, 1회성이 아니라 매일 돈다.

## 2. 3주 일정

### 일정이 이렇게 된 이유

**운영테스트는 시간을 먹는다.** 일봉은 거래일 1회, 장중 스냅샷은 장중에만 온다. `streak(3거래일 연속)`은 가동 후 3영업일이 지나야 처음 관측되고, `EDGE_REARM` 재발화는 조건이 참→거짓→참을 거쳐야 한다. 미국 장은 한국 시간 밤에 열린다.

그래서 **가동과 관찰을 분리한다.**

| | 언제부터 | 왜 |
|---|---|---|
| 포트폴리오 스냅샷 | **보유 스냅샷 생성기 가동일 — 목표 10/19** · 계좌 연동이 그보다 앞서야 한다 | `position_line`이 하루 한 벌 쌓인다. 3주차에 자산 변화·일간 변화를 볼 이력이 그때부터 만들어진다. 가동에는 생성기 배포와 데이터 쪽 `cln_balance` · `cln_deposit` 적재가 함께 필요하다. 10/21까지 라인이 쌓이지 않으면 포트폴리오 운영 관찰은 시드로 덮고 범위 제외로 기록한다 |
| 알림 평가기 | **2주차 월 (10/19)** | 가동일부터 10/30까지 영업일 10일을 확보한다. 3주차에 켜면 5영업일뿐이고 연속·재발화 조건을 못 본다 |
| 집중 관찰 | **3주차 (10/26~)** | 쌓인 기록을 해석하고, 자연히 안 생기는 분기를 인위적으로 만든다 |

즉 3주차는 "가동 개시"가 아니라 **"집중 관찰 + 인위적 분기 생성"** 주차다. 가동은 그 전에 켜둔다. 켜두는 것 자체는 사람 손이 안 간다.

## 3. 준비

준비가 테스트의 절반이다. 여기서 막히면 3주가 1주가 된다. 각 항목에 **막히면 어떻게 하나**를 함께 적는다.

### 3.1 테스트 환경 — 두 갈래

| 어디 | 무엇을 | 파이프라인 | 쓰기 |
|---|---|---|---|
| **로컬 + CI** | 분기 전수. 결함 주입·재생 | 없음 — **의도된 것** | 자유 |
| **클러스터 DB** | 알림 연속 가동 · 포트폴리오 실계좌 · 통합테스트 `연계` | 꽂힘 | 운영테스트 사용자 행위 + 테스트 계정의 `연계` 실행 |

클러스터 DB 하나를 운영테스트와 통합테스트 `연계`가 같이 쓴다. 그 DB에서 운영테스트가 영업일 10일간 연속 가동되고, 쌓이는 발화 이력·평가 상태·일지가 산출물이다. 그래서 같이 쓰는 조건을 둔다.

1. **계정으로 가른다.** `연계`는 테스트 전용 계정(`it1@a.com` · `it2@a.com`)으로만 돈다. 운영테스트 계정(`yhr` · `hhj` · `jdh`)으로 통합테스트를 돌리지 않는다. 발화가 실제냐 테스트냐는 `user_id`로 가린다.
2. **주입은 로컬에서만 한다.** 가짜 휴장일, 완료 신호 삭제, 스냅샷 시각 밀기는 모든 사용자의 알림에 걸린다. 클러스터 DB에 걸리면 종료 조건의 "오발화 0건"을 판정할 수 없다.
3. **골든 비교는 로컬에서 한다.** 같은 입력에 같은 결과가 나와야 하는 비교는 매일 변하는 클러스터 DB에서 성립하지 않는다.
4. **백엔드 CI는 자기 Postgres로 돈다.** 클러스터 DB를 건드리지 않는다.
5. **데이터팀과 맞추는 지연·부분 적재는 모든 사용자에게 걸린다.** 그날을 운영 일지에 적고, 그날의 발화는 오발화 판정에서 따로 본다.

- [ ] 테스트 전용 계정 두 개를 만든다. 절차는 §3.2와 같다
- [ ] 클러스터 백엔드에 웹 출처 허용(`APP_WEB_ORIGINS`)을 배포한다 — `연계`를 크롬으로 돌리기 위해서다([설계](../test/2026-10-16-test-design.md) §3.1)
- [ ] 클러스터 DB에 쓰기 전에 백업이 있다(§3.8)
- [ ] 테스트 기간이 끝나면 테스트 계정의 행을 지우고 남은 행이 0인지 확인한다

**읽기는 권한다.** 클러스터 DB를 읽어 로컬 시드로 복사하면 픽스처보다 데이터 모양이 정확하다.

### 3.2 테스트 사용자

회원가입 경로가 없다(포트폴리오 스펙 §12). 사용자 행은 마이그레이션이 심는다. 클러스터 DB에는 V1이 심은 세 계정(`yhr@a.com` · `hhj@a.com` · `jdh@a.com`)이 있고, 셋 다 README에 공개된 개발용 비밀번호의 해시를 갖는다. 추가·교체 절차는 [`back-end/docs/ops/app-user.md`](../../../back-end/docs/ops/app-user.md)다.

- [ ] **운영테스트용 1명** — 본인(`yhr@a.com`). **계좌를 붙이기 전에 비밀번호를 교체한다**
- [ ] **스코프 격리 확인용 2명** — `hhj@a.com` · `jdh@a.com`. 비밀번호를 교체해 본인에게 전달한다
- [ ] 개발용 해시 확인 질의가 전부 `false`인지 본다
- [ ] 팀원이 각자 폰에서 Expo Go로 운영 API에 붙는 안내서를 둔다 — SSM 터널 · `port-forward --address 0.0.0.0` · `.env`
- [ ] 비밀번호·해시를 저장소에 커밋하지 않는다

`UserScopeIsolationTest`가 이미 격리를 검증하지만, **배포 환경에서 실제로 남의 데이터가 안 보이는지는 사람이 한 번 봐야 한다.**

### 3.3 계좌 연동

**보유 스냅샷 생성기가 켜지는 순간부터 라인이 쌓이려면 계좌가 그 전에 붙어 있어야 한다.** 계좌 연동이 늦으면 생성기가 돌아도 그 계좌의 라인이 없고, 3주차에 볼 자산 변화 이력이 그만큼 짧아진다. 이력은 하루 한 벌씩만 쌓여 나중에 메울 수 없다.

운영테스트 계좌는 **KIS 모의계좌**다. 실계좌가 아니므로 범위 축소로 기록한다.

- [ ] **계좌를 앱의 계좌 연동으로 붙인다.** 계좌 연동 API가 생성기 가동 전에 배포되지 않으면 `account` 행을 SQL로 넣는다 — `account_ref`는 포트폴리오 스펙 §7.1의 발급 규칙, `credential_ref`는 SSM SecureString 파라미터 이름(`/stock-project/accounts/…`, [생성기 설계](../specs/portfolio-management/2026-10-15-position-line-builder-design.md) §12)
- [ ] 연동 전 보안 확인 — DB에는 `credential_ref`만 들어가고 값은 SSM에만 있다 / 다른 사용자로 로그인해 내 계좌가 안 보인다 / 앱키·계좌번호가 DB·레이크·로그에 원문으로 남지 않는다 / SSM 그 경로를 읽을 수 있는 주체
- [ ] 데이터 수집 워커가 모의 환경(`KIS_ENV=demo`)으로 돈다 — 데이터 담당에 요청
- [ ] **계좌를 2개 이상 확보한다.** 멀티계좌 합산이 이 기능의 존재 이유이므로 1개로는 핵심이 검증되지 않는다
  - 막히면: 1개로 돌리고 합산·계좌별 비중·계좌 필터는 시드로만 덮는다. **범위 축소로 기록한다**
- [ ] 보유에 **국내 주식 · ETF 1개 · 미국 종목 1개**를 담는다. 미국이 없으면 `PRICE_LAG_MARKET`·환율·통화 병기 분기가, ETF가 없으면 렌즈 분기가 안 열린다
- [ ] `link_state`를 연동 → 해제 → 재연동으로 실제로 만든다. `REAUTH_REQUIRED`는 KIS 계좌에서 데이터 워커가 내지 않으므로 주입으로 만든다([설계](../test/2026-10-16-test-design.md) §7)

### 3.4 데이터 실연계 확인

**운영테스트의 유일한 블로커다. 10/12 월요일 첫 일로 확인한다.**

[데이터 요구사항](../specs/data-requirements.md)의 테이블별로 흐르는지 본다. 품질까지 보는 건 §5이고, 여기선 **오느냐 안 오느냐**만 본다.

- [ ] 종목 마스터 — 채워져 있고 검색이 되나
- [ ] 수정주가 일봉 — 국내 300거래일이 있나. 미국은 어느 종목까지 오나
- [ ] 투자자별 순매수 — 확정치가 다음 영업일 개장 전에 오나
- [ ] 장중 스냅샷 — `alert_watchlist` 기반으로 5분마다 오나. 앱 DB `data` 스키마에 직접 들어오나
- [ ] `market_data_run` — 거래일마다 `DONE`이 찍히나
- [ ] 영업일 캘린더 — `open_at` · `close_at`이 있나
- [ ] 포트폴리오 쪽 — `cln_*` · `collection_run` · `fx_rate` · `etf_constituent` · 커버리지
- [ ] 백엔드 역할이 `data` 스키마를 읽을 권한이 있나

**막히면:** 어느 테이블까지 되는지 선을 긋고, 안 되는 것에 의존하는 기능은 시드로만 덮는다. 운영테스트 범위를 줄이되 **가동일을 미루지 않는다** — 되는 것부터 켠다.

### 3.5 실기기와 푸시

알림 스펙 §9.6이 v1 플랫폼을 제약한다. **마지막 주에 확인하면 늦는다.**

기기는 iOS 2대 · Android 1대다.

- [ ] 운영 deployment에서 푸시 발송이 켜져 있나(`EXPO_PUSH_ENABLED`) — 꺼져 있으면 운영에서 울려도 푸시가 나가지 않는다
- [ ] iOS 실기기에 Expo Go로 앱이 올라가나 — **Expo Go SDK 상한 54.** 그보다 최신 SDK면 실기기가 거부한다
- [ ] 수신 권한을 허용하면 `push_device`에 토큰이 등록되나
- [ ] **실제로 푸시 한 건이 기기에 도착하나** — 앱이 떠 있을 때 / 백그라운드 / 완전히 꺼져 있을 때 각각
- [ ] 푸시를 탭하면 의도한 화면이 열리나
- [ ] Android는 앱 안 알림만인 제약이 화면에서 어떻게 보이나
- [ ] 로그아웃 시 기기가 지워지고 `DeviceNotRegistered` 영수증이 처리되나

**막히면:** 발송 대기열(`alert_delivery`)까지 쌓이는 것으로 판정하고 실기기 수신은 **범위 제외로 기록**한다. 다만 기능의 마지막 한 칸이라 가능하면 끝까지 붙잡는다.

### 3.6 관측 수단 — 운영테스트의 전제

**관측이 없으면 운영테스트 결과를 해석할 수 없다.** 알림이 안 울렸을 때 조건이 거짓이어서인지, 데이터가 안 와서인지, 평가기가 죽어서인지 구분이 안 되면 그날의 관찰은 기록할 값이 없다.

대시보드는 필요 없다. 조회 수단 하나면 된다.

- [ ] 마지막 `market_data_run` 수신 시각 — 시장 · 종류별
- [ ] 직전 평가 사이클 — 평가 건수 / 발화 건수 / 건너뛴 건수와 사유 / 소요 시간
- [ ] `alert_delivery` 상태별 건수와 마지막 실패 사유
- [ ] 알림별 마지막 평가 시점과 결과 — 참 / 거짓 / 확인 불가 + 사유
- [ ] 포트폴리오 — 마지막 `collection_run` · `sync_run` 상태, 계좌별 `source_as_of`, 캐리포워드 여부

운영자 조회 API 하나 또는 psql 질의 묶음으로 충분하다. **에이전트에 맡길 수 있다.**

### 3.7 CI 보강

- [ ] **프론트엔드 CI가 없다.** 테스트 파일 31개가 있는데 아무것도 자동으로 안 돈다. 워크플로 하나로 테스트·린트·타입체크를 게이트로 만든다
- [ ] 백엔드 CI는 이미 실제 Postgres로 테스트를 돌리고 통과하지 못한 이미지를 올리지 않는다. 그대로 쓴다
- [ ] 새로 쓰는 통합테스트가 CI에서 돌아가는지 확인한다. 로컬에서만 도는 테스트는 2주 뒤에 썩는다

### 3.8 DB 백업 — 보험

클러스터 DB가 클러스터 안의 단일 파드다(`back-end/k8s/postgres.yaml`). 3주간 쌓는 운영 기록이 산출물이므로 중간에 날아가면 메울 수 없다. 통합테스트 `연계`도 이 DB에 쓰므로, 백업은 클러스터 DB에 쓰기 전에 있어야 한다.

- [ ] `pg_dump` CronJob을 걸고 산출물을 클러스터 밖에 둔다
- [ ] **복구를 한 번 실제로 해본다.** 해보지 않은 백업은 백업이 아니다

## 4. 테스트 설계

통합테스트는 와이어플로우와 앱 정보 구조의 모든 화면 · 전이를 지나는 **시나리오**를 먼저 확정하고, 스펙의 나열에서 **케이스**(분기)를 뽑아 서로 대조한다. 케이스 표는 하나이고 실행 환경은 `로컬` · `연계` · `둘 다` 셋이며, 등급은 1~3등급이다. 운영테스트는 §7의 루틴으로 돈다.

화면 · 전이 목록 · 시나리오 · 케이스 추출 기준 · 기존 테스트 매핑 · 실행 환경 · 등급 · 범위 제외는 [통합테스트 설계](../test/2026-10-16-test-design.md)에 있다.

- 시나리오를 승인받고 케이스로 넘어간다. 시나리오 없이 뽑은 케이스는 빠진 경로를 찾아 줄 대조 상대가 없다
- 등급과 종료 판정은 사람이 정한다(§11)

## 5. 데이터 품질·계약 검사

데이터 요구사항이 약속한 모양대로 왔는지 **데이터 자체를 검사**한다. 통합테스트와 성격이 다르다 — 기능 분기와 무관하고, 1회성이 아니라 **매일 돈다.** 어제 맞았던 데이터가 오늘 틀릴 수 있다.

- **어디서**: 클러스터 DB를 **읽기 전용**으로
- **언제부터**: 2주차 수(10/21)부터 3주차 끝까지 매일
- **산출물**: 검사 질의 묶음 + 매일의 결과 한 줄

검사 항목은 [통합테스트 설계](../test/2026-10-16-test-design.md) §9에 있다.

### 검사가 실패하면

**데이터팀에 전달할 결함으로 분리해 기록한다.** 우리 코드 결함과 같은 목록에 섞지 않는다 — 고치는 주체가 다르고, 고쳐지기까지 우리가 할 수 있는 건 기능이 그 상황을 견디는지 확인하는 것뿐이다. 그 확인은 §6의 주입으로 한다.

## 6. 결함 주입과 재생

### 왜 필요한가 — 3주 창에서 자연 관측이 안 되는 것

| 분기 | 왜 안 되나 | 어떻게 하나 |
|---|---|---|
| 국내 휴장일 | 10/12~10/30에 주말 외 휴장일이 없다(캘린더로 확인할 것) | 캘린더 주입 |
| 20거래일 연속 조건 | 가동 기간이 영업일 10일이다 | 과거 데이터 재생 |
| 데이터 결측·지연 | 데이터팀이 정상 운영하면 안 생긴다 | 신호·시각 주입 |
| 기업행위 보정 누락 | 해당 종목에 기업행위가 있어야 한다 | 과거 분할 종목 재생 |
| 계좌 재인증 요구 | 증권사 사정이다 | 자격증명 무효화 |
| 수집 부분 실패 | 드물게 생긴다 | 일부만 성공시키기 |

**이 수단을 만들지 않으면 스펙의 "충족 안 될 때" 분기를 3주가 지나도 한 번도 못 본다.** 그리고 이 수단이 그대로 통합테스트의 절반이다 — 재생이 있으면 "3일 연속 순매수"를 3일 기다리지 않고 검증할 수 있다.

주입 수단과 안전장치는 [통합테스트 설계](../test/2026-10-16-test-design.md) §7에 있다. 주입은 로컬에서만 돈다. 클러스터 DB에서 동작하지 않게 환경 플래그 뒤에 두고, 되돌릴 수 없는 주입은 쓰지 않는다.

## 7. 운영테스트 운영 방식

10/19 가동일부터 3주차 끝까지 **하루 30분~1시간.** 루틴을 고정한다. 2주차에는 통합테스트와 병행하므로 짧게, 3주차에는 길게 본다.

### 아침 — 장 전, 09:00 이전

- [ ] 관측 조회 — 간밤 미국 일봉·수급 확정치가 왔나. `market_data_run`에 `DONE`이 찍혔나
- [ ] 미국 알림이 울렸나. 울렸으면 푸시가 왔나. **안 울렸으면 왜 안 울렸는지 관측으로 구분한다** — 조건 거짓인가, 확인 불가인가, 평가기가 안 돌았나
- [ ] 데이터 품질 검사 결과 확인(§5)
- [ ] 앱을 열어 6개 뷰를 본다. 어제와 숫자가 이어지나. 배너가 떴으면 내용이 이해되나

### 장중 — 1회

- [ ] 장중 스냅샷이 5분 주기로 오나. 허용 지연을 넘지 않나
- [ ] 장중 알림이 평가되고 있나. 사이클 소요 시간이 주기보다 짧나

### 저녁 — 장 마감 후

- [ ] 국내 일봉이 당일 중에 왔나. 종가 알림이 평가됐나
- [ ] `alert_delivery`에 실패가 쌓이지 않았나
- [ ] 그날의 포트폴리오 스냅샷이 생겼나. 캐리포워드면 왜인가

### 일지

`docs/yhr/operations/2026-10-operation-log.md` 한 파일에 날짜순으로 쌓는다.

```
## 10/22 (목)
- 데이터: KR 일봉 18:40 DONE · US 일봉 07:10 DONE · 수급 08:20 DONE · 장중 결측 2회(10:35, 14:05)
- 품질검사: 통과. 단 미국 일봉 3종목 이력 280일 (< 300) → DT-003
- 알림: 평가 7건 / 발화 1건(삼성전자 가격) / 확인 불가 2건(INSUFFICIENT_HISTORY)
- 푸시: 1건 발송 · 1건 수신 확인(iOS, 백그라운드, 지연 4초)
- 포트폴리오: 정상. 계좌 2개 모두 source_as_of 당일
- 이상: 장중 결측 2회 동안 배너가 안 떴다 → D-012
- 느낌: 발화 문구에 기준일이 없어 "언제 기준인지" 헷갈렸다 → D-013
```

**"느낌" 줄을 반드시 쓴다.** 통합테스트가 절대 찾아주지 않는 결함이 거기서 나온다.

## 8. 결함 관리

### 두 목록을 따로 둔다

| 목록 | 무엇 | 고치는 주체 |
|---|---|---|
| **D-** 결함 | 우리 코드가 설계대로 동작하지 않는다 | 백엔드 · 앱 |
| **DT-** 데이터 결함 | 데이터가 요구사항대로 오지 않는다 | 데이터 |

섞으면 "우리가 고칠 수 있는 게 몇 개인가"가 안 보인다. DT-는 전달하고, 고쳐지기 전까지 **그 상황을 기능이 견디는지**를 §6 주입으로 확인한다.

### 등급과 처리

| 등급 | 뜻 | 처리 |
|---|---|---|
| **S1** | 못 쓴다. 틀린 숫자를 믿게 되거나 알림이 안 온다 | 즉시. 동결 후에도 고친다 |
| **S2** | 기능이 깨졌지만 우회로가 있다 | 동결 전까지 |
| **S3** | 표시·문구 문제 | 시간 남으면 |
| **S4** | 사소함 | 기록만 |

### 기록

열: `ID · 발견일 · 발견 경로(통합/연계/운영/품질) · 등급 · 현상 · 기대 · 근거 절 · 상태 · 수정 커밋`

- **결함마다 근거 절을 적는다.** 적을 근거가 없으면 결함이 아니라 **스펙 공백**이다. 별도 목록으로 분리하고 코드를 고치기 전에 보고한다
- **S1 · S2를 고칠 때는 자동 테스트를 함께 남긴다.** 안 남기면 같은 게 돌아온다
- **10/28 동결 후에는 S1만 고친다.** 그 외는 목록에 적고 넘긴다

## 9. 종료 조건

10/30에 "됐다"를 판정하는 기준. 미달이면 미달로 기록한다 — 억지로 채우지 않는다.

**통합테스트**
- [ ] 1등급 케이스 100% 실행, S1 잔여 0
- [ ] 2등급 케이스 90% 이상 실행
- [ ] **승인된 시나리오 전부**([통합테스트 설계](../test/2026-10-16-test-design.md) §3) 1회 이상 통과. 유보로 돌린 단계는 이유와 함께 기록
- [ ] `둘 다` 케이스에서 로컬과 연계 결과가 어긋난 건이 없다
- [ ] 테스트 계정의 행을 지웠고 남은 행이 0이다
- [ ] 새로 쓴 자동 테스트가 CI에서 돈다
- [ ] 프론트엔드 테스트가 CI 게이트에 들어갔다

**운영테스트**
- [ ] **영업일 10일 가동** (10/19 ~ 10/30)
- [ ] 종가 알림 발화 후 **실기기 푸시 수신** 1건 이상
- [ ] 장중 알림 발화 1건 이상
- [ ] 미국 종목 알림 발화 1건 이상
- [ ] `EDGE_REARM` 재발화 1건 이상
- [ ] **오발화 0건** — 조건이 거짓인데 울린 일이 없다
- [ ] 결측·지연 발생 시 사용자에게 보인 안내가 설계대로였던 사례 기록
- [ ] 운영 일지가 가동일수만큼 쌓였다

**데이터 품질**
- [ ] 검사 질의가 매일 돌았다
- [ ] DT- 목록이 데이터팀에 전달되었다

**산출물**
- [ ] 케이스 결과표
- [ ] 운영 일지
- [ ] 결함 목록 — D- · DT- 각각 상태별
- [ ] 스펙 공백 목록 — 테스트가 찾은, 스펙이 답하지 않는 것
- [ ] 운영 런북 — 배포 · 장애 시 확인 순서 · 데이터 미도착 시 점검 · 롤백 · 백업 복구

| **클러스터가 장중·야간에 꺼져 있다** | 가동 시간이 화·수·목 19:00~24:00 · 일 10:00~24:00이다 | 테스트 기간 상시 가동을 협의한다(§2 가동 시간). 안 되면 장중·미국 관찰은 주입으로만 덮고 범위 축소로 기록한다 |
| **알림 데이터가 매일 적재되지 않는다** | `market_data_run`에 거래일마다 `DONE`이 찍히지 않는다 | 데이터 담당에 전달한다. 적재가 재개되기 전까지 종가 알림은 `DATA_MISSING`으로 남고, 발화 관찰은 주입으로 덮는다 |
| **데이터 실연계가 안 된다** | 10/12에 알게 된다 | 되는 테이블까지만으로 범위를 줄인다. 안 되는 건 시드로 덮고 범위 제외 기록 |
| **실기기 푸시가 막힌다** | 10/14에 알게 된다 | 발송 대기열까지로 판정 범위를 줄인다. iOS가 막히면 Android 앱 내 알림으로 최소 경로 확보 |
| **연계 테스트 날 데이터팀 시간이 안 맞는다** | 10/22 | 주입으로 대체 가능한 케이스를 미리 가려둔다. 사람이 맞춰야 하는 건 "일부만 적재된 `DONE`" 하나뿐이다 |
| **알림이 한 번도 안 울린다** | 10/22까지 발화 0건 | 기준값을 현재가에 더 붙인 알림을 추가한다. 그래도 안 울리면 평가기 문제이므로 S1 |
| **결함이 쏟아져 수정이 테스트를 잡아먹는다** | 2주차 중반 | 등급으로 끊는다. S3 · S4는 고치지 않고 기록만 한다 |
| **클러스터 DB가 날아간다** | 예고 없음 | §3.8 백업. 복구를 미리 해본다 |
| **테스트 데이터가 운영테스트 기록에 섞인다** | 운영테스트 계정에 테스트 계정의 알림 · 계좌가 보이거나, 발화 집계에 테스트 계정이 들어간다 | `연계`는 테스트 계정으로만 돈다(§3.1). 운영 집계 질의는 운영테스트 계정으로 거른다. 끝나면 테스트 계정의 행을 지운다 |
| **동결을 못 지킨다** | 10/29~30에 커밋이 쌓인다 | 동결 후 커밋은 S1만. 그 외는 목록에 적고 넘긴다 |

## 11. 사람과 에이전트

| 에이전트 | 사람 |
|---|---|
| **화면 · 전이 목록과 시나리오 설계**([설계](../test/2026-10-16-test-design.md) §2 · §3) — 전수성 점검 | **시나리오 승인** — 빠진 길이 없는지 판단 |
| 케이스 추출([설계](../test/2026-10-16-test-design.md) §4) — 스펙에서 표로 옮기고 시나리오와 대조 | 등급 부여 — 무엇이 치명적인지 판단 |
| 기존 테스트 매핑([설계](../test/2026-10-16-test-design.md) §5) | 자격증명 입력 · 실기기 조작 — 푸시 · 앱 뒤 · 앱 꺼짐 · 1등급 경로의 네이티브 확인 · KIS 앱 대조 |
| 시나리오 · 케이스 실행 — 크롬으로 웹 실행을 조작하고 API · DB로 대조([설계](../test/2026-10-16-test-design.md) §1) | |
| 자동-신규 테스트 작성 | 운영테스트 — 사용자가 되어 보기 |
| 관측 수단 구현(§3.6) | 일지의 "느낌" 줄 |
| 데이터 품질 검사 질의(§5) | 품질 결과 해석 — 전달할 것과 견딜 것 구분 |
| 결함 주입·재생 수단(§6) | 스펙 공백 판정 — 결함인지 설계 누락인지 |
| 프론트 CI · 백업 CronJob | 동결 판단 · 종료 조건 판정 |
| 런북 초안 | 런북 검증 — 실제로 그 순서로 되나 |

케이스 추출과 테스트 작성은 분량이 크고 기계적이라 맡기는 편이 낫다. 다만 **등급과 종료 판정은 맡기지 않는다** — 무엇이 치명적인지는 이 서비스를 쓸 사람이 정한다.
