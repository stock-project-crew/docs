# ADR 0008. 입출금 멱등 키

- 상태: 채택 (사후 정리, 2026-11-16)
- 관련: [포트폴리오 4.6 입출금 입력과 미입력 판정](../specs/portfolio.md) · [포트폴리오 8.4 입출금 응답](../specs/portfolio.md) · [포트폴리오 8.6 오류](../specs/portfolio.md) · [공통 5.4 사용자 스코프 · 소유 검사](../specs/common.md) · [ADR 0001 리더 없는 다중 복제본](0001-leaderless-replicas.md) · [ADR 0004 조회 정합성](0004-read-consistency.md)

## 맥락

입출금은 사용자가 앱에서 직접 넣는 유일한 돈 기록이다. KIS에 입출금 이력 조회가 없어 자산 변화의 "넣은 돈"은 이 입력에서만 오고, 투자손익은 그 나머지로 계산된다. 같은 입출금이 두 줄 들어가면 넣은 돈과 투자손익이 함께 틀린다.

처음 저장은 `POST /portfolio/cashflows`였고 id는 서버가 만들었다. 앱은 연달아 누른 두 번째를 막으려고 저장 버튼을 ref로 잠갔다. 상태값(`isPending`)은 다음 렌더에야 바뀌어 늦기 때문이다. 이 잠금은 연타만 막는다. 서버가 커밋했는데 응답만 잃으면 앱은 실패로 보이고 입력값을 남긴다(금액은 성공 때만 비운다). 사용자가 다시 누르면 같은 입출금이 두 줄이 된다(진단 N11). 2026-11-15에 앱 요청에 15초 상한을 걸면서(front-end e83e24c) "서버는 저장했는데 앱은 연결 오류"인 경우가 하나 더 생겼다.

내용으로는 거를 수 없다. 같은 날 같은 금액의 입금이 정상일 수 있다. 서버는 복제본 두 대라, 다시 보낸 요청이 앞 요청과 다른 복제본에서 동시에 처리될 수도 있다.

## 결정

POST와 서버가 만든 id 대신, 앱이 만든 id를 주소에 싣는 `PUT /portfolio/cashflows/{id}`를 골랐다. 그 id가 표의 기본 키다.

- 같은 id가 없으면 넣고 `201`, 내 행이고 내용이 같으면 새로 넣지 않고 `200`, 내 행인데 내용이 다르면 덮어쓰지 않고 `409 CASHFLOW_ID_CONFLICT`다. 남의 행이거나 소유 확인 뒤 계좌가 사라졌어도 같은 `409`다. 표는 [포트폴리오 4.6](../specs/portfolio.md).
- 이미 저장된 요청은 날짜 범위를 다시 보지 않는다. 그 뒤 잔고가 바뀌어 지금 규칙이 거절하더라도, 이미 들어간 입력을 실패로 답하면 앱과 DB가 어긋난다.
- 겹친 저장은 기본 키가 막는다. 넣기는 `INSERT … SELECT … FROM account … ON CONFLICT (id) DO NOTHING`이고, 0건이면 내 행을 다시 찾아 위 규칙으로 답한다.
- 이 저장은 기본 격리 수준(READ COMMITTED)에서 돈다.
- 앱은 입력 한 번마다 `expo-crypto`의 `randomUUID`로 id를 만든다. 실패하면 id를 그대로 두고, 성공하거나 `409`를 받았을 때만 새로 만든다. `409`면 서버 문장을 띄우고 목록과 자산 변화를 다시 받는다.
- POST는 없앴다. 이 API를 부르는 것은 이 앱뿐이라 옛 경로를 남겨 둘 이유가 없었다.

**id를 주소에 싣는 이유.** 키가 곧 행 id라 따로 저장할 칸이 없다. 기본 키(V1부터 `manual_cashflow.id uuid PRIMARY KEY`)가 유일성을 이미 들고 있어 마이그레이션 없이 바꿨다(98b7f04에는 마이그레이션이 없다). 다시 온 요청에 돌려줄 "처음 결과"도 그 id로 행을 읽으면 된다. 삭제가 이미 `DELETE /portfolio/cashflows/{id}`라 주소 모양도 같아진다.

**경합을 기본 키에 맡기는 이유.** 먼저 찾아보기(`findOwned`)로는 다른 트랜잭션이 넣고 아직 커밋하지 않은 행이 보이지 않는다. 그래서 "찾아보고 없으면 넣는다"만으로는 겹친 두 저장이 모두 넣는다. 기본 키가 있으면 뒤 넣기가 앞 트랜잭션이 끝날 때까지 기다렸다가, 앞이 커밋하면 0건, 되돌리면 넣는다.

**READ COMMITTED가 필요한 이유.** 넣기가 0건일 때 다시 찾는 문장은 그사이 커밋된 다른 트랜잭션의 행을 봐야 한다. READ COMMITTED는 문장마다 새 시점을 보므로 보인다. REPEATABLE READ는 트랜잭션의 첫 문장 시점에 고정돼 그 행이 보이지 않고, PostgreSQL은 이때 그 넣기를 직렬화 오류로 끝낸다(`ManualCashflowService.save`의 주석). 조회 서비스는 한 시점을 보려고 REPEATABLE READ를 쓰므로([ADR 0004](0004-read-consistency.md)), 그 설정을 여기로 옮기면 깨진다.

**남의 행도 409인 이유.** `query` · `cashflow` 패키지 매퍼의 모든 메서드는 첫 인자로 `UserScope`를 받는다. `ScopeSignatureTest`가 `query` · `cashflow` 패키지의 매퍼를 훑어 이를 검사하고, `ManualCashflowWriteMapper`를 대상에 명시해 둔다. "남의 행이라서 0건"과 "계좌가 사라져서 0건"을 가르려면 스코프 없이 `manual_cashflow`를 id로 찾아야 한다. 이 규칙에 예외를 두지 않으려고 두 경우를 같은 `409`로 답한다. 응답만으로는 그 id의 행이 누구 것인지 알 수 없다([공통 5.4](../specs/common.md)).

## 검토한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| 앱의 이중 탭 잠금만 둔다 | 서버를 바꾸지 않는다 | 연타만 막는다. 응답을 잃은 뒤 다시 누르면 두 줄이 된다 |
| 내용(계좌 · 날짜 · 금액)으로 중복을 거른다 | 키가 필요 없다 | 같은 날 같은 금액이 정상일 수 있다 |
| POST에 `Idempotency-Key` 헤더 | 리소스 id와 따로 키를 둘 수 있다 | 행 id와 다른 키를 하나 더 저장해야 한다(칸과 유일 제약, 마이그레이션). 다시 온 요청에 처음 결과를 돌려주려면 그 키로 행을 찾는 길도 따로 둬야 한다 |
| POST 본문에 요청 id 필드 | 헤더와 같고, 본문 검증과 한자리에서 다룬다 | 헤더와 같은 이유다 |
| 같은 id에 다른 내용이면 덮어쓴다 | 마지막 입력이 남는다 | 조용히 바뀌면 처음 입력이 사라진다 |

헤더와 필드 가운데 무엇으로 할지는 B단계 분류(`review/triage.md`의 N11)에서 미뤄 둔 질문이었다. 2026-11-15에 둘 다 아니고 리소스 id로 정했다.

## 결과

얻은 것
- 응답을 잃고 다시 보내도 한 줄만 남고, 앱은 성공으로 안다.
- 실패 뒤 금액을 고쳐 다시 보내면 같은 id라, 앞 요청이 저장됐으면 두 줄로 넣지 않고 `409`로 알린다. 앞 요청이 저장되지 않았으면(예: 칸 오류) 그 id로 그대로 넣는다.
- 겹친 저장도 PK 하나로 막혀 복제본 수와 무관하다. 잠금이나 별도 키 표가 없다(원칙은 [ADR 0001](0001-leaderless-replicas.md)).

감수한 비용
- `409`는 처음 저장된 내용을 싣지 않는다. 앱이 목록을 다시 받아 사용자가 보고 판단한다.
- 계좌가 사라진 경우의 응답이 `403 FORBIDDEN_ACCOUNT`에서 `409`로 바뀌었다. 소유 확인은 넣기 전에 따로 하므로 남의 계좌 · 없는 계좌는 여전히 `403`이고, 이 `409`는 소유 확인과 넣기 사이에 계좌가 사라진 경우뿐이다. 코드에 계좌 행을 지우는 경로가 없어(해제는 상태만 바꾼다) 지금은 이론상의 경우다.
- 저장이 id 경로로 옮겨 가 웹 CORS 허용을 다시 짰다. `/portfolio/cashflows`는 GET만, `/portfolio/cashflows/*`는 GET · PUT · DELETE다. 같은 자리의 계좌 목록(`GET /portfolio/cashflows/accounts`)이 웹에서 막혀 있던 것도 함께 열렸다(98b7f04).

지금 있는 곳
- 백엔드 `api/CashflowController.save`(201 · 200), `cashflow/ManualCashflowService.save`(찾기 → 범위 검증 → 넣기 → 0건이면 다시 찾기), `ManualCashflowWriteMapper.insertIfAbsent` · `findOwned`, `StoredCashflow.sameAs`(금액은 `compareTo`로 견줘 `1000000`과 `1000000.0`을 같게 본다), `CashflowIdConflictException`, `ApiExceptionHandler`.
- 표 `manual_cashflow`(PK `id`).
- 앱 `screens/cashflows/CashflowForm.tsx`(`saveId` ref와 `busy` ref), `api/queries/useCashflowActions.ts`(`isSaveIdConflict`), `api/endpoints.ts`의 `saveCashflow`.

## 돌아보며

**어떻게 드러났나.** 처음 POST에 멱등 키를 일부러 안 뒀는지 빠뜨렸는지는 원천에 기록이 없다(`review/decision-inventory.md`의 AMB-15). 회고 진단에서 N11로 드러났고, 결정 점수표에서는 "앱 이중 탭 잠금"(38행, CC-22)이 혼자서는 부족하다고 적었다. 서버 멱등이 없으면 앱 잠금은 반쪽이다.

**무엇을 고쳤나.** 백엔드 98b7f04, 앱 1a45b90(둘 다 2026-11-15).
- 백엔드 `CashflowApiTest`가 같은 id · 같은 내용 `200`과 한 줄, 메모 앞뒤 공백만 다르면 같은 내용, 다른 내용 `409`와 처음 행 유지, 남의 행 id의 `409`와 그 행 불변, 이미 저장된 요청은 날짜 범위가 바뀌어도 `200`을 본다.
- `CashflowSaveConcurrencyTest`는 앞 저장을 테스트가 연 연결에서 커밋하지 않은 채 두고, 뒤 저장이 `pg_stat_activity`에서 `INSERT INTO manual_cashflow`의 잠금 대기로 보일 때까지 기다린 뒤 커밋하거나 되돌린다. 스레드 둘을 동시에 띄우지 않아 겹치는 순서가 매번 같다. 앞이 커밋하면 뒤는 `created=false`이고 행은 하나, 앞이 되돌리면 뒤가 넣고 행은 하나, 내용이 다르면 `409`이고 처음 금액이 남는다.
- 앱 테스트(`cashflows.test.tsx`)가 앱이 만든 id의 주소로 보내는지, 실패한 뒤 금액을 고쳐도 같은 id인지, 성공 뒤 새 id인지, `409`면 서버 문장 · 목록 다시 받기 · 입력 유지 · 새 id인지를 본다.

**남은 것.**
- READ COMMITTED는 주석과 설계서에만 적혀 있다. 조회 서비스는 테스트가 REPEATABLE READ를 고정하는데(`ViewTransactionTest` 등), 이 저장의 격리 수준을 고정하는 테스트는 없다. REPEATABLE READ에서 직렬화 오류가 나는지도 테스트로 확인하지 않았다.
- 소유 확인과 넣기 사이에 계좌가 사라지는 경로는 테스트가 없다.
- 앱의 id는 입력 화면의 메모리(ref)에만 있다. 응답을 잃은 뒤 화면을 떠났다 돌아오거나 앱을 끄면 새 id가 생기므로, 그 뒤 같은 입력을 다시 넣으면 두 줄이 될 수 있다. 코드에서 읽은 것이고 따로 시험하지 않았다.
- 클러스터가 꺼진 채 main에 넣어 운영 반영은 다음 가동 때다(`review/triage.md` 6-1). 운영에서 응답을 잃고 다시 보낸 사례는 확인하지 않았다.
- 이중 탭 잠금이 화면마다 두 방식으로 남아 있다(진단 `review/diagnosis.md` §5, 분류는 그냥 둠). 둘 다 동작한다.
