# ADR 0007. 서버 세션과 토큰 회전

- 상태: 채택 (사후 정리, 2026-11-16)
- 관련: [공통 4 로그인·세션](../specs/common.md) · [공통 4.2 토큰과 갱신](../specs/common.md) · [공통 4.4 세션이 끝날 때](../specs/common.md) · [공통 4.5 앱 동작](../specs/common.md) · [공통 7.1 주기 작업](../specs/common.md) · [ADR 0001 리더 없는 다중 복제본](0001-leaderless-replicas.md)

## 맥락

처음 로그인은 서버가 세션을 들지 않는 무상태 JWT였다. 로그인하면 12시간짜리 토큰을 주고, 갱신 토큰과 강제 로그아웃은 없었다. 백엔드 옛 결정 기록([`docs/decisions.md`](https://github.com/stock-project-crew/back-end/blob/d3b619d/docs/decisions.md)의 인증 절)은 이것을 "세션을 들지 않는 선택의 대가"로 적고, 되돌리는 조건으로 "강제 로그아웃 요구가 생기면 세션 저장소를 두고 다시 정한다"를 적어 두었다.

두 요구가 이 조건을 건드렸다. 하나는 쓰는 중에 12시간마다 로그인 화면으로 밀려나는 것이다. 로그인을 "로그인 후 12시간 고정"에서 "마지막 사용 후 일정 시간"으로 바꾸려면 서버가 마지막 사용을 알아야 한다. 다른 하나는 푸시다. 알림 기능에는 처음부터 "공용 기기에서 로그아웃한 사람의 알림이 오면 안 된다"는 원칙이 있었고, 무상태 토큰에서는 로그아웃 때 앱이 `DELETE /devices/{id}`로 폰 등록을 지워 지켰다. 빈틈은 로그아웃이 서버에 닿지 못했을 때다. 폰 등록에는 만료가 없어 그 폰으로 푸시가 기한 없이 갈 수 있었고, 토큰도 만료까지 살아 있었다. 서버가 끝낼 수 있는 세션이 없었다. 세션 설계는 이 원칙을 "세션이 끝나면 그 세션으로 등록한 폰으로는 보내지 않는다"로 바꿔 적었다.

제약은 이렇다. 클라이언트는 폰 앱이고 갱신 응답을 잃는 일(지하철 등)이 흔하다. 서버는 복제본 두 대가 같은 DB를 본다. 계정은 운영자가 만들고 사용자는 적다. 이 전환은 2026-11-11 로그인 세션 설계([보관본](../archive/specs/portfolio-management/2026-11-11-auth-session-design.md))로 정했다.

## 결정

무상태 JWT 12시간 대신 서버 세션(`auth_session`)과 30분 접근 토큰, 갱신마다 바뀌는 갱신 토큰을 골랐다.

- 접근 토큰은 HMAC-SHA로 서명한 JWT 30분이고(알고리즘은 서명 키 길이로 정해져 32바이트 이상이면 HS256 이상이다) 사용자 · 세션(`sid`) · 세대(`gen`)를 싣는다. 요청마다 세션 행이 살아 있는지 확인해, 끝난 세션의 토큰은 만료 전이라도 `401`이다.
- 수명은 유휴 7일(마지막 토큰 갱신 기준, 저장하지 않고 계산) · 절대 30일이다. 규칙은 [공통 4.1](../specs/common.md).
- 갱신 토큰은 32바이트 난수이고 서버는 SHA-256 해시만 둔다. 갱신마다 새것으로 바꾼다(회전).
- 재사용 판정은 "바로 전 토큰 해시 + 확인 표시"로 한다. 바로 전 토큰이 왔을 때 새 세대가 아직 확인 전이면 응답 유실로 보고 다시 주고, 확인 뒤면 재사용으로 세션을 지운다. 갱신은 맞은 행을 `FOR UPDATE`로 잡고 판정한다. 표는 [공통 4.2](../specs/common.md).
- 끝난 세션은 행을 지운다. 폰 등록은 세션을 `ON DELETE CASCADE`로 참조해 함께 지워진다. 유휴 · 절대 만료는 한 시간마다 도는 정리 작업이 지운다.
- 거절은 이유를 가리지 않고 모두 `401`이다.
- 앱은 세 값을 보안 저장소의 한 키에 쓰고, 갱신은 한 번에 하나만 돌리며, `401`을 받은 요청은 갱신 뒤 한 번만 다시 보낸다. 만료 직전 사전 갱신은 하지 않는다. 규칙은 [공통 4.3 · 4.5](../specs/common.md).

## 검토한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| 무상태 JWT 12시간 유지 | 서버가 상태를 들지 않고 요청마다 DB를 보지 않는다 | 로그아웃이 서버에 닿지 못하면 폰 등록이 기한 없이 남고 토큰도 만료까지 산다. 그 경우를 막을 수 없다. 쓰는 중에 12시간마다 로그인 화면으로 간다 |
| 세션 쿠키 | 서버가 세션을 끝낼 수 있다 | 처음 무상태를 고를 때 함께 버린 선택지다. 버린 이유는 원천에 적혀 있지 않다 |
| 옛 갱신 토큰이 오면 곧바로 세션 종료 | 재사용 감지에 빈틈이 없다 | 갱신 응답을 잃거나 저장에 실패한 정상 사용자가 쓰는 중에 밀려난다 |
| 갱신 토큰을 느린 해시로 저장 | 저장소가 새도 원문을 되찾기 어렵다 | 32바이트 난수라 사전 공격이 성립하지 않는다 |
| 끝난 세션 기록 보존 | 세션 이력을 볼 수 있다 | 보여 줄 화면이 없고, 행이 없어도 그 토큰은 똑같이 거절된다 |
| 거절 이유별 응답 · 없는 이메일은 바로 실패 | 원인을 앱에서 알 수 있다 | 앱이 할 일은 모두 "로그인 화면으로"다. 이유를 가르면 가입 여부가 응답이나 응답 시간으로 드러난다 |
| 앱이 세 값을 키별로 저장 | 값 하나만 고쳐 쓸 수 있다 | 쓰는 도중 앱이 죽으면 새 접근 토큰과 옛 갱신 토큰이 섞여 남고, 다음 갱신이 재사용으로 판정된다 |
| 만료 직전 사전 갱신 | `401` 왕복이 없다 | 아끼는 것이 왕복 한 번뿐이다 |

## 결과

얻은 것
- 로그아웃 · 재사용 감지가 그 자리에서 세션을 끝내고, 그 세션의 폰 등록과 발송 대기도 함께 지운다. 로그아웃이 서버에 닿지 못해도 서버가 그 폰으로 보낼 수 있는 기간은 7일을 넘지 않는다([공통 4.4](../specs/common.md)).
- 쓰는 중에 로그인 화면으로 가는 경우가 "로그인 후 30일"과 "토큰이 새어 나간 경우"로 줄었다.
- 로그인마다 새 세션이라 한 사람이 폰과 웹을 함께 쓸 수 있다.

감수한 비용
- 요청마다 세션 행을 PK로 읽고, 새 세대의 첫 요청에는 확인 표시를 쓴다. 이 비용은 재지 않았다.
- 재사용 감지에 빈틈이 있다. 주인이 갱신한 뒤 새 토큰으로 요청하기 전에 훔친 쪽이 옛 토큰을 쓰면 응답 유실과 구분되지 않는다. 받아들였다([공통 4.7](../specs/common.md)).
- 전환 배포에서 옛 접근 토큰은 `sid`가 없어 모두 거절되고, V19가 기존 폰 등록을 모두 지운다. 모든 사용자가 한 번 다시 로그인해야 한다.
- 앱 쪽 경합이 늘었다. 갱신과 로그아웃이 겹칠 때를 다루는 수정이 이어졌다(front-end e645b5c, 9ef743b, 3faad4d).

지금 있는 곳
- 백엔드 `auth/session/SessionService`(열기 · 갱신 · 로그아웃 · 요청 확인), `RefreshDecision`(ROTATE · REISSUE · EXPIRED · REUSED), `RefreshTokens`, `AuthSessionMapper.lockByHash`(`FOR UPDATE`), `auth/JwtAuthenticationFilter`, `auth/JwtCodec`(`sid` · `gen`이 없으면 거절), `AuthSessionJobs`(`@Scheduled` 1시간).
- 표 `auth_session`(V19: `refresh_hash` · `prev_refresh_hash` 각각 UNIQUE, `generation`, `confirmed`, `last_refreshed_at`, `absolute_expires_at`), `push_device.session_id`.
- 설정 `portfolio.auth.access-ttl` · `idle-ttl` · `absolute-ttl`(환경변수 `PORTFOLIO_AUTH_*`).
- 앱 `api/client.ts`(갱신 single-flight), `auth/tokenStore.ts`(한 키 JSON), `auth/AuthContext.tsx`.
- 정리 작업은 두 복제본에서 함께 돌아도 결과가 같다. 같은 행을 지우는 일이라 누가 먼저 해도 된다(원칙은 [ADR 0001](0001-leaderless-replicas.md)).

## 돌아보며

**뒤집은 결정.** 백엔드는 2026-11-11~12 커밋 여덟 개(47155af · 5c443d6 · 3fb27b3 · 5e3781e · b81157e · 5f926b9 · 70a426d · 811e664)로, 앱은 2026-11-11~12 커밋(ed7e7de · 3d5b6b0 · e645b5c · 4cf41d6 · a4b879f · 50acc22 · 9ef743b · 3faad4d)으로 바꿨다. 70a426d가 V19를 고쳤다. `push_device`를 비운 뒤 NOT NULL 열을 더하기 전에 다른 연결의 등록이 커밋되면 열 추가가 실패하므로, 비우기 전에 표를 잠근다. 그 결정 기록은 지금 백엔드의 [기술 선택](https://github.com/stock-project-crew/back-end/blob/main/docs/tech-choices.md)으로 줄였고, 옛 인증 절은 코드와 맞지 않아 뺐다.

**서버는 지켰는데 앱이 샜다(R2).** 서버는 공용 기기 원칙을 세션 · 폰 등록 · 발송 대기까지 이었다. 앱은 로그인 · 로그아웃 · 만료 때 조회 캐시를 비우지 않았고 캐시 키에 사용자가 없었다. 같은 폰에서 계정을 바꾸면 30초 안에는 앞사람의 총자산 · 계좌 · 알림이 보이고, 5분 안에는 앞사람 값이 먼저 그려졌다(진단 `review/diagnosis.md`의 R2). 세션 경계 테스트는 테스트용 캐시 설정(gcTime 0)이 앱과 달라 이것을 구조적으로 잡지 못했다. front-end e83e24c(2026-11-15)가 세션이 끝날 때와 로그인할 때 캐시를 비우고, 테스트도 앱과 같은 캐시 설정(`createQueryClient`)으로 만들게 했다. 원칙을 서버 표에만 적용하고 앱 메모리까지 따라가 보지 않은 것이 원인이다.

**정리 작업이 스케줄 풀을 넘었다(O4).** 1시간 정리 작업은 다섯 번째 주기 작업이었는데 스케줄 풀은 4였다(주석은 "넷"). d700b97이 풀을 5로 맞추고 종료 유예를 늘렸고, 가린 계좌번호 채우기가 여섯 번째 작업으로 들어온 뒤 ed41477이 6으로 올리며 작업 수와 풀 크기를 견주는 `SchedulingPoolSizeTest`를 두었다. 작업이 서로를 기다려 늦어진 일이 운영에서 있었는지는 확인하지 않았다.

**남은 것.**
- 재사용 감지의 빈틈, 로그인 시도 횟수 제한 없음(서버가 같은 네트워크 안에서만 닿는다는 전제, 진단 R4), 다른 폰의 세션 보기 · 원격 로그아웃 없음은 받아들였다([공통 4.7](../specs/common.md)).
- 다른 요청이 이미 갱신한 뒤 도착한 `401`에 갱신을 한 번 더 한다. 손해가 쓸데없는 갱신 한 번이라 그냥 뒀다.
- 요청마다 세션을 확인하는 비용과 갱신 행 잠금의 대기는 잰 적이 없다.
