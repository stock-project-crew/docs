# ADR 0001. 리더 없는 다중 복제본

- 상태: 채택 (사후 정리, 2026-11-16)
- 관련: [공통 7.1 · 7.2](../specs/common.md) · [알림 5.2](../specs/alert.md) · [포트폴리오 6.9](../specs/portfolio.md) · [ADR 0002](0002-snapshot-pipeline.md) · [ADR 0003](0003-delivery-queue.md)

## 맥락

API 서버는 쿠버네티스에서 복제본 두 대로 돈다(`k8s/deployment.yaml`의 `replicas: 2`). 파드 하나가 교체되는 동안에도 요청을 받기 위해서다. 서버는 상태를 메모리나 디스크에 들지 않고, 로그인 세션도 DB에 있다.

같은 서버가 요청 처리 말고도 주기 작업 여섯 개를 돌린다. 알림 평가기 · 발송기 · 영수증 확인기, 보유 스냅샷 생성기, 끝난 세션 정리, 가린 계좌번호 채우기다. 이 가운데 넷은 "한 번만"이 결과의 일부다. 알림은 한 데이터 시점에 한 번 울려야 하고, 푸시는 기기마다 한 번 가야 하며, 수집 실행 하나는 한 번 반영되고, 한 날은 한 번 확정돼야 한다.

두 대가 같은 작업을 동시에 돌면 이 "한 번"을 누군가 지켜야 한다. 시스템에는 Postgres 하나만 있고 메시지 브로커나 조정 서비스(ZooKeeper · etcd 같은)는 없다. 2026-09-27 알림 설계 보강(알림 스펙 보강과 설계 회의)이 이 문제를 처음 다뤘고, 런타임 구현(2026-10-11)과 보유 스냅샷 생성기(2026-10-15)가 같은 원칙을 따랐다.

## 결정

리더 선출 · 분산 잠금 대신, 모든 복제본이 모든 주기 작업을 돌리고 중복은 데이터 조건으로 막았다.

- 주기 작업은 앱 안의 `@Scheduled` 메서드다. 별도 앱이나 Deployment를 두지 않는다.
- 같은 일을 두 대가 해도 결과가 하나가 되도록 쓰기에 조건을 건다. 수단은 조건부 UPDATE(읽을 때의 값이 그대로일 때만), 유일 제약(`ON CONFLICT DO NOTHING`), 처리 기록 표, 행 잠금 · advisory 잠금, 잠긴 행 건너뛰기(`SKIP LOCKED`)다. 쓰기 자체가 멱등하면(같은 값 덮기 · 지우기 · 빈 값만 채우기) 조건 없이 둔다.
- 어디까지 처리했는지는 데이터에 둔다(알림의 `evaluated_as_of`, `position_build`, `snapshot_run`). 재시작해도 복구할 메모리 상태가 없다.
- 주기는 끝난 뒤부터 센다(`fixedDelay`). 한 복제본 안에서 같은 작업이 겹쳐 돌지 않는다.
- 스케줄러 스레드는 작업 수와 같게 둔다. 작업끼리 서로를 기다리지 않게 하기 위해서다.
- 평가 한 주기가 주기의 절반(30초)을 넘거나 API 응답이 평가 주기에 맞춰 느려지면, 같은 이미지로 알림 런타임을 맡을 워커 Deployment를 따로 띄우고 API 파드에서는 알림 런타임을 끈다(`ALERT_RUNTIME_ENABLED`). 중복 방지가 데이터에 있어서 코드는 바뀌지 않는다.

작업마다 무엇으로 막는지는 다음과 같다. 세부는 오른쪽 문서에 있다.

| 작업 | 막는 수단 | 자세히 |
|---|---|---|
| 알림 평가 | `version` · 직전 데이터 시점을 건 조건부 UPDATE, 울림은 `(alert_id, as_of)` 유일 제약 | [알림 5.2](../specs/alert.md) |
| 푸시 발송 | `FOR UPDATE SKIP LOCKED`로 집고 임대를 건다 | [ADR 0003](0003-delivery-queue.md) |
| 영수증 확인 | 잠그지 않는다. 두 대가 같은 티켓을 물어도 같은 결과를 쓴다 | [알림 6.4](../specs/alert.md) |
| 보유 스냅샷 생성 | 처리 기록 표, 날짜 잠금 → 계좌 잠금 | [ADR 0002](0002-snapshot-pipeline.md) |
| 끝난 세션 정리 | 끝난 세션을 지운다. 두 번 지워도 결과가 같다 | [공통 4.6](../specs/common.md) |
| 가린 계좌번호 채우기 | 빈 값만 채운다 | [포트폴리오 5.2](../specs/portfolio.md) |

## 검토한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| 리더 선출(한 대만 작업) | 같은 계산을 두 번 하지 않는다 | 데이터 조건이 복제본 수와 무관하게 "한 번"을 지키므로 필요 없다. 평가 반영의 조건부 UPDATE는 평가 도중의 사용자 변경도 막는 것이라, 리더를 두어도 없앨 수 없다 |
| 분산 잠금(잠금을 잡은 쪽만 실행) | 같은 계산을 두 번 하지 않는다 | 따로 따지지 않았다. 두 대가 같은 계산을 하는 중복 비용을 재지 않았고, 재 본 뒤 정한다 |
| 별도 라이브러리 | 직접 짜지 않는다 | 분산 잠금과 같다 |
| 지금 별도 워커 앱 · Deployment | API와 작업의 자원이 나뉜다 | 평가 소요가 주기의 절반을 넘기 전에는 나눌 이유가 없다. 같은 이미지를 스위치로 나눌 수 있게 해 두었다 |
| 스케줄러 스레드 하나(기본값) | 설정이 없다 | 평가 한 번이 길어지면 발송이 그동안 멈춘다 |
| 알림마다 신호 처리 기록을 따로 둠 | 처리 여부가 명시적이다 | 평가한 데이터 시점(`evaluated_as_of`)이 이미 그 기록이다. 신호 뒤에 만든 알림도 다음 주기에 평가된다 |

근거: 알림 스펙([archive](../archive/specs/buy-sell-timing-alert/2026-07-12-buy-sell-timing-alert-spec.md)), 알림 설계 회의([2026-09-27](../archive/meetings/2026-09-27-buy-sell-timing-alert-design-review.md)), 런타임 계획서([plan](../plan/2026-10-11-alert-backend-runtime-plan.md)), back-end 옛 결정 기록([`docs/decisions.md`](https://github.com/stock-project-crew/back-end/blob/d3b619d/docs/decisions.md))의 "알림 런타임" 절.

## 결과

**얻은 것**

- 조정 서비스를 들이지 않았다. 리더 장애나 선출 지연이 없다.
- 복제본을 늘리거나 줄여도 코드가 같다. 같은 버전의 파드가 셋이 되어도 중복 방지는 같다. 버전이 섞일 때의 엣지 손실은 아래 "감수한 비용"에 있다.
- 파드가 어느 단계에서 죽어도 DB 안의 결과는 트랜잭션이 함께 롤백돼 다음 주기가 같은 결과를 낸다. 트랜잭션 밖에서 Expo를 부르는 발송은 예외로, 같은 푸시가 한 번 더 갈 수 있다([ADR 0003](0003-delivery-queue.md)).

**감수한 비용**

- 두 대가 같은 알림을 읽고 계산한다. 반영에서 진 쪽(`Outcome.LOST`)의 계산은 버려진다. 보유 스냅샷도 늦은 쪽이 잠금을 기다렸다가 처리 기록을 보고 돌아선다.
- 템플릿 · 업캐스팅을 바꾸는 롤링 배포에서는 옛 파드와 새 파드가 조건 해시(`spec_hash`)의 재기준을 번갈아 하며 거짓→참 전환(엣지)을 놓칠 수 있다. 드문 배포라 감수했다. 잦아지면 상태에 평가기 코드 버전을 두고 낮은 버전이 반영하지 않게 한다.
- 정합성이 쓰기 조건 하나하나에 흩어져 있다. 새 작업을 더할 때마다 "두 대가 동시에 하면?"을 그 작업에서 다시 따져야 한다.

**지금 어디에 있나**

- 작업: `AlertJobs`(평가 1분 · 발송 5초 · 영수증 5분), `SnapshotJobs`(1분), `AuthSessionJobs`(1시간), `AccountNumberMaskJobs`(1시간).
- 스레드: `spring.task.scheduling.pool.size: 6`. `SchedulingPoolSizeTest`가 `@Scheduled` 메서드 수와 견준다.
- 종료: 요청 대기 20초 + 작업 대기 20초, `terminationGracePeriodSeconds: 50`.
- 조건: `RuntimeMapper.applyState`, `alert_event_once_per_point`(V4), `DeliveryMapper.lockDue`, `position_build.run_id` 유일(V8).

## 돌아보며

**스레드 수가 작업 수를 따라가지 못했다.** 스레드는 알림 런타임과 함께 3개(`eb56f84`, 10/11)였고, 보유 스냅샷 생성기를 올리며 4개(`6c09025`, 10/16)가 됐다. 그 뒤 끝난 세션 정리(`811e664`, 11/11)를 더할 때는 올리지 않았다. 작업은 다섯인데 풀은 4였고, 설정 주석은 여전히 "넷"이었다. 11/14 진단(O4)이 이를 찾았고, 같은 진단이 웹 종료 20초와 작업 종료 20초의 합이 종료 유예 30초를 넘는 것도 짚었다. `d700b97`(11/15)이 풀을 5로, 종료 유예를 50초로 고쳤다. 같은 날 가린 계좌번호 채우기(`9d9566b`)가 main에 들어와 여섯 번째 작업이 됐고, `ed41477`이 풀을 6으로 맞추며 다시 어긋나지 않게 `SchedulingPoolSizeTest`를 더했다. 스레드가 모자라면 작업이 서로를 기다릴 뿐 결과는 틀리지 않는다. 그래서 테스트로는 드러나지 않았다.

**비용을 잰 적이 없다.** 이 결정의 대가는 중복 계산과 LOST인데, main에서는 LOST를 어디에서도 세지 않는다. 평가 주기 로그(`TickReport`)에는 소요 · 대상 알림 수 · 평가한 데이터 시점 수만 남는다. 평가 한 주기의 소요는 주기마다 로그에 남지만, 운영 로그를 모아 분포를 본 적은 없다. 워커로 나누는 기준(30초)을 세워 두고, 그 기준을 볼 지표는 로그 한 줄뿐이다(O2). [E-base 실습](../practice/E-base.md)에서 반영 결과 계수기(`outcome="lost"` 포함)를 실습 브랜치에 만들었고 main에는 아직 없다. 복제본 비용 측정(D 과제)은 시작 전이다.

**롤링 중 엣지 손실도 재지 않았다.** 감수한다고 적었을 뿐 얼마나 자주 생기는지는 모른다. 운영 롤링 배포에서 파드가 실제로 몇 대 겹치는지도 확인하지 않았다. 매니페스트에 배포 전략이 없어 쿠버네티스 기본값(maxSurge 25%, 두 대면 올림해 1)이 적용된다는 것은 [실습 C](../practice/C.md)가 매니페스트를 읽고 추론한 것이다.

**동시성 테스트는 있지만 테스트 케이스와 묶이지 않았다.** `AlertRuntimeWriterTest`의 "다른 복제본이 먼저 반영했으면 진다", `DeliveryDispatcherTest`의 "다른 복제본이 집고 있는 행은 건너뛴다", 보유 스냅샷의 `SnapshotConcurrencyTest` 같은 테스트가 원칙을 지킨다. 그런데 테스트 문서의 케이스에는 연결돼 있지 않다(T6).
