# ADR 0006. 배포 중 스키마 호환

- 상태: 채택 (사후 정리, 2026-11-16)
- 관련: [공통 2 시스템 구성](../specs/common.md) · [공통 7.2 두 대 동시 실행 전제](../specs/common.md) · [데이터 계약 2.2 놓이는 곳](../specs/data-contract.md) · [ADR 0001 리더 없는 다중 복제본](0001-leaderless-replicas.md)

## 맥락

`main`에 푸시하면 곧 운영 배포다. CI가 테스트를 통과한 커밋만 이미지로 만들고, 매니페스트의 이미지 태그를 고치는 커밋을 남긴다. ArgoCD가 그 커밋을 보고 파드를 롤링으로 바꾼다. 평소 배포에는 사람이 태그를 고치는 단계가 없다(태그를 손으로 되돌리는 것은 롤백 때뿐이다). 흐름은 [공통 2](../specs/common.md).

API 서버는 복제본 두 대(`replicas: 2`)이고 하나씩 교체된다. 새 파드가 뜨면서 마이그레이션을 운영 DB에 적용하면 DB는 새 스키마가 되는데, 옛 파드는 몇 분 더 살아서 요청을 받는다. 롤링 중에는 "옛 코드 + 새 스키마"가 반드시 생긴다. 롤백할 때도 같다.

스키마는 소유로 갈린다. `app`은 백엔드 마이그레이션이 만들고, `data`는 데이터팀이 따로 바꾼다. 배포가 바꾸는 것은 `db/migration`뿐이고, 데이터팀 표의 사본(`db/external`, 미러)은 로컬 · 테스트에서만 적용된다.

클러스터는 계속 켜 두지 않는다. 꺼진 동안에도 CI는 푸시마다 매니페스트 태그를 올리므로, 켤 때 그동안 쌓인 마이그레이션이 한꺼번에 적용된다.

## 결정

별도 마이그레이션 Job 대신 앱이 기동할 때 Flyway로 적용하고, 롤링 중 공존은 "한 배포에는 옛 코드가 깨지지 않는 스키마 변경만 넣는다"는 규칙과 CI의 정적 검사로 막는다.

- **기동 시 Flyway.** 각 복제본이 기동할 때 시도한다. 두 대가 함께 떠도 한쪽이 적용하고 다른 쪽은 "up to date"로 넘어가는 것을 확인했다.
- **평문 SQL.** Liquibase를 쓰지 않는다.
- **번호는 `db/migration` · `db/external`을 통틀어 한 순열.** 운영에 적용된 파일은 고치지 않는다.
- **호환 규칙.** 컬럼 삭제 · 이름 변경 · 옛 코드가 채우지 않는 NOT NULL 추가는 다음 배포로 미룬다. 규칙 문장은 [공통 7.2](../specs/common.md).
- **CI의 정적 검사(`MigrationCompatLintTest`)가 깨지는 문형(컬럼 삭제 · 이름 변경 · 테이블 삭제 · 기본값 없는 NOT NULL 추가 · SET NOT NULL · CHECK 교체)을 잡는다. 문형만 보므로 의미까지 막지는 못한다.** 걸려도 되는 파일은 이유와 함께 허용 목록에 둔다. 지금 목록은 이미 운영에 적용돼 다시 돌지 않는 판(V13 · V15 · V19 — 옛 코드를 깨지 않아서가 아니다, 아래 돌아보며)과 허용 값을 더하기만 하는 CHECK 교체(V22 · V25)다. 규칙 문장은 [공통 7.2](../specs/common.md).
- **새 컬럼은 NULL 허용으로 더하고 읽을 때 메운다.** `alert_event.cadence`는 NULL을 받고 읽는 쪽이 `COALESCE(e.cadence, a.cadence)`로 읽는다. 이 컬럼을 모르는 옛 파드의 INSERT도 받는다.
- **enum은 `text` + `CHECK`.** 값을 더하고 빼는 마이그레이션이 가볍다.
- **API가 바뀌는 배포는 백엔드 먼저, 앱은 직후.** 롤링 중 몇 분의 불일치는 감수한다.
- **옛 코드 테스트는 손으로 돌리는 도구로 둔다.** 새 스키마에서 옛 커밋의 테스트를 Flyway 없이 돌리는 스크립트(`scripts/compat/old-code-test.sh`)다. 클러스터를 켜기 전에, 끄기 전 마지막으로 돌던 판으로 돌린다.

## 검토한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| 별도 마이그레이션 Job | 앱 기동과 스키마 변경이 갈리고, 적용 순서를 배포 단계로 잡을 수 있다 | 버렸다기보다 정하지 않았다. 기동 시 실행으로 두 대 동시 기동이 문제없음을 확인했고, 옛 백엔드 배포 결정 기록([`d3b619d`의 decisions-deploy.md](https://github.com/stock-project-crew/back-end/blob/d3b619d/docs/decisions-deploy.md))의 "아직 정하지 않은 것"에 있었고, 지금은 이 ADR의 "남은 것"에 둔다 |
| Liquibase | DB 추상화, 변경 기록 형식 | DB가 PostgreSQL 하나라 추상화가 값을 하지 않는다. 평문 SQL이면 "비율 컬럼 금지" 같은 검사가 파일 읽기로 끝난다 |
| 폴더별 번호대 예약 | 백엔드 · 미러 파일이 섞이지 않는다 | 두 폴더가 이력 표 하나를 쓰므로 낮은 번호가 뒤늦게 나타나 순서 검증에 걸린다 |
| 새 컬럼을 처음부터 NOT NULL | DB가 값을 보장한다 | 롤링 중 옛 파드의 INSERT가 실패한다 |
| PostgreSQL ENUM | 타입이 값 집합을 강제한다 | 값 추가 · 삭제 마이그레이션이 번거롭고 매핑에서 이득이 없다 |
| 앱 먼저 배포 | — | 앱이 아직 없는 API를 부른다. 로그인 세션 전환 때는 갱신이 `404`로 거절돼 만료마다 로그인 화면으로 간다 |
| 옛 코드 테스트를 CI에 붙이기(정적 검사와 함께, 또는 단독) | 옛 코드가 실제로 쓰는 경로만 잡는다. CHECK를 넓히는 안전한 변경은 통과시킨다 | 클러스터를 자주 꺼서 "매니페스트의 직전 태그"가 실제로 돌던 판이 아니다. 엉뚱한 판과 비교하게 된다. 테스트 단계가 약 2배가 된다 |

## 결과

얻은 것
- 배포가 푸시 하나로 끝나고, 마이그레이션을 돌리는 별도 단계가 없다.
- 운영에 들어가는 V 파일이 옛 코드를 깨는 문형을 쓰면 이미지가 올라가지 않는다. 검사는 0.04초다.
- 허용 목록이 이유를 들고 있어, 왜 이 파일이 걸려도 되는지가 테스트 코드에 남는다.

감수한 비용
- 검사는 일반 단위 테스트라 로컬 `./gradlew test`에서도 돌지만, CI는 `main` 푸시에서만 돈다(PR 검사 없음). 로컬에서 돌리지 않고 푸시하면 `main`에 들어간 뒤에야 걸려, 되돌리거나 고친 커밋을 다시 푸시해야 한다.
- 깨지는 변경은 확장 → 이전 → 축소로 여러 배포에 나눠야 한다.
- CHECK는 넓히는지 줄이는지 문장만으로 알 수 없어 교체 자체를 잡는다. 넓힐 때마다 허용 목록에 한 줄을 더한다.
- 테스트가 실패하면 그 뒤의 `main` 푸시가 모두 배포되지 않는다(아래 D-41).

지금 있는 곳
- 정적 검사: `src/test/java/.../migration/MigrationCompatRules.java`(규칙 6개) · `MigrationCompatLintTest`(게이트, 허용 목록) · `MigrationCompatRulesTest`(규칙 경계).
- CI: `.github/workflows/build-and-push.yml`의 테스트 단계(`./gradlew test`)에 정적 검사가 들어 있다.
- 손으로 돌리는 도구: `scripts/compat/old-code-test.sh`.
- 푸시 전 확인 목록: 백엔드 `docs/ops/deploy.md`의 "푸시 전에 본다".

## 돌아보며

**처음에는 막는 장치가 없었다(O3).** 규칙은 사람 머리에만 있었고, CI는 새 코드의 테스트만 돌렸다. 2026-11-14 진단이 이것을 O3로 적었다. 사례는 2026-11-11 `47155af`의 V19다. V19는 `push_device`를 비우고 `session_id NOT NULL`을 더한다. 확장과 축소를 한 배포에서 한 셈이라, 옛 코드의 기기 등록 INSERT는 이 열을 채우지 못한다. 로그인 세션 설계([보관본](../archive/specs/portfolio-management/2026-11-11-auth-session-design.md))는 이 실패를 알고 받아들였다. "옛 파드로 간 기기 등록은 실패한다. 앱이 앞으로 올 때 다시 등록한다." 즉 V19는 몰라서 깨뜨린 것이 아니라 감수한 것이었다. 다만 그 판단을 강제하거나 기록하는 장치가 없었다. 운영 롤링 중 실제로 등록이 실패했는지는 확인하지 않았다.

**V19는 배포 전에 한 번 고쳤다.** 첫 판은 잠그지 않고 비웠다. 비운 뒤 NOT NULL 열을 더하기 전에 다른 연결의 등록이 커밋되면 그 행에 `session_id`가 없어 열 추가가 실패한다. 2026-11-12 `70a426d`가 비우기 전에 `LOCK TABLE push_device IN ACCESS EXCLUSIVE MODE`를 걸었다. 운영 적용 전에 고쳤으므로 "적용된 파일은 고치지 않는다"는 규칙 안이다.

**새 컬럼을 기존 판정이 따라가지 않았다(O5).** V18의 `alert_event.cadence`는 호환 규칙대로 NULL 허용으로 들어갔고 읽는 곳은 `COALESCE`를 썼다. 그런데 발송 기한 판정은 계속 알림의 `a.cadence`를 봐서, 데이터 닫힘으로 종가 평가된 장중 알림의 울림도 30분 기한을 받았다. 2026-11-15 `d700b97`이 기한을 울림의 평가 시점(`COALESCE(e.cadence, a.cadence)`)으로 판정하게 고쳤다. 스키마는 호환됐는데 의미가 따라가지 못한 경우다. 정적 검사도 옛 코드 테스트도 이 유형은 잡지 못한다.

**테스트 실패가 배포를 멈췄다(D-41).** 2026-11-09 `de1ccbc`가 수집 일정을 바꿔 동기화 테스트 2개가 실패했고(결함으로 적은 날은 2026-11-10), 그 뒤의 `main` 푸시가 배포되지 않아 매니페스트 태그가 `77e48b1`에 머물렀다. 동작은 맞고 테스트 시각이 틀렸던 것이라 `f65358a`가 테스트 시계를 옮겼다. 게이트는 의도대로 막았지만, 막는 이유가 스키마가 아니어도 배포 전체가 멈춘다.

**검사를 만들고 두 방식을 견줬다.** 2026-11-15 실습(`yhr/practice/F.md`)에서 정적 검사(`6d6c18c`)와 옛 코드 테스트 스크립트(`cb55d7f`)를 만들고 CI 주석(`d0d22d0`)까지 `main`에 넣었다. 로컬 Docker(Postgres 16.15, Flyway 10.20.1)에서 조합마다 1회 쟀다.
- V18 코드 + V19 스키마: 두 방식 모두 잡았다. 옛 코드 테스트는 1,154개 중 30개 실패였고 모두 `push_device.session_id` NOT NULL 위반이었다.
- V14 코드 + V15 스키마(CHECK 축소): 계획했던 4규칙으로는 못 잡아 SET NOT NULL · CHECK 교체 규칙을 더했다. 옛 코드 테스트는 970개 중 361개 실패였는데, 대부분은 옛 fixture가 넣던 값 때문이고 옛 앱 코드의 경로에서 난 진짜 신호는 몇 건뿐이었다.
- 추가 시간: 정적 검사 0.04초, 옛 코드 테스트 104~109초(새 코드 전체 테스트 114초).
- Flyway는 자기가 모르는 미래 V 버전을 경고만 남기고 무시했다. 반대로 옛 코드에 없는 반복 마이그레이션(`R__`)이 적용돼 있으면 검증에서 실패해 기동하지 못했다. 그래서 `R__app_column_comments.sql`이 생긴 `0dd4498`보다 앞선 판으로는 롤백하지 못할 것으로 본다. 로컬에서 재현했고 운영에서는 확인하지 않았다.

처음에는 두 방식을 함께 CI에 붙이자고 했다가, 클러스터를 자주 끈다는 조건을 넣고 정적 검사만 붙였다. 판단을 바꾼 것은 성능 숫자가 아니라 운영 조건이었다.

남은 것
- 의미 변경(O5 유형)을 막는 것은 여전히 리뷰뿐이다. 데이터팀 미러의 V26이 `cln_trade_coverage`를 계좌당 시장별 두 행으로 바꾼 것이 후보인데 확인하지 않았다.
- 클러스터가 꺼진 동안 쌓인 마이그레이션이 한꺼번에 적용되면, 푸시마다 확장 → 축소를 지켰어도 한 번에 축소까지 갈 수 있다. 푸시 단위 검사로는 잡지 못한다.
- `R__` 때문에 롤백할 수 없는 판이 생기는 문제, 클러스터를 끌 때 돌던 판을 기록할지는 정하지 않았다.
- 별도 마이그레이션 Job으로 뺄지는 아직 정하지 않았다.
