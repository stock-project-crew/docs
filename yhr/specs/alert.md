# 매수·매도 타이밍 알림

종목에 조건을 걸어 두면 서버가 시세·수급·보유 상태로 평가하다가 조건이 참이 되면 울리는 기능의 설계서다. 서비스 전체 원칙·로그인·API 공통 규칙은 [common.md](common.md), 데이터팀이 주는 표의 모양은 [data-contract.md](data-contract.md)가 정한다. 사용자 상태 지표가 읽는 보유 값은 [portfolio.md](portfolio.md)를 따른다.

---

## 1. 개요

### 1.1 기능 요약

사용자가 종목 하나에 조건을 건다. 서버는 정해진 평가 시점마다 그 조건을 평가하고, 조건이 참이 되면 **울림**을 기록한다. 울림은 앱 안 기록(울린 알림 목록·탭 배지)으로 반드시 남고, 푸시를 받을 수 있는 기기에는 푸시로도 간다.

조건의 예는 가격 도달, 박스권 상단 돌파·하단 이탈, 외국인 3일 연속 순매수, 평가손익률 −10% 도달이다. 예시일 뿐 지원 범위를 닫는 목록이 아니다. 조건의 모양은 세 축(3.1)으로, 지원하는 지표와 프리셋은 카탈로그(3.3 · 3.5)로 정한다.

알림은 **보유 종목에 한정되지 않는다.** 종목 마스터의 어떤 종목에도 걸 수 있고, 보유 상태를 읽는 지표(평가손익률·비중)만 보유 종목에 걸린다. 그래서 알림은 계좌가 아니라 사용자에게 직접 속한다(7절 `alert`).

### 1.2 하이브리드

조건을 만드는 길은 둘이고 저장 모양은 하나다.

| 길 | 사용자가 하는 일 | 저장 |
|---|---|---|
| 직접 조건(`COMPOSABLE`) | `지표 + 변형 + 연산자 + 기준값`을 최대 5개 AND로 조합한다 | `trigger_type = COMPOSABLE` + `trigger_spec`(조건 목록) |
| 프리셋(`PRESET`) | 만들어 둔 유형 카드를 골라 입력 칸만 채운다 | `trigger_type = PRESET` + `trigger_spec`(프리셋 키와 입력값) |

프리셋은 모두 직접 조건으로 펼쳐지는 템플릿이라 평가기는 하나다(3.5).

### 1.3 v1 범위

| 항목 | v1 |
|---|---|

### 1.4 용어

두 기능이 함께 쓰는 말은 [common.md](common.md)의 "용어"가 정한다. 이 문서에서만 쓰는 말은 다음과 같다.

| 용어 | 뜻 | 코드 이름 |
|---|---|---|
| 알림 | 종목 하나에 건 조건 · 평가 시점 · 알림 방식 · 유효기간 묶음. 동사는 "알림 걸기" | `alert` |
| 울림 · 울린 알림 | 조건이 한 데이터 시점에서 참이 되어 알림 방식 규칙에 따라 기록과 푸시가 생긴 것. 알림을 지워도 기록은 남는다 | `alert_event`, `fired_at` |
| 푸시 | 울림을 기기로 보내는 것 | `push_device`, `alert_delivery` |
| 조건 | 지표와 기준값을 연산자로 견준 식. 한 줄만 가리킬 때는 "조건 한 줄" | `trigger_spec`, `conditions[]` |
| 지표 · 기준값 | 조건의 왼쪽 값과 오른쪽 값. 기준값은 상수이거나 비교 지표다 | `left` · `right`, `Operand` |
| 변형 | 지표에 씌우는 함수 — 그대로 · 최근 N일 집계 · N일 전 대비 변화 · 변화율 | `transform` |
| 유지 방식 | 조건이 N일 연속(종가) 또는 N분 이상(장중) 참이어야 울리게 하는 덧붙임 | `modifier` (`streak` · `persist_min`) |
| 평가 시점 | 언제 평가하나. 값은 장중 · 종가 | `cadence` (`INTRADAY` · `CLOSE`) |
| 평가 | 한 데이터 시점의 값으로 조건을 참 · 거짓 · 확인 불가 중 하나로 정하는 일 | `evaluate` |
| 데이터 시점 | 한 번의 평가가 기준으로 삼은 데이터의 시각. 종가는 그 거래일의 마감 시각, 장중은 스냅샷 시각 | `as_of`, `evaluated_as_of` |
| 확인 불가 | 값이 없거나 이력이 모자라 참 · 거짓을 정할 수 없는 평가 결과 | `UNKNOWN`, `unknown_reason` |
| 엣지 기준 | 울릴지 정할 때 쓰는 직전의 참 · 거짓. 확인 불가는 이 값을 바꾸지 않는다 | `last_known_result` |
| 알림 방식 | 돌파할 때마다 · 한 번만 · N분마다 다시. 간격은 "다시 알림 간격" | `notify_mode`, `cooldown_min` |
| 꺼짐 · 일시중지 | 꺼짐은 사용자가 평가를 멈춘 상태, 일시중지는 데이터 닫힘으로 서버가 평가를 건너뛰는 상태 | `PAUSED` / `data_closure.kind = HELD` |
| 데이터 닫힘 | 데이터를 아예 확보하지 못하는 동안 그 데이터에 기대는 조건을 닫는 운영 규칙 | `data_closure` (`AS_CLOSE` · `HELD`) |
| 완료 신호 | "이 시장의 이 데이터가 이 시점까지 다 들어왔다"를 알리는 행 | `market_data_run` · `snapshot_run` |
| 거래일 | 시장 캘린더에서 장이 열린 날. 알림 기간의 "일"은 그 종목이 실제로 거래된 날이다(거래정지일 제외) | `is_trading_day` |

## 2. 화면

화면 목록·진입 경로·탭 배지·푸시를 눌렀을 때 여는 곳은 [common.md](common.md)의 "앱 구조"가 정한다. 이 절은 화면마다 무엇을 어떻게 보이고 무엇을 왜 빼는지를 정한다.

### 2.1 조건 문장

같은 조건이 다섯 자리에 문장으로 나온다 — 알림 카드, 알림 상세, 편집기의 문장 상자, 푸시 본문, 울린 알림 상세. **문장은 모두 서버가 만든다.** 다섯 자리가 어긋나지 않고, 문구를 고쳐도 앱 배포가 필요 없다. 서버는 목록·상세를 읽을 때마다 저장된 조건을 지금 코드로 컴파일해 문장을 만든다. 지금 코드가 읽지 못하는 조건은 그 알림만 `조건을 읽을 수 없어요`로 보인다.

| 문체 | 쓰는 곳 | 예 |
|---|---|---|
| 짧은 형 | 알림 카드, 푸시 본문 | `종가 · RSI(14) 3일 연속 ≥ 70` |
| 문장형 | 알림 상세, 편집기의 문장 상자 | `종가 기준으로 RSI(14)가 3일 연속 70 이상이면 알려요` |

두 문체는 같은 조각 규칙에서 나온다.

| 조각 | 짧은 형 | 문장형 |
|---|---|---|
| 평가 시점 | `장중 ·` `종가 ·` (미국 종목은 `미국 장중 ·` `미국 종가 ·`) | `장중에` `종가 기준으로` |
| 지표 | `현재가`(장중 가격) · `종가`(종가 가격) · `등락률` · `오늘 거래량`(장중) / `거래량` · `거래량 배수(20일)` · `고가` · `저가` · `가격 폭(20일)` · `20일 이동평균` · `RSI(14)` · `이격도(20)` · `외국인 순매수` · `기관 순매수` · `평가손익률` · `비중` | 같음 |
| 윈도우 | 오늘을 뺀 윈도우는 `직전 20일 최고 고가`, 넣은 윈도우는 `최근 5일 외국인 순매수 합계` | 같음 |
| 변화 | `5일 전 대비 종가 변화` · `5일 전 대비 종가 변화율` | 같음 |
| 연산자 | `≥` `≤` `>` `<` `상향 돌파` `하향 이탈` | `이상` `이하` `초과` `미만` `상향 돌파하면` `하향 이탈하면` |
| 유지 방식 | `3일 연속` · `10분 유지` | `3일 연속` · `…인 상태가 10분 이상 유지되면` |
| 결합 | ` 그리고 ` | `…이고, …이면` |

- **기간 단위는 `일`이다.** 내부적으로는 그 종목이 거래된 봉이지만 사용자에게는 일로 읽힌다. 휴장일·거래정지일을 빼고 센다는 사실은 알림 상세의 도움말 `기간의 "일"은 그 종목이 거래된 날로 세요. 휴장일과 거래정지일은 빼요.`로 알린다.
- **`직전`과 `최근`이 오늘 포함 여부를 드러낸다.** 오늘을 넣을지는 맞은편으로 자동으로 정해지므로(3.2), 사용자는 문장으로만 그 차이를 읽는다.
- **프리셋은 전용 문장을 쓴다.** 컴파일한 조건을 풀어 쓰면 박스권이 "가격 폭 ≤ 15% 그리고 종가 > 직전 20일 최고 고가"가 되어 프리셋을 고른 의도가 사라진다.
- **부호.** 등락률 · 수익률 · 순매수 금액 · 변화량 · 변화율의 관측값에는 `+` · `−`를 붙이고, 가격 폭처럼 늘 양수인 값에는 붙이지 않는다. 반올림해 0이 되는 값(`0.0%`)에는 부호를 붙이지 않는다. 하락 쪽 갈래는 상승 쪽과 같은 틀에 `하락` · `하향 이탈` · `이하 진입` · `하단 이탈` · `순매도`를 쓴다.

| 프리셋 | 짧은 형 예 | 관측값 줄 예 (푸시 본문 · 현재값 상자 · 울린 이유) |
|---|---|---|
| 가격 도달 | `현재가 ≥ 70,000원` | `현재가 70,200원 ≥ 70,000원` |
| 급등락 | `5% 이상 상승` | `등락률 +5.4% ≥ 5%` |
| 거래량 급증 | `거래량 20일 평균의 3배 이상` | `거래량 20일 평균의 3.4배 ≥ 3배` |
| 골든·데드크로스 | `5일선이 20일선 상향 돌파` | `5일선 72,100원이 20일선 70,850원 상향 돌파` |
| RSI 과매수·과매도 | `RSI(14) 70 이상 진입` | `RSI(14) 71.3 ≥ 70` |
| 박스권 돌파 | `20일 박스권(폭 15% 이내) 상단 돌파` | `종가 72,100원 > 직전 20일 최고 고가 71,800원 (폭 11.2%)` |
| 외국인·기관 연속 순매수 | `외국인 3일 연속 순매수` | `외국인 +312억원 · 3일째` |
| 외국인·기관 순매수 전환 | `외국인 순매수 전환` | `외국인 +312억원 (어제 −45억원)` |
| 수익률 도달 | `손실 10% 도달` | `평가손익률 −10.4% ≤ −10%` |

울림 문구(제목·본문)는 6.7이 정한다.

### 2.2 알림 탭과 카드

| | |
|---|---|
| 답하는 질문 | 무엇을 걸어 뒀고, 지금 어떤 상태인가 |
| 위쪽 | `울린 알림 전체 →`(항상 보인다) / `새로 울린 알림` 블록 — 안 읽은 울림 최대 3건, 넘치면 `외 N건 →` |
| 카드 | 1줄 `종목명 · 시장 배지 · 상태 배지` / 2줄 조건(짧은 형) / 3줄 `알림 이름 · 최근 울림 <시각>` / 데이터 닫힘이면 4줄 `data_closure.message` |
| 카드 오른쪽 | 감시 중 · 꺼짐: 토글 / 울린 뒤 종료: `다시 켜기` / 만료: `다시 켜기` → 유효기간 시트(무기한 · 1주 · 1개월 · 3개월 · 날짜 지정) |
| 정렬 | 서버가 정한다. 조건 충족 중 → 감시 중 → 확인 불가 · 일시중지 → 꺼짐 → 울린 뒤 종료 → 만료. 같은 묶음 안에서는 최근 울린 순, 울린 적이 없으면 만든 순(최근 것이 위) |
| 머리 | `알림` · `＋ 새 알림`. 기준 표기는 `최근 평가 <시각>` |

- **제목 줄은 종목명이다.** 사용자가 알림을 찾는 첫 손잡이는 종목이다. 알림 이름은 3줄에 작게 두어 같은 종목에 건 비슷한 알림을 가르는 몫을 한다.
- **종목명 자리.** 종목 마스터의 이름(미국 종목은 영문명)을 보인다. 종목이 마스터에서 빠졌으면 알림을 만들거나 고칠 때 남겨 둔 이름, 그것도 없으면 종목코드, 그것도 없으면 `종목 정보 없음`이다. 어느 알림인지 알아볼 수 있어야 끄거나 지울 수 있다.
- **현재값을 카드에 두지 않는다.** 카드가 답하는 질문은 "걸어 둔 것과 그 상태"다. 현재값을 두면 목록 전체를 계속 갱신해야 한다. 현재값은 알림 상세와 편집기가 보인다.
- **카드에서 지우지 않는다.** 밀어서 지우는 동작은 실수가 잦다. 삭제는 알림 상세에서 확인을 거친다.
- **종목명과 조건은 각 1줄이고 넘치면 말줄임한다.** 상태 배지는 자르지 않는다. 확인 불가는 배지에 사유를 담는다(`확인 불가 · 거래 없음`). 상태 배지는 오른쪽 끝에 두고, `일시중지`만 시장 배지 바로 옆에 둔다.
- **상태 순 정렬**은 주의가 필요한 알림을 위로 올리기 위해서다. 일시중지된 알림은 직전 결과가 참이어도 확인 불가 묶음에 둔다 — 몇 주 전의 충족이 지금 충족으로 읽히지 않게.
- **탭을 여는 것만으로 읽음 처리하지 않는다.** 블록에는 제목만 보였지 내용을 본 것이 아니다. 읽음은 울린 알림 상세를 열 때와 `모두 읽음`으로만 생긴다.
- 알림이 없어도 안 읽은 울림(삭제된 알림의 울림)이 있으면 빈 상태 위에 위쪽 블록을 그대로 둔다.

카드 상태 문구는 4.8이 정한다.

### 2.3 울린 알림 · 울린 알림 상세

**울린 알림(목록)**

| | |
|---|---|
| 행 | 1줄 제목 · 안 읽음 점 / 2줄 본문(1줄 말줄임) / 3줄 울린 시각 · `삭제된 알림` 배지 |
| 정렬 | 울린 시각 최신순, 같으면 울림 ID 내림차순. 날짜로 묶지 않는다 |
| 머리 | `모두 읽음` |
| 쪽 | 기본 20건, 아래로 내리면 다음 쪽 |

알림 상세의 `전체 →`로 들어오면 그 알림의 울림만 보인다. 삭제된 알림의 울림도 그대로 보인다 — 받은 푸시를 눌렀을 때 내용이 사라져 있으면 무엇이 울렸는지 알 방법이 없다.

**울린 알림 상세**

| | |
|---|---|
| 답하는 질문 | 무엇이, 왜 울렸나 |
| 구성 | 제목 / `<데이터 시점> 기준 · <울린 시각> 울림` / 울린 이유 상자(조건마다 한 줄) / 이 알림(이름 · 지금 상태 배지 또는 `삭제된 알림`) / `알림 보기 →` · `이 알림 끄기` |
| 열면 | 그 울림을 읽음 처리한다 |
| 찾을 수 없음 | 남의 울림·없는 울림이면 `찾을 수 없는 알림이에요` |

- **울린 당시의 문구만 보인다.** 알림이 뒤에 수정돼도 그때 울린 이유는 바뀌지 않는다(6.7).
- **지금 값을 두지 않는다.** 두 시점의 값이 나란히 있으면 어느 쪽이 울린 이유인지 헷갈린다. 지금 값은 `알림 보기 →`(알림 상세의 현재값 상자)가 답한다.
- `이 알림 끄기`는 알림이 감시 중(`ACTIVE`)일 때만 보인다. 알림이 삭제됐으면 `알림 보기`와 `이 알림 끄기`를 모두 숨긴다.
- 이 알림이 데이터 닫힘에 걸렸으면 지금 상태 배지가 그것을 따른다(4.11).

> **결정 필요 — 미국 종목 울림의 기준 표기.** 울린 알림 상세의 응답(`GET /alert-events/{id}`)에 종목 시장이 없어, 앱은 이 화면의 기준 표기를 늘 국내 형식으로 그린다. 미국 종목의 울림은 목록·알림 상세에서는 `미국 9/26 종가 기준`인데 이 화면에서만 `9/26 종가 기준`으로 보인다. 푸시 본문과 울린 이유 상자는 서버가 만든 문구라 맞다.

### 2.4 알림 상세

| | |
|---|---|
| 답하는 질문 | 이 알림은 무엇을 보고 있고, 지금 어디쯤인가 |
| 구성 | 머리(`종목명 · 시장 배지 · 상태 배지` · `수정`) / 알림 이름 / 조건(문장형) / 데이터 닫힘이면 그 문구와 `다시 제공되면 자동으로 재개돼요` / 기간 도움말 / 현재값 상자(2.5) / 평가 시점 · 알림 방식 · 유효기간(`무기한` · `<날짜>까지`) · 마지막 평가(`아직 평가 전이에요`) / 최근 울린 알림 5건 + `전체 →`(없으면 `아직 울리지 않았어요`) / `감시` 토글 또는 `다시 켜기` / `알림 삭제` |
| 수정 | 머리의 `수정`. 프리셋 입력 또는 직접 조건 만들기가 값이 채워진 채 열린다. 종목과 프리셋·직접 조건의 구분은 바꿀 수 없다 |
| 삭제 | 확인 시트 `이 알림을 삭제할까요?` / `울린 기록은 남아요` |
| 만료 | `다시 켜기` → 유효기간 시트 |

- **현재값 상자를 둔다.** "왜 아직 안 울리지?"에 답한다. 평가 상태에는 결과만 저장하므로(4.7) 조건별 값을 보이려면 화면을 열 때 미리보기를 한 번 부른다. 요청에 `alert_id`를 실어 수정 규칙(보유를 묻지 않음 · 자기 자신은 중복이 아님)을 적용한다. 검증 오류가 있어도 계산할 수 있는 조건의 현재값은 채운다.
- **종목을 바꿀 수 없다.** 종목이 바뀌면 가격 기준값·통화·쓸 수 있는 지표가 달라져 조건이 대부분 무너지고, 울린 기록이 다른 종목에 붙는다. 다른 종목에는 새 알림을 만든다.
- **수정은 상태를 바꾸지 않는다.** 꺼진 알림은 꺼진 채, 끝났거나 만료된 알림은 그 상태로 남고 평가 상태만 처음으로 돌아간다(4.6).

> **결정 필요 — 만료된 알림의 수정.** 만료된 알림을 수정하며 새 유효기간을 넣어도 상태는 `만료`로 남는다. 사용자는 저장 뒤 `다시 켜기`를 눌러 유효기간 시트에서 다시 골라야 감시가 시작된다. 선택지는 ① 지금대로 둔다(수정과 다시 켜기를 별개 조작으로 유지) ② 만료된 알림의 수정 화면에서 유효기간을 미래로 바꿔 저장하면 감시 중으로 되돌린다. 사용자 피해는 "고쳤는데 계속 만료로 보이는" 혼란 정도이고 잘못 울리지는 않는다. 추천은 ①이다 — 수정이 상태를 바꾸지 않는다는 규칙 하나가 끄기·종료에도 같이 성립한다.

### 2.5 새 알림 흐름

새 알림 흐름은 루트 스택 위의 모달이다. 들어온 곳에 따라 첫 단계가 다르다 — `＋ 새 알림`은 종목 선택, 종목 상세 `알림 걸기`는 조건 선택(종목이 채워짐), 알림 상세 `수정`은 프리셋 입력 또는 직접 조건 만들기(값이 채워짐). 닫으면 들어온 자리로 돌아가고, 저장하면 알림 상세가 열린다. 작성 중에 닫으면 `작성 중인 알림을 버릴까요?`로 묻는다.

```
종목 선택 → 조건 선택 ─┬─ 프리셋 입력 ──────┬─→ 공통 설정 → 저장 → 알림 상세
                        └─ 직접 조건 만들기 ─┘
```

**종목 선택(`대상 종목`)**

| | |
|---|---|
| 검색어 없음 | `보유 종목` 구역(가나다순). 보유 종목이 없으면 `종목명이나 종목코드로 검색하세요` |
| 검색 | 이름·종목코드 부분 일치. 1글자부터, 입력이 0.3초 멈추면 부른다. 최대 30건. 없으면 `검색 결과가 없어요` |
| 행 | `종목명 · 종목코드 · 시장 배지 · 보유 배지`. 미국 종목은 영문명과 티커(`Apple Inc. · AAPL`) |

- **보유 종목을 검색 결과 앞으로 당기지 않는다.** 보유 배지만 붙인다. 화면에 보이지 않는 기준으로 정렬하면 순서가 무작위로 보인다. 보유 구역도 같은 이유로 가나다순이다 — 이 화면에는 평가금액이 없다. 정렬은 8.6.

**조건 선택**

맨 위에 `＋ 직접 조건 만들기`, 그 아래 프리셋 9종 카드. 카드에는 평가 시점 칩(`장중·종가` · `종가`)을 단다. 쓸 수 없는 프리셋은 숨기지 않고 비활성 + 사유 한 줄로 둔다 — 왜 없는지 모르면 찾아 헤맨다.

| 사유 | 언제 |
|---|---|
| `국내 종목만` | 미국 종목의 수급 프리셋 |
| `보유 종목만` | 보유하지 않은 종목의 수익률 도달 |
| 서버의 `unavailable_reason` | 데이터 닫힘으로 닫힌 프리셋(4.11). 수정으로 연 알림에 저장돼 있던 프리셋은 닫혀 있어도 고를 수 있다 |

**프리셋 입력**

| 프리셋 | 입력 칸 (기본값) | 평가 시점 (기본) |
|---|---|---|
| 가격 도달 | 방향 `이상 / 이하` · 가격(**직전 종가로 미리 채움**) | 장중·종가 (장중) |
| 급등락 | 방향 · 등락률 `5`% | 장중·종가 (장중) |
| 거래량 급증 | 비교 기간 `20`일 · 배수 `3`배 | 장중·종가 (장중) |
| 골든·데드크로스 | 종류 `골든 / 데드` · 짧은 선 `5`일 · 긴 선 `20`일 | 종가 |
| RSI 과매수·과매도 | 구간 `과매수 / 과매도`(기준 기본 70 / 30) · 기준 · 기간 `14` | 종가 |
| 박스권 돌파 | 관찰 기간 `20`일 · 최대 폭 `15`% · 방향 `상단 돌파 / 하단 이탈` | 종가 |
| 외국인·기관 연속 순매수 | 주체 `외국인 / 기관` · `순매수 / 순매도` · 일수 `3`일 | 종가 |
| 외국인·기관 순매수 전환 | 주체 · `순매수로 / 순매도로` | 종가 |
| 수익률 도달 | 방향 `수익 / 손실` · 수익률 `10`% (손실은 음수로 저장, 손실 기본 −10) | 종가 |

- 칸은 카탈로그의 `param_schema` 순서대로 그린다. 두 갈래 선택은 칩 두 개, 기간은 값 칩(`5 · 20 · 60 · 120` 중 범위 안의 것) + 직접 입력, 숫자는 단위가 붙은 입력칸이다.
- 장중·종가 겸용 프리셋은 **장중이 기본**이다. 장중이 닫혀 있으면(4.11) 종가가 기본이고 장중 선택지는 같은 사유로 비활성이다. 종가로 바꾸면 `장 마감 뒤 하루 한 번 확인해요`를 한 줄 둔다. 종가 전용 프리셋에는 `이 프리셋은 종가로만 평가해요`를 둔다.
- **가격 도달을 직전 종가로 채운다.** 사용자는 대개 지금 가격에서 조금 위·아래를 넣는다. 입력칸 아래에 `9/26 종가 기준`(미국은 `미국 9/26 종가 기준`)을 밝힌다. 장중 스냅샷은 장중 알림이 걸린 종목에만 있어 새 알림에서는 쓸 수 없고, 일봉은 두 시장 상장 종목 전부에 있다. 그대로 저장하면 "이미 충족" 경고가 뜰 수 있다.
- 폼 아래에 문장 상자(문장형)와 현재값 상자를 두고, 입력이 0.5초 멈추면 미리보기를 다시 받는다.

**직접 조건 만들기**

| 요소 | 동작 |
|---|---|
| 평가 시점 | 맨 위 `[장중 \| 종가]` — 이 알림 전체에 적용된다. 카탈로그 `cadence_options`가 닫은 값은 비활성 + 사유. 맞지 않는 칸이 있으면 `장중으로 바꾸면 맞지 않는 조건이 초기화돼요` [취소] [바꾸기]. 바꾸면 맞지 않는 칸만 비운다 |
| 지표 | 바텀시트. 묶음은 `시세 · 기술지표 · 수급 · 내 보유`. 쓸 수 없는 지표는 비활성 + 사유(`종가에만 계산돼요` · `국내 종목만` · `보유 종목만` · `다른 지표와 함께 쓸 수 없어요` · 닫힌 지표는 서버 사유) |
| 변형 | `그대로` · `최근 N일 최고 / 최저 / 평균 / 합계` · `N일 전 대비 변화` · `N일 전 대비 변화율`. 오늘 포함 여부는 고르지 않는다(3.2) |
| 연산자 | 지표가 허용하는 것만 |
| 기준값 | `상수 / 지표` 토글. 상수는 단위가 붙은 입력칸(`원` `$` `%` `배` `주`). 수급 금액도 원으로 넣고 칸 아래에 `= 1,000억원`처럼 읽기용 환산을 보인다. 교차 연산자는 지표끼리만 견주어 상수 칸을 내놓지 않는다. 장중 알림의 비교 지표 시트 머리는 `어제까지 확정된 값` |
| 유지 방식 | 종가 `N일 연속`, 장중 `N분 이상 유지`. 교차 연산자와 내 보유 지표에서는 숨긴다 |
| 조건 상자 | 최대 5개. 2개 이상이면 상자마다 `✕`. 5개가 차면 `＋ 조건 추가 (AND)`를 숨긴다 |
| 문장 상자 | 문장형. 미리보기 응답에서 받는다 |
| 칸 오류 | 미리보기가 돌려준 `errors[].path`의 칸 아래에 `message`. **사용자가 그 칸을 한 번 만진 뒤부터** 보인다. 수정으로 연 알림의 저장된 조건은 사용자가 채운 것이라 처음부터 보인다. 칸에 붙지 않는 오류는 화면 아래에 모은다 |

**현재값 상자**는 조건마다 한 줄, 맨 아래에 알림 전체 결과를 둔다.

```
9/26 종가 기준
✓ 5일 이동평균 72,100원 > 20일 이동평균 70,850원
✕ 거래량 배수(20일) 1.4배 ≥ 2배
→ 아직 충족하지 않아요
```

이 상자의 몫은 셋이다 — ① 감이 없는 지표(RSI·거래량 배수)의 기준값을 정하게 돕는다 ② 여러 조건 중 어느 것이 막는지 보인다 ③ 평가할 수 없는 조건(`RSI(14) — 이력 부족 (15일 필요, 8일뿐)`)을 저장 전에 알린다.

- 조건별 줄은 `✓` · `✕` · `?`(확인 불가, 사유와 함께) 중 하나다. 입력이 틀린 조건 줄은 `<지표> — 입력을 확인해 주세요`이고 전체 결과를 참으로 만들지 않는다. 결과 줄은 `충족하고 있어요` · `아직 충족하지 않아요` · `확인할 수 없어요` 셋이다. 머리와 결과 줄은 서버가 완성해 보낸다(`header` · `result_text`).
- 오늘 산 종목의 내 보유 조건 줄은 `<조건> — 오늘 저녁 확정 후 첫 판정을 해요`다(4.10).
- **새 장중 알림의 현재값은 대개 일봉 기준이다.** 장중 스냅샷은 장중 알림이 이미 걸린 종목에만 있다. 그 시장의 최신 장중 신호가 허용 지연 안이고 그 시각에 이 종목의 스냅샷이 있으면 그 스냅샷으로, 아니면 가장 최근 일봉 종가를 스냅샷 하나로 삼아 계산하고 머리에 `9/26 종가 기준`을 쓴다. 저장한 뒤 다음 스냅샷부터 장중 값으로 평가한다.
- 미리보기를 받지 못하면(서버 오류·닿지 못함) 문장 상자가 비고 `다음`이 잠긴 이유를 보인다.

**공통 설정**

| 요소 | 동작 |
|---|---|
| 알림 방식 | 종가 알림: `돌파할 때마다` · `한 번만`. 장중 알림: 여기에 `N분마다 다시`(간격 입력) |
| 유효기간 | `무기한`(기본) · `1주` · `1개월` · `3개월` · `날짜 지정` |
| 알림 이름 | 기본값 — 프리셋 `종목명 + 프리셋 라벨`, 직접 조건 `종목명 + 첫 조건의 지표`. 1~40자 |
| 경고 | 아래 표 |
| 저장 | OS 권한이 정해지지 않았으면 권한 안내 시트, 거부 상태면 설정 열기 시트(2.7) → 저장 → 알림 상세. 시트에서 어느 답을 골라도 저장은 한다 — 권한이 없어도 울림은 앱 안 목록과 배지로 남는다 |
| 앞 단계 오류 | 앞 단계 칸의 오류는 `앞 단계의 조건을 확인해 주세요`와 함께 위에 모은다 |

| 미리보기 | 경고 |
|---|---|
| `already_satisfied` | `지금 이미 조건을 충족하고 있어 곧 알림이 와요` |
| `already_satisfied` + `already_fired`(수정 중인 알림이 그 데이터 시점에 이미 울림) · 종가 | `지금 조건을 충족하고 있어요. 9/26 종가 알림은 이미 보냈으니, 다음 종가에도 충족하면 다시 알려요` |
| 같은 경우 · 장중 | `지금 조건을 충족하고 있어요. 이 시세로는 이미 알림을 보냈으니, 다음 시세에도 충족하면 다시 알려요` |
| `duplicate_of`가 있음 | `같은 조건의 알림이 이미 있어요` (저장은 막지 않는다, 8.4) |

`다시 켜기` 버튼에는 이미 충족 중 안내가 없다.

### 2.6 표시 규칙

| 값 | 표시 |
|---|---|
| 국내 가격 | `70,000원` |
| 미국 가격 | `$612.30` (소수 둘째 자리) |
| 등락률 · 수익률 | 관측값은 부호를 붙인다: `+5.2%` `−10.0%`. 조건의 기준값은 부호 없이 `5%` |
| 거래량 · 배수 | `1,234,567주` · `2.5배` |
| 수급 금액 | 억·만 단위: `+123억원` `−4,500만원` |
| RSI · 이격도 | 소수 첫째 자리: `71.3` · `105.2` |
| 데이터 시점 (국내) | 장중 `10:15 기준`, 종가 `9/26 종가 기준` |
| 데이터 시점 (미국) | 장중 `미국 장중 · 02:15 기준`(한국 시간), 종가 `미국 9/26 종가 기준`(미국 거래일) |
| 울린 시각 | 24시간 안이면 `2시간 전`, 그 밖은 `9/24 13:05` |

비교는 계산값 그대로 하고 반올림은 문장에서만 한다.

**색은 뜻을 하나씩만 갖는다.**

- **빨강·파랑은 증감 전용이다.** 앱 전체에서 빨강은 상승, 파랑은 하락이다. 부호가 있는 값(등락률·수익률·순매수 금액)에만 쓴다.
- **상태 배지는 증감색을 쓰지 않는다.** 감시 중 · 오늘 저녁 첫 판정은 감시 색, 조건 충족 중은 충족 색, 확인 불가 · 일시중지 · 꺼짐 · 울린 뒤 종료 · 만료는 회색 계열이다.
- **안 읽음 점과 탭 배지는 증감색과 다른 배지 전용 색이다.** 빨강은 상승으로, 앱 강조색은 하락 파랑과 가까워 하락으로 읽힌다.

## 3. 조건 모델

### 3.1 세 축

모든 직접 조건은 세 축의 조합이다.

**축 1 — 무엇을 보나.** 시세(가격·등락률·거래량·고가·저가), 수급(외국인·기관 순매수), 기술지표(이동평균·RSI·이격도·가격 폭), 내 보유(이 종목의 평가손익률·비중 — 시세가 아니라 보유 스냅샷에서 온다). 목록은 3.3.

**축 2 — 어떻게 보나.**

| 단계 | 형태 | 직접 조건 표현 |
|---|---|---|
| L0 | 지금 값 | 변형 `identity` |
| L1 | 최근 N봉 최고·최저·평균·합계 | 변형 `window` |
| L2 | N봉 전 대비 변화량·변화율 | 변형 `delta` · `pct` |
| L3 | 교차 | 연산자 `crosses_above` · `crosses_below` |
| L4 | 연속·유지 | 유지 방식 `streak` · `persist_min` |
| L5 | 상태 전이 | v1에 없다(11절) |

**평가기는 매번 저장된 이력을 다시 읽어 계산한다.** 윈도우·변화량·교차·연속은 모두 시세 이력의 함수라 알림마다 링버퍼나 연속 카운터를 들고 있을 이유가 없다. 알림마다 저장하는 것은 엣지 기준과 평가한 데이터 시점 같은 몇 개의 값뿐이다(4.7). 그래서 재시작해도 복구할 것이 없고, 장 시작 때 예열도 필요 없다.

**축 3 — 무엇과 견주나.** 상수(가격 ≥ 70,000), 다른 지표(5일 이동평균 > 20일 이동평균), 자기 과거(종가 > 직전 20일 최고가).

### 3.2 저장 구조

알림의 공통 속성은 관계형 컬럼으로, 조건(`trigger_spec`)은 종류마다 모양이 달라 JSON(jsonb)으로 둔다. 조건은 평가 때 늘 통째로 읽히고, 직접 조건·프리셋마다 모양이 다르며, 지표·프리셋을 늘려도 스키마가 바뀌지 않는다. 대가로 DB가 조건의 무결성을 보장하지 않으므로 **저장 전 검증(9절)이 사실상의 계약**이다. 조건 안을 검색하는 일은 없고, 평가에 필요한 데이터 종류는 카탈로그에서 코드로 구한다(3.6).

평가 상태는 별도 표(`alert_state`)에 둔다. 규칙은 사용자가, 상태는 평가기가 쓰므로 바뀌는 주기와 쓰는 쪽이 다르다.

**직접 조건**

```
trigger_spec = {
  conditions: [                                   // AND (OR 없음, 11절)
    { left:  { indicator, indicator_params, transform },
      op:    "gte|lte|gt|lt|crosses_above|crosses_below",
      right: { const: <number> } | { indicator, indicator_params, transform },
      modifier: { streak: <N> } | { persist_min: <N> } | null }
  ]
}
transform = {type:"identity"} | {type:"window", fn:"max|min|avg|sum", n} | {type:"delta", n} | {type:"pct", n}
```

- 지표 자체가 기간(`n`)을 가질 수 있다(RSI 기간, 이동평균 기간 등). 비우면 카탈로그 기본값이다.
- 윈도우·변화량의 N과 `streak`의 N은 **봉** 단위, `persist_min`의 N은 분이다. 봉은 그 종목이 거래된 날의 일봉이다.
- **오늘 포함 여부(`lag`)는 서버가 정한다.** 직전 조건의 요청에 `lag`가 있으면 거부한다(`LAG_NOT_ALLOWED`). 종가 알림에서 윈도우의 맞은편이 오늘 값(지표 그대로·변화량·변화율)이면 오늘을 빼고(직전 N봉), 맞은편이 다른 윈도우이거나 상수면 오늘을 넣는다(최근 N봉). 오늘 값과 견줄 때 빼는 것은 오늘 값이 묶음에 들어가면 자기 자신과 견주게 되기 때문이다 — 오늘 고가가 묶음에 있으면 "종가 > 20일 최고가"는 영원히 참이 되지 않는다. 장중 알림의 이력 지표는 현재 봉이 이미 직전 거래일이라(4.1) 오늘을 넣는 쪽으로 정하고 문장에는 `직전`을 쓴다. 프리셋만 `lag`를 직접 정한다(예: 순매수 전환의 어제 값).
- **저장 모양은 요청 원문이 아니라 해석한 모델에서 다시 쓴다.** 모르는 필드가 섞이지 않고, 변형이 늘 명시되며, 직접 조건에는 `lag`가 없다. 수정 화면이 받은 `trigger_spec`을 그대로 다시 보내도 거부되지 않는다.

**프리셋**

```
trigger_spec = { preset_key: "box_breakout", params: { window_days: 20, max_range_pct: 15, direction: "up" } }
```

프리셋은 **평가할 때 펼친다.** DB에는 프리셋 키와 입력값을 그대로 둔다. 수정할 때 프리셋 폼이 다시 떠야 하고, 템플릿을 고치면 이미 만든 알림에도 반영되기 때문이다. 펼친 결과가 바뀌면 평가 상태를 울리지 않고 다시 기준 잡는다(4.9).

| `disparity` | 이격도 · 기술지표 | 20 (2~120) | — / 종가 ÷ n봉 이동평균 × 100 | percent | ✕ | KR · US |
| `foreign_net_buy` | 외국인 순매수 · 수급 | — | — / 순매수 금액(원) | krw | ✕ | KR |
| `institution_net_buy` | 기관 순매수 · 수급 | — | — / 순매수 금액(원) | krw | ✕ | KR |
| `unrealized_pnl_pct` | 평가손익률 · 내 보유 | — | — / 이 종목의 평가손익률 | percent | ✕ | KR · US |
| `weight_pct` | 비중 · 내 보유 | — | — / 이 종목의 비중 | percent | ✕ | KR · US |

**지표별 허용 변형과 연산자**

| 지표 | 허용 변형 (n 범위) | 연산자 |
|---|---|---|
| 시세 6종 · `sma` | 전부 (1~120) | 전부 |
| `range_pct` · `disparity` | `identity` · `delta`(1~120) | 전부 |
| `rsi` | `identity` · `delta`(1~5) | 전부 |
| 수급 | `identity` · `delta`(1~5) · `window`(1~10) | 전부 |
| 내 보유 | `identity` | `gte` · `lte` · `gt` · `lt` |

- 수급과 RSI의 상한은 필요 이력이 데이터팀이 보장하는 길이를 넘지 않게 하려는 것이다. 수급의 최대 필요 봉 수는 1 + 10 + 연속 19 = 30이다. 교차에는 유지 방식을 붙일 수 없어 둘이 한 조건에 함께 나오지 않는다.
- **장중 알림의 왼쪽은 장중 왼쪽 지표(○)의 `identity`뿐이다.** 오른쪽에 오는 이력 지표는 위 표의 변형을 쓸 수 있다.
- **RSI는 각 봉에서 끝나는 250봉 위에서 Wilder 평활로 계산한다.** 참·거짓을 정하는 데 필요한 최소는 `n+1`봉이고, 더 있으면 250봉까지 읽는다. Wilder 평활은 전체 이력에 기대므로 계산 창을 고정해야 같은 데이터에서 같은 값이 나온다. 증권사 앱의 RSI와 소수점 아래에서 다를 수 있다.
- **내 보유 지표는 포트폴리오 종목 화면의 그 종목 한 행과 같은 값이다.** 모든 계좌를 합한 그 종목의 평가손익률과, 예수금을 포함한 총자산 대비 비중이다([portfolio.md](portfolio.md)의 "뷰 사양"). 평가가 읽는 날짜는 확정 스냅샷의 기준일이다(4.10).
- **내 보유 지표는 종가 알림에만 쓴다.** 보유 스냅샷은 하루 한 벌이다. 그날 스냅샷 하나만 읽으므로 유지 방식과 교차를 쓸 수 없다. 데이터 시점은 스냅샷 기준일의 국내 마감 시각이다.
- **내 보유 지표와 시장 지표는 한 알림에 섞지 않는다.** 내 보유의 데이터 시점은 국내 거래일이고 시장 지표는 그 종목 시장의 거래일이라, 두 달력을 한 평가에 맞출 수 없다.
- 계산할 봉이 모자라면 확인 불가(이력 부족)다. 나눗셈의 분모가 0이면(거래량 0인 봉 등) 값이 정의되지 않아 확인 불가(거래 없음)다.

### 3.4 변형·연산자

```
변형:   identity | window{fn, n} | delta{n} | pct{n}
연산자: gte · lte · gt · lt            (상수 또는 지표와 비교)
      | crosses_above · crosses_below   (지표끼리만)
```

- **교차**는 직전 데이터 시점의 두 값과 이번 두 값을 견준다. 상향 돌파는 직전에 왼쪽 ≤ 오른쪽이고 이번에 왼쪽 > 오른쪽이다. 종가 알림의 직전 시점은 직전 봉, 장중 알림은 같은 날 직전 스냅샷이다. 장중 알림에서 같은 날 직전 스냅샷이 없거나 두 스냅샷 간격이 허용 지연(4.2)을 넘으면 확인 불가(데이터 없음)다.
- 상수와의 교차는 두지 않는다. "상수를 위로 넘는 순간"은 `gte`와 엣지 울림(4.5)으로 이미 표현된다.
- **단위.** 기준값이 지표면 두 쪽 단위가 같아야 한다. 단위는 변형 뒤의 단위다 — `pct`는 percent, 나머지 변형은 지표 단위 그대로다.

### 3.5 프리셋

v1 프리셋은 9종이고 모두 템플릿이다. 입력 범위는 펼친 결과가 쓰는 지표·변형·유지 방식의 범위를 따르고, 펼친 결과에도 직접 조건 규칙(9절)을 다시 적용한다.

| key | 라벨 | 입력 (기본, 범위) | 평가 시점 | 펼친 결과 |
|---|---|---|---|---|
| `price_reach` | 가격 도달 | `direction` up/down · `price`(필수) | 장중 · 종가 | `price gte price` / `price lte price` |
| `change_move` | 급등락 | `direction` · `pct` 5 (0.1~30) | 장중 · 종가 | `change_pct gte pct` / `change_pct lte −pct` |
| `volume_surge` | 거래량 급증 | `n` 20 (5~120) · `multiple` 3 (1.1~50) | 장중 · 종가 | `volume_ratio(n) gte multiple` |
| `ma_cross` | 골든·데드크로스 | `direction` golden/dead · `short` 5 · `long` 20 (2~120) | 종가 | `sma(short) crosses_above sma(long)` / `crosses_below` |
| `rsi_zone` | RSI 과매수·과매도 | `zone` overbought/oversold · `level` 70/30 (1~99) · `n` 14 (2~30) | 종가 | `rsi(n) gte level` / `rsi(n) lte level` |
| `box_breakout` | 박스권 돌파 | `window_days` 20 (5~120) · `max_range_pct` 15 (1~100) · `direction` | 종가 | `range_pct(window_days) lte max_range_pct` AND `price gt 직전 window_days봉 최고 고가` (up) / `price lt 직전 window_days봉 최저 저가` (down) |
| `investor_streak` | 외국인·기관 연속 순매수 | `investor` foreign/institution · `side` buy/sell · `days` 3 (1~20) | 종가 | `<investor>_net_buy gt 0` + `streak: days` (sell은 `lt 0`) |
| `investor_turn` | 외국인·기관 순매수 전환 | `investor` · `side` | 종가 | `<investor>_net_buy gt 0` AND 어제 값 `lte 0` (sell은 부호 반대) |
| `pnl_reach` | 수익률 도달 | `direction` profit/loss · `pct` 10 (손실 기본 −10) | 종가 | `unrealized_pnl_pct gte pct` / `lte pct` (보유 종목만) |

- **박스권은 "직전 n일이 좁은 폭 안에 있었고, 오늘 그 폭을 벗어났다"다.** 폭 조건이 없으면 "n일 신고가"와 같아진다. 이 정의가 직접 조건으로 표현되므로 상태 라벨이 필요 없다.
- **순매수 전환은 "오늘 순매수이고 어제는 순매수가 아니었다"다.** 엣지 울림만으로 표현하면 알림을 만든 첫날 이미 순매수인 종목이 "전환"으로 울린다.
- **연속 순매수는 순매수 금액이 매일 0보다 큰 것이다.** 금액이 매일 늘어나는 것(`delta > 0`)과 다르다.
- 수익률 도달의 `pct`는 수익이면 0.1 이상, 손실이면 −0.1 이하여야 한다(`수익은 양수, 손실은 음수로 입력해 주세요`).
- 조건 문장·관측값 문장의 틀은 프리셋마다 따로 있다(2.1).

### 3.6 필요 데이터 유도

알림이 기다리는 데이터 종류는 펼친 조건의 지표마다 정한 종류의 합집합이다. 평가 시점에 따라 다르다.

| 데이터 종류 | 뜻 | 주는 쪽 |
|---|---|---|
| `INTRADAY_QUOTE` | 장중 스냅샷(현재가 · 당일 누적 거래량) | 데이터팀 |
| `DAILY_BAR` | 수정주가 일봉 | 데이터팀 |
| `DAILY_FLOW` | 투자자별 순매수 | 데이터팀 |
| `PORTFOLIO_SNAPSHOT` | 확정 보유 스냅샷(`snapshot_run`) | 백엔드 |

| 지표 | 장중 알림 | 종가 알림 |
|---|---|---|
| `price` · `volume`의 `identity` | `INTRADAY_QUOTE` | `DAILY_BAR` |
| `change_pct` · `volume_ratio`의 `identity` | `INTRADAY_QUOTE` + `DAILY_BAR`(직전 거래일까지) | `DAILY_BAR` |
| 그 밖의 시세·기술지표, 변형이 붙은 지표 | `DAILY_BAR`(직전 거래일까지) | `DAILY_BAR` |
| 수급 | — | `DAILY_FLOW` |
| 내 보유 | — | `PORTFOLIO_SNAPSHOT` |

필요한 봉 수는 현재 봉을 포함해 센다.

```
지표의 필요 봉 수 = 지표 이력      price·volume·high·low·수급 1 · change_pct 2 · volume_ratio·range_pct n+1 · sma·disparity n · rsi n+1
                 + 변형분          window n − 1 + lag · delta·pct n · identity 0
                 + 교차분          교차면 1
조건의 필요 봉 수 = 두 지표 중 큰 값 + (streak − 1)
```

읽은 봉이 필요 봉 수보다 적으면 확인 불가(이력 부족)다. 실제로 읽는 봉 수는 RSI의 이력만 계산 창(250)으로 바꿔 구한다. 카탈로그 상한 안에서 읽는 봉 수의 최대는 250 + `delta` 5 + 연속 19 = 274봉이라 데이터팀이 보장하는 300봉 안에 든다. 평가기는 일봉 300봉, 수급 30봉을 읽는다.

### 3.7 버전과 폐기

- **`spec_version`은 `trigger_spec`의 포맷 버전이다.** 서버가 정하고 요청에서 받지 않는다. 지금 버전은 1 하나이고, 읽을 때 옛 포맷을 올려 읽는 코드는 아직 없다. 포맷이 바뀌면 읽을 때 최신으로 올리고 저장할 때 최신으로 쓴다. 올려 읽기는 뜻을 바꾸지 않는다 — 계산이 달라지는 변경은 새 지표·프리셋 키로 더한다. 템플릿의 펼친 결과를 고치는 것은 예외이며, 그때는 평가 상태를 다시 기준 잡는다(4.9).
- **카탈로그는 덧붙이기만 한다.** 지표·프리셋을 지우지 않고 `deprecated`로 표시한다. 폐기된 항목은 새 알림에서 고를 수 없고 이미 만든 알림은 계속 평가된다. v1에 폐기된 항목은 없어 `deprecated`는 늘 거짓이다.
- 지금 코드가 저장된 조건을 읽지 못하면(카탈로그에서 키가 빠진 배포 등) 그 알림만 평가하지 않고 목록·상세에서 `조건을 읽을 수 없어요`로 보인다. 알림 하나 때문에 목록·평가 전체가 멈추지 않는다.
- **잠시 닫는 것은 폐기가 아니다.** 데이터를 확보하지 못해 닫는 것은 4.11이다. 폐기된 항목을 쓰는 알림은 계속 평가되지만, 닫힌 항목을 쓰는 알림은 닫힌 동안 일시중지되거나 종가로 평가된다.

## 4. 평가

### 4.1 평가 시점

| 평가 시점 | 평가하는 때 | 데이터 시점 | 왼쪽 | 오른쪽 | 유지 방식 |
|---|---|---|---|---|---|
| 장중(`INTRADAY`) | 그 시장의 새 장중 완료 신호마다 | 스냅샷 시각 | 장중 왼쪽 지표의 `identity` | 상수 · 장중 지표 · **직전 거래일까지 확정된** 일봉 지표 | `N분 이상 유지`만 |
| 종가(`CLOSE`) | 그 알림이 기다리는 데이터 종류가 그 거래일에 모두 완료됐을 때 1회 | 그 거래일의 마감 시각 | 카탈로그 전부 | 상수 · **같은 거래일까지 확정된** 일봉 지표 | `N일 연속`만 |

한 알림 안의 조건은 모두 같은 평가 시점을 쓴다.

- **종가로만 뜻이 있는 지표는 종가로만 평가한다.** 이동평균·RSI·수급은 하루가 끝나야 값이 정해진다. 형성 중인 봉으로 평가하면 울린 뒤 종가에서 조건이 성립하지 않는 일이 생긴다. 장중에 바로 알아야 가치가 있는 가격·등락률·거래량·거래량 배수만 장중 평가를 연다.
- **장중 조건은 확정된 과거를 기준선으로 쓸 수 있다.** "현재가가 직전 20일 최고가를 넘음"은 왼쪽이 장중 가격, 오른쪽이 어제까지 확정된 윈도우 값이다. 오른쪽이 이미 확정돼 있어 평가가 흔들리지 않는다.
- **장중 알림의 지표가 장중 값인지 이력인지는 이렇게 가른다.** 장중 왼쪽 지표가 `identity`로 오면 장중 값이고, 그 밖은 직전 거래일까지의 일봉 이력으로 계산한다. 장중 값이라도 직전 종가·직전 n봉 평균을 쓰는 등락률·거래량 배수는 직전 거래일 일봉을 함께 기다린다. 직전 거래일의 일봉 신호가 완료가 아니면 그 지표들은 확인 불가(데이터 없음)다.
- **장중 평가는 그 시각의 그 종목 스냅샷으로만 한다.** 그 시각 스냅샷이 없으면 앞선 스냅샷을 지금 값으로 쓰지 않고 확인 불가(데이터 없음)다 — 장중 알림을 막 건 종목은 다음 수집부터 스냅샷이 생긴다. 일봉이 하나도 없는 종목은 직전 종가가 없어 장중 등락률·거래량 배수가 확인 불가이고, 장중 가격·거래량만 동작한다.
- 평가는 평가 시점이 정한 때에만 일어나므로 장 운영 시간을 따로 정하는 설정이 없다. 장중 평가는 장중 스냅샷이 있을 때만, 종가 평가는 마감 데이터가 있을 때만 일어난다.

### 4.2 시장별 지원

| 시장 | 장중 | 종가 | 장중 허용 지연 |
|---|---|---|---|
| 국내(KR) | ○ | ○ | 10분 |
| 미국(US) | ○ | ○ | 20분(15분 지연 시세 허용) |

- 허용 지연은 스냅샷 시각부터 잰다. 최신 스냅샷이 허용 지연을 넘었으면 장중 알림을 평가하지 않는다.
- 미국 장은 한국 시간으로 자정을 넘기므로 미국 종목의 거래일과 "당일"은 미국 현지 날짜로 정한다.
- 미국 종목의 가격 기준값은 종목 통화(USD)로 넣는다. 원화로 바꿔 견주지 않는다 — 환율 변동만으로 조건이 참이 되면 그 알림은 종목이 아니라 환율을 감시하게 된다.
- 거래일과 마감 시각은 시장 캘린더(`dim_market_calendar`)에서만 읽는다. 두 팀이 마감 시각을 따로 계산하면 조기 폐장일에 값이 어긋난다. 캘린더에 행이 없는 날은 월~금을 거래일로, 정규 개장·마감(국내 09:00 · 15:30, 미국 09:30 · 16:00 현지)을 그날 시각으로 어림한다. 이 어림은 알림만 한다 — 보유 스냅샷은 캘린더가 채워질 때까지 기다린다.

### 4.3 가동 중단과 재개

평가기가 멈춰 있던 동안의 데이터는 평가 시점마다 다르게 다룬다.

| 평가 시점 | 재개 뒤 | 이유 |
|---|---|---|
| 종가 | 이미 감시 중이던 알림(평가한 데이터 시점이 있음)은 밀린 거래일을 **날짜 순서대로** 모두 평가한다. 한 주기에 알림마다 최대 20거래일씩 이어 간다. 울림 문구에 기준일(`9/26 종가 기준`)이 들어간다 | "3일 연속" 같은 조건이 날짜를 건너뛰면 틀린다. 종가 조건의 울림은 하루 늦어도 뜻이 남는다 |
| 장중 | 가장 최근 스냅샷 하나만 평가한다. 그 스냅샷도 허용 지연을 넘었으면 평가하지 않는다 | "10시에 7만원을 넘었다"를 오후에 받으면 쓸모가 없고 지금 가격으로 오해된다 |
| 내 보유 | 종가와 같이 밀린 국내 거래일을 차례로 평가한다. 보유 스냅샷 완료 신호가 없는 국내 거래일은 그 데이터 없이 평가해 확인 불가(데이터 없음)가 된다 | 종가와 같다 |

- 데이터 시점은 앞으로만 간다. 이미 평가한 데이터 시점보다 이르거나 같은 시점은 반영하지 않는다(5.2).
- 새로 만들거나, 다시 켜거나, 수정한 알림은 최신 시점 하나에서 시작한다(4.6).
- 만료는 데이터 시점이 아니라 실제 시각으로 정한다. 평가기는 주기마다 만료를 먼저 옮기고, 유효기간이 지난 알림은 밀린 거래일도 평가하지 않는다.

### 4.4 평가 결과

조건 한 줄의 결과는 참(`TRUE`) · 거짓(`FALSE`) · 확인 불가(`UNKNOWN`) 중 하나다. 확인 불가 사유는 4.10.

AND 결합은 이 순서로 정한다.

1. 하나라도 거짓이면 거짓
2. 아니고 하나라도 확인 불가면 확인 불가(사유는 첫 확인 불가 조건의 것)
3. 모두 참이면 참

확정된 거짓 하나가 결론을 정하므로, 다른 조건의 데이터가 없어도 거짓은 거짓이다.

조건 한 줄 안에서는 확인 불가를 먼저 가린다 — 종목을 알 수 없음, 기다리는 데이터가 완료되지 않음, 지금 값이 없음(거래 없음·미보유·이월값), 연속·교차 구간의 데이터 누락일, 국내 ±30% 변동. 그 뒤에 값을 계산한다.

- **N일 연속**: 현재 봉부터 N봉이 모두 참이어야 참이다. 하나라도 거짓이면 거짓이 먼저이고, 계산할 수 없는 봉이 있으면 확인 불가(이력 부족)다.
- **N분 이상 유지**: 조건이 참인 당일 스냅샷이 끊김 없이 이어진 구간의 시작부터 현재 스냅샷까지가 N분 이상이면 참이다. 현재에서 거슬러 오르며 거짓 스냅샷이나 그날 첫 스냅샷을 만날 때까지 본다. 구간 안에 스냅샷 간격이 허용 지연을 넘는 공백이 있으면 확인 불가(데이터 없음), 계산할 수 없는 스냅샷이 있으면 확인 불가(이력 부족)다. N은 스냅샷 주기 이상(5분 이상)이어야 뜻이 있다.

### 4.5 알림 방식

| `notify_mode` | 화면 문구 | 울리는 때 | 울린 뒤 |
|---|---|---|---|
| `EDGE_REARM` (기본) | 돌파할 때마다 | 결과가 참이고 엣지 기준이 거짓 | 계속 감시. 거짓으로 내려갔다 다시 참이 되면 다시 울린다 |
| `ONE_SHOT` | 한 번만 | EDGE_REARM과 같음 | 울린 뒤 종료(`ENDED`) |
| `COOLDOWN` | N분마다 다시 | 결과가 참이고, 엣지 기준이 거짓이거나 마지막 울림의 데이터 시점부터 다시 알림 간격(`cooldown_min`)이 지남 | 계속 감시 |

- **계속 참인 동안 평가마다 울리지 않게 엣지 울림이 기본이다.**
- **N분마다 다시는 장중 알림에만 있다.** 종가 알림은 하루에 한 번 평가되므로 분 단위 억제가 뜻이 없다. 다시 알림 간격은 5분~1440분이다. 장중이 닫혀 종가로 평가되는 장중 알림의 N분마다 다시는 4.11.
- 마지막 울림 기록이 없으면 "마지막 울림부터"의 기준이 없어 엣지로만 정한다.
- **확인 불가는 울리지 않고 엣지 기준도 바꾸지 않는다.** `참 → 확인 불가 → 참`은 울리지 않고, `거짓 → 확인 불가 → 참`은 울린다. 데이터 공백이 다시 울림을 일으키지도 막지도 않는다.
- 다시 켜기라는 조작 말고 따로 "다시 감시"하는 조작은 없다. 돌파할 때마다 · N분마다 다시는 스스로 다시 감시하고, 한 번만 알림을 다시 쓰려면 `다시 켜기`를 한다.

### 4.6 첫 평가

알림을 만들거나, 다시 켜거나, 수정하면 **엣지 기준을 거짓으로 두고 시작한다.** 그래서 이미 조건을 충족 중이면 첫 평가에서 울린다. 이때 평가한 데이터 시점·마지막 결과·사유·일시중지 표시를 비우고, 지금 코드의 해시를 새로 쓴다.

- **평가한 데이터 시점이 빈 알림은 그 순간 기다리는 데이터의 최신 완료 시점 하나만 평가하고, 그 이전 시점은 평가하지 않는다.** 몇 주 꺼져 있던 알림을 다시 켰을 때 지난 날짜로 울리지 않게 하기 위해서다. 밀린 거래일 따라잡기(4.3)는 이미 감시 중이던 알림에만 적용된다. 종가 알림의 최신 시점은 기다리는 종류마다 최신 완료 거래일을 구해 그중 가장 이른 날이다.
- **이 사실을 저장 전에 알린다.** 미리보기가 지금 충족 여부를 돌려주고, 충족 중이면 공통 설정이 경고를 보인다(2.5). 알림을 만든 사용자는 지금 상태를 알고 싶어 하므로 침묵하는 쪽보다 알리는 쪽이 낫다.
- **이미 울린 데이터 시점을 다시 평가할 때.** 다시 켜거나 수정한 알림이 그 알림이 이미 울린 데이터 시점을 평가해 참이 나오면, 그 시점으로는 다시 울리지 않고 엣지 기준을 거짓으로 둔다. 다음 시점에도 충족 중이면 울린다. 엣지 기준을 참으로 두면 다음 시점에 충족해도 이어진 참으로 보아 울리지 않기 때문이다. 수정 화면은 이 경우를 `already_fired`로 받아 "곧 알림이 와요" 대신 다음 시점을 말하는 경고를 보인다(2.5). 다시 켜기 버튼에는 안내가 없다.

### 4.7 평가 상태

알림마다 `alert_state` 한 행에 다음만 둔다.

| 값 | 뜻 |
|---|---|
| `last_result` | 마지막 평가 결과. 평가 전에는 비어 있다 |
| `last_known_result` | 엣지 기준(참 · 거짓) |
| `unknown_reason` | 마지막 결과가 확인 불가일 때 사유 |
| `evaluated_as_of` | 마지막으로 평가한 데이터 시점. 중복 평가를 막는 기준 |
| `spec_hash` | 평가에 쓴 펼친 조건의 해시(4.9) |
| `held_since` | 데이터 닫힘으로 평가를 처음 건너뛴 시각(4.11) |
| `version` | 사용자 변경(수정·끄기·다시 켜기·삭제), 만료, 한 번만 알림의 종료마다 오른다. 평가와 이 변경들의 경쟁을 가른다(5.2) |

마지막 울림 시각은 저장하지 않고 울림 기록에서 구한다. 같은 사실을 두 곳에 두면 어긋날 자리가 생긴다.

### 4.8 알림 상태

| `status` | 뜻 | 들어오는 길 |
|---|---|---|
| `ACTIVE` | 감시 중 | 만들기 · 다시 켜기 |
| `PAUSED` | 꺼짐 | 끄기(감시 중에서만) |
| `ENDED` | 한 번만 알림이 울려 끝남 | 한 번만 알림의 울림(울림과 같은 트랜잭션) |
| `EXPIRED` | 유효기간이 지남 | 감시 중 · 꺼짐에서 `expires_at`이 지남 |

- 꺼짐 · 울린 뒤 종료 · 만료는 `다시 켜기`로 감시 중이 된다. 만료는 이때 새 유효기간(또는 무기한)을 함께 받는다. 감시 중인 알림의 다시 켜기, 감시 중이 아닌 알림의 끄기는 `INVALID_STATUS_TRANSITION`이다. 읽은 상태가 그 사이 바뀌었으면(평가기가 끝냈거나 만료함) 같은 오류다.
- 수정은 상태를 바꾸지 않는다(2.4).
- 평가 대상은 감시 중이고 삭제되지 않은 알림뿐이다.

**카드 상태 문구**는 상태와 마지막 결과로 정한다. 위에서부터 먼저 맞는 줄이다.

| 조건 | 문구 | 색 |
|---|---|---|
| 감시 중 · 데이터 닫힘으로 일시중지(`HELD`) | `일시중지` | 회색 |
| 감시 중 · 마지막 결과 참 | `조건 충족 중` | 충족 |
| 감시 중 · 확인 불가 · 사유 `AWAITING_FINAL` | `오늘 저녁 첫 판정` | 감시 |
| 감시 중 · 확인 불가 | `확인 불가 · <사유>` (4.10) | 회색 |
| 감시 중 · 마지막 결과 거짓 또는 평가 전 | `감시 중` | 감시 |
| 꺼짐 | `꺼짐` | 회색 |
| 울린 뒤 종료 | `울린 뒤 종료` | 회색 |
| 만료 | `만료` | 회색 |

- 일시중지는 평가되지 않으므로 직전 결과 대신 `일시중지`를 보인다. 몇 주 전 `조건 충족 중`이 지금 충족 중으로 읽히지 않게 하기 위해서다. 종가로 평가 중(`AS_CLOSE`)인 알림은 실제로 평가되므로 배지는 결과 그대로다.
- 데이터 닫힘 표시(`data_closure`)는 감시 중 · 꺼짐 알림에만 싣는다. 끝났거나 만료된 알림은 평가되지 않는다.
- 카드 셋째 줄의 `최근 울림`은 그 알림의 가장 최근 울림의 울린 시각이다.

### 4.9 조건 모양이 바뀔 때

`spec_hash`는 펼친 조건과 평가 시점의 해시다. 조건은 모두 AND라 순서를 무시하고, 숫자는 꼬리 0을 떼며, 지표 기간은 기본값까지 채워 쓴다. 그래서 프리셋으로 만든 것과 직접 조건으로 만든 것도 펼친 결과가 같으면 같은 해시다.

| 바뀐 까닭 | 처리 |
|---|---|
| 사용자가 알림을 수정 | 저장하는 트랜잭션에서 같은 상태 행을 처음으로 돌린다 — 엣지 기준 거짓, 평가한 데이터 시점 비움, 새 해시, `version` 증가(4.6). 행을 지우고 다시 만들지 않는다 |
| 템플릿 로직이 바뀐 배포 | 평가기가 해시가 다른 것을 보면 **울리지 않고** 이번 결과로 엣지 기준을 잡고 새 해시를 쓴다. 이번 결과가 확인 불가면 기준을 잡지 못했으므로 옛 해시를 둬서 다음 확정 결과에서 다시 잡는다 |

사용자 수정은 저장 때 해시를 갱신하므로, 평가 때의 불일치는 늘 코드 변경에서 온다. 배포 한 번에 알림이 일제히 울리지 않게 하기 위해서다. 장중이 닫혀 종가로 평가하는 장중 알림도 해시는 원래 평가 시점으로 구한다(4.11). 다시 켜기도 지금 코드로 구한 해시를 새로 쓴다.

### 4.10 결측·지연

**완료 신호.** 평가기는 데이터가 "왔다"는 것을 완료 신호로 안다. 데이터팀이 (시장, 데이터 종류, 데이터 시점)마다 `market_data_run`에 한 행을 남기고, 그 행이 완료(`DONE`)면 그 시장의 대상 종목 전체가 그 시점까지 들어왔다는 뜻이다. 행의 모양과 상태 전이는 [data-contract.md](data-contract.md)의 "알림 테이블"이 정한다.

```
KR · INTRADAY_QUOTE · 2026-09-26 10:15   DONE
KR · DAILY_BAR      · 2026-09-26         DONE
KR · DAILY_FLOW     · 2026-09-26         RUNNING
```

- 장중 알림은 그 시장의 새 `INTRADAY_QUOTE` 완료마다 평가한다.
- 종가 알림은 **자기에게 필요한 데이터 종류(3.6)가 그 거래일에 모두 완료됐을 때** 평가한다. 가격만 보는 알림은 수급 도착을 기다리지 않는다. 종류마다 신호를 나누는 것은 도착 시각이 달라서다 — 하나로 묶으면 가장 늦는 데이터가 모든 알림을 붙잡는다.
- 실패(`FAILED`) 신호는 완료가 아닌 것으로 본다.
- 내 보유 지표의 신호는 백엔드가 남기는 `snapshot_run`이다. 그 기준일의 보유 스냅샷이 모든 계좌에 대해 확정되면 한 행을 쓴다([portfolio.md](portfolio.md)의 "확정"). 데이터 시점은 그 기준일(국내 거래일)이고 미국 종목도 같다 — 스냅샷이 담은 미국 가격은 직전 미국 종가다.
- **영원히 오지 않는 데이터로 멈추지 않는다.** 어떤 거래일 D의 신호가 완료되기 전에 다음 거래일의 같은 종류가 완료되면, D는 그 데이터 없이 평가한다. 그 데이터에 기대는 조건은 확인 불가(데이터 없음)가 된다.
- 완료 신호는 데이터팀 파이프라인이 돌기 시작한 날부터 쌓이므로, 그 종류의 첫 완료 거래일 전의 날은 누락일로 보지 않는다.

**확인 불가 사유**

| 코드 | 언제 | 카드 문구 |
|---|---|---|
| `DATA_MISSING` | 필요한 데이터 종류가 그 시점에 완료되지 않음 · 연속·교차 구간 안에 데이터 누락일이 있음 · 장중 평가에 필요한 직전 거래일 일봉이 완료되지 않음 · 장중 그 시각의 그 종목 스냅샷이 없음 · N분 유지 구간이나 장중 교차에 허용 지연을 넘는 공백 · 내 보유 지표인데 그 종목 행 중 하나라도 이월값 · 내 보유 완료 신호가 없는 날 | `데이터 없음` |
| `INSUFFICIENT_HISTORY` | 필요한 봉 수보다 봉이 적음(신규 상장 등) | `이력 부족` |
| `NO_TRADE` | 거래일인데 그 종목의 현재 봉이 없음(거래정지 등) · 분모가 0이라 값이 정의되지 않음 | `거래 없음` |
| `PRICE_ADJUSTMENT_SUSPECTED` | 수정주가 미반영 의심(아래) | `가격 보정 대기` |
| `NOT_HELD` | 내 보유 지표인데 그 기준일 확정 스냅샷의 연동 중인 계좌에 그 종목이 없고, 지금도 보유하지 않음 | `미보유` |
| `AWAITING_FINAL` | 내 보유 지표인데 그 기준일 확정 스냅샷에는 그 종목이 없지만, 최신 스냅샷(확정 전 포함)의 연동 중인 계좌에서는 보유 중 | `오늘 저녁 첫 판정` |
| `INSTRUMENT_UNKNOWN` | 종목 마스터에 그 종목이 없음 · 상장폐지된 종목 | `종목 정보 없음` |

- **계열은 있는 봉으로 만든다.** 거래정지일(그 시장 신호는 완료인데 그 종목 봉이 없음)과 데이터 누락일(그 시장 신호가 끝내 완료되지 않은 거래일 — 그날 봉이 일부 들어와 있어도 쓰지 않는다)은 모두 계열에서 빠진다. 하루의 공백이 그 뒤 250봉 동안 RSI를, 120봉 동안 이동평균을 막지 않게 하기 위해서다. 늦게 완료되면 다음 평가부터 그날이 계열에 들어간다.
- **결측은 거짓을 만들지 않는다.** 현재 봉이 없거나, 연속·교차가 걸친 구간(현재 봉부터 `streak − 1`봉, 교차는 직전 1봉)에 데이터 누락일이 있으면 확인 불가다. 모르는 날을 연속으로 세면 거짓 울림이 된다. 거래정지일은 연속을 끊지도 잇지도 않고 건너뛴다. 거짓으로 두면 엣지 기준이 바뀌어 데이터가 돌아온 날 다시 울린다. 지표마다 자기 데이터 종류(수급은 수급, 나머지는 일봉)의 누락일만 본다.
- **오늘 산 종목은 미보유가 아니다.** 평가는 확정 스냅샷으로 하므로 결과는 확인 불가(`AWAITING_FINAL`)이고 울리지 않는다. 그날 저녁 확정 스냅샷이 생기면 실제 결과로 바뀐다. 연동 첫날이라 그 사용자의 확정 스냅샷이 아직 없어도, 지금 보유 중이면 미리보기는 가장 최근 확정된 날로 계산해 같은 말을 한다.
- **미보유는 알림을 무효로 만들지 않는다.** 다시 사면 그날부터 평가가 이어진다. 매도로 알림이 사라지면 다시 살 때마다 새로 만들어야 한다.
- 보유 스냅샷의 이월 행은 낡은 시세라 평가손익률·비중이 그날 값이 아니다. 그래서 확인 불가(데이터 없음)다. "보유 중"의 뜻은 [portfolio.md](portfolio.md)의 "보유 중 판정"을 따른다 — 연동을 해제한 계좌는 해제한 순간부터 보유로 세지 않는다.
- **상장폐지된 종목**은 시세가 남아 있어도 모든 조건이 확인 불가(종목 정보 없음)이고 울리지 않는다. 감시 중으로 남으면 울릴 수 없는 알림을 믿고 기다린다.

**수정주가 미반영 의심.** 액면분할·병합이 보정되지 않은 계열로 지표를 계산하면, 분할 당일 그 종목의 이동평균 교차·거래량 급증·RSI가 한꺼번에 참이 된다. **국내 종목은 그 조건이 읽는 봉 범위 안에 하루 종가 변동이 ±30%(가격제한폭)를 넘는 봉이 있으면 확인 불가(가격 보정 대기)로 둔다.** 정상 거래로는 넘을 수 없는 폭이라 보정되지 않은 기업행위의 증거다. 계열의 첫 봉은 앞 봉이 없어 견주지 않으므로 신규 상장 첫날은 저절로 빠진다. 데이터팀이 보정된 계열을 주면 평가기가 이력을 다시 읽으므로 저절로 풀린다. 미국 종목은 가격제한폭이 없어 이 확인을 두지 않는다 — 수정주가 계열 제공이 그대로 요구사항이다(알려진 한계).

**사용자에게 보이는 것**

| 자리 | 표시 |
|---|---|
| 알림 카드 | `확인 불가 · <사유>`, 사유가 `AWAITING_FINAL`이면 `오늘 저녁 첫 판정` (4.8) |
| 알림 카드 · 알림 상세 · 울린 알림 상세의 이 알림 (데이터 닫힘) | 일시중지면 `일시중지` 배지, 둘 다 서버의 `data_closure.message` (4.11) |
| 알림 목록 · 울린 알림 위쪽 | `MARKET_DATA_DELAYED` notice (아래) |
| 울림 문구 | 데이터 시점 (6.7) |

**데이터 지연 안내(`MARKET_DATA_DELAYED`).** 사용자의 감시 중 알림이 기다리는 (시장, 데이터 종류)마다 최신 완료가 기대 시각보다 늦었는지 본다. 기다리는 데이터는 실제로 평가에 쓰는 컴파일로 센다 — 종가로 평가 중인 장중 알림은 일봉을 기다리고, 일시중지된 알림은 아무것도 기다리지 않는다. 그래서 닫힌 종류의 지연 안내는 뜨지 않는다. 늘 떠 있는 안내는 다른 지연을 가리고, 카드의 닫힘 표시가 같은 사실을 알린다. 보유 스냅샷은 시장 데이터가 아니라 보지 않는다.

| 종류 | 늦었다고 보는 때 | 문구 예 |
|---|---|---|
| 장중 | 그 시장 거래일의 장 시간 안에서만 본다. 오늘 개장 뒤 마지막 완료(없으면 개장 시각) + 허용 지연이 지났을 때 | `국내 장중 시세가 10:05 이후 들어오지 않았어요` · `미국 장중 시세가 아직 들어오지 않았어요` |
| 일봉 | 기대 시각이 지난 가장 최근 거래일 D보다 최신 완료 거래일이 이를 때. 기대 시각은 국내 D 다음 날 0시(당일 중), 미국 D 다음 미국 거래일 개장 | `국내 일봉이 9/25 이후 들어오지 않았어요` |
| 수급 | 같은 방식. 기대 시각은 D 다음 국내 거래일 개장 | `국내 수급이 9/25 이후 들어오지 않았어요` |

notice는 시장(국내 → 미국)·종류(장중 → 일봉 → 수급) 순으로 싣고, `params`에 `market` · `kind` · `last_done`을 담는다. 배치는 [common.md](common.md)의 "notice 배치"를 따른다.

장중 스냅샷이 늦어 평가하지 못한 구간은 따로 기록하지 않는다. 기록할 수 있는 것은 "평가하지 못했다"뿐이고, 그 사이 조건이 참이었는지는 알 수 없다.

### 4.11 데이터 닫힘

수급(`DAILY_FLOW`)이나 장중 스냅샷(`INTRADAY_QUOTE`)을 아예 확보하지 못하는 동안, 운영자가 그 데이터에 기대는 조건을 닫는다. 닫힘은 다시 열리는 상태라 폐기(3.7)와 다르다.

| 스위치 | 기본 | 닫히는 것 |
|---|---|---|
| 수급 | 열림 | 수급 지표 `foreign_net_buy` · `institution_net_buy`, 수급 프리셋 `investor_streak` · `investor_turn` |
| 장중 | 열림 | 평가 시점 장중 — 프리셋과 직접 조건 모두 |

- **운영자가 정한다.** 데이터 유무를 보고 저절로 닫지 않는다. 그렇게 하면 일시적인 장애에도 닫혀, 하루 늦게 올 데이터를 기다리던 알림까지 멈춘다. 며칠 늦거나 빠지는 것은 데이터 지연 안내(4.10)가 알린다. 두 데이터는 따로 끊기므로 스위치도 따로 둔다. 값은 서버가 기동할 때 읽는다. 롤아웃 중 복제본끼리 값이 달라도 데이터 시점이 뒤로 가지 않으므로(5.2) 같은 시점을 두 번 반영하지 않는다. 바꾸는 절차는 런북이 정한다.

**새로 고를 수 없다.**
- 카탈로그는 닫힌 지표 · 프리셋 · 평가 시점을 목록에 남기고 `available: false`와 사유를 붙인다(8.2). 편집기는 숨기지 않고 비활성 + 사유 한 줄로 둔다.
- 저장은 `DATA_UNAVAILABLE`로 거부한다. 수정은 닫힌 항목을 **새로 넣을 때만** 거부한다 — 저장된 조건에 없던 닫힌 지표, 저장된 것과 다른 닫힌 프리셋, 저장된 평가 시점이 종가인데 장중으로 바꾸는 것. 저장된 알림에 이미 있던 닫힌 값은 수정 화면에서 선택된 채 열리고 다시 고를 수 있다. 그래서 이름 · 유효기간만 고치거나 종가로 바꾸는 수정은 막히지 않는다.
- 미리보기도 같은 규칙으로 `errors`에 `DATA_UNAVAILABLE`을 싣는다. 이 오류는 입력이 틀린 것이 아니라 현재값 계산을 막지 않는다.

**이미 만든 알림.** 알림 상태(`status`)는 바꾸지 않는다. 스위치를 다시 열면 사용자가 손대지 않아도 이어진다.

| 알림 | 닫힌 동안 | `data_closure.kind` |
|---|---|---|
| 수급 지표가 있는 알림(왼쪽·오른쪽 어느 쪽이든) | 평가하지 않는다. 결과 · 엣지 기준 · 평가한 데이터 시점을 그대로 두고 처음 건너뛴 시각만 남긴다 | `HELD` |
| N분 이상 유지가 있는 장중 알림 | 평가하지 않는다. 종가에는 유지 방식이 없고, 떼고 평가하면 사용자가 요구하지 않은 순간값으로 울린다 | `HELD` |
| 그 밖의 장중 알림 | 종가 알림으로 컴파일해 종가로 평가한다 | `AS_CLOSE` |

- 장중 알림의 왼쪽에는 수급 지표가 올 수 없어 한 알림이 두 줄에 함께 걸리지 않는다.
- **종가로 평가 중(`AS_CLOSE`)은 평가만 종가로 한다.** 해시는 원래 평가 시점(장중)으로 컴파일한 결과로 견주고 기록한다. 평가 시점이 바뀌었다고 기준을 다시 잡으면 닫힌 날과 다시 열린 날의 울림을 잃는다.
  - 장중에서 종가로 넘어간 첫 평가(평가한 데이터 시점이 장중 스냅샷 시각일 때)는 최신 확정 종가 하나만 평가한다. 장중 데이터가 끊긴 뒤 며칠 지나 닫아도 그 사이 거래일의 지난 날짜 울림이 한꺼번에 오지 않고, 닫은 날의 종가는 대개 이 최신 종가라 놓치지 않는다. 그날 종가가 아직이면 최신 종가가 이미 평가한 장중 시각보다 앞이라 기다린다. 그 뒤 밀린 거래일은 4.3의 종가 규칙을 따른다.
  - N분마다 다시는 참인 동안 거래일 종가마다 다시 울린다. 두 종가 사이가 다시 알림 간격보다 짧으면(1440분에 조기 폐장일 등) 그 종가에서는 울리지 않는다.
  - 다시 열리면 장중 규칙(4.3)으로 돌아가 가장 최근 스냅샷 하나를 평가한다.
  - 이렇게 울린 울림은 평가 시점을 종가로 기록해 `9/26 종가 기준`으로 보인다.
- **일시중지(`HELD`)는 다시 열려도 쌓인 시점을 따라잡지 않는다.** 처음 건너뛴 시각이 남아 있는 알림은 다시 열린 뒤 최신 확정 시점 하나만 평가하고(엣지 기준은 그대로) 그 표시를 비운다. 최신 확정 시점이 오늘 전 마지막 거래일보다 이르면 데이터팀이 지난 날짜부터 채우는 중이므로, 다 채워질 때까지 평가하지 않고 기다린다. 데이터가 지난 날짜를 나중에 채워도 몇 주 전 날짜로 울리지 않게 하기 위해서다. 사용자의 수정 · 다시 켜기는 4.6대로 최신 시점에서 시작하므로 이 표시도 함께 비운다.
- **문구는 서버가 정한다**(2.7). 원인이 수집 실패든 수집하지 않는 시간이든 맞도록 `제공하지 않아요`로 쓴다.

## 5. 평가 런타임

### 5.1 실행 형태

평가기 · 발송기 · 영수증 확인기는 백엔드 앱 안의 스케줄 작업이다. 별도 앱을 두지 않고 모든 복제본에서 돈다. 주기는 앞 실행이 끝난 뒤부터 세어 한 번이 길어져도 겹쳐 돌지 않는다. 서버 작업 전체의 목록과 스위치는 [common.md](common.md)의 "서버 런타임"이 정한다.

| 작업 | 주기 | 하는 일 |
|---|---|---|
| 평가기 | 1분 | 만료를 먼저 옮기고, 감시 중이고 삭제되지 않은 알림마다 평가할 데이터 시점을 골라 앞에서부터 평가·반영한다 |
| 발송기 | 5초 | 보낼 발송 행을 묶어 Expo Push로 보낸다(6.3). 한 묶음이 꽉 차면 이어 보낸다 |
| 영수증 확인기 | 5분 | 보낸 푸시의 전달 영수증을 묻는다(6.4) |

- 신호를 처리했는지는 따로 기록하지 않는다. 알림마다의 평가한 데이터 시점이 그 기록이라, 신호가 온 뒤에 만든 알림도 다음 주기(1분 안)에 평가된다.
- 같은 주기 안에서 같은 (종목, 평가 시점, 데이터 종류, 데이터 시점)의 입력은 한 번만 읽고 그 종목에 걸린 알림들이 함께 쓴다. 내 보유 입력만 사용자마다 따로 읽는다.
- 알림 하나의 평가 실패나 만료 전이 실패는 나머지 알림의 평가를 막지 않는다.

### 5.2 중복 방지

복제본 여럿이 같은 신호를 동시에 처리해도 울림은 한 번이다. 잠금이 아니라 데이터 조건으로 막는다 → [ADR: 리더 없는 다중 복제본](../decisions/).

1. **평가 결과 반영은 조건부 갱신이다.** 읽을 때의 `version`과 읽을 때 본 평가한 데이터 시점이 그대로이고, 새 데이터 시점이 그보다 뒤이며, 유효기간이 지나지 않았을 때만 상태를 바꾼다. 바뀐 행이 없으면 다른 복제본이 먼저 반영했거나 평가 도중 사용자가 알림을 바꾼 것이라 결과를 버린다. 평가기는 `version`을 알림 규칙과 같은 조회에서 읽는다 — 따로 읽으면 그 사이 커밋된 수정의 새 `version`을 들고 옛 규칙의 결과를 반영할 수 있다. 그래서 끈 알림이 평가 중이던 결과로 울리거나, 새 조건의 첫 울림이 옛 조건의 결과에 덮이는 일이 없다.
2. **울림은 (알림, 데이터 시점)마다 하나다.** 1을 통과한 뒤에도 같은 울림이 두 번 들어가지 못한다(DB 유일 제약).
3. **상태 갱신 · 울림 기록 · 기기별 발송 행 · 한 번만 알림의 종료는 한 트랜잭션이다.** 울렸는데 기록이 없거나, 기록했는데 상태가 그대로인 경우가 생기지 않는다. 한 번만 알림은 종료할 때 알림 행을 바꾸므로 알림 행을 먼저 잡는다 — 사용자 변경·만료와 같은 잠금 순서(알림 → 평가 상태)다. 종료는 `version`도 올려 다른 복제본이 뒤 시점을 반영하지 못하게 한다.
4. **사용자 변경과 만료는 같은 트랜잭션에서 `version`을 올리고 알림 대상 종목(7절)을 갱신한다.** 만료는 조건부 갱신이라 두 복제본이 동시에 돌아도 한 알림은 한쪽만 옮긴다.
5. **발송기는 발송 행을 `FOR UPDATE SKIP LOCKED`로 집는다.** 한 발송 행은 한 복제본만 처리한다(6.3).

복제본 수와 무관하게 성립하는 성질이라 리더 선출·분산 잠금·별도 라이브러리가 필요 없다.

### 5.3 재시작

메모리에 들고 있는 상태가 없다. 이력은 DB에 있고 알림 상태는 `alert_state`에 있으므로, 재시작하면 평가 대상 알림을 다시 찾아 이어 간다. 밀린 신호는 4.3을 따른다. 발송 중이던 행은 임대가 끝나면 다시 집힌다(6.3).

### 5.4 되돌리는 조건

평가 한 주기가 주기(1분)의 절반을 넘기거나 API 응답이 평가 주기에 맞춰 느려지면, 같은 이미지를 알림 런타임만 켠 워커로 따로 띄우고 API 파드에서는 끈다. 중복 방지가 데이터에 있으므로 코드는 바뀌지 않는다.

평가기는 주기마다 걸린 시간 · 대상 알림 수 · 평가한 데이터 시점 수 · 파드 이름을 로그 한 줄로 남기고, 30초를 넘으면 경고로 남긴다. 복제본마다 평가기가 따로 돌아 값은 파드별로 나온다. 실제 소요는 측정하지 않았다. 지표 수집 경로(Prometheus 등)는 두지 않는다. 로그를 읽는 법과 워커로 떼어 내는 절차는 런북이 정한다.

## 6. 울림 전달

### 6.1 울림 기록이 대기열

```
평가기 ─(한 트랜잭션)─▶ 평가 상태 갱신 + 울림 기록 + 살아 있는 세션의 iOS 기기마다 발송 행(PENDING)
발송기 ─▶ 보낼 행을 SKIP LOCKED로 집어 SENDING → (트랜잭션 밖에서) Expo Push 전송 → SENT / 다시 시도 / FAILED
영수증 ─▶ 전달 영수증 조회. 기기 미등록이면 그 기기를 지운다
앱     ─▶ 울림 기록을 읽어 울린 알림 목록 · 탭 배지
```

울림 기록(`alert_event`) 한 표가 **울림 이력 · 앱 안 목록 · 안 읽음 배지 · 푸시 발송의 원천**을 모두 떠받친다. 울림과 상태 갱신이 같은 DB 트랜잭션이라 울림이 사라지거나 두 번 생기지 않는다.

메시지 브로커를 두지 않는다. 브로커로 발행하면 DB 커밋과 발행을 한 번에 성공시킬 수 없어 결국 같은 대기 표가 필요하고, 앱의 목록도 DB 표를 요구한다. 지금 소비자는 푸시 발송 하나뿐이다 → [ADR: 발송 대기열](../decisions/).

### 6.2 수신 폰 등록

- 앱은 **알림을 저장할 때** OS 권한이 아직 정해지지 않았으면 안내 시트를 먼저 띄우고, `허용하기`를 누르면 시스템 권한을 묻는다(2.7). 허용되면 곧바로 기기를 등록한다.
- 권한이 있으면 Expo 푸시 토큰을 `POST /devices`로 등록하고 받은 `device_id`를 앱의 보안 저장소에 둔다. 로그인한 동안 앱이 켜질 때와 앞으로 올 때마다 다시 등록해 토큰 교체를 따라간다. 등록은 같은 행을 고쳐 쓰므로 여러 번 보내도 된다.
- **등록은 그 요청의 로그인 세션에 묶인다.** 토큰이 이미 등록돼 있으면 지금 사용자와 지금 세션으로 옮긴다. 세션이 끝날 때 기기 등록이 어떻게 되는지(로그아웃·유휴 만료·절대 상한, 서버에 닿지 못한 로그아웃)는 [common.md](common.md)의 "세션이 끝날 때"가 정한다.
- **권한이 꺼진 기기는 등록을 지운다.** 앱이 앞으로 올 때 권한이 꺼져 있으면 등록하지 않고, 보관한 `device_id`가 있으면 `DELETE /devices/{id}`로 지운다. 권한이 꺼진 기기의 등록은 푸시가 닿지 않는데도 발송 대상으로 남기 때문이다. 권한을 다시 켜면 다음 실행·앞으로 옴에서 다시 등록한다.
- Android 기기는 등록하지 않는다(6.6). EAS 프로젝트 ID가 없는 빌드도 등록하지 않는다.
- 등록과 해제가 실패하면 조용히 넘어간다. 울림은 앱 안 목록과 배지로 반드시 보인다.

### 6.3 발송

발송 행 하나는 (울림, 기기) 한 쌍이다. 보내기 전과 보내는 중의 규칙은 이렇다.

| 단계 | 규칙 |
|---|---|
| 집기 | 한 트랜잭션에서 먼저 보내지 않을 행을 끝내고(아래 표), 보낼 때가 된 대기 행과 임대가 끝난 발송 중 행을 최대 100건 잠가 집고, 발송 중(`SENDING`)으로 바꿔 임대(2분)를 건 뒤 커밋한다. 기기의 지금 사용자가 알림의 사용자와 같고 기기의 세션이 살아 있는 행만 집는다 |
| 전송 | 트랜잭션 밖에서 Expo에 묶음으로 보낸다. Expo가 느려도 행 잠금과 DB 연결을 쥐지 않는다 |
| 기록 | 결과를 한 트랜잭션에 쓴다. 기록은 "아직 발송 중이고 집을 때의 시도 횟수 그대로"인 행만 바꾸므로 다시 실행해도 같은 결과다. 일시적인 잠금·교착 실패면 세 번까지 다시 시도한다 |
| 기기 정리 | 기록이 커밋된 뒤 등록이 풀린 기기를 하나씩 지운다. 그 기기의 발송 행도 함께 지워진다 |

| 결과 | 처리 |
|---|---|
| 접수됨 | 보냄(`SENT`). 15분 뒤 영수증을 묻는다 |
| 기기 미등록(`DeviceNotRegistered`) | 다시 시도하지 않고 실패(`FAILED`), 그 기기를 지운다 |
| 요청 한도 초과 · 연결 실패 · 429 · 5xx | 30초 · 1분 · 2분 · 4분 뒤 다시 시도, 다섯 번째 시도도 실패하면 실패 |
| 그 밖의 4xx · 응답 형식 오류 · 그 밖의 티켓 오류 | 다시 시도하지 않고 실패 |

요청 자체가 실패하거나 요청 한도 초과가 섞이면 그 주기의 이어 보내기를 멈춘다 — 장애 중에 대기열 전체의 시도 횟수를 쓰지 않는다.

**보내지 않고 끝내는 행**

| 사유(`last_error`) | 언제 |
|---|---|
| `EXPIRED` | 울린 지 오래됨 — 장중 울림 30분, 종가 울림 12시간. 울림의 평가 시점으로 정한다(종가로 평가된 장중 알림의 울림은 종가) |
| `OWNER_CHANGED` | 기기가 다른 사용자에게 옮겨짐 |
| `SESSION_ENDED` | 기기의 로그인 세션이 유휴 만료나 절대 상한을 넘김 |
| `LEASE_EXPIRED` | 임대가 끝났는데 시도 횟수를 다 씀 |

다른 발송기가 임대 중인 행은 건드리지 않는다. **발송 실패는 울림을 취소하지 않는다.** 울림 기록과 배지는 그대로 남는다.

**푸시 페이로드**

```json
{ "to": "ExponentPushToken[…]", "title": "삼성전자 · 가격 도달",
  "body": "현재가 70,200원 ≥ 70,000원 · 10:15 기준", "sound": "default",
  "data": { "event_id": "…" } }
```

`data`에는 `event_id`만 싣는다. 푸시를 눌렀을 때와 앱이 앞에 떠 있을 때 온 푸시의 동작은 [common.md](common.md)의 "푸시를 눌렀을 때"가 정한다.

**알려진 한계**
- 같은 푸시가 두 번 나갈 수 있다. Expo가 받았는데 결과를 기록하지 못했거나(파드 종료, 기록 트랜잭션이 계속 실패), Expo가 받은 뒤 읽기 시간 제한이 걸린 경우다. 다시 보내는 때는 임대가 끝난 뒤이거나 재시도 일정이 왔을 때뿐이다.
- 발송 처리량은 측정하지 않았다.

### 6.4 영수증

Expo는 전송 요청에 접수 티켓을 주고 실제 전달 결과는 나중에 영수증으로 준다. 영수증 확인기는 보낸 지 15분이 지난 행의 티켓을 최대 1000건씩 트랜잭션 밖에서 묻고, 결과를 한 트랜잭션에 쓴 뒤 등록이 풀린 기기를 지운다. 행을 잠그지 않는다 — 두 복제본이 같은 티켓을 물어도 기록이 같다.

| 영수증 | 처리 |
|---|---|
| 성공 | 티켓을 비운다 |
| 실패 | 실패로 바꾸고 사유를 남긴다. 기기 미등록이면 그 기기를 지운다 |
| 아직 없음 | 15분 뒤 다시 묻는다. 보낸 지 24시간(Expo 보관 기간)이 지나면 티켓을 비우고 더 묻지 않는다 |
| 조회 자체가 실패 | 아무것도 바꾸지 않고 다음 주기에 다시 묻는다 |

### 6.5 권한 거부·폰 없음

기기가 하나도 없거나 권한을 거부한 사용자도 **울림 기록은 남는다.** 발송 행이 생기지 않을 뿐, 울린 알림 목록과 탭 배지로 반드시 보인다. 권한을 거부한 상태는 알림 탭 위쪽 배너로 알리고 설정으로 이끈다. 배너는 닫을 수 있고, 권한이 꺼진 채 저장하면 시트가 다시 알린다(2.7).

### 6.6 플랫폼 제약

**v1의 푸시는 iOS에서만 동작한다.** 앱은 Expo Go로 실기기 검증을 하는데, Expo Go는 SDK 53부터 Android에서 원격 푸시를 지원하지 않는다. 그래서 앱은 Android에서 토큰을 등록하지 않고, 서버도 iOS로 등록된 기기에만 발송 행을 만든다. Android 사용자는 앱 안 목록과 배지로만 확인하고, 알림 탭에 `Android에서는 앱 안에서만 알림을 확인할 수 있어요`를 보인다. 발송 경로(Expo Push)는 플랫폼과 무관하므로 개발 빌드로 바꾸면 Android 푸시가 열린다(11절).

### 6.7 울림 문구

제목과 본문은 **울릴 때 서버가 완성해 저장한다.** 나중에 알림을 수정·삭제해도 그때 울린 내용은 바뀌지 않는다.

```
제목  삼성전자 · 가격 도달
본문  현재가 70,200원 ≥ 70,000원 · 10:15 기준

제목  카카오 · RSI 과매수
본문  RSI(14) 71.3 ≥ 70 · 3일째 · 9/26 종가 기준
```

| 부분 | 규칙 |
|---|---|
| 제목 | 프리셋은 `종목명 · 프리셋 이름`, 직접 조건은 `종목명 · 알림 이름`. 갈래를 고르는 프리셋은 고른 갈래의 이름을 쓴다 — `RSI 과매수` · `RSI 과매도` · `골든크로스` · `데드크로스` · `박스권 상단 돌파` · `박스권 하단 이탈` · `급등` · `급락` · `외국인 연속 순매수` · `기관 순매도 전환` 등. 가격 도달 · 거래량 급증 · 수익률 도달은 라벨 그대로다. 종목 이름을 모르면 이름 부분만 쓴다 |
| 본문 | 조건마다 관측값 줄(`지표 관측값 연산자 기준값`, 진행 상황 `3일째` · `12분째`)을 ` · `로 잇고 끝에 데이터 시점을 붙인다. 관측값 줄은 미리보기 현재값 상자와 같은 규칙에서 나오고, 줄마다 따로 `lines`에 저장한다 |
| 평가에 쓴 값 | 조건마다 왼쪽 값 · 오른쪽 값 · 진행 상황을 `observed`에 저장한다. 계산할 수 없던 값은 비운다 |

- 본문은 관측값과 데이터 시점을 반드시 담는다. 밀린 종가를 따라잡아 울린 경우(4.3)에도 기준일이 문구에 있어 오해가 없다.
- 계좌번호·금액 등 계좌 정보는 문구에 넣지 않는다. 푸시는 잠금 화면에 보인다.

## 7. 데이터 모델

백엔드가 소유하는 표다. 컬럼 목록은 마이그레이션이 정한다. 데이터팀이 주는 표(종목 마스터 `instrument` · 수정주가 일봉 · 투자자별 순매수 · 장중 스냅샷 · 완료 신호 `market_data_run` · 시장 캘린더 `dim_market_calendar`)는 [data-contract.md](data-contract.md)의 "알림 테이블"과 "공용 테이블"이 정한다. 백엔드는 그 표를 읽기만 한다. 알림 표 중 데이터팀이 읽는 것은 [data-contract.md](data-contract.md)의 "데이터팀이 읽는 백엔드 테이블"을 따른다.

**소유 축은 `alert.user_id` 하나다.** 평가 상태·울림·발송 행은 모두 알림을 거쳐 소유자가 정해진다. 포트폴리오가 계좌로 소유를 가르는 것과 다른 것은 알림이 보유하지 않은 종목에도 걸려 계좌를 거칠 수 없어서다. 그래서 한 사용자의 알림은 계좌 연동·해제와 무관하게 유지된다.

| 표 | 역할 · 그레인 | 키 · 유일성과 보장 | 쓰는 쪽 · 읽는 쪽 | 수명 |
|---|---|---|---|---|
| `alert` | 알림 한 건 | 알림 ID. 이름 1~40자, 다시 알림 간격은 N분마다 다시일 때만 있고 5~1440이며 장중만 — DB 제약과 저장 전 검증이 함께 지킨다. `user_id`는 만든 뒤 바뀌지 않는다. `instrument_id`는 데이터팀 표를 가리키되 FK를 걸지 않는다 — 두 팀의 배포 순서를 묶지 않으려고 | 쓰기: 사용자 요청(만들기·수정·끄기·다시 켜기·삭제), 평가기(만료·한 번만 종료). 읽기: 목록·상세·평가기 | 삭제는 소프트 삭제(`deleted_at`)라 행이 남는다 |
| `alert_state` | 알림마다 평가 상태 한 행(4.7) | 알림 ID(1:1) | 쓰기: 평가기(결과 반영·일시중지 표시), 사용자 요청(처음으로 돌리기·`version` 올리기). 읽기: 평가기·목록·상세 | 알림과 같다 |
| `alert_event` | 울림 한 건 | 울림 ID. **(알림, 데이터 시점)이 유일**(DB 유일 제약) — 한 알림은 한 데이터 시점에 최대 한 번 울린다 | 쓰기: 평가기(울림), 사용자 요청(읽음). 읽기: 울린 알림·새로 울린 알림·배지·발송기 | 지우는 작업이 없다. 알림을 지워도 남는다 |
| `alert_delivery` | (울림, 기기)마다 발송 한 행 | (울림 ID, 기기 ID). 기기를 지우면 함께 지워진다(FK 연쇄) | 쓰기: 평가기(만들기), 발송기·영수증 확인기(상태). 읽기: 같다 | 지우는 작업이 없다. 기기가 지워질 때만 사라진다 |
| `push_device` | 푸시를 받을 기기 하나 | 기기 ID. **Expo 푸시 토큰이 유일**(DB 유일 제약) — 같은 토큰을 다시 등록하면 지금 사용자·세션으로 옮긴다. 로그인 세션을 가리키고 세션 행이 지워지면 함께 지워진다(FK 연쇄) | 쓰기: 기기 등록·해제 요청, 발송기·영수증 확인기(미등록 기기 삭제), 세션 정리. 읽기: 평가기·발송기 | 세션이 끝나 정리되거나 등록이 풀리거나 앱이 해제할 때까지 |
| `alert_watchlist` | 알림 대상 종목 — 삭제되지 않은 감시 중 알림이 하나 이상 걸린 종목마다 한 행 | 종목 ID. 같은 종목의 갱신은 종목별 권고 잠금으로 한 번에 하나씩 한다 | 쓰기: 알림을 바꾸는 모든 트랜잭션(만들기·수정·끄기·다시 켜기·삭제·만료·한 번만 종료)이 그 종목 행을 다시 계산한다. 읽기: 데이터팀(수집 대상) | 걸린 감시 중 알림이 없어지면 행이 빠진다 |
| `snapshot_run` | 보유 스냅샷 완료 신호 — 기준일마다 한 행 | 기준일. 같은 날을 다시 쓰면 첫 기록이 남는다 | 쓰기: 포트폴리오 확정 단계가 그 기준일을 확정할 때. 읽기: 평가기(내 보유 지표 신호), 미리보기 | 지우는 작업이 없다 |

규칙에 나오는 값의 뜻:

- `alert.status`: 4.8. `alert.trigger_type` · `trigger_spec` · `spec_version`: 3.2 · 3.7. `alert.instrument_name` · `instrument_symbol`: 알림을 만들거나 고칠 때 종목 마스터에 있던 이름·코드. 종목이 마스터에서 빠졌을 때 화면이 대신 보인다(2.2).
- `alert_event.as_of`: 울림을 만든 데이터 시점. `alert_event.cadence`: 울림을 만든 평가 시점 — 기준 표기(`10:15 기준` · `9/26 종가 기준`)와 발송 기한을 이 값으로 정하고, 비어 있으면 알림의 평가 시점으로 본다. 종가로 평가되어 울린 장중 알림은 종가다. `fired_at`: 기록 시각 — 울린 시각 표시와 정렬의 기준. `read_at`: 읽은 시각, 비어 있으면 안 읽음.
- `alert_delivery.state`: `PENDING`(보낼 차례를 기다림) · `SENDING`(발송기가 집어 보내는 중, 임대 중) · `SENT`(Expo가 접수) · `FAILED`(끝). `next_attempt_at`은 대기면 다음 전송 시각, 발송 중이면 임대가 끝나는 시각, 보냄이면 영수증을 물을 시각이다. `last_error`는 Expo 오류 코드나 HTTP 상태, 6.3의 사유 같은 짧은 값이고 푸시 토큰과 응답 본문을 넣지 않는다.
- `push_device.platform`: `IOS` · `ANDROID`. `user_id`는 지금 이 기기로 로그인한 사용자다.
- `alert_watchlist.intraday`: 그 종목에 장중 알림이 있는가. 데이터팀이 이 목록으로 수집 대상을 정한다(어느 데이터를 어느 종목에 대해 만드는지는 [data-contract.md](data-contract.md)의 "알림 테이블"). 장중 스냅샷을 전 종목에 대해 몇 분 간격으로 수집하는 것은 원천 호출 한도로 성립하지 않을 수 있어 알림이 걸린 종목만 요구한다. 이 표는 누가 알림을 걸었는지 담지 않는다 — 데이터팀은 어느 종목을 수집할지만 알면 된다.

인덱스는 마이그레이션이 정한다. 사용자별 울림을 읽을 때 알림 표를 거쳐 조인하는 비용, 종목 검색의 부분 일치 비용은 실행 계획 미확인이다.

## 8. API

인증·응답 봉투·오류 모양·사용자 스코프는 [common.md](common.md)의 "API 공통 규칙"을 따른다. 모든 엔드포인트가 로그인을 요구하고, 사용자 ID는 경로·쿼리·본문 어디에서도 받지 않는다. 알림 저장 본문은 형이 틀린 값도 경로가 붙은 칸 오류로 돌려주기 위해 서버가 JSON을 직접 해석한다.

### 8.1 엔드포인트

| 구분 | 경로 | 성공 |
|---|---|---|
| 알림 | `GET /alerts` (봉투) · `GET /alerts/{id}` | 200 |
| | `POST /alerts` | 201 `{ "alert_id" }` |
| | `PUT /alerts/{id}` | 200 `{ "alert_id" }` |
| | `DELETE /alerts/{id}` | 204 |
| 상태 전환 | `POST /alerts/{id}/pause` · `POST /alerts/{id}/resume` | 204 |
| 미리보기 | `POST /alerts/preview` | 200 (검증 오류가 있어도) |
| 카탈로그 | `GET /alerts/catalog` | 200 |
| 종목 검색 | `GET /instruments?q=&held=` | 200 |
| 울린 알림 | `GET /alert-events?alert_id=&cursor=&limit=` (봉투) · `GET /alert-events/{id}` | 200 |
| | `POST /alert-events/{id}/read` · `POST /alert-events/read-all` | 204 |
| 배지 | `GET /alert-events/unread-count` | 200 `{ "count" }` |
| 기기 | `POST /devices` | 200 `{ "device_id" }` |
| | `DELETE /devices/{id}` | 204 |

만들기·수정은 알림 ID만 돌려준다. 저장 뒤 화면은 알림 상세를 다시 받는다.

### 8.2 요청·응답

**만들기 · 수정 · 미리보기 요청**

```json
{ "instrument_id": "…", "name": "카카오 RSI 과열",
  "cadence": "CLOSE", "notify_mode": "EDGE_REARM", "cooldown_min": null, "expires_at": null,
  "trigger_type": "PRESET",
  "trigger_spec": { "preset_key": "rsi_zone", "params": { "n": 14, "zone": "overbought", "level": 70 } } }
```

`notify_mode`(기본 `EDGE_REARM`) · `cooldown_min` · `expires_at`(비우면 무기한)은 생략할 수 있다. 미리보기는 같은 모양에 수정 중이면 `alert_id`를 싣는다. `spec_version`은 받지 않는다.

**`GET /alerts`** — 봉투

```json
{ "as_of": "2026-09-26T10:15:00+09:00",
  "data": {
    "rows": [
      { "alert_id": "…", "name": "삼성전자 7만원",
        "instrument": { "id": "…", "label": "삼성전자", "market": "KR" },
        "cadence": "INTRADAY", "notify_mode": "EDGE_REARM", "status": "ACTIVE",
        "summary": { "short": "장중 · 현재가 ≥ 70,000원" },
        "last_result": "UNKNOWN", "unknown_reason": "NO_TRADE",
        "evaluated_as_of": "2026-09-26T10:15:00+09:00",
        "last_fired_at": "2026-09-25T09:42:00+09:00",
        "data_closure": null } ],
    "unread": [
      { "event_id": "…", "title": "카카오 · RSI 과매수", "cadence": "CLOSE", "market": "KR",
        "as_of": "2026-09-25T15:30:00+09:00", "fired_at": "2026-09-25T16:02:10+09:00",
        "alert_deleted": false } ],
    "unread_more": 0 },
  "empty_reason": null,
  "notices": [
    { "code": "MARKET_DATA_DELAYED", "severity": "warn",
      "message": "국내 장중 시세가 10:05 이후 들어오지 않았어요",
      "params": { "market": "KR", "kind": "INTRADAY_QUOTE", "last_done": "2026-09-26T10:05:00+09:00" } } ] }
```

- `as_of`는 이 사용자의 삭제되지 않은 알림이 평가된 가장 늦은 데이터 시점이다. 평가된 알림이 없으면 null이고 앱은 기준 표기를 숨긴다. 울린 알림 봉투도 같은 값이다.
- `rows`는 서버가 2.2의 순서로 정렬한다. 삭제된 알림은 없다.
- `instrument.label`은 2.2의 종목명 자리 규칙대로이고 남은 값이 없으면 null이다. `market`은 종목 마스터에서만 읽어 마스터에 없으면 null이다.
- `summary`는 서버가 완성한 조건 문장이다(2.1). 목록은 `short`만, 상세와 미리보기는 `short` · `sentence` 둘 다 싣는다.
- `unread`는 새로 울린 알림 블록이며 최대 3건, 울린 시각 최신순(같으면 울림 ID 내림차순)이다. 넘친 건수는 `unread_more`다. 삭제된 알림의 울림도 든다.
- 울린 시각 표시와 `last_fired_at`은 `fired_at` 기준이다. 데이터 시점(`as_of`)은 `10:15 기준` · `9/26 종가 기준` 같은 기준 표기에만 쓰고, 형식은 `cadence`와 `market`으로 정한다. 울림 행의 `cadence`는 울림을 만든 평가 시점이다.
- `data_closure`: 데이터 닫힘에 걸린 감시 중·꺼짐 알림이면 `{ "kind": "AS_CLOSE" | "HELD", "message": "…" }`, 아니면 null. 목록·상세·울린 알림 상세가 같은 값을 싣고 앱은 `message`를 그대로 그린다.
- `empty_reason`: `NO_ALERTS`(내 알림이 없음) · `NO_EVENTS`(울린 알림 첫 쪽이 비어 있음).
- notices는 `MARKET_DATA_DELAYED` 하나다(4.10). 울림 전달 실패는 notice가 아니다 — 울림 기록이 남아 사용자가 잃는 정보가 없다.

봉투는 기준 시점이 있는 조회 결과의 모양이라 상세·만들기·수정·미리보기·카탈로그는 봉투를 쓰지 않는다.

**`GET /alerts/{id}`**

```json
{ "alert_id": "…", "name": "삼성전자 7만원",
  "instrument": { "id": "…", "label": "삼성전자", "market": "KR" },
  "cadence": "INTRADAY", "notify_mode": "EDGE_REARM", "cooldown_min": null,
  "expires_at": null, "status": "ACTIVE",
  "trigger_type": "PRESET",
  "trigger_spec": { "preset_key": "price_reach", "params": { "direction": "up", "price": 70000 } },
  "summary": { "short": "장중 · 현재가 ≥ 70,000원", "sentence": "장중에 현재가가 70,000원 이상이면 알려요" },
  "last_result": "FALSE", "unknown_reason": null,
  "evaluated_as_of": "2026-09-26T10:20:00+09:00", "data_closure": null,
  "recent_events": [ { "event_id": "…", "title": "삼성전자 · 가격 도달",
                       "as_of": "2026-09-26T10:15:00+09:00", "cadence": "INTRADAY", "read": true } ] }
```

`recent_events`는 울린 시각 최신순(같으면 울림 ID 내림차순) 최근 5건이다. 그 알림의 전체 울림은 `GET /alert-events?alert_id=`로 본다. `trigger_spec`을 싣는 것은 수정이 편집기를 값이 채워진 채 열기 때문이다.

**`POST /alerts/preview`** → 200

```json
{ "valid": true, "errors": [],
  "summary": { "short": "종가 · RSI(14) 70 이상 진입", "sentence": "종가 기준으로 RSI(14)가 70 이상이면 알려요" },
  "current": { "result": "TRUE", "as_of": "2026-09-26T15:30:00+09:00",
               "header": "9/26 종가 기준", "result_text": "충족하고 있어요",
               "conditions": [ { "result": "TRUE", "unknown_reason": null, "text": "RSI(14) 71.3 ≥ 70" } ] },
  "already_satisfied": true, "already_fired": false, "duplicate_of": null }
```

미리보기는 저장 전 초안 하나로 **검증 오류 · 지금 값 · 지금 충족 여부 · 이미 울린 시점인가 · 중복**을 한 번에 돌려준다.

- 검증 규칙은 저장과 같다(9절). 오류가 있어도 200으로 `errors`에 싣는다 — 입력 중인 폼의 상태이지 요청의 실패가 아니다. 요청 모양이 틀려 해석하지 못하면 `summary` · `current`가 null이다. 프리셋은 입력 칸이 맞아야, 직접 조건은 조건 목록이 맞아야 문장과 현재값을 만든다. 직접 조건은 틀린 조건 줄만 빼고 나머지를 계산한다.
- `current`는 평가와 같은 데이터로 계산한다(내 보유는 확정 스냅샷, 장중은 2.5의 규칙). 다만 보유 확인 오류(`NOT_HELD`)가 있으면 `current`는 null이다 — 저장할 수 없는 알림의 현재값, 특히 확정 스냅샷에 남은 어제 수익률을 오류와 함께 보이지 않는다.
- 데이터 닫힘 동안 장중 초안은 종가로 컴파일해 계산하고 머리는 `9/26 종가 기준`이다. N분 이상 유지가 있는 장중 초안은 `current`가 null이다 — 종가에는 유지 방식이 없어 평가와 같은 값을 낼 수 없다. 수급 초안은 확보된 마지막 거래일로 계산하므로 머리의 날짜가 그 거래일을 밝힌다.
- `already_satisfied`는 `current.result`가 참인가, `already_fired`는 수정 중인 알림이 `current`의 데이터 시점에 이미 울렸는가다(4.6).
- 알림 상세는 같은 경로에 `alert_id`를 실어 현재값 상자를 채우고 `already_*` · `duplicate_of`는 쓰지 않는다.

**`GET /alert-events?cursor=&limit=`** — 봉투

```json
{ "as_of": "2026-09-26T10:15:00+09:00",
  "data": {
    "rows": [ { "event_id": "…", "alert_id": "…", "title": "삼성전자 · 가격 도달",
                "body": "현재가 70,200원 ≥ 70,000원 · 10:15 기준",
                "cadence": "INTRADAY", "market": "KR",
                "as_of": "2026-09-26T10:15:00+09:00", "fired_at": "2026-09-26T10:15:41+09:00",
                "read": false, "alert_deleted": false } ],
    "next_cursor": "…" },
  "empty_reason": null, "notices": [] }
```

정렬은 울린 시각 내림차순, 같으면 울림 ID 내림차순이다. `limit`은 1~50(기본 20), `cursor`는 앞 쪽의 `next_cursor`(마지막 행의 울린 시각과 울림 ID를 이은 불투명 문자열)이고 `next_cursor`가 null이면 마지막 쪽이다. `alert_id`를 주면 그 알림의 울림만 — 삭제된 내 알림이어도 찾은 것으로 본다.

**`GET /alert-events/{id}`**

```json
{ "event_id": "…", "title": "삼성전자 · 가격 도달",
  "body": "현재가 70,200원 ≥ 70,000원 · 10:15 기준",
  "lines": [ "현재가 70,200원 ≥ 70,000원" ],
  "as_of": "2026-09-26T10:15:00+09:00", "cadence": "INTRADAY", "fired_at": "2026-09-26T10:15:41+09:00",
  "observed": { "conditions": [ { "left": 70200, "right": 70000, "progress": null } ] },
  "read_at": "2026-09-26T10:20:03+09:00",
  "alert": { "alert_id": "…", "name": "삼성전자 7만원", "cadence": "INTRADAY", "notify_mode": "EDGE_REARM",
             "status": "ACTIVE", "last_result": "FALSE", "unknown_reason": null,
             "deleted": false, "data_closure": null,
             "instrument": { "id": "…", "label": "삼성전자" } } }
```

울린 당시의 문구와 지금 알림의 상태를 함께 싣는다. 종목 시장은 싣지 않는다(2.3 결정 필요).

**그 밖의 요청**

```json
// POST /alerts/{id}/resume — 만료된 알림은 expires_at이 필수(null이면 무기한). 그 밖의 상태는 본문이 없어도 된다
{ "expires_at": null }

// POST /devices → 200 { "device_id": "…" }. 등록은 이 요청의 로그인 세션에 묶인다
{ "expo_push_token": "ExponentPushToken[…]", "platform": "IOS" }

// GET /alerts/catalog (발췌)
{ "indicators": [ { "key": "rsi", "label": "RSI", "category": "기술지표", "unit": "index",
                    "params": [ { "key": "n", "default": 14, "min": 2, "max": 30 } ],
                    "intraday_left": false, "markets": ["KR", "US"],
                    "allowed_transforms": ["identity", "delta"],
                    "transform_ranges": { "delta": { "min": 1, "max": 5 } },
                    "allowed_operators": ["gte", "lte", "gt", "lt", "crosses_above", "crosses_below"],
                    "scope": "market", "deprecated": false,
                    "available": true, "unavailable_reason": null } ],
  "presets": [ { "key": "box_breakout", "label": "박스권 돌파", "cadences": ["CLOSE"], "markets": ["KR", "US"],
                 "scope": "market", "param_schema": [ { "key": "window_days", "kind": "int", "min": 5, "max": 120,
                                                        "default": 20, "choices": [], "required": false }, … ],
                 "available": true, "unavailable_reason": null } ],
  "cadence_options": [ { "key": "INTRADAY", "available": false, "unavailable_reason": "지금은 장중 시세를 제공하지 않아요" },
                       { "key": "CLOSE", "available": true, "unavailable_reason": null } ],
  "transforms": [ { "key": "window", "label": "최근 N일", "fns": [ { "key": "max", "label": "최고" }, … ] }, … ],
  "operators": [ { "key": "gte", "symbol": "≥", "word": "이상" }, … ] }
```

- `available` · `unavailable_reason`은 데이터 닫힘을 싣는다. 폐기(`deprecated`)와 따로다.
- 최상위 `cadence_options`는 지금 고를 수 있는 평가 시점이다. 직접 조건은 이것으로 고른다. 프리셋 `cadences`는 닫힘과 상관없이 그 프리셋이 허용하는 평가 시점이라 프리셋 폼은 둘 다 열린 값만 고르게 한다.
- `param_schema`의 `kind`는 `int` · `decimal` · `choice`다. `required`인 칸(가격 도달의 가격)은 기본값이 없고 화면이 직전 종가로 채운다.
- 카탈로그는 서버가 기동할 때 한 번 만든다(닫힘 스위치도 기동 때 읽는다).

### 8.3 오류

| 상황 | HTTP | `error.code` |
|---|---|---|
| 저장 검증 실패 | 400 | `INVALID_ALERT` + `fields[]`. 닫힌 조건은 칸 코드 `DATA_UNAVAILABLE` |
| 상태 전이가 맞지 않는 끄기 · 다시 켜기(4.8) | 400 | `INVALID_STATUS_TRANSITION` |
| 울린 알림 목록의 `alert_id` · `limit` · `cursor`가 틀림 | 400 | `INVALID_PARAMETER` |
| 기기 등록 본문이 틀림(토큰 없음·200자 초과, 플랫폼이 `IOS` · `ANDROID`가 아님) | 400 | `INVALID_DEVICE` |
| 남의 알림 · 없는 알림 · 삭제된 알림 — 조회 · 수정 · 삭제 · 끄기 · 다시 켜기 · 미리보기의 `alert_id`. 울린 알림 목록의 `alert_id`만은 삭제된 내 알림도 찾은 것으로 본다 | 404 | `ALERT_NOT_FOUND` |
| 남의 울림 · 없는 울림 | 404 | `EVENT_NOT_FOUND` |
| 남의 기기 · 없는 기기 | 404 | `DEVICE_NOT_FOUND` |

로그인 실패·세션 끝남(401)은 [common.md](common.md)의 "로그인·세션"이 정한다.

```json
{ "error": { "code": "INVALID_ALERT", "message": "조건을 확인해 주세요",
             "fields": [ { "path": "trigger_spec.conditions[0].modifier",
                           "code": "MODIFIER_NOT_ALLOWED",
                           "message": "종가 알림에는 N분 지속을 쓸 수 없어요" } ] } }
```

- `fields[].path`는 요청 JSON 경로다. 편집기는 그 칸 아래에 `message`를 그대로 띄운다. 프리셋을 펼친 결과에서 나온 오류는 사용자가 고칠 칸이 없어 `trigger_spec`에 단다.
- 오류는 첫 오류에서 멈추지 않고 모은다 — 편집기가 칸마다 한 번에 띄운다.
- 칸 코드: `REQUIRED` · `INVALID_TYPE` · `INVALID_VALUE` · `OUT_OF_RANGE` · `PAST` · `IMMUTABLE` · `UNKNOWN_INSTRUMENT` · `NOT_HELD` · `MARKET_NOT_SUPPORTED` · `CADENCE_NOT_ALLOWED` · `OPERATOR_NOT_ALLOWED` · `TRANSFORM_NOT_ALLOWED` · `MODIFIER_NOT_ALLOWED` · `UNIT_MISMATCH` · `SCOPE_MIXED` · `LAG_NOT_ALLOWED` · `DATA_UNAVAILABLE`.
- **남의 것과 없는 것을 구분하지 않는다.** 구분하면 남의 알림 ID가 있는지가 응답 차이로 드러난다. 스코프 규칙은 [common.md](common.md)의 "사용자 스코프·소유 검사"다.

### 8.4 중복 경고

같은 사용자에게 **같은 종목 · 같은 평가 시점 · 같은 해시**를 가진 감시 중 알림이 있으면 미리보기가 `duplicate_of`에 가장 먼저 만든 그 알림의 ID를 싣는다. 저장은 막지 않는다. 프리셋으로 만든 것과 직접 조건으로 만든 것도 펼친 결과가 같으면 중복이다(4.9). 수정 중인 알림의 미리보기는 요청의 `alert_id`로 자기 자신을 검사에서 뺀다. 꺼졌거나 끝났거나 만료된 알림은 중복으로 보지 않는다.

### 8.5 삭제

알림은 소프트 삭제한다. 삭제는 `version`을 올리고 알림 대상 종목을 갱신한다. 삭제된 알림은 평가 · 목록 · 중복 검사 · 상세 조회에서 빠진다.

**울림 기록은 남는다.** 울린 알림 목록 · 새로 울린 알림 · 울린 알림 상세는 삭제된 알림의 울림을 `삭제된 알림` 표시와 함께 그대로 보인다. 이미 받은 푸시를 눌렀을 때 내용이 사라져 있으면 무엇이 울렸는지 알 방법이 없다.

### 8.6 종목 검색

`GET /instruments`는 알림 전용이 아니다. 종목을 고르는 모든 화면이 쓰는 앱 공통 검색이다.

```json
// GET /instruments?q=삼성
{ "rows": [ { "id": "…", "label": "삼성전자", "symbol": "005930", "market": "KR", "held": true,
              "last_close": 63010, "last_close_on": "2026-09-25" } ] }
```

| 요청 | 결과 |
|---|---|
| `q`가 비고 `held=true` | 보유 종목 전부, 이름순 |
| `q`가 비고 `held`가 없거나 거짓 | 빈 목록 |
| `q`가 있음 | 이름 또는 종목코드에 검색어가 든 종목, 최대 30건. 정렬은 ① 종목코드 완전 일치(대소문자 무시) ② 이름이 검색어로 시작 ③ 그 밖(종목코드 일부 일치 포함), 각 단계 안에서 이름순 |

- 이름순은 DB 정렬 설정과 무관하게 Latin이 한글보다 앞서고 한글은 가나다순이다(`삼성SDI`가 `삼성전자`보다 위).
- 검색어의 `%` · `_` · `\`는 글자 그대로 찾는다.
- 예수금 종목(`asset_class = CASH`)과 상장폐지 종목은 검색 결과와 보유 종목 구역에 내리지 않는다.
- `held`는 로그인한 사용자의 최신 스냅샷(확정 전 포함, 포트폴리오 종목 화면과 같은 날짜)에서 연동이 유효한 계좌에 그 종목이 있는지다([portfolio.md](portfolio.md)의 "보유 중 판정"). 스냅샷이 없으면 보유 종목이 없다.
- `label`은 종목 마스터의 이름이다(미국 종목은 영문명). `last_close`는 그 종목의 가장 최근 수정주가 일봉 종가이고 `last_close_on`은 그 거래일이다. 일봉이 없으면 둘 다 null이다. 새 알림의 가격 도달 칸을 채우는 데 쓴다.

## 9. 검증 규칙·불변식

저장 전 반드시 통과하는 규칙이다. 조건은 JSON이라 DB가 무결성을 보장하지 않으므로 이 관문이 사실상의 계약이다. 미리보기와 저장이 같은 규칙을 쓰고, 오류는 모두 모아 돌려준다.

**공통**

| 필드 | 규칙 |
|---|---|
| `instrument_id` | 종목 마스터에 있고, 예수금 종목이 아니며, 상장폐지되지 않음 |
| `name` | 앞뒤 공백을 뗀 뒤 1~40자 |
| `cadence` · `notify_mode` · `trigger_type` | 열거값 |
| `notify_mode = COOLDOWN` | 장중이고 `cooldown_min`이 5~1440. 그 밖의 알림 방식에는 `cooldown_min`이 없어야 한다 |
| `expires_at` | 비어 있거나 지금 이후 |
| 수정 | 종목과 `trigger_type`은 바꿀 수 없다(`IMMUTABLE`) |
| 내 보유 지표를 쓰는 알림 | 종가. **만들 때** 최신 스냅샷(확정 전 포함)의 연동 중인 계좌에서 보유 중(`NOT_HELD`). 수정·다시 켜기는 보유를 묻지 않는다 — 판 종목은 확인 불가(미보유)로 남는다 |
| 데이터 닫힘 | 닫힌 평가 시점 · 지표 · 프리셋을 새로 넣으면 `DATA_UNAVAILABLE`. 수정은 저장된 알림에 없던 것만 거부한다(4.11) |

**직접 조건**

| 규칙 |
|---|
| `conditions` 1~5개 |
| 지표가 카탈로그에 있고, 종목 시장이 지표 `markets`에 든다 |
| 지표 기간이 카탈로그 범위 안. 카탈로그에 없는 설정은 거부 |
| 변형이 지표별 허용 변형이고 n이 그 범위 안(3.3). 요청에 `lag`가 있으면 거부 |
| 연산자가 왼쪽과 오른쪽 지표 모두의 허용 연산자. 교차는 오른쪽이 지표일 때만 |
| `right.const`는 유한한 숫자. 오른쪽이 지표면 같은 규칙을 다시 적용하고 두 쪽 단위가 같다(변형 뒤 단위) |
| 장중이면 왼쪽은 장중 왼쪽 지표의 `identity` |
| 유지 방식: 장중은 비어 있거나 `persist_min` 5~60, 종가는 비어 있거나 `streak` 1~20. 교차와 내 보유 지표에는 붙일 수 없다 |
| 내 보유 지표는 종가에만, 시장 지표와 한 알림에 섞지 않는다(`SCOPE_MIXED`) |

**프리셋**

| 규칙 |
|---|
| `preset_key`가 카탈로그에 있다 |
| `cadence`가 프리셋 `cadences`에 들고, 종목 시장이 `markets`에 든다 |
| `params`가 `param_schema`를 만족한다 — 필수 칸, 정수·숫자·선택지, 범위 |
| 수익률 도달은 수익이면 양수, 손실이면 음수 |
| 펼친 결과가 직접 조건 규칙을 통과한다 |

**런타임 불변식**

| 규칙 |
|---|
| 평가 대상은 감시 중이고 삭제되지 않은 알림뿐이다 |
| 평가 상태 반영은 읽을 때의 `version` · 평가한 데이터 시점이 그대로이고, 데이터 시점이 앞으로 가며, 유효기간이 지나지 않았을 때만 한다 |
| 사용자 변경·만료·한 번만 종료는 같은 트랜잭션에서 `version`을 올리고 알림 대상 종목을 갱신한다. 평가기는 `version`을 알림 규칙과 같은 조회에서 읽는다 |
| 울림은 (알림, 데이터 시점)마다 최대 하나다. 이미 울린 시점을 다시 평가하면 울리지 않고 엣지 기준을 거짓으로 둔다 |
| 평가한 데이터 시점이 빈 알림은 최신 완료 시점 하나만 평가한다 |
| 상태 갱신 · 울림 기록 · 발송 행 · 한 번만 종료는 한 트랜잭션이다 |
| 확인 불가는 울리지 않고 엣지 기준을 바꾸지 않는다 |
| AND 결합은 거짓이 먼저, 그다음 확인 불가다 |
| 해시가 다르면 울리지 않고 기준을 다시 잡는다. 결과가 확인 불가면 옛 해시를 둔다 |
| 계열은 있는 봉으로 만든다. 연속·교차 구간의 데이터 누락일과 현재 봉 부재만 확인 불가다 |
| 허용 지연을 넘은 장중 스냅샷은 평가하지 않는다 |
| 일시중지 동안 결과 · 엣지 기준 · 평가한 데이터 시점을 바꾸지 않는다(처음 건너뛴 시각만 쓴다). 종가로 평가 중인 알림의 해시는 원래 평가 시점으로 구한다. 다시 열린 뒤 처음 건너뛴 시각이 있는 알림은 최신 확정 시점 하나만 평가하고, 그 시점이 오늘 전 마지막 거래일보다 이르면 기다린다 |
| 발송 행은 한 복제본만 집고, 결과는 집을 때의 시도 횟수 그대로인 발송 중 행에만 쓴다 |
| 세션이 끝났거나 다른 사용자에게 옮겨진 기기에는 보내지 않는다 |

소유 규칙(모든 조회·변경은 로그인한 사용자로 스코프, 남의 것과 없는 것은 같은 404, 기기 토큰이 다른 사용자·세션에 있으면 지금 사용자·세션으로 옮김)은 [common.md](common.md)의 "사용자 스코프·소유 검사"를 따른다.

## 11. 범위 밖

일부러 뺀 것이다.

- **OR · 불리언 트리**: AND 평탄 목록만 둔다. OR는 "알림 2개"로 대신한다. 트리 UI는 일반 사용자에게 과하다.
- **지표 산술**: 두 지표의 비율·배수를 조건 안에서 계산하지 않는다. 자주 쓰는 비율은 지표로 정의한다(`volume_ratio` · `disparity` · `range_pct`).
- **한 알림 안에 장중·종가 섞기**: 한 알림은 평가 시점 하나다. 장중 조건이 확정된 종가 값을 오른쪽에 쓰는 것으로 대부분의 수요가 충족된다(4.1).
- **방해 금지 시간대**: 미국 장중 알림은 한국 시간 새벽에 울린다. 시간대별 푸시 억제를 두지 않는다 — 울림 기록은 남고 푸시만 늦출 대상이라 전달 계층에 붙이면 된다.
- **상태 전이 프리셋(L5)**: v1 프리셋은 모두 템플릿이다. 직접 조건으로 표현되지 않는 프리셋이 생기면 전용 평가기를 둔다.
- **레버리지 장기보유 괴리 경고**: 레버리지 여부·배율·기초지수·보유 시작일이 필요하고 넷 모두 원천이 없다.
- **보유기간 지표**: 보유 시작일 원천이 없다. 거래내역 확보 시작일은 보유 시작일이 아니다.
- **ETF 구성종목 가중 합산 수급**: 국내 ETF 구성종목 확보에 달려 있다.
- **MACD · 볼린저밴드 등 추가 기술지표**: 카탈로그에 지표를 더하는 일이며 스키마는 그대로다.
- **Android 푸시**: 개발 빌드로 바꾸면 서버 변경 없이 열린다(6.6).
- **메시지 브로커 발행**: 울림을 다른 시스템이 소비해야 할 때 울림 기록에서 내보낸다(6.1).
- **평가하지 못한 장중 구간의 기록**: 조건이 참이었는지 알 수 없어 기록할 내용이 없다(4.10).
- **종목 선택의 최근 조회**: 기기별 저장소가 필요하다.
- **검색 결과의 시가총액 순 정렬**: 종목 마스터에 시가총액이 없다.
- **미국 종목 한글명**: 원천을 확보하면 종목 마스터에 한글명을 더하고 서버가 검색 대상과 `label`에 넣는다. 앱은 바뀌지 않는다.
- **사용자당 알림 수 상한**: 두지 않는다. 평가 비용이 문제가 되면 들인다.
- **울림 · 발송 행 보관 기한**: 지우는 작업을 두지 않는다.
- **알림 공유 · 템플릿 마켓 · 백테스트**: 후속 과제다.

**알려진 한계** (위 본문에 흩어진 것을 모은다)

- 미국 종목은 수정주가 미반영을 가려낼 수단이 없다. 보정되지 않은 일봉이 오면 잘못 울릴 수 있다(4.10).
- 일봉이 하나도 없는 종목은 장중 등락률·거래량 배수가 확인 불가다(4.1). 장중 시세에 직전 종가를 함께 받는 방안은 데이터팀 계약의 미결 항목이다([data-contract.md](data-contract.md)의 "알려진 한계").
- 같은 푸시가 두 번 나갈 수 있다(6.3).
- 평가 한 주기의 소요와 발송 처리량은 측정하지 않았다(5.4 · 6.3).
- 미국 종목 울림의 울린 알림 상세 기준 표기가 국내 형식이다(2.3, 결정 필요).
