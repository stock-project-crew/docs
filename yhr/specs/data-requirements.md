# 데이터 요구사항 — 포트폴리오 종합 관리 · 매수·매도 타이밍 알림

- **기준일**: 2026-10-05
- **출처**: [포트폴리오 종합 관리 스펙](./portfolio-management/2026-07-28-portfolio-management-spec.md) v1 §5.1 · §7.7 · §11 / [매수·매도 타이밍 알림 스펙](./buy-sell-timing-alert/2026-07-12-buy-sell-timing-alert-spec.md) v1 §5.1 · §7 · §10.2 · §16
- **대상**: 데이터 담당. 이 문서만 보고 DDL과 적재 파이프라인을 쓸 수 있게 쓴다
- **이름**: 화면 이름은 [앱 정보 구조](./app-information-architecture.md) §6을 쓰고, 화면에 걸리지 않는 것은 동작 이름(스냅샷 생성 · 등급 판정 · 실현손익 산출 · ETF 분해 · 평가 · 발화 · 발송)으로 적는다

> **이 문서의 지위.** 두 기능이 데이터에 요구하는 것의 출처는 각 기능의 스펙이다. 이 문서는 그 요구를 테이블 단위의 한 형식으로 모은 것이다.
>
> - 스펙과 이 문서가 다르면 스펙이 맞고, 이 문서를 고친다.
> - 스펙의 데이터 요구를 고치는 변경은 같은 변경 안에서 이 문서도 고치고 기준일을 올린다.
> - 두 기능을 함께 놓고서야 정해지는 것(§8)은 이 문서가 먼저 정한다. 그 항목은 스펙에 반영될 때까지 §9 목록에 남고, 반영되면 목록에서 지운다.

## 1. 읽는 법

### 1.1 테이블 블록

테이블 하나가 한 블록이다. 블록은 항목표와 컬럼표로 이루어진다.

| 항목 | 뜻 |
|---|---|
| 소유 | 그 테이블에 쓰는 팀. `데이터` · `백엔드` · `양방향` |
| 그레인 · PK | 한 행이 무엇인가 |
| 컬럼 | 이름 · 타입 · null 허용 · 비고 (컬럼표) |
| 범위 | 어느 시장 · 어느 종목 · 어느 기간 |
| 갱신 주기 | 얼마나 자주 바뀌나 |
| 도착 시점 | 백엔드가 읽는 위치(§2.2)에 언제까지 있어야 하나 |
| 완료 신호 | 적재가 끝났음을 무엇으로 알리나 |
| 충족 안 될 때 | 데이터가 없거나 늦거나 틀렸을 때 **기능이 어떻게 동작하나** |
| 쓰는 기능 | `포트폴리오` · `알림` · `공용` |
| 현재 상태 | 아래 네 값 중 하나와 그 내용 |

**현재 상태**

| 값 | 뜻 |
|---|---|
| **합의** | 팀 경계 회의에서 결정됐다 |
| **부분** | 일부는 정해졌고(합의 또는 데이터 설계가 이 요구와 일치) 나머지가 열려 있다 |
| **미결** | 이 문서가 요구를 정했고 데이터 담당의 답을 기다린다 |
| **어긋남** | 데이터 설계나 구현이 이 요구와 충돌한다 |

합의와 구현이 다를 수 있다. 그때는 `합의 · 구현 어긋남(…)`처럼 한 칸에 둘 다 적는다. `Q`·`N` 번호는 §10 질문 목록이다.

### 1.2 이 문서가 다루지 않는 것

- 원천 선택과 수집 방법(어느 API·파일을 어떻게 부르는가). 데이터 담당이 정한다.
- 레이크 내부 모델(Bronze / Silver / Gold 구성). 백엔드가 읽는 모양만 정한다.
- 백엔드 안에서만 쓰는 테이블(`position_line` · `alert` · `snapshot_run` 등). 단, 데이터가 읽는 백엔드 테이블은 §7에 둔다.

## 2. 공통 규칙

### 2.1 경계 — 기관 고유성이 사라지는 지점

원천마다 다른 응답을 흡수해 **기관 중립적인 공통 모양**으로 만드는 것까지가 데이터, 그 위에 도메인 규칙(평단 · 기업행위 상태 보정 · 캐리포워드 · 등급 판정 · 지표 계산 · 평가 · 발화)을 얹는 것이 백엔드다.

**사용자 개념은 백엔드 안에만 있다.** 백엔드가 읽는 데이터 산출물에 `user_id`가 없다. 계좌는 백엔드가 발급하는 불투명 문자열 `account_ref`로만 식별하고, 그 계좌가 누구 것인지는 백엔드가 해석한다. 알림 대상 종목 목록(`alert_watchlist`)도 종목만 담고 누가 알림을 걸었는지는 담지 않는다. 소유를 경계 너머로 넘기면 두 팀이 같은 사실을 각자 들고 있게 되고, 스코프가 어느 쪽에서 걸리는지가 흐려진다.

**지표는 백엔드가 계산한다.** 사용자가 기간을 고르므로(RSI 9·14, 이동평균 5·20·60) 미리 계산한 고정 메뉴로는 알림 조건이 성립하지 않는다. 데이터가 줄 것은 지표가 아니라 **일봉 원재료**다.

### 2.2 놓이는 곳과 경로

**백엔드는 레이크를 읽지 않는다.** 백엔드가 읽는 테이블은 전부 앱 DB(PostgreSQL)의 **`data` 스키마**에 있어야 한다. 테이블마다 갈리는 것은 그곳까지 오는 경로다.

| 경로 | 테이블 | 이 경로인 이유 |
|---|---|---|
| **직접 적재** — 레이크를 거치지 않는다 | 장중 스냅샷 · `market_data_run` · `collection_run` | 장중 평가는 분 단위라 레이크 → 리버스ETL 지연을 견디지 못한다. `collection_run`은 백엔드도 쓰는 양방향 큐다 |
| **리버스ETL** — 레이크에서 되돌려 채운다 | `instrument` · `dim_market_calendar` · `corporate_action` · 일봉 · 수급 · `etf_constituent` · `etf_coverage` · `ca_coverage` · `fx_rate` · `cln_*` · `cln_*_coverage` | 일 단위 이상이라 홉 하나의 지연을 감당한다 |
| **레이크 전용** — 백엔드가 읽지 않는다 | `raw_*` · `mart_*` | — |

| 위치 | 권한 |
|---|---|
| `data` 스키마 | 데이터가 쓴다. 백엔드는 **읽기만** 한다. 예외는 `collection_run` 하나이며, 백엔드는 정해진 컬럼에만 쓴다(§6.10) |
| `app` 스키마 | 백엔드가 쓴다. 데이터는 `alert_watchlist`를 읽는다(§7.1). 그 밖의 백엔드 테이블은 CDC로 읽는다(§7.2) |

`mart_*` 등 레이크 전용 산출물은 리버스ETL · ClickHouse 어디로도 앱에 내보내지 않으며, 사용자 화면이 그 값을 읽지 않는다. 백엔드 화면과 같은 숫자를 계산하는 마트가 화면으로 나가면, 둘이 어긋날 때 어느 쪽이 맞는지 판정할 기준이 없다.

### 2.3 키와 제약

- **종목 키는 `instrument_id`(uuid)다.** `symbol`은 표시·검색용이며 `(symbol, market)`이 유일하지 않으므로 식별에 쓰지 않는다.
- **소유 팀이 다른 테이블 사이에는 FK를 걸지 않는다.** 교차 FK는 두 팀의 배포 순서를 묶는다. 고아 키는 정합성 검사가 잡는다.
- 열거형은 `text` + CHECK로 둔다. 값 목록은 블록의 비고에 적는다.

### 2.4 시각과 날짜

- **거래일(`date`)은 그 시장의 현지 날짜다.** 미국 장은 한국 시간으로 자정을 넘기므로, 미국 종목의 거래일은 미국 현지 날짜로 판정한다.
- 시각은 `timestamptz`로 둔다.
- "KR 영업일"은 `dim_market_calendar`에서 `market = KR`이고 `is_trading_day = true`인 날이다.

## 4. 공용 테이블

### 4.1 `instrument` — 종목 마스터

| 항목 | 내용 |
|---|---|
| 소유 | 데이터 |
| 그레인 · PK | 종목 1행 · PK `instrument_id` |
| 범위 | 아래 다섯 집합의 **합집합**. ① 국내 상장 주식(우선주 포함)·ETF 전체 ② 미국 NYSE·NASDAQ 상장 보통주·ETF ③ `cln_balance`에 나타난 모든 종목 ④ `etf_constituent`의 구성종목 중 시장이 KR·US인 것 ⑤ 예수금 의사종목 2행(`KRW 예수금` · `USD 예수금`, `asset_class = CASH`). 상장폐지 종목도 행을 지우지 않는다 |
| 갱신 주기 | KR 영업일 1회 |
| 도착 시점 | 매 KR 영업일 **KR 개장 전**. 그 시점까지 공표된 KR·US 신규상장·변경을 반영한다 — 당일 신규상장 종목에 장중 알림을 걸 수 있어야 한다 |
| 완료 신호 | 없음. 늦으면 직전 상태로 동작한다 |
| 충족 안 될 때 | **비어 있으면** 종목 선택 화면이 `종목 마스터 비어 있음`이 되고 알림을 만들 수 없다. 포트폴리오 화면은 종목명·분류를 채우지 못하고 미매칭을 안내한다. **한 종목이 빠지면** 그 종목의 보유 라인이 미매칭이 되고, 그 종목에 걸린 알림은 `확인 불가 · 종목 정보 없음`(`INSTRUMENT_UNKNOWN`)이 된다. **상장폐지 종목을 지우면** 그 종목의 과거 보유분이 과거 총자산에서 빠진다 — 지우지 않는다. **갱신이 늦으면** 신규상장 종목이 검색되지 않는다 |
| 쓰는 기능 | 공용 — 포트폴리오는 축(종목·섹터·시장·통화·자산군·레버리지)의 원천으로, 알림은 종목 검색과 시장 판정으로 쓴다. 검색(`GET /instruments`)은 앱 공통이다 |
| 현재 상태 | **부분.** 합의: 알림 범위 ①② · 검색 가능한 형태 · 거래일 1회 갱신(알림 안건 6). 미결: 노출 객체명 `data.instrument` 뷰와 컬럼 목록(Q4) · `sector_source`(Q5) · 상장폐지 종목 유지(Q6) · ISIN 미매칭 처리(Q16) · 범위 ③④⑤와 `delisted_on`(N6). 구현: 운영 DB에 비어 있다. 데이터 쪽 SCD2 마스터(`dim_instrument`)가 미착수이고, 클러스터에는 백엔드가 만든 임시 미러가 `public`에 있다 — 실제 표가 `data`에 채워지면 지운다 |

| 컬럼 | 타입 | null | 비고 |
|---|---|---|---|
| `instrument_id` | uuid | N | PK. 같은 종목이면 티커가 바뀌어도 유지한다. 백엔드의 모든 종목 참조(`position_line` · `alert` · `alert_watchlist`)가 이 값이다 |
| `isin` | text | Y | 국내·미국 공통 키. 종목 발견 시점과 ISIN 매칭 시점이 달라 null일 수 있다. CASH 행은 null |
| `symbol` | text | N | 종목코드 / 티커. 표시·검색용. 유일하지 않다 |
| `name` | text | N | 화면 종목명. 검색 대상 |
| `asset_class` | text | N | `STOCK` · `ETF` · `CASH` |
| `market` | text | N | `KR` · `US` |
| `currency` | text | N | `KRW` · `USD` |
| `sector` | text | Y | 원천 라벨 그대로. 분류가 없으면 null(화면은 `미분류`) |
| `sector_source` | text | Y | `YFINANCE` · `NAVER_WICS`. 두 분류 체계가 한 섹터 축에 섞이므로 화면이 체계를 밝히려면 출처가 필요하다 |
| `is_leveraged` | boolean | Y | 원천 확보 전 null. null이면 레버리지 축이 비활성이다 |
| `delisted_on` | date | Y | 상장폐지일. null이면 상장 중. 검색은 null인 행만 내리고, 집계는 이 값과 무관하게 조인한다 |

- **검색.** 이름·종목코드 부분 일치(`삼성` → `삼성전자`, `0059` → `005930`)를 지원하는 인덱스를 데이터가 함께 관리한다. 추천은 `name`·`symbol`에 `pg_trgm` GIN 인덱스다. 인덱스 변경은 검색 성능을 바꾸므로 백엔드와 맞춘다.
- **SCD2 이력 컬럼(`instrument_sk` · `valid_from` · `valid_to` · `is_current`)을 노출하지 않는다.** `data.instrument`는 현재 버전만 위 컬럼으로 보여주는 뷰다. 백엔드 쿼리에 SCD2 개념이 들어오지 않고, 백엔드 계약 테스트가 컬럼 목록을 고정하고 있다.
- **상장폐지는 버전의 종료가 아니다.** 폐지된 종목도 마지막 버전을 현재 버전으로 남기고 `delisted_on`만 채운다.
- 범위 ④의 구성종목 중 KR·US로 분류할 수 없는 종목(다른 거래소 상장 등)은 행을 만들지 않는다. 그 비중은 ETF 분해에서 `기타` 버킷으로 간다.
- 범위가 합집합인 이유는 §8.1.

| 항목 | 내용 |
|---|---|
| 소유 | 데이터 |
| 그레인 · PK | 종목 × 기업행위 1행 · PK `(instrument_id, ex_date, type)` |
| 범위 | `instrument`의 KR·US 주식·ETF. 기간은 `ca_coverage`가 덮는 구간 |

| 완료 신호 | 없음. 일봉 쪽은 `DAILY_BAR` 완료 신호가 이 테이블의 반영을 포함한다 |
| 충족 안 될 때 | 포트폴리오: 커버리지 밖이면 `ca_unknown`이 서고 실현손익·종목 상세에 기업행위 경고가 붙는다. **커버리지 안인데 행이 빠지면** 틀린 평단·실현손익이 경고 없이 `신뢰`로 나간다 — 가장 나쁜 경우다. 알림: 일봉이 보정되지 않아, 국내는 `확인 불가 · 가격 보정 대기`로 평가를 보류하고 미국은 분할 당일 이동평균 교차·거래량 급증·RSI 알림이 **잘못 울릴 수 있다** |

| 현재 상태 | **부분.** 데이터 설계가 스키마를 스펙과 일치시켰다. 0행이다 — 원천(DART 등)이 미확정이고 데이터 쪽 최우선 미결이다. 보정 범위(배당 제외)와 같은 적재 단위 계약은 미결(N7 · N8) |

| 컬럼 | 타입 | null | 비고 |
|---|---|---|---|
| `instrument_id` | uuid | N | |
| `type` | text | N | `SPLIT`(분할·병합) · `RIGHTS`(증자) · `MERGER`(합병) |
| `ratio` | decimal(18,8) | N | **행위 후 주식 수 ÷ 행위 전 주식 수.** 2:1 분할은 `2`, 5:1 병합은 `0.2`. 백엔드는 `수량 × ratio`, `평단 ÷ ratio`로 상태를 고친다 |
| `ex_date` | date | N | 권리락·분할 기준일. 이 거래일 봉부터 새 주식 수 기준이다 |

- 일봉 가격 보정은 **주식 수만 바꾸는 행위**(분할·병합·무상증자)에만 적용하고 배당은 보정하지 않는다. 국내 증권사 수정주가와 같은 기준이라, 알림 지표가 사용자가 보는 차트와 가깝다.
- 백엔드는 과거 체결을 다시 쓰지 않고 `ex_date` 시점에 상태만 고친다. 그래서 백엔드에는 보정된 가격 계열이 아니라 **이 원본**이 필요하다(§8.4).

### 5.1 `adjusted_price_daily` — 수정주가 일봉

| 항목 | 내용 |

| 소유 | 데이터 |
| 그레인 · PK | 종목 × 거래일 1행 · PK `(instrument_id, date)` |

| 현재 상태 | **합의 · 구현 어긋남.** 합의: `instrument_id` 키 · 300거래일 · 보정 계열은 국내부터 · 미국은 보유 종목과 알림 대상 종목 · 미국 도착은 다음 미국 장 개장 전(알림 안건 1, 데이터 재확인 필요). 구현: 레이크에만 있고 `data`에 없다. 키가 `symbol`이다. 조정계수가 전부 `1.0`이다(기업행위 원천 없음). 미국은 수집하지 않는다. 미결: 테이블명(N1) · US 범위 ③(N4) · 백필 시점(N5) · 미국 도착 시점 재확인(N14) |

| 컬럼 | 타입 | null | 비고 |
|---|---|---|---|
| `instrument_id` | uuid | N | |
| `date` | date | N | 시장 현지 거래일. **그 종목이 거래된 날만** 행이 있다 — 거래정지일은 행이 없다 |
| `open` · `high` · `low` · `close` | decimal(20,4) | N | 보정 계열. 종목 통화 단위 |
| `volume` | decimal(20,4) | N | 보정 거래량(분할 비율을 곱하므로 소수가 생길 수 있다) |
| `adj_factor` | decimal(18,8) | N | `보정 가격 = 원시 가격 × adj_factor`. 그 봉 이후 기업행위가 없으면 `1`. 보정 근거를 `corporate_action`과 대조할 수 있게 둔다 |

- **왜 300거래일인가.** 알림 카탈로그 상한 안에서 평가기가 읽는 봉 수의 최대가 275다(RSI 계산 창 250 + 변화량 5 + 교차 1 + 연속 19).
- **왜 보정 계열인가.** 보정되지 않은 계열로 지표를 계산하면, 액면분할 당일 그 종목의 이동평균 교차·거래량 급증·RSI 알림이 한꺼번에 울린다. 국내는 가격제한폭(±30%)을 넘는 봉으로 이를 감지할 수 있지만 미국은 감지 수단이 없다.
- **거래정지일에 행을 만들지 않는다.** 알림은 그 종목이 거래된 봉으로 계열을 만든다. 영업일인데 현재 봉이 없으면 `거래 없음`으로 판정하므로, 직전 값으로 채운 행은 정지를 가린다.
- 보정 이력은 데이터만 쓴다. 지표(`mart_technical_daily` 등)를 레이크에 만들더라도 백엔드는 읽지 않는다(§2.1, N9).
- 미국 범위가 전 종목이 아닌 이유는 원천 호출 한도다. 알림이 걸린 종목과 보유 종목만 필요하다.
- 범위 ③과 구성종목 종가에 대한 판단은 §8.5.

| `institution_net_buy_krw` | decimal(20,0) | N | 기관 순매수 금액(원). 순매도는 음수 |

- **장 마감 후 확정치만 넣는다. 장중 잠정치로 채우지 않는다.** 잠정치와 확정치의 부호가 갈리면 "연속 순매수"가 울렸는데 확정치로는 순매도인 날이 생기고, 울린 알림은 되돌릴 수 없다. 확정치가 아직 없으면 행을 만들지 않는다.
- **왜 30거래일인가.** 연속 일수 최대 20 + 순매수 전환 판정 1, 그리고 수급 윈도우 변형(최대 10봉)의 여유분이다.

### 5.3 `intraday_quote` — 장중 스냅샷

| 항목 | 내용 |
|---|---|
| 소유 | 데이터 |
| 그레인 · PK | 종목 × 스냅샷 시각 1행 · PK `(instrument_id, snapshot_at)` |
| 범위 | `alert_watchlist`에서 `intraday = true`인 종목. KR · US |
| 갱신 주기 | 장중(`open_at` ~ `close_at`) **5분 이하** 간격으로 한 벌씩 |
| 도착 시점 | 각 벌이 `snapshot_at` + 허용 지연 안에 `data`에 있어야 한다. 허용 지연은 **KR 10분 · US 20분**(미국은 15분 지연 시세를 허용) |
| 완료 신호 | 한 벌마다 `market_data_run`(`market`, `INTRADAY_QUOTE`, `snapshot_at`) |
| 충족 안 될 때 | 장중 알림이 평가되지 않고 알림 목록 상단에 `데이터 지연` 배너(`MARKET_DATA_DELAYED`)가 뜬다. 허용 지연을 넘은 벌은 도착해도 평가하지 않는다 — "10시에 7만원을 넘었다"를 오후에 받으면 지금 가격으로 오해된다. 벌 사이 간격이 허용 지연을 넘으면 `N분 지속` 조건이 `확인 불가`가 된다. 종가 알림은 영향이 없다. 이 데이터를 아예 확보하지 못하면 장중 평가를 닫고 모든 알림을 종가로만 평가한다 |
| 쓰는 기능 | 알림 |
| 현재 상태 | **합의 · 미착수.** 합의: 국내·미국 · `alert_watchlist` 기반 · 앱 DB 직접 적재 · 5분 · 당일분 보관 · 허용 지연(알림 안건 3). 미결: 테이블명(N1) · `snapshot_at`의 정의(N3) |

| 컬럼 | 타입 | null | 비고 |
|---|---|---|---|
| `instrument_id` | uuid | N | |
| `snapshot_at` | timestamptz | N | **그 벌이 나타내는 시세 기준 시각.** 수집 시각이 아니다 — 원천이 15분 지연 시세면 15분 이른 시각이다. 한 벌의 모든 행이 같은 값을 갖고, 그 벌의 `market_data_run.as_of`와 같다 |
| `price` | decimal(20,4) | N | 현재가. 종목 통화 단위. 원시 가격이다 — 일봉 보정 계열은 가장 최근 주식 수 기준으로 과거를 고치므로 당일 원시 가격과 같은 척도다 |
| `cum_volume` | decimal(20,0) | N | 당일 누적 거래량 |

- 인덱스: `(snapshot_at)` — 보관 기간이 지난 행을 지우고 한 벌을 읽는 데 쓴다.
- **보관**: 최소 당일분. 미국은 현지 거래일 기준이다. `N분 지속` 판정이 당일 스냅샷을 다시 읽는다.
- **왜 직접 적재인가.** 몇 분 단위 평가가 레이크 → 리버스ETL 경로의 지연을 견디지 못한다.
- **왜 목록 종목만인가.** 전 종목을 5분마다 받는 것은 원천 호출 한도로 성립하지 않을 수 있다. 목록 크기는 사용자 수와 장중 알림 수에 비례한다.
- **`snapshot_at`을 시세 기준 시각으로 두는 이유.** 허용 지연과 `N분 지속`은 "그 가격이 언제의 가격인가"로 판정한다. 수집 시각으로 두면 15분 지연 시세가 방금 시세로 보여 허용 지연 판정이 뜻을 잃는다.

### 5.4 `market_data_run` — 시장 데이터 완료 신호

| 항목 | 내용 |
|---|---|
| 소유 | 데이터 |
| 그레인 · PK | 시장 × 데이터 종류 × 데이터 시점 1행 · PK `(market, kind, as_of)` |
| 범위 | KR: `INTRADAY_QUOTE` · `DAILY_BAR` · `DAILY_FLOW`. US: `INTRADAY_QUOTE` · `DAILY_BAR` |
| 갱신 주기 | 해당 데이터의 적재마다 |
| 도착 시점 | 해당 데이터의 도착 시점과 같다(§5.1 ~ §5.3) |
| 완료 신호 | 이 테이블 자체 |
| 충족 안 될 때 | 신호가 없으면 백엔드는 그 데이터를 기다리고 평가하지 않는다. 어떤 거래일의 신호가 `DONE`이 되기 전에 다음 거래일의 같은 종류가 `DONE`이 되면, 그 거래일은 그 데이터 없이 평가한다(`확인 불가 · 데이터 없음`). 기대 시각보다 늦으면 `데이터 지연` 배너가 뜬다. **일부만 적재된 상태에서 `DONE`을 쓰면** 빠진 종목이 `거래 없음`으로 오판되고 연속 N거래일 조건이 끊긴다 |
| 쓰는 기능 | 알림 |
| 현재 상태 | **부분.** 합의: 테이블 하나 · 종류별 행 · 백엔드 읽기만(알림 안건 4). 미결: `DONE`의 기준점을 앱 DB 반영 완료로 두는 것(N2). 미구현 |

| 컬럼 | 타입 | null | 비고 |
|---|---|---|---|
| `market` | text | N | `KR` · `US` |
| `kind` | text | N | `INTRADAY_QUOTE` · `DAILY_BAR` · `DAILY_FLOW` |
| `as_of` | timestamptz | N | 장중은 그 벌의 `snapshot_at`, 일별은 그 거래일의 `dim_market_calendar.close_at` |
| `state` | text | N | `RUNNING` · `DONE` · `FAILED` |
| `finished_at` | timestamptz | Y | `DONE`·`FAILED`가 된 시각 |

- **`DONE`의 뜻**: 그 시장의 대상 종목 **전체**가 그 시점까지 **`data` 스키마에 반영됐다.** 레이크 적재가 끝난 시점이 아니다. 리버스ETL을 거치는 일봉·수급은 리버스ETL이 끝난 뒤에 쓴다.
- **상태 전이**: `RUNNING → DONE`, `RUNNING → FAILED`, `FAILED → RUNNING`(재시도). `DONE`이 된 행은 바꾸지 않는다. 기업행위로 과거 봉을 다시 쓸 때는 새 신호가 필요 없다 — 백엔드는 평가할 때마다 이력을 다시 읽는다.
- `FAILED`는 `DONE`이 아닌 것으로 본다.
- **종류마다 행을 나누는 이유.** 일봉과 수급은 도착 시각이 다르다. 하나로 묶으면 가장 늦는 데이터가 가격 알림까지 붙잡는다.
- 포트폴리오의 `collection_run`과 합치지 않는 이유는 §8.3.

### 6.1 `etf_constituent` — ETF 구성비중

| 항목 | 내용 |
|---|---|
| 소유 | 데이터 |
| 그레인 · PK | 기준일 × ETF × 최종 구성종목 1행 · PK `(as_of, etf_instrument_id, underlying_instrument_id)` |
| 범위 | `cln_balance`에 나타난 ETF 중 구성종목 원천이 있는 것. 현재 원천은 미국(SPDR)뿐이며 국내 ETF는 미분해다 |
| 갱신 주기 | 운용사 파일이 갱신될 때마다 |
| 도착 시점 | 운용사 파일 공개 후 **다음 KR 영업일의 보유 스냅샷 생성 전** |
| 완료 신호 | 없음. 늦으면 백엔드는 가장 최근 `as_of`를 쓴다 |
| 충족 안 될 때 | `etf_coverage`가 `UNAVAILABLE`(또는 행 없음)인 ETF는 분해하지 않고 ETF 한 행으로 남기며, 미분해 평가금액을 `CONSTITUENT_UNAVAILABLE` notice로 알린다. 늦게 오면 이전 구성비중으로 분해하고 `CONSTITUENT_AS_OF` notice가 기준일을 밝힌다 |
| 쓰는 기능 | 포트폴리오(비중 분석 · 종목별 렌즈 · 요약 자산 구성) |
| 현재 상태 | **부분.** 컬럼·PK·타입·평탄화를 데이터 설계가 수용했다. 미결: 깊이 제한과 순환 참조 처리(Q7). 비중 합이 100%를 넘는 경우는 백엔드가 정규화한다(스펙 반영 대기) |

| 컬럼 | 타입 | null | 비고 |
|---|---|---|---|
| `as_of` | date | N | 구성비중 파일 기준일 |
| `etf_instrument_id` | uuid | N | |
| `underlying_instrument_id` | uuid | N | **최종** 구성종목. 중첩 ETF는 이미 펼쳐져 있다 |
| `weight` | decimal(9,6) | N | 0~1 비율. ETF별 합이 1과 다를 수 있다 |

- **중첩을 펼쳐 한 겹으로 준다.** 재귀 분해 · 깊이 제한 · 순환 참조 차단 · 종목 매칭은 데이터가 끝낸다. 백엔드는 `ETF 평가금액 × weight` 한 겹 곱셈만 한다.
- `instrument`에 매칭되지 않는 구성종목(현금·선물·채권, 다른 시장 종목)은 행을 만들지 않는다. 그 몫은 합의 부족분으로 남아 `기타` 버킷이 된다.
- **비중 합은 원본 그대로 둔다.** 1을 넘거나 모자라도 데이터는 정규화하지 않는다. 정규화 방식은 도메인 판단이라 백엔드가 `Σ weight`로 나누고 잔차를 `기타`로 흡수한다.

### 6.2 `etf_coverage` — ETF 구성종목 커버리지

| 항목 | 내용 |

| 소유 | 데이터 |
| 그레인 · PK | ETF 1행 · PK `etf_instrument_id` |
| 범위 | `cln_balance`에 나타난 모든 ETF |
| 갱신 주기 · 도착 시점 | `etf_constituent`와 같다 |

| 쓰는 기능 | 포트폴리오 |
| 현재 상태 | **부분.** 데이터 설계가 백엔드 미러와 컬럼명·타입·상태값까지 일치한다. 합의 기록은 없다 |

### 6.3 `ca_coverage` — 기업행위 커버리지

| 항목 | 내용 |

### 6.4 `fx_rate` — 일별 환율

| 항목 | 내용 |
|---|---|
| 소유 | 데이터 |
| 그레인 · PK | 기준일 × 통화쌍 × 환율 종류 1행 · PK `(as_of, currency_pair, rate_type)` |
| 범위 | `USD/KRW`. 과거는 가장 이른 체결(`cln_trade_coverage.covered_from`의 최솟값)부터 |
| 갱신 주기 | KR 영업일 1회 |
| 도착 시점 | 그 KR 영업일의 **보유 스냅샷 생성 전** |
| 완료 신호 | 없음. 늦으면 폴백한다 |
| 충족 안 될 때 | 백엔드는 **그 날짜 이하의 가장 최근 행**으로 폴백하고 `fx_as_of`에 그 날짜를 기록한다. 화면의 적용 환율 표기(`FX_APPLIED`)가 그 날짜를 보여주고, KR 영업일 5일을 넘으면 `FX_STALE` 경고가 뜬다. 과거 범위가 모자라면 그 매입일의 외화 실현손익이 가장 이른 환율로 계산된다 |
| 쓰는 기능 | **포트폴리오 전용.** 알림은 원화로 환산해 비교하지 않는다 — 환율 변동만으로 조건이 참이 되면 그 알림은 종목이 아니라 환율을 감시하게 된다. 미국 종목의 기준값은 USD로 입력한다 |
| 현재 상태 | **부분.** 자릿수가 일치한다. 데이터 설계가 PK를 `rate_type`까지 넓혔고 그 의미가 데이터 쪽 미결이다(Q3) |

| 컬럼 | 타입 | null | 비고 |
|---|---|---|---|
| `as_of` | date | N | 고시일(KR) |
| `currency_pair` | text | N | `USD/KRW` |
| `rate_type` | text | N | `BASE`(매매기준율) · `CLOSE` · `TT_BUY` · `TT_SELL` |
| `rate` | decimal(18,6) | N | 1 USD당 원화 |
| `source` | text | N | 원천 |

- **백엔드는 한 `rate_type`만 쓴다.** 평가액 환산 · 매입원가 환산 · 매도 환산 세 곳이 같은 값을 써야 "원화 평가손익에 환손익이 들어가지 않는다"(양변을 같은 환율로 환산)가 성립한다. 추천은 `BASE`이며 확정은 Q3.
- **비영업일 행은 만들지 않아도 된다.** 폴백이 캘린더가 아니라 행의 존재로 정해진다.
- 실현손익은 매입일 환율과 매도일 환율을 각각 쓰므로 과거 전 구간의 일별 값이 필요하다.

### 6.5 `cln_balance` — 잔고

| 항목 | 내용 |

### 6.7 `cln_trade` — 체결

| 항목 | 내용 |

### 6.10 `collection_run` — 수집 실행

| 항목 | 내용 |
|---|---|
| 소유 | **양방향.** `data` 스키마에 두고, 이 테이블 하나에만 백엔드 쓰기 권한을 준다. 컬럼마다 쓰는 쪽이 정해져 있다(아래 표) |
| 그레인 · PK | 계좌 × 수집 실행 1행 · PK `run_id` |
| 범위 | 연동이 유효한(`DISCONNECTED`가 아닌) 모든 계좌 |
| 갱신 주기 | EOD 일배치는 KR 영업일마다 계좌당 1행. 수동 새로고침·재인증 완료 시 추가 행 |
| 도착 시점 | EOD 행은 KR 장 마감 후 당일 중에 `DONE`과 `silver_synced_at`까지 채워져야 한다. 수동 행은 픽업 주기(Q1)만큼 늦게 시작한다 |
| 완료 신호 | 이 테이블 자체. 백엔드는 `state = DONE`이고 `silver_synced_at`이 채워진 행을 그 계좌의 수집 완료로 본다 |
| 충족 안 될 때 | 그날 그 계좌의 최종 상태가 `DONE`이 아니면 그 계좌를 이월한다(§6.5). `REAUTH_REQUIRED`면 계좌 상태를 재인증 필요로 옮기고 계좌별 화면에 재인증 안내를 띄운다. 이 테이블이 없으면 수동 새로고침·계좌 연동·재인증이 성립하지 않는다 |
| 쓰는 기능 | 포트폴리오(계좌 연동·동기화, 스냅샷 생성의 시작 조건) |
| 현재 상태 | **어긋남.** 데이터 설계에 이 테이블의 스키마가 없고 서빙 매핑에서도 빠져 있다. 데이터 설계의 권한 규칙("백엔드는 `data` 스키마에 읽기만")이 백엔드의 요청 행 삽입을 막는다. 백엔드는 이 계약을 기다리는 스텁으로 동작 중이다. 미결: 스키마 · 상태 전이 · 픽업 주기 · 재시도 정책 · 쓰기 권한(Q1) |

| 컬럼 | 타입 | null | 쓰는 쪽 | 비고 |
|---|---|---|---|---|
| `run_id` | uuid | N | 행을 만든 쪽 | PK |
| `account_ref` | text | N | 행을 만든 쪽 | |
| `requested_by` | text | N | 행을 만든 쪽 | `SCHEDULE`(데이터가 만든 EOD 행) · `USER`(백엔드가 만든 수동 행) |
| `as_of` | date | N | 행을 만든 쪽 | 수집 대상 기준일. 백엔드는 실행 시각이 아니라 이 값으로 스냅샷 날짜를 정한다 — 자정을 걸쳐 끝난 수동 새로고침도 요청한 날짜에 기록된다 |
| `requested_at` | timestamptz | N | 행을 만든 쪽 | |
| `credential_ref` | text | Y | 백엔드 | 픽업 시 쓰는 단기 자격증명 참조. 값 자체가 아니다 |
| `state` | text | N | 데이터 | `REQUESTED` · `RUNNING` · `DONE` · `FAILED` · `REAUTH_REQUIRED` |
| `finished_at` | timestamptz | Y | 데이터 | |
| `failure_reason` | text | Y | 데이터 | 화면 문구가 아니라 코드(`SCRAPE_TIMEOUT` 등) |
| `silver_synced_at` | timestamptz | Y | 데이터 | 이 실행의 `cln_*`가 `data`에 반영된 시각 |

```
수동 새로고침   백엔드가 REQUESTED 행 삽입 → 데이터 잡이 집어 RUNNING
EOD 일배치      데이터 잡이 스스로 REQUESTED 행 생성
수집 종료       데이터가 cln_* 적재 후 DONE / FAILED / REAUTH_REQUIRED 로 전이
반영 종료       데이터가 리버스ETL 후 silver_synced_at 기록
스냅샷 생성     백엔드가 계좌별 최종 상태를 읽어 진행
```

- **두 팀이 같은 행을 쓰지만 같은 컬럼을 쓰지 않는다.** 행을 만드는 컬럼은 만든 쪽이, 진행 상태 컬럼은 데이터만 쓴다. 그래서 같은 행을 두 팀이 덮어쓰는 일이 생기지 않는다.
- **계좌 단위로 독립이다.** 한 계좌가 `FAILED`여도 나머지는 진행한다.
- `REAUTH_REQUIRED`인 계좌도 EOD 행을 만들고 즉시 같은 상태로 끝낸다. 그러면 이월 규칙이 "그날 최종 상태가 `DONE`이 아니면 이월" 하나가 된다. `DISCONNECTED` 계좌는 행을 만들지 않는다.
- 자격증명은 이 테이블의 `credential_ref`로만 전달한다. 데이터는 백엔드 계좌 테이블의 자격증명 컬럼을 읽지 않는다.
- 시장 데이터 완료 신호(`market_data_run`)와 합치지 않는 이유는 §8.3.

| 범위 | 삭제되지 않은 `ACTIVE` 알림이 하나 이상 걸린 종목 |
| 갱신 주기 | 알림이 생기거나 바뀔 때마다 백엔드가 즉시 갱신한다 |
| 도착 시점 | 데이터는 장중 스냅샷의 **매 벌 시작 시**와 **US 일봉 적재 시작 시**에 읽는다(N11). 새 장중 알림은 다음 벌부터, 새 미국 종목의 일봉은 다음 `DAILY_BAR`부터 수집된다 |
| 완료 신호 | 없음 |
| 충족 안 될 때 | 데이터가 읽지 못하면 새로 걸린 종목의 장중 스냅샷·미국 일봉이 오지 않아, 그 알림은 `데이터 지연` 또는 `확인 불가 · 데이터 없음`이 된다. 알림이 사라진 종목을 계속 수집하는 것은 무해하다 |
| 쓰는 기능 | 알림 |
| 현재 상태 | **합의 · 미착수.** 합의: 데이터가 읽을 수 있다 · 사용자 정보를 담지 않는다(알림 안건 3). 백엔드 테이블은 아직 없다. 미결: 읽는 주기(N11) |

| 컬럼 | 타입 | null | 비고 |
|---|---|---|---|
| `instrument_id` | uuid | N | PK |
| `market` | text | N | `KR` · `US` |
| `intraday` | boolean | N | 그 종목에 장중 알림이 있는가. 참인 종목만 장중 스냅샷 대상이다 |

이 테이블 때문에 데이터 파이프라인이 백엔드 테이블에 의존한다. 사용자 정보를 담지 않으므로 §2.1의 경계는 유지된다.

### 7.2 CDC로 읽는 백엔드 테이블

데이터는 백엔드 테이블을 CDC로 레이크에 가져가 대사·분석에 쓴다. 백엔드가 요구하는 것은 다음 셋이다.

| 항목 | 요구 | 이유 |
|---|---|---|
| `account.account_ref` | CDC 대상에 포함한다 | `cln_*`(`account_ref` 키)와 백엔드 스냅샷(`account_id` 키)을 대사하려면 둘을 잇는 매핑이 필요하다. 개인정보도 자격증명도 아니다 |
| 자격증명 · 개인정보 컬럼 | CDC에서 제외한다 — `account.credential_ref` · `app_user.email` · `app_user.password_hash` | 분석에 쓸 데가 없고 공격 표면만 넓힌다 |
| 레이크로 간 사용자 축 | 레이크 전용으로만 쓴다(§2.2) | 백엔드가 읽는 산출물에 `user_id`가 없어야 경계가 유지된다 |

`account_ref`의 성질: 백엔드가 계좌를 등록할 때 `기관코드 + 계좌번호`를 소금과 함께 해시해 발급한다. 계좌를 해제했다 다시 연동해도 같은 계좌면 같은 값이며, 생성 후 바뀌지 않는다. 계좌번호가 아니므로 계좌번호를 알아낼 수 없다.

**현재 상태: 부분.** 백엔드 `account` 테이블에 `account_ref`가 있다. 데이터 쪽 계좌 차원에 포함됐는지는 확인되지 않았다(Q2). 백엔드 테이블은 아직 `public` 스키마에 있고 `app` / `data` 분리는 시행 전이다.

## 8. 두 기능을 합쳐서 정한 것

### 8.1 종목 마스터 범위는 합집합이다

알림 범위(국내 상장 주식·ETF 전체 + 미국 NYSE·NASDAQ 보통주·ETF)는 포트폴리오가 필요로 하는 종목을 다 덮지 **않는다.**

| 알림 범위 밖인데 포트폴리오에 필요한 종목 | 예 |
|---|---|
| NYSE Arca · Cboe 상장 ETF | 미국 ETF 상당수(SPDR 다수 포함) |
| 미국 보통주가 아닌 상장 증권 | ADR(TSM 등) |
| ETF 구성종목 | 미국 ETF가 담은 종목 중 위 범위 밖의 것 |
| 예수금 의사종목 | `KRW 예수금` · `USD 예수금` |
| 상장폐지 종목 | 과거 보유 스냅샷의 종목 |

그래서 범위를 "보유 종목(`cln_balance`)과 구성종목(`etf_constituent`)을 더한 합집합"으로 정한다(§4.1). 데이터는 사용자를 몰라도 이 집합을 안다. 두 기능이 쓰는 컬럼은 겹치지만 부딪히지 않는다 — 포트폴리오는 `isin` · `asset_class` · `sector` · `is_leveraged`를, 알림은 검색 가능한 `name` · `symbol`과 `delisted_on`을 쓰고, `market` · `currency`는 둘 다 쓴다.

### 8.2 영업일 캘린더는 공용이다

포트폴리오는 보유 스냅샷을 KR 영업일에만 만들고, 시장별 가격 기준일과 환율 폴백 경고를 영업일로 판정한다. 그 판정 원천이 `dim_market_calendar`다. 알림이 정의한 컬럼(개장·마감 시각 포함)을 그대로 쓰며, 두 기능의 판정 규칙은 §4.2의 표 하나에 모은다. 판정 원천이 하나라 조기 폐장일·개장 지연일에 두 기능의 날짜가 어긋나지 않는다.

### 8.3 완료 신호는 둘이다 — `collection_run`과 `market_data_run`

둘 다 "데이터가 왔다"를 알리지만 하나로 합치지 않는다. 다음이 모두 다르다.

| | `collection_run` | `market_data_run` |
|---|---|---|
| 그레인 | 계좌 × 실행 | 시장 × 데이터 종류 × 데이터 시점 |
| 쓰는 쪽 | 양방향 — 백엔드가 요청하고 데이터가 진행 상태를 쓴다 | 데이터만 쓴다 |
| 방향 | 백엔드가 수집을 **요청**한다 | 데이터가 적재를 **알린다** |
| 상태 | `REQUESTED` · `RUNNING` · `DONE` · `FAILED` · `REAUTH_REQUIRED` | `RUNNING` · `DONE` · `FAILED` |
| 시점 타입 | date — 하루 한 벌의 스냅샷 기준일 | timestamptz — 장중 스냅샷은 분 단위 |
| `DONE`의 뜻 | 그 계좌 하나의 수집과 반영이 끝났다 | 그 시장 대상 종목 **전체**의 적재가 끝났다 |
| 실패의 단위 | 계좌마다 독립 — 실패 계좌만 이월 | 시장 단위 — 다음 시점이 오면 넘어감 |
| 민감 정보 | 자격증명 참조가 실린다 | 없다 |

합치면 한 테이블이 두 그레인을 갖게 되고, 상태 값의 절반이 행마다 뜻이 없으며, 자격증명 참조가 실리는 테이블에 시장 데이터 신호까지 섞여 권한을 좁힐 수 없다.

### 8.4 수정주가 — 포트폴리오는 원본, 알림은 보정 계열

같은 기업행위 사실을 두 기능이 다른 모양으로 받는다. **둘 다 필요하다.**

| | 받는 것 | 이유 |
|---|---|---|
| 포트폴리오 | `corporate_action` 원본 + `ca_coverage` | 가격이 아니라 **보유 수량과 평단 상태**를 고친다. 보정된 가격 계열로는 수량을 고칠 수 없다 |
| 알림 | 보정된 `adjusted_price_daily` | 지표를 가격 계열로 계산한다. 백엔드가 매 평가마다 기업행위를 적용하면 같은 계산이 평가기마다 반복된다 |

두 계산은 같은 사실에서 나온 서로 다른 결과다. 사실이 하나로 유지되도록 다음을 계약으로 둔다.

1. **일봉 보정은 `corporate_action`에 있는 행만으로 한다.** 다른 원천으로 보정하면 포트폴리오가 보는 사실과 알림이 보는 계열이 갈라진다.
2. **`corporate_action`의 새 행과 그로 다시 보정한 일봉은 같은 적재 단위로 반영되고, 그 뒤에 `DAILY_BAR` 완료 신호를 쓴다.**
3. **일봉에 `adj_factor`를 둔다.** 보정 결과를 `corporate_action`과 대조할 수 있다.

계약을 지켜도 두 기능의 판정이 다를 수 있으며, 그것이 정상이다. 포트폴리오의 `ca_unknown`은 "이 보유 기간의 기업행위를 확인했는가", 알림의 `가격 보정 대기`는 "이 계산 창에 보정 누락의 증거가 있는가"를 묻는다.

| 상황 | 포트폴리오 | 알림(국내) |
|---|---|---|
| 커버리지 안 · 기업행위 반영 · 일봉 보정됨 | 경고 없음 | 정상 평가 |
| 커버리지 밖 · 실제로는 기업행위 없음 | `ca_unknown` — 확인하지 못했으므로 | 정상 평가 — 누락 증거가 없으므로 |
| 커버리지 밖 · 실제로 분할 있음 | `ca_unknown` | 분할일 봉이 계산 창에 있으면 `가격 보정 대기` |
| 커버리지 안인데 일봉이 보정되지 않음 | 경고 없음 | `가격 보정 대기` — **계약 2 위반이며 데이터 품질 사고다** |

미국은 가격제한폭이 없어 알림에 누락 감지 수단이 없다. 미국 종목에서는 계약 1·2가 유일한 방어다.

### 8.5 구성종목 종가는 일봉에서 가져온다

ETF를 분해하면 구성종목 행에 환산수량(`ETF 평가금액 × 구성비중 ÷ 구성종목 가격`)이 나간다. 그 가격을 제공하는 테이블이 따로 없으므로 **`adjusted_price_daily`의 종가를 쓴다.** 그래서 미국 일봉 범위에 보유 ETF의 구성종목을 넣는다(§5.1). 같은 가격 데이터를 한 곳에서 받으면 원천도 품질 관리도 하나다. 쓰는 종가는 보유 스냅샷 기준의 시장별 가격 기준일(§4.2) 종가다.

## 10. 데이터 담당에게 되물을 질문

`N`은 두 기능을 합치며 새로 생긴 질문, `Q`는 [08-30 검토](../reviews/2026-08-30-data-team-olap-schema-review.md) §5에서 물었으나 답이 확인되지 않은 질문이다. 각 질문 아래 줄은 백엔드의 추천안이다.

### 최우선 — 알림 구현 착수를 막는 것

**N1. 알림용 세 테이블의 물리 이름을 확정해 달라.**
→ `data.adjusted_price_daily` · `data.investor_flow_daily` · `data.intraday_quote`. 일봉은 레이크에 이미 있는 이름을 따랐다.

**N2. `market_data_run`의 `DONE`을 "`data` 스키마 반영 완료" 시점에 쓸 수 있는가.**
→ 리버스ETL을 거치는 일봉·수급은 리버스ETL이 끝난 뒤에 쓴다. 레이크 적재 시점에 쓰면 백엔드가 아직 오지 않은 데이터를 "거래 없음"으로 판정한다.

**N3. 장중 `snapshot_at`을 벌의 시세 기준 시각으로 쓸 수 있는가.** 한 벌의 모든 행에 같은 값을 쓰고 `market_data_run.as_of`도 같은 값으로 쓴다.
→ 원천이 종목마다 다른 시각을 주면, 벌의 가장 이른 시세 시각을 그 벌의 기준으로 쓴다(지연을 보수적으로 판정).

**N6. 종목 마스터 범위를 합집합으로 채울 수 있는가.** 보유 종목 · 구성종목 · CASH 의사종목 2행 · 상장폐지 종목 유지 · `delisted_on` 컬럼.
→ §4.1. NYSE Arca·Cboe 상장 ETF와 ADR은 보유하는 순간 필요하다.

**N7. 일봉 보정 범위를 분할·병합·무상증자로 하고 배당은 보정하지 않는 것에 동의하는가. `RIGHTS`(유상증자)는 어떻게 다루는가.** 08-30의 Q14(`corporate_action.type`에 배당이 없다)를 이 질문이 대신한다.
→ 배당 미보정. 유상증자는 국내 증권사 수정주가 관행을 따른다.

**N8. `corporate_action`의 새 행과 다시 보정한 일봉을 같은 적재 단위로 반영할 수 있는가.**
→ §8.4 계약 2. 어긋나면 국내는 평가 보류, 미국은 잘못 울린다.

### 높음

**N4. 미국 일봉 범위에 보유 ETF의 구성종목을 넣을 수 있는가.** 원천 호출 한도 안에서 가능한 규모인가.
→ §8.5. 넣지 못하면 ETF를 분해한 화면의 구성종목 행에서 환산수량이 빠진다.

**N5. 미국 일봉 대상에 새로 들어온 종목의 300거래일 백필은 언제 끝나는가.**
→ 편입 후 첫 `DAILY_BAR` 완료 신호까지. 그 전까지 그 종목의 알림은 `이력 부족`으로 보인다.

**N9. 레이크의 기술지표 마트(`mart_technical_daily`) 계획은 어디에 쓰는가.**
→ 백엔드는 지표를 직접 계산하며 이 마트를 읽지 않는다. 레이크 전용 분석용으로 남기는 것은 무방하다(§2.2).

**N10. 수급의 `기관`은 기관계 합계인가. 대상은 국내 ETF를 포함한 전 종목인가.**
→ 기관계 합계 · ETF 포함.

**N11. `alert_watchlist`를 언제 읽는가.**
→ 장중 스냅샷 매 벌 시작 시와 미국 일봉 적재 시작 시.

**N12. `ca_coverage`의 시장 단위 행을 어떻게 표현하는가.** PK 컬럼인 `instrument_id`는 null이 될 수 없다.
→ 시장 단위 행과 종목 단위 행을 같은 테이블에 두되 PK를 대리키로 바꾸거나, 시장 단위는 별도 표로 둔다. 데이터 쪽이 정한다.

**N13. 포트폴리오 테이블의 도착 시점 제안값을 확인해 달라.**
→ `instrument`: KR 개장 전 · `fx_rate`: 보유 스냅샷 생성 전 · `etf_constituent`: 파일 공개 후 다음 KR 영업일 스냅샷 생성 전 · `cln_*`: KR 장 마감 후 당일 중.

**N14. 미국 일봉을 다음 미국 장 개장 전까지, 국내 휴장과 무관하게 적재할 수 있는가.**
→ 미국 장중 알림이 직전 일봉을 기준선으로 쓰므로, 국내 휴장일에도 미국 일봉이 와야 한다.
