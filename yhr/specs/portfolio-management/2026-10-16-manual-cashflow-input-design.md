# 입출금 입력 설계 — `manual_cashflow` 쓰기 API와 입출금 화면

[포트폴리오 스펙](2026-07-28-portfolio-management-spec.md) §2.9 · §4.6이 정한 "넣은 돈은 사용자 입력에서 온다"를 백엔드 쓰기 경로와 앱 화면으로 만드는 설계다. 스펙이 정한 것(넣은 돈의 원천 · 소유 · 오류 형태)은 다시 적지 않고, 스펙이 열어 둔 것(경로 · 검증 · 화면 · 미입력 판정)을 정한다. 스펙과 이 문서가 다르면 스펙이 맞다. 스펙 문구를 해석하거나 스펙 문장과 다르게 정한 곳은 [§7](#7-스펙--ia-반영-후보)에 모았다.

| 근거 | 위치 |
|---|---|
| 넣은 돈의 원천 · 미입력 경고 · `넣은 돈` 행에서 입력으로 유도 | 스펙 §2.9 · §4.6 · §9.1 자산 변화 |
| 소유 · 남의 계좌 `403` | 스펙 §3.8 · §8.8 · §9.3 |
| 오류 형태 · 빈 상태 | 스펙 §8.6 |
| `manual_cashflow` 표 | 스펙 §5.1 · `V1__initial_schema.sql` |
| 화면 · 탭 · 진입 경로 · 공통 이름 | [앱 정보 구조](../app-information-architecture.md) §1 · §2.2 · §6.1 |
| 와이어플로우 | [`wireflow_src.py`](wireflow_src.py) → [`wireflow.png`](wireflow.png) · [`wireflow.drawio`](wireflow.drawio) |

## 1. 범위

**만든다**

- 입출금 생성 · 목록 · 삭제 API (`/portfolio/cashflows`).
- 자산 변화와 입출금 목록이 함께 쓰는 "견준 두 잔고" 계산(§2.4).
- 자산 변화의 미입력 경고. `CASHFLOW_UNCOVERED`가 계좌별 입출금 미입력도 판정한다(§4).
- 앱의 입출금 화면(`cashflows`)과 자산 변화의 `넣은 돈` 진입점.
- 와이어플로우의 입출금 화면과 진입 흐름(§5.4).

**만들지 않는다**

- 수정 API. 월 1~2건이라 지우고 다시 넣는 것으로 충분하다.
- USD 입력. 입출금은 원화 이체이고 계좌 안 환전은 데이터 제공 단계에서 빠진다(스펙 §11.2 현금흐름 배제 규칙). 바디의 `currency` 필드는 두어, 열 때 요청 모양이 바뀌지 않게 한다.
- 계좌 간 이체 식별(스펙 §12).
- 미입력 경고에서 입력 화면으로 가는 누름 동작. 경고 줄(`NoticeList`)은 모든 화면이 쓰는 `ScreenFrame`에 묶여 있고, 같은 화면으로 가는 `넣은 돈 입력 →`이 늘 보인다(§5.2).
- 마이그레이션. 표는 V1에 있고 이 설계는 컬럼을 더하지 않는다.

## 2. API

### 2.1 엔드포인트

| 동작 | 경로 | 성공 |
|---|---|---|
| 생성 | `POST /portfolio/cashflows` | `201 { "id": "…" }` |
| 목록 | `GET /portfolio/cashflows?from=&to=&account=` | `200` |
| 삭제 | `DELETE /portfolio/cashflows/{id}` | `204` |

`/accounts/{id}/cashflows`로 두지 않는다. 목록이 여러 계좌에 걸친 기간 조회라 계좌 하나에 매달리지 않는다.

```json
// POST /portfolio/cashflows
{ "account_id": "…", "type": "DEPOSIT", "amount": 2000000,
  "currency": "KRW", "occurred_on": "2026-07-25", "memo": "월급 이체" }

// GET /portfolio/cashflows?from=2026-07-01&to=2026-07-31
{ "window": { "after": "2026-07-24", "through": "2026-07-27" },
  "cashflows": [
    { "id": "…", "account_id": "…", "account_label": "한국투자 위탁",
      "type": "DEPOSIT", "amount": 2000000, "currency": "KRW",
      "occurred_on": "2026-07-25", "memo": "월급 이체" } ] }
```

- 목록은 응답 봉투(`as_of` · `notices` · `empty_reason`)를 쓰지 않는다. 뷰가 아니라 사용자가 넣은 기록을 돌려주는 것이라 배너 · 경고가 붙을 자리가 없다. 비어 있으면 `cashflows: []`다.
- `from` · `to`는 필수이고 양 끝을 포함한다. `account`는 선택이고 여러 값을 받는다(`?account=A&account=B`).
- 정렬은 `occurred_on` 최근순, 같은 날이면 `id`순이다.
- `window`는 같은 `from` · `to`로 자산 변화를 열었을 때 넣은 돈을 세는 구간 `(after, through]`다(§2.4). 그 사용자에게 잔고가 없으면 `null`. 목록의 행 중 이 구간 밖의 것은 그 기간 자산 변화에 들어가지 않는다. 앱이 행과 날짜 칸에 그 사실을 적는 데 쓴다(§5.3).
- `POST`의 `currency`는 생략할 수 있고 생략하면 `KRW`다.

### 2.2 검증과 오류

| 상황 | 상태 | `error.code` |
|---|---|---|
| 칸 값이 틀림 | `400` | `INVALID_CASHFLOW` + `fields[]` |
| `account_id`가 남의 계좌이거나 없는 계좌 | `403` | `FORBIDDEN_ACCOUNT` |
| 목록 `account` 필터에 남의 계좌 | `403` | `FORBIDDEN_ACCOUNT` |
| 목록 `account` 값이 UUID가 아님 | `400` | `UNKNOWN_FILTER_VALUE` |
| 목록 `from` · `to` 누락 · 형식 오류 · `from > to` | `400` | `INVALID_PERIOD` |
| 삭제할 `id`가 남의 것이거나 없음 | `404` | `CASHFLOW_NOT_FOUND` |
| 토큰 없음 · 만료 | `401` | `UNAUTHENTICATED` |

남의 입출금과 없는 입출금은 같은 `404`, 같은 본문이다. 다르면 남의 행이 존재하는지가 응답 차이로 드러난다(스펙 §3.8과 같은 이유). 계좌를 지정하는 경우만 `403`인 것은 스펙 §9.3이 정한 것이다.

**칸별 규칙** — 오류마다 `path`를 붙여 폼이 그 칸 아래에 `message`를 그대로 띄운다.

| `path` | 규칙 |
|---|---|
| `account_id` | 필수 · UUID. 그 계좌에 잔고가 하나도 없으면 `이 계좌는 아직 잔고가 없어 입력할 수 없어요` |
| `type` | `DEPOSIT` · `WITHDRAW` |
| `amount` | 1 이상의 정수 · 15자리 이하 |
| `currency` | `KRW`만. `USD`면 `지금은 원화만 입력할 수 있어요` |
| `occurred_on` | 필수 · `YYYY-MM-DD` · 아래 날짜 범위 안 |
| `memo` | 100자 이하. 앞뒤 공백을 지우고 빈 문자열이면 `null` |

**날짜 범위는 그 계좌의 잔고가 정한다.**

| 경계 | 규칙 | 오류 문구 |
|---|---|---|
| 하한 | 그 계좌의 첫 잔고 날짜 **다음 날**부터 | `07-24 잔고 다음 날부터 입력할 수 있어요` |
| 상한 | 오늘(`portfolio.zone`)까지 | `오늘 이후 날짜는 입력할 수 없어요` |
| 상한(`DISCONNECTED`) | 그 계좌의 마지막 잔고 날짜까지 | `연동을 해제한 계좌는 07-27까지만 입력할 수 있어요` |

첫 잔고보다 앞선 입출금은 그 잔고에 이미 들어 있다. 그 계좌가 기간 중에 들어왔으면 첫 잔고 전체가 `계좌 편입`으로 세어지므로, 그 날짜의 입금을 받으면 같은 돈이 편입과 넣은 돈에 두 번 들어간다. 해제한 계좌는 마지막 잔고 뒤로 라인이 없어, 그 뒤 날짜의 입출금은 어느 잔고의 변화와도 짝이 맞지 않는다. 첫 잔고 당일을 빼는 것은 넣은 돈을 세는 구간이 기초 잔고 날짜를 빼는 것(§2.4)과 같은 규칙이다.

연동 상태는 이 상한 하나에만 쓴다. `DISCONNECTED` 계좌도 마지막 잔고까지는 쓸 수 있다. 해제한 계좌의 과거 라인은 남아 지난 기간의 자산 변화에 그대로 들어가므로(스펙 §7.2), 막으면 그 기간의 넣은 돈을 고칠 길이 없어진다.

칸 오류가 여럿이면 `fields[]`에 모두 담는다. 응답 모양은 알림 저장 오류와 같은 `{ "error": { "code", "message", "fields" } }`다. 기존 `ApiError`에 `fields`를 더하지 않고 별도 레코드로 둔다 — 다른 오류 응답에 `"fields": null`이 생기지 않게 하기 위해서다.

### 2.3 서버 구성

```
api/CashflowController                요청 해석 → 서비스. 저장소를 직접 부르지 않는다
api/dto/CashflowDtos                  목록 응답 · 칸별 오류 응답 레코드
cashflow/CashflowRequestParser        JsonNode → 요청 값 + 칸 오류 목록
cashflow/CashflowValidator            칸별 규칙 · 날짜 범위. 오늘은 Clock으로 받는다
cashflow/InvalidCashflowException     칸 오류 목록을 싣는다 → 400
cashflow/ManualCashflowService        해석 → 소유 확인 → 검증 → 쓰기 · 목록 · 삭제
cashflow/ManualCashflowWriteMapper    insert · list · deleteOwned · lineRange
view/SnapshotPairResolver             견준 두 잔고 (§2.4). 자산 변화와 목록이 함께 쓴다
query/ManualCashflowMapper            + accountsWithEntries (§4)
```

- **요청은 `JsonNode`로 받아 직접 해석한다.** enum · 숫자 · 날짜를 Jackson 바인딩에 맡기면 유형 오타나 소수 금액이 칸 정보 없는 `400`으로 끝난다. 알림 저장(`AlertRequestParser`)과 같은 방식이다. 목록의 `from` · `to`도 문자열로 받아 직접 해석해 `INVALID_PERIOD`로 돌려준다.
- 순서는 해석 → 소유 확인 → 검증이다. `account_id`가 남의 것이면 칸 오류보다 `403`이 먼저다. 날짜 범위는 그 계좌의 잔고를 읽어야 판정할 수 있어서, 소유가 확인된 뒤에 본다.
- 소유 확인은 기존 `AccountOwnershipGuard.check`를 쓴다. 생성은 `{account_id}`, 목록은 필터 계좌 집합이다. 목록 `account` 값의 해석은 기존 `RequestParams` 규칙(`UNKNOWN_FILTER_VALUE`)을 따른다.
- 집계용 `query/ManualCashflowMapper.totalsBetween`은 그대로 둔다. 쓰기와 목록은 새 매퍼로 나눠, 읽기 계층이 조회 전용이라는 경계를 지킨다.
- 새 매퍼의 모든 메서드는 첫 인자로 `UserScope`를 받는다. `ScopeSignatureTest`는 `query`와 `cashflow` 두 패키지의 매퍼를 검사한다.
- `deleteOwned`는 `DELETE FROM manual_cashflow m USING account a WHERE m.account_id = a.account_id AND a.user_id = #{scope.userId} AND m.id = #{id}`로 지우고 지운 행 수를 돌려준다. 0이면 `RequestRejected("CASHFLOW_NOT_FOUND", …, true)`로 `404`다(기존 처리기).
- `list`는 `account`를 조인해 `account_label`을 읽고 스코프를 SQL에서 건다.
- `lineRange(scope, accountId)`는 그 계좌의 `min(as_of)` · `max(as_of)`다. 라인이 없으면 둘 다 `null`.
- `id`는 서버가 만든다(`UUID.randomUUID()`).
- 칸 오류는 `ApiExceptionHandler`에 `InvalidCashflowException` 처리기를 더한다.

### 2.4 견준 두 잔고와 넣은 돈을 세는 구간

자산 변화는 기간 `[from, to]`에 대해 두 잔고를 고른다. 기초는 `from` 직전의 가장 늦은 잔고이고, 없으면 기간 안의 가장 이른 잔고로 대신한다. 기말은 `to` 이하의 가장 늦은 잔고다. 넣은 돈은 그 사이 `(기초 as_of, 기말 as_of]`에서 센다. 기초 잔고 날짜의 입금은 이미 그 잔고에 들어 있기 때문이다.

이 선택을 `SnapshotPairResolver`가 맡아 `SnapshotPair(opening, closing, openingSubstituted)`를 돌려준다. 자산 변화 서비스는 이것으로 기초 · 기말과 `PERIOD_TRUNCATED`를 정하고, 목록 API는 `window = { after: opening, through: closing }`으로 내린다. 두 화면이 같은 계산을 쓰므로 목록이 "들어간다"고 표시한 행은 자산 변화의 넣은 돈에 들어간다.

| `occurred_on` | 그 기간 자산 변화 |
|---|---|
| `after` 다음 날 ~ `through` | 넣은 돈에 들어간다 |
| `after` 이하 | 들어가지 않는다 — 기초 잔고에 이미 반영된 돈이다. 기초가 대신 잡힌 기간(`07-24부터 계산`)에서 생긴다 |
| `through` 뒤 | 들어가지 않는다 — 다음 잔고가 쌓이면 그 잔고가 기말인 구간에 들어간다 |

`opening`과 `closing`이 같은 날이면 구간이 비어 어떤 입출금도 세지 않는다.

## 3. 무엇이 바뀌지 않나

- `manual_cashflow` 스키마 · 자산 변화 응답 모양 · 넣은 돈 계산식.
- 자산 변화가 고르는 두 잔고. `SnapshotPairResolver`는 자산 변화 서비스 안에 있던 선택을 그대로 옮긴 것이고, 기존 자산 변화 테스트가 그 동작을 지킨다.
- `totalsBetween`은 `currency`를 보지 않는다. 쓰기가 `KRW`만 받으므로 저장된 행은 모두 원화다.

## 4. 미입력 경고

판정 단위는 계좌다(스펙 §4.6의 "(계좌, 유형)"). **기말 잔고에 있는 계좌 중, 넣은 돈을 세는 구간에 입출금이 한 건도 없는 계좌**를 센다. 계좌 필터를 걸었으면 그 계좌들 안에서 센다. 기간 중에 빠진 계좌는 기말 잔고에 없으므로 세지 않는다. 기말 날에 처음 잔고가 생긴 계좌도 세지 않는다. 입출금은 첫 잔고 다음 날부터 받으므로(§2.3) 이 구간에 넣을 수 있는 날짜가 없다.

`query/ManualCashflowMapper.accountsWithEntries(scope, after, through, filter)`가 그 구간에 입력이 있는 계좌 집합을 돌려주고, 기말 계좌 중 기말보다 앞선 잔고가 있는 계좌(`SnapshotFactsMapper.accountsLinedBefore`)만 남기고 이것을 뺀 수가 미입력 계좌 수다.

미입력 계좌가 하나 이상이면 `CASHFLOW_UNCOVERED`의 `params.types`에 `DEPOSIT` · `WITHDRAW`를 더하고 `params.manual_uncovered_account_count`에 그 수를 싣는다. 기존 `params.account_count`는 배당 · 수수료를 확보하지 못한 계좌 수 그대로다. 문구는 빠진 것에 따라 고른다.

| 빠진 것 | `message` |
|---|---|
| 입출금만 | `2개 계좌에 이 기간 입출금이 입력되지 않아 투자손익이 정확하지 않을 수 있어요` |
| 배당 · 수수료만 | `배당·수수료 내역이 확보되지 않아 투자손익이 정확하지 않을 수 있어요` |
| 둘 다 | `2개 계좌에 입출금이 입력되지 않았고 배당·수수료 내역도 없어 투자손익이 정확하지 않을 수 있어요` |

- 넣은 돈을 세는 구간이 비어 있으면(§2.4) 판정하지 않는다. 그 구간에는 어떤 입력도 들어갈 수 없다.
- 스냅샷이 없어 빈 응답을 내는 경우에는 입출금 미입력을 판정하지 않는다.
- 이 판정은 "그 계좌에 입출금이 정말 없었던 기간"과 "입력하지 않은 기간"을 가르지 못한다. 입출금이 드문 연금 계좌는 대부분의 달에 미입력으로 세어진다. 문구가 단정하지 않는 것은 그래서다.
- 스펙 §4.6 예시는 `7월 입출금이…`인데, `올해` · `지정` 기간은 월로 말할 수 없어 `이 기간`으로 쓴다.

## 5. 앱

### 5.1 이름과 자리

| 화면 문구 | 문서 용어 | 코드 (`screen`) | 형태 | 들어오는 곳 |
|---|---|---|---|---|
| 입출금 | 입출금 입력 | `cashflows` | 스택 | 자산 변화 `넣은 돈` 행 |

탭이 아니다. "넣은 돈이 맞나?"는 자산 변화를 보던 중에 생기는 질문이라, 그 자리에서 들어가고 `‹`로 돌아간다(IA §1의 원칙).

라우트 파라미터 `cashflows: { from: string; to: string; account?: string[] }`. 자산 변화 응답의 `period`와 그 화면의 계좌 선택을 그대로 넘긴다.

### 5.2 자산 변화의 `넣은 돈` 행

```
│   넣은 돈                              +600만 │   그룹 헤더
│   넣은 돈 입력 →                             │   이 줄만 누른다
│     ＋ 입금             +6,000,000  ▮       │
```

- `넣은 돈 입력 →`은 같은 화면의 `실현손익 뷰 →`(`SplitBlock`)와 같은 링크 모양(`type.body` · `palette.primary` · `accessibilityRole="link"`)으로 그룹 헤더 바로 아래에 둔다. 위아래 여백으로 누르는 높이를 넓힌다.
- 누르는 곳은 링크 줄뿐이다. 그룹을 통째로 누르게 하면 스크린리더가 링크 이름만 읽고 그룹 합계와 항목 금액을 건너뛴다.
- **넣은 돈이 0이어도 그룹 헤더와 링크는 남는다.** 숨기는 것은 금액이 0인 입금 · 출금 항목 줄이다. 스펙 §2.9의 "값이 0인 항목은 행을 숨긴다"를 항목 단위로 읽은 것이다(§7).
- 미입력 경고는 지금 자리(`NoticeList`)에 그대로 나온다. 경고 줄은 누르는 곳이 아니다 — 입력으로 가는 길은 이 링크다.

### 5.3 입출금 화면

```
┌──────────────────────────────────────────┐
│ ‹              입출금                     │
├──────────────────────────────────────────┤
│ [한국투자 위탁 ▽]                         │
│ [  입금  |  출금  ]                       │
│ 금액   [        2,000,000 원 ]            │
│ 날짜   [ 2026-07-15 ]                     │
│ 메모   [ 월급 이체 (선택)    ]            │
│ ┌──────────────────────────────────────┐ │
│ │                저장                  │ │
│ └──────────────────────────────────────┘ │
├──────────────────────────────────────────┤
│ 07-01 ~ 07-31 · 2건                       │
│ 07-15  입금  한국투자 위탁   +2,000,000 ✕ │
│ 07-03  입금  한국투자 IRP    +4,000,000 ✕ │
└──────────────────────────────────────────┘
```

**폼**

| 칸 | 기본값 · 동작 |
|---|---|
| 계좌 | 넘겨받은 계좌가 하나면 그것, 사용자 계좌가 하나뿐이면 그것. 그 밖에는 비어 있고 고르지 않으면 저장할 때 칸 오류. 고르기는 `BottomSheet`에 카탈로그 계좌를 한 개만 고르는 목록으로 두고, `DISCONNECTED` 계좌는 맨 아래에 `해제됨` 배지와 함께 둔다 |
| 유형 | 입금 |
| 금액 | 숫자 키패드. 천 단위 구분을 보여주고 보낼 때는 정수 |
| 날짜 | `min(오늘, to)` — 지난달을 보다 들어왔으면 그 달 말일. 오늘 뒤는 고를 수 없다(`DateField max`). 계좌별 하한 · 해제 계좌 상한은 서버 칸 오류로 알린다 |
| 메모 | 선택 |

**날짜 칸 안내** — 목록 응답의 `window`로 고른 날짜가 이 기간 넣은 돈에 들어가는지 알린다. `window`가 `null`이면 띄우지 않는다.

| 고른 날짜 | 안내 |
|---|---|
| `through` 뒤 | `07-27 잔고 이후라 다음 잔고부터 반영돼요` |
| `after` 이하 | `07-24 잔고에 이미 들어간 돈이라 이 기간에는 세지 않아요` |

**저장**

- 저장 요청이 진행되는 동안 저장 버튼을 막는다. 두 번 눌러 같은 행이 둘 생기지 않게 한다.
- 성공하면 금액 · 메모만 비우고 계좌 · 유형 · 날짜는 둔다. 한 달 치를 연달아 넣기 쉽게 하려는 것이다.
- 성공하면 `['asset-change']` · `['cashflows']`를 무효화한다. `‹`로 돌아가면 자산 변화가 새 값을 그린다.
- `400`이면 `fields[].path`별로 칸 아래에 `message`를 띄운다. 칸을 고치면 그 칸의 문구를 지운다(알림 편집기와 같다).
- `403` · 네트워크 오류는 저장 버튼 위에 한 줄로 띄운다.

**목록**

- 넘겨받은 기간과 계좌로 `GET /portfolio/cashflows`를 부른다. 머리줄은 `MM-DD ~ MM-DD · N건`.
- 행: 날짜 · 유형 · 계좌 이름 · 부호 붙은 금액(입금 `+` 빨강, 출금 `-` 파랑 — 앱의 증감색). 메모가 있으면 둘째 줄에.
- `window` 밖의 행은 금액을 흐리게 하고 둘째 줄에 날짜 칸 안내와 같은 문구를 붙인다.
- `✕` → `ConfirmSheet` `07-15 입금 2,000,000원을 지울까요?` → `DELETE` → 저장과 같은 무효화. 확인 중에는 확인 버튼을 막는다.

**상태**

| 상태 | 표현 |
|---|---|
| 목록 로딩 | 행 `Skeleton` |
| 목록 실패 | `ErrorState`(다시 시도) |
| 목록 비어 있음 | `이 기간에 입력한 입출금이 없어요` |
| 칸 오류 | 칸 아래 서버 문장 |
| 넣은 돈 구간 밖 날짜 | 날짜 칸 아래 안내 · 행 둘째 줄 |
| 해제된 계좌 선택 | 계좌 칸에 `해제됨` 배지 |
| 저장 · 삭제 실패 | 버튼 위 한 줄 · 시트 안 한 줄 |

**구성과 상태 관리** — 기존 관례를 따른다.
- 목록 응답은 봉투가 없으므로 `ScreenFrame`을 쓰지 않고, 로딩 · 실패를 `Skeleton` · `ErrorState`로 직접 그린다.
- 조회는 React Query `useCashflows`(키 `keys.cashflows({from, to, account})`), 쓰기는 `useMutation`과 무효화 함수 하나(`invalidateCashflowData`).
- 엔드포인트는 `api/endpoints.ts`, 타입은 `api/types.ts`.
- 칸은 `TextField` · `DateField` · `SegmentedControl` · `BottomSheet`(계좌 하나 고르기) · `ConfirmSheet`를 쓴다.

### 5.4 와이어플로우

입출금 화면은 밴드 3 **자산 변화 바로 오른쪽**에 있다. 보던 화면에서 한 단계 들어가는 흐름을 이 와이어플로우는 가로 화살표로 그린다(`기관 선택 →` · `종목 탭 →`).

```
밴드 2   [요약]────────[종목별]──────…
           │ 왜? →         │ 손익 탭(레인 1485)   │ 행 탭(레인 1455)
밴드 3   [자산 변화]─넣은 돈 입력 →─[입출금]  [실현손익]  [종목 상세]  [상태 전수]  [등급]
              ▲                                    │
              └──── 이 기간 전체 투자손익 → ────────┘ (레인 2165)
```

| 요소 | 위치 · 내용 |
|---|---|
| P11 자산 변화 | x 360. `넣은 돈` 그룹 아래 `넣은 돈 입력 →`. 금액이 0인 `－ 출금` 줄은 없다 |
| P14 입출금 | x 760. 헤더 `‹ 입출금`. 폼 · 기간 목록(07-15 +2,000,000 · 07-03 +4,000,000, 합이 P11의 `＋ 입금`과 같다) · mono `manual_cashflow · 넣은 돈은 여기서만 온다\n저장·삭제 → 자산 변화 재조회` |
| P12 실현손익 · P13 종목 상세 | x 1160 · 1560 |
| 상태 전수 노트 · 등급 노트 | x 1960 · 2540. 상태 전수에 `입출금 — 입력 없음 · 넣은 돈 구간 밖 날짜 · 해제된 계좌 · 칸별 저장 오류` 줄 |
| 엣지 | `넣은 돈 입력 →`: P11 → P14 가로. `손익 탭`은 레인 1485, `행 탭`은 레인 1455이라 서로 교차하지 않는다. `이 기간 전체 투자손익 →`은 P12 중심(1310)에서 레인 2165로 P11에 돌아온다 |
| 페이지 폭 | `PGW` 3160 |

뒤로 가기는 그리지 않는다(스펙 §10 각주 — `‹`로 일관 제공). 저장 뒤의 갱신은 P14의 mono 주석이 말한다.
