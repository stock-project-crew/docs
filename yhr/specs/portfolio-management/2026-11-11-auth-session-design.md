# 로그인 세션 설계 — 갱신 토큰과 세션에 묶인 기기 등록

로그인을 "로그인 후 12시간 고정"에서 "마지막 사용 후 일정 시간"으로 바꾸고, 푸시 수신 기기 등록을 그 세션에 묶는 설계다. 백엔드와 앱을 함께 바꾼다. 스펙에 들어갈 문구는 [§10](#10-스펙-반영)에 모았다.

| 근거 | 위치 |
|---|---|
| 인증 · API 목록 | [포트폴리오 스펙](2026-07-28-portfolio-management-spec.md) §8.1 · §8.8 |
| 푸시 수신 기기 · 발송 · 소유 | [알림 스펙](../buy-sell-timing-alert/2026-07-12-buy-sell-timing-alert-spec.md) §9.1 · §9.2 · §9.3 · §14.5 |
| 로그인 화면 · 로그아웃 · 앱 상태별 동작 | [앱 정보 구조](../app-information-architecture.md) §2.2 · §2.6 · §4.2 |

## 1. 범위

**만든다**

- 서버 세션 `auth_session`과 갱신 토큰. 갱신 API `POST /auth/refresh`, 로그아웃 API `POST /auth/logout`.
- 접근 토큰에 세션을 싣고, 요청마다 그 세션이 살아 있는지 확인하는 일.
- `push_device`를 세션에 묶는 일. 끝난 세션의 기기를 발송에서 빼고 지우는 일.
- 앱의 갱신(`401` → 갱신 → 다시 보내기), 부팅 때의 갱신, 로그아웃을 세션 기준으로 바꾸는 일.

**만들지 않는다**

- 회원가입 · 비밀번호 재설정(포트폴리오 스펙 §12).
- 다른 기기의 세션 목록 보기 · 원격 로그아웃. 세션 테이블이 있으니 나중에 열 수 있지만 화면이 없다.
- 푸시 문구 줄이기(잠금화면에 종목 · 가격을 싣지 않기).

## 2. 수명

| 값 | 기준 | 설정 |
|---|---|---|
| 접근 토큰 | 발급 후 30분 | `portfolio.auth.access-ttl: PT30M` |
| 유휴 만료 | 마지막 갱신(처음은 로그인) 후 7일 | `portfolio.auth.idle-ttl: P7D` |
| 절대 상한 | 로그인 후 30일. 갱신해도 늘지 않는다 | `portfolio.auth.absolute-ttl: P30D` |

세 값 모두 환경변수(`PORTFOLIO_AUTH_ACCESS_TTL` · `PORTFOLIO_AUTH_IDLE_TTL` · `PORTFOLIO_AUTH_ABSOLUTE_TTL`)로 덮을 수 있다. 통합테스트가 짧은 값으로 띄운다. 기존 `portfolio.auth.ttl`은 없앤다.

**앱을 쓰는 중에 로그인 화면으로 밀려나는 조건**은 다음뿐이다.

- 로그인 후 30일이 지났다.
- 갱신 토큰 재사용이 감지됐거나, 훔친 쪽이 먼저 갱신해 주인의 갱신 토큰이 맞지 않게 됐다(§4.2). 둘 다 토큰이 새어 나간 경우다.

7일 동안 앱을 한 번도 쓰지 않았으면 다음에 열 때 로그인 화면이다. 이때는 안내 배너가 없다(§7.4). 앱을 쓰고 있는데 서버에 닿지 않아 갱신이 실패하면 밀려나지 않는다. 화면은 평소의 연결 오류를 보인다.

## 3. 서버 저장 — V19

### 3.1 `auth_session`

```sql
CREATE TABLE auth_session (
    session_id          uuid        PRIMARY KEY,
    user_id             uuid        NOT NULL REFERENCES app_user (id),
    refresh_hash        bytea       NOT NULL UNIQUE,
    prev_refresh_hash   bytea       UNIQUE,
    generation          integer     NOT NULL,
    confirmed           boolean     NOT NULL,
    created_at          timestamptz NOT NULL,
    last_refreshed_at   timestamptz NOT NULL,
    absolute_expires_at timestamptz NOT NULL
);
CREATE INDEX idx_auth_session_user ON auth_session (user_id);
```

- `refresh_hash`는 지금 쓸 수 있는 갱신 토큰의 SHA-256이다. `prev_refresh_hash`는 바로 전 갱신 토큰의 해시다. 갱신 응답이 유실된 경우를 가려내는 데만 쓴다(§4.2).
- `generation`은 갱신할 때마다 1씩 오른다. 처음 로그인하면 1이다. 접근 토큰이 발급 당시의 값을 `gen`으로 싣는다.
- `confirmed`는 지금 세대의 접근 토큰으로 요청이 한 번이라도 들어왔는지다. 새 갱신 토큰이 앱에 닿았다는 증거로 쓴다.
- 유휴 만료 시각은 저장하지 않는다. `last_refreshed_at + idle-ttl`로 계산한다. 설정값을 바꾸면 기존 세션에도 바로 적용된다.
- **세션이 살아 있다**는 `last_refreshed_at > now − idle-ttl AND absolute_expires_at > now`이다. 아래에서 "살아 있는 세션"은 모두 이 조건이다.

**끝난 세션은 행을 지운다.** 로그아웃과 재사용 감지는 그 자리에서 지운다. 유휴 만료와 절대 상한은 살아 있는 세션 조건에서 빠지는 순간부터 끝난 것으로 보고, 정리 작업이 지운다(§5.3). 끝난 세션의 기록을 남기지 않는다. 보여 줄 화면이 없고, 끝난 세션의 토큰은 행이 없으면 똑같이 거절된다.

### 3.2 `push_device`

```sql
DELETE FROM push_device;
ALTER TABLE push_device
    ADD COLUMN session_id uuid NOT NULL REFERENCES auth_session (session_id) ON DELETE CASCADE;
CREATE INDEX idx_push_device_session ON push_device (session_id);
```

- 세션 행이 지워지면 그 세션의 기기 행이 함께 지워진다. 기기 행이 지워지면 그 기기의 발송 행은 기존 `ON DELETE CASCADE`로 함께 지워진다.
- 기존 행은 모두 지운다. 기존 행은 세션이 없어 묶을 곳이 없고, 옛 접근 토큰은 배포와 함께 거절된다(§6). 각 사용자가 다시 로그인하면 앱이 켜질 때의 등록으로 행이 새로 생긴다. 그 전까지는 푸시가 가지 않는다. 울린 알림 목록과 배지에는 남는다.
- `user_id`는 남긴다. 세션에서 알 수 있지만 발송 쿼리와 소유 판정이 지금처럼 기기 행만 보고 사용자를 가른다.

## 4. 토큰과 API

### 4.1 접근 토큰

JWT HS256이다. 싣는 것은 `sub`(사용자) · `sid`(세션) · `gen`(세대) · `iat` · `exp`이다. `sid`나 `gen`이 없는 토큰은 서명이 맞아도 거절한다.

### 4.2 갱신 토큰

- 32바이트 난수를 base64url로 적은 문자열이다. 서버는 SHA-256 해시만 저장한다. 난수라 사전 공격이 성립하지 않아 느린 해시가 필요 없다.
- 갱신할 때마다 새것으로 바뀐다(회전).

`POST /auth/refresh`는 한 트랜잭션에서 다음을 한다. 해시가 `refresh_hash`나 `prev_refresh_hash`와 같은 행을 `FOR UPDATE`로 잡고 판정한다. 같은 토큰으로 동시에 들어온 갱신은 행 잠금으로 줄을 서서 하나씩 처리된다.

| 잡힌 행 | 처리 | 응답 |
|---|---|---|
| 없음 | — | `401` |
| 살아 있지 않음 | 행을 지운다 | `401` |
| `refresh_hash`와 같음 | `prev_refresh_hash ← refresh_hash`, 새 `refresh_hash`, `generation + 1`, `confirmed = false`, `last_refreshed_at = now` | 새 쌍 |
| `prev_refresh_hash`와 같고 `confirmed = false` | 응답이 유실된 것으로 본다. 새 `refresh_hash`, `generation + 1`, `last_refreshed_at = now`. `prev_refresh_hash`는 그대로 | 새 쌍 |
| `prev_refresh_hash`와 같고 `confirmed = true` | 재사용이다. 행을 지운다 | `401` |

두 번째 이전의 갱신 토큰은 어느 행과도 맞지 않아 `401`일 뿐 세션을 끊지 않는다. `confirmed`는 요청 필터가 세운다(§4.4).

**재사용 감지가 잡는 것과 놓치는 것**

| 순서 | 결과 |
|---|---|
| 훔친 쪽이 먼저 갱신하고 새 토큰으로 요청한 뒤 주인이 옛 토큰으로 갱신 | 재사용으로 세션이 끝난다. 둘 다 로그인 화면 |
| 주인이 갱신하고 새 토큰으로 요청한 뒤 훔친 쪽이 옛 토큰으로 갱신 | 재사용으로 세션이 끝난다 |
| 주인이 갱신한 뒤 새 토큰으로 요청하기 전에 훔친 쪽이 옛 토큰으로 갱신 | 응답 유실과 구분되지 않아 훔친 쪽이 새 쌍을 받는다. 주인의 갱신 토큰은 맞는 행이 없어 주인만 로그인 화면으로 간다. 훔친 쪽 세션은 유휴 만료 · 절대 상한까지 남는다 |

셋째 경우의 창은 보통 갱신과 다시 보내기 사이의 짧은 시간이다. 다시 보낸 요청이 연결 오류로 끝나면 길어진다. 이 창은 받아들인다.

- 막으려면 옛 토큰이 오는 즉시 세션을 끊어야 한다. 그러면 갱신 응답이 유실되거나 저장이 실패한 정상 사용자가 쓰는 중에 밀려난다.
- 훔치려면 먼저 폰의 보안 저장소에서 갱신 토큰을 꺼내야 한다.
- 밀려난 주인이 다시 로그인하면 새 세션이 생긴다.

### 4.3 API

```json
// POST /auth/login     { "email": "…", "password": "…" }
// POST /auth/refresh   { "refresh_token": "…" }
{ "access_token": "eyJ…", "expires_at": "2026-11-11T10:30:00+09:00", "refresh_token": "…" }

// POST /auth/logout    { "refresh_token": "…" }
// → 204
```

- 로그인은 세션 행을 새로 만든다. 같은 사용자의 다른 세션은 건드리지 않는다. 한 사람이 폰과 웹을 함께 쓸 수 있다.
- `expires_at`은 접근 토큰의 만료 시각이다. 갱신 토큰의 만료는 내리지 않는다. 앱이 판단할 일이 없다.
- 로그아웃은 해시가 `refresh_hash`나 `prev_refresh_hash`와 같은 세션 행을 지운다. 그 세션의 기기 행이 함께 지워진다. 맞는 행이 없어도 `204`다. 그래서 몇 번을 보내도 결과가 같다. 접근 토큰을 요구하지 않는다. 접근 토큰이 만료된 뒤에도 로그아웃이 된다.
- `refresh_token`이 비었거나 없으면 갱신 · 로그아웃 모두 `400`이다.
- 세 API는 인증 없이 열린다(`permitAll`). 웹 출처 허용(CORS)에 `/auth/refresh` · `/auth/logout`의 `POST`를 더한다.
- 갱신 거절은 모두 `401` `UNAUTHENTICATED`다. 모르는 토큰 · 끝난 세션 · 재사용을 응답으로 구분하지 않는다. 앱이 할 일은 모두 "로그인 화면으로"로 같다.

### 4.4 요청마다 세션 확인

요청 필터가 서명 · 만료를 확인한 뒤 `sid`로 세션 행을 읽는다. 다음을 모두 만족해야 요청이 인증된다.

- 행이 있다.
- 행의 `user_id`가 `sub`와 같다.
- 세션이 살아 있다.

`gen`이 행의 `generation`과 같고 `confirmed = false`이면 `confirmed = true`로 바꾼다. 세대마다 한 번만 쓴다. `gen`이 그보다 작은 토큰(갱신 전에 받은 접근 토큰이 아직 30분 안이다)도 받는다. 다만 `confirmed`를 세우지 않는다.

인증된 요청에는 사용자와 세션을 함께 붙인다. 기존 사용자 스코프 인자는 그대로 사용자만 꺼낸다. 기기 등록만 세션을 꺼내 쓴다.

비용은 인증된 요청마다 PK 조회 한 번이다. 세대가 바뀐 뒤의 첫 요청에서만 쓰기 한 번이 더해진다.

## 5. 기기 등록과 발송

### 5.1 등록

`POST /devices`는 요청의 세션으로 기기를 묶는다. 같은 Expo 토큰이 이미 있으면 그 행의 `user_id` · `session_id` · `platform` · `last_seen_at`을 지금 요청의 것으로 바꾸고 기존 `device_id`를 돌려준다. 같은 사람이 다시 로그인한 경우도, 다른 사람이 로그인한 경우도 같은 규칙이다. 앱은 켜질 때마다 등록하므로, 로그인 직후 첫 등록에서 기기가 새 세션으로 옮겨진다.

`DELETE /devices/{id}`는 그대로 둔다. 자기 기기 하나만 지우고, 아니면 `404`다. 새 앱은 로그아웃에 쓰지 않는다. 옛 앱의 로그아웃이 쓴다.

### 5.2 발송

| 자리 | 바뀌는 것 |
|---|---|
| 발화 때 발송 대기 행 만들기(`insertDeliveries`) | 그 사용자의 iOS 기기 가운데 **살아 있는 세션에 묶인 기기**로만 만든다 |
| 보내기 전 정리 | 지금의 "기기 주인이 바뀌었으면 `FAILED`(`OWNER_CHANGED`)" 옆에 "기기의 세션이 살아 있지 않으면 `FAILED`(`SESSION_ENDED`)"를 더한다. 대상은 같다. 대기 행과 임대가 끝난 전송 중 행이다 |
| 보낼 행 집기(`lockDue`) | 살아 있는 세션 조건을 조인에 더한다. 정리와 집기 사이에 세션이 끝난 행을 보내지 않는다 |

세션 행이 지워진 기기의 발송 행은 연쇄 삭제로 이미 없다. 위의 `SESSION_ENDED`는 유휴 만료 · 절대 상한이 지났지만 정리 작업이 아직 지우지 않은 사이를 맡는다.

### 5.3 정리 작업

한 시간마다 살아 있지 않은 세션 행을 지운다. 기기 행과 발송 행이 연쇄로 지워진다. 모든 복제본에서 돌아도 결과가 같다. 발송에서 빼는 일은 §5.2가 즉시 하므로, 정리 주기는 표의 크기만 정한다.

## 6. 배포와 옛 앱

- **옛 접근 토큰은 배포 즉시 거절된다.** `sid`가 없기 때문이다. 앱을 쓰던 사람은 다음 요청에서 만료 배너와 함께 로그인 화면으로 간다.
- **옛 앱(갱신을 모르는 앱)도 동작한다.**
  - 로그인 응답의 `refresh_token`을 무시한다.
  - 접근 토큰이 30분이라, 앱이 나올 때까지 30분마다 다시 로그인해야 한다.
  - 로그아웃은 `DELETE /devices/{id}`로 기기만 지운다. 세션은 유휴 만료로 끝난다.
- 그래서 백엔드를 배포한 뒤 바로 앱을 내보낸다. 앱이 먼저 나가면 없는 갱신 API를 부르게 된다. 그러면 갱신이 `404`로 거절돼 만료 때마다 로그인 화면으로 간다.
- 배포는 V19 마이그레이션을 함께 적용한다. 기존 기기 등록이 모두 지워진다(§3.2).
- 배포는 지금의 롤링 그대로 한다. 옛 파드와 새 파드가 함께 도는 몇 분 동안 일이 셋 생길 수 있다. 모두 그 몇 분 안에서 끝난다.
  - 옛 파드에서 한 로그인은 새 파드에서 거절돼 다시 로그인해야 한다.
  - 옛 파드로 간 기기 등록은 실패한다. 앱이 앞으로 올 때 다시 등록한다(§7.3.1).
  - 새 앱의 갱신이 옛 파드에 닿으면 로그인 화면으로 간다.

## 7. 앱

### 7.1 저장

접근 토큰 · 만료 시각 · 갱신 토큰을 보안 저장소의 **한 키**(`portfolio.session`)에 JSON 하나로 쓴다. 키마다 따로 쓰면 앱이 쓰기 도중에 죽었을 때 새 접근 토큰과 옛 갱신 토큰이 섞여 남는다. 그 상태로 다음에 갱신하면 서버가 재사용으로 판정한다. 마지막 이메일은 지금처럼 따로 둔다.

옛 키(`portfolio.access_token` · `portfolio.expires_at`)만 남은 저장 상태는 옛 앱이 남긴 것이다. 없는 것으로 치고 지운다.

### 7.2 갱신 — `client.ts`

- 요청이 `401`을 받으면 갱신한 뒤 새 접근 토큰으로 **한 번만** 다시 보낸다. 다시 보낸 요청이 또 `401`이면 갱신하지 않고 만료 처리를 부른다.
- 갱신은 한 번에 하나만 돈다. 진행 중인 갱신 약속(Promise)을 모듈에 하나 두고, 그동안 `401`을 받은 요청은 모두 그것을 기다린다. 갱신이 끝나면 비운다.
- 갱신 결과:
  - 성공: **저장소에 먼저 쓰고**, 쓰기가 끝난 뒤에 메모리에 넣고 원래 요청을 다시 보낸다. 새 접근 토큰이 서버에 닿아야 `confirmed`가 선다. 그래서 그 전에 앱이 죽으면 저장소에는 옛 갱신 토큰이 남는다. 이때 서버는 그 토큰을 응답 유실로 보고 새로 준다. 쓰기가 실패하면 메모리의 새 쌍으로 계속 쓴다. 이번 실행은 이어진다. 다음 실행에서 옛 갱신 토큰이 재사용으로 판정되면 로그인 화면이다. 보안 저장소 쓰기가 실패하는 일은 드물고, 여기서 막으면 쓰는 중에 밀려나기 때문이다.
  - `401` · `404`(갱신 API가 없는 서버) · 그 밖의 `4xx`: 만료 처리를 부른다. 다시 보내도 결과가 바뀌지 않는 답이다.
  - 응답 없음 · `5xx` · `408` · `429`: 세션을 지우지 않는다. 원래 요청은 연결 오류로 끝난다.
  - `200`인데 접근 토큰 · 만료 시각 · 갱신 토큰 중 하나라도 없음: 중간의 무언가가 답한 것으로 보고 응답 없음과 같이 다룬다.
  - 메모리에 갱신 토큰이 없음: 요청을 보내지 않고 만료 처리를 부른다.
- 갱신을 부르지 않는 요청:
  - 로그인 · 갱신 · 로그아웃 요청 자체.
  - `sendAs`로 보낸 요청. 로그아웃 뒤에 끝나는 요청과 정해 둔 토큰으로 보내는 기기 등록이 쓴다.
- 만료 직전에 미리 갱신하지 않는다. 아끼는 것이 왕복 한 번뿐이다.

### 7.3 부팅

| 저장된 세션 | 첫 화면 |
|---|---|
| 없음 | 로그인. 배너 없음 |
| 접근 토큰이 살아 있음 | 탭. 서버에 묻지 않는다 |
| 접근 토큰이 만료됨 | 갱신을 먼저 보낸다. 그동안 지금의 로딩 화면이다. 최대 5초만 기다린다 |
| └ 갱신 성공 | 탭 |
| └ 갱신 `401` · `404` | 로그인. 배너 없음. 저장된 세션을 지운다 |
| └ 응답 없음 · `5xx` · 5초 초과 | 탭. 세션을 지우지 않는다. 5초를 넘긴 갱신은 계속 돌고, 그 결과는 쓰는 중의 갱신과 같이 반영된다 |

### 7.3.1 기기 등록 시점

- 기기 등록(`PushRouter`)은 탭이 그려진 뒤에 나가므로 부팅 갱신이 끝난 접근 토큰을 싣는다.
- 등록은 지금처럼 정해 둔 토큰으로 보낸다(`sendAs`). 보내기 전에 접근 토큰이 만료돼 있으면 공용 갱신(§7.2)을 먼저 기다린다.
- 로그인한 동안 **앱이 앞으로 올 때마다 다시 등록한다.** 지금은 앱이 켜질 때 한 번만 등록한다. 이제는 등록이 세션에 묶이므로 등록이 한 번 실패한 채 두면 다음 실행까지 푸시가 오지 않는다.
  - 등록이 실패하는 경우: 부팅 갱신이 연결 오류로 끝난 경우, 로그인 직후 등록이 닿지 않은 경우.
  - 다음 경우도 이 재등록이 메운다. 앞사람의 로그아웃 재시도(§7.5)가 앞사람 세션에 남아 있던 기기 행을 지우는 경우다.
  - 등록은 진행 중인 로그아웃 재시도가 끝난 뒤에 나간다. 08의 순서 그대로다.
- 등록은 같은 행을 고쳐 쓰는 upsert라 여러 번 보내도 결과가 같다.

### 7.4 갱신이 거절됐을 때의 화면

쓰는 중에 거절되면 지금의 만료 배너(`로그인이 만료되었어요. 다시 로그인해 주세요`)를 띄우고 이메일 칸을 채운다. 부팅 때 거절되면 배너 없이 이메일만 채운다. 며칠 만에 연 사람에게 만료 안내는 사고가 난 것처럼 읽힌다. 두 경우 모두 지금의 동작과 같다.

### 7.5 로그아웃

`logout`은 지금처럼 화면을 막지 않는다. 기기 해제(`releaseOnLogout`)를 다음처럼 바꾼다.

- 보내는 것: `POST /auth/logout`에 갱신 토큰을 싣는다. 접근 토큰을 싣지 않는다. 서버가 세션과 그 세션의 기기 등록을 함께 지운다.
- 상한은 지금처럼 3초다.
- 결과:
  - `2xx` · `408` · `429`를 뺀 `4xx`: 끝난 것으로 본다. 서버는 모르는 토큰에도 `204`로 답하므로, 이 `4xx`는 요청 모양이 틀린 경우뿐이다. 다시 보내도 같다.
  - 응답 없음 · `5xx` · `408` · `429` · 3초 초과: OS 푸시 등록을 끊는다(`unregisterForNotificationsAsync`). 갱신 토큰을 메모리의 대기 목록에 남겨 다시 보낸다. 이미 목록에 있는 토큰은 다시 넣지 않는다. 목록이라서, 두 사람이 연달아 닿지 못한 채 로그아웃해도 앞사람 몫이 덮이지 않는다.
- 다시 보내는 때: 앱이 켜져 있는 동안 앱이 앞으로 올 때마다 보낸다. **로그인 상태와 상관없다.** 다음 로그인의 등록이 성공해도 버리지 않는다.
  - 이 요청은 끝난 사람의 세션만 끝낸다.
  - 기기 행은 이미 새 세션으로 옮겨졌으므로 지워지지 않는다.
  - 같은 사람이 다시 로그인했어도 새 세션은 다른 행이라 영향이 없다.
  - 다시 보내는 요청에도 3초 상한이 있다. 등록이 재시도를 기다리므로, 걸린 요청이 등록을 막지 않게 한다.
  - 끝난 것으로 보는 답을 받으면 목록에서 버린다. 앱을 끄면 사라진다.
- 메모리에만 두는 이유: 로그아웃한 사람의 갱신 토큰이 저장소에 남으면 그것으로 세션을 다시 살릴 수 있다.
- 갱신 토큰이 없으면(저장된 세션이 없던 경우) 보내지 않는다. OS 푸시 권한이 있으면 수신만 끊는다. 지금 동작과 같다.
- 08의 "진행 중인 등록을 기다렸다가 그 `device_id`로 해제" 단계는 없앤다. 로그아웃 전에 나간 등록이 로그아웃보다 늦게 서버에 닿아도 기기가 남지 않는다.
  - 로그아웃이 먼저 처리되면 세션 행이 없어 그 등록의 접근 토큰이 `401`이다.
  - 등록이 먼저 처리되면 로그아웃이 그 행을 함께 지운다.
- 로그아웃마다 오르는 세대 번호는 남긴다. 로그아웃 뒤에 끝난 등록의 `device_id`를 저장소에 쓰지 않게 하는 데 쓴다.
- **갱신이 진행 중일 때 로그아웃하면** 그 갱신이 끝나기를 기다린다. 기다림은 3초 상한 안에 든다. 그 뒤 가장 최근의 갱신 토큰으로 로그아웃을 보낸다. 갱신이 성공했는데 옛 토큰으로 로그아웃을 보내도 서버는 직전 토큰으로 세션을 찾아 지운다. 그래도 최신 토큰을 쓴다.
- 로그아웃이 시작된 뒤에 끝난 갱신 결과는 저장소에도 메모리에도 넣지 않는다. 로그아웃의 세대 번호로 가린다. 넣으면 로그아웃한 사람의 살아 있는 세션이 디스크에 남는다. 앱을 다시 켜면 그 사람으로 로그인돼 있게 된다.
- 로그아웃이 시작된 뒤에 나온 `401`과 갱신 거절은 만료 처리를 부르지 않는다. 직접 로그아웃한 사람에게 만료 배너가 뜨지 않게 한다.
- 로그아웃이 갱신을 기다리기 전에 메모리의 세션부터 비운다. 상한을 넘겨 화면이 로그인으로 간 뒤 다시 로그인했을 때, 늦게 끝난 갱신이 새 세션을 지우지 않게 한다.
- 로그아웃이 도는 동안에는 앱이 앞으로 와도 기기를 다시 등록하지 않는다. 등록은 시작할 때와 기다린 뒤마다 이를 확인한다.
- 만료 처리(갱신 거절)도 로그아웃과 같이 세대를 올리고 메모리를 비운다. 만료 전에 시작해 뒤에 끝난 갱신 결과가 다시 들어오지 않게 한다.

### 7.6 로그아웃 뒤 그 폰으로 푸시가 올 수 있는 최대 시간

| 로그아웃 | 서버 등록 | 그 폰으로 푸시 |
|---|---|---|
| 서버에 닿음 | 그 자리에서 지워진다 | 오지 않는다 |
| 닿지 않음, 앱이 켜진 채 다시 연결 | 다음에 앱이 앞으로 올 때 지워진다 | 그 사이는 OS 수신 끊기가 막는다 |
| 닿지 않음, 앱을 끔 | 세션이 마지막 갱신 후 7일에 끝나며 발송에서 빠진다 | OS 수신 끊기가 막는다. iOS에서 관찰된 동작이다. 그마저 듣지 않아도 최대 7일 |

마지막 갱신은 로그아웃 시각보다 앞이므로, 서버가 보낼 수 있는 기간은 로그아웃 시각부터 7일을 넘지 않는다. v1 푸시는 iOS로만 나간다(알림 스펙 §9.6).

### 7.7 13과의 관계

13(울린 알림 정렬 · iOS 날짜 칸 · 만료 뒤 누른 푸시)이 `AuthContext.tsx`와 `pushInbox.ts`를 고친다. 이 설계를 쓴 시점에는 13의 브랜치가 없다. 이 설계는 `pushInbox.ts`를 고치지 않는다. `AuthContext.tsx`에서는 부팅 판정 · 로그인 저장 · `logout` · 재시도 구독을 고친다. 로그인 실패 때 `discardPendingOpen`을 부르는 자리와 로그아웃 때 그것을 부르는 자리는 그대로 둔다. 구현을 시작할 때 13이 있으면 그 설계와 겹치는지 먼저 본다.

| 끝나는 경우 | 세션 행 | 기기 행 | 이미 만든 발송 대기 행 |
|---|---|---|---|
| 로그아웃(`POST /auth/logout`) | 바로 지움 | 연쇄로 지움 | 연쇄로 지움 |
| 갱신 토큰 재사용 | 바로 지움 | 연쇄로 지움 | 연쇄로 지움 |
| 유휴 만료 · 절대 상한 | 정리 작업이 한 시간 안에 지움 | 그때까지 발송에서 빠지고 정리 때 지움 | `SESSION_ENDED`로 `FAILED` |
| 다른 사람이 같은 폰에서 로그인 · 등록 | 앞사람 세션은 남음 | 새 세션 · 새 사용자로 옮김 | 지금처럼 `OWNER_CHANGED` |

## 9. 테스트

### 9.1 백엔드

- DB를 쓰지 않는 단위 테스트
  - 토큰 코덱: `sid` · `gen`을 싣고 읽는다. `sid`나 `gen`이 없는 토큰은 거절한다.
  - 갱신 토큰 해시: 같은 입력은 같은 해시를 낸다.
  - 갱신 판정 표(§4.2)의 다섯 경우를 저장소를 흉내 내어 확인한다.
- DB 테스트(브랜치 전용 DB `portfolio_test_auth_session`)
  - API 경로
    - 로그인이 세 값을 준다.
    - 접근 토큰이 만료돼도 갱신하면 새 토큰으로 조회된다.
    - 유휴 만료 · 절대 상한이 지난 세션은 갱신이 `401`이고 행이 지워진다.
    - 재사용이면 `401`이고 세션과 기기가 지워진다. 응답 유실(직전 토큰 · 미확인)은 새 쌍을 준다.
    - 로그아웃 뒤 그 접근 토큰은 만료 전에도 `401`이다. 모르는 토큰의 로그아웃은 `204`다.
    - `sid` 없는 옛 토큰은 `401`이다.
  - 기기 · 발송
    - 등록이 세션을 묶는다. 같은 토큰을 다른 세션에서 등록하면 행이 옮겨진다.
    - 로그아웃하면 그 세션의 기기 행과 발송 행이 지워진다.
    - 유휴 만료된 세션의 기기에는 발화 때 발송 대기 행이 생기지 않는다.
    - 대기 중에 세션이 끝난 행은 `SESSION_ENDED`로 끝나고 집히지 않는다.
    - 정리 작업이 끝난 세션과 그 기기를 지운다.
  - 시간은 주입한 `Clock`으로 움직인다.

### 9.2 앱

- 접근 토큰 수명이 지나도 앱을 쓰는 동안 로그인 화면으로 가지 않는다. 첫 요청이 `401` → 갱신 → 다시 보내기로 성공한다.
- 동시에 `401`을 받은 요청 셋이 갱신을 한 번만 부른다.
- 갱신 결과별로 확인한다.
  - `401`이면 만료 배너가 있는 로그인 화면이다.
  - 응답이 없으면 로그인 화면으로 가지 않는다.
- 부팅 표(§7.3)의 각 행.
- 로그아웃이 갱신 토큰으로 `POST /auth/logout`을 보낸다. 닿지 않으면 OS 수신을 끊고, 앞으로 올 때 다시 보낸다. 다시 로그인한 뒤에도 다시 보낸다.
- 갱신 성공은 저장이 끝난 뒤에 다시 보낸다. 세 값은 한 키에 쓰인다.
- 갱신이 진행 중일 때 로그아웃하면, 그 갱신이 끝난 뒤 최신 갱신 토큰으로 로그아웃한다. 로그아웃 뒤에 끝난 갱신 결과는 저장되지 않는다. 그 뒤의 `401`은 만료 배너를 띄우지 않는다.
- 로그인한 동안 앱이 앞으로 오면 기기를 다시 등록한다. 접근 토큰이 만료돼 있으면 갱신한 뒤에 등록한다.
- `npx jest` · `npx tsc --noEmit`.

**§8.1 표의 인증 행** →

**§8.1 표 아래 첫 문장** "`POST /auth/login`을 뺀 전 엔드포인트가 인증을 요구하며" →

> 로그인 · 갱신 · 로그아웃을 뺀 전 엔드포인트가 인증을 요구하며

**§8.8 첫 문단과 표**(뒤의 "토큰에 계좌 목록을 싣지 않는다"와 "사용자 ID는 요청에서 받지 않는다"는 그대로 둔다) →

> 사용자를 식별해야 데이터 범위가 갈리므로(§3.8) 인증은 선택이 아니다. 이메일·비밀번호로 로그인하면 서버가 **세션**을 하나 만들고 **접근 토큰**과 **갱신 토큰**을 준다. 요청은 접근 토큰을 Bearer 헤더로 보낸다. 접근 토큰이 만료되면 앱이 갱신 토큰으로 새 쌍을 받는다. 그래서 앱을 쓰는 동안에는 로그인 화면으로 가지 않는다.
>
> | 항목 | 값 |
> |---|---|
> | 접근 토큰 | JWT, HS256 서명. 비밀키는 환경변수 |
> | 실린 것 | `sub`(= `user_id`) · `sid`(세션) · `gen`(갱신 세대) · `iat` · `exp` |
> | 전달 | `Authorization: Bearer <token>` |
> | 접근 토큰 수명 | 30분 |
> | 갱신 토큰 | 난수. 서버는 해시만 저장한다. 갱신할 때마다 새것으로 바뀐다 |
> | 유휴 만료 | 마지막 갱신 후 7일. 처음은 로그인 시각부터 센다 |
> | 절대 상한 | 로그인 후 30일. 갱신해도 늘지 않는다 |
> | 서버 상태 | 세션. 요청마다 접근 토큰의 세션이 살아 있는지 확인한다 |
>
> **세션이 끝나는 경우는 넷이다.** 로그아웃 · 유휴 만료 · 절대 상한 · 갱신 토큰 재사용이다. 끝난 세션의 접근 토큰은 만료 전이라도 거절한다. 세션이 끝나면 그 세션으로 등록한 푸시 수신 기기로도 보내지 않는다([알림 스펙](../buy-sell-timing-alert/2026-07-12-buy-sell-timing-alert-spec.md) §9.2).
>
> **이미 바뀐 갱신 토큰이 다시 오면 세션을 끝낸다.** 토큰이 새어 나가 두 곳에서 쓰인 것으로 본다. 다만 바로 전 갱신 토큰이 왔는데 새 토큰으로는 아직 요청이 온 적이 없으면 갱신 응답이 앱에 닿지 않은 것으로 보고 새로 준다. 지하철에서 갱신하다 끊긴 사람이 밀려나지 않게 하기 위해서다. 그래서 그 사이에 훔친 토큰이 먼저 오면 재사용으로 잡지 못한다. 이 경우 주인이 로그인 화면으로 가고, 다시 로그인하면 새 세션이 생긴다.

**§8.8 JSON 예시** →

> ```json
> // POST /auth/login     { "email": "…", "password": "…" }
> // POST /auth/refresh   { "refresh_token": "…" }

>

>

> { "user_id": "…", "email": "…", "display_name": "yhr" }
> ```
>
> 로그아웃은 접근 토큰을 요구하지 않는다. 접근 토큰이 만료된 뒤에도 로그아웃할 수 있어야 한다.

**§8.8 오류 표의 첫 행** →

**§9.3 인증 규칙 행** "`POST /auth/login`을 뺀 모든 요청은 유효한 토큰을 요구한다" →

**§10 "인증 만료는 화면별 상태가 아니다" 문단** →

> **인증 만료는 화면별 상태가 아니다.** 앱은 `401`을 받으면 먼저 갱신하고, 갱신이 거절됐을 때만 로그인으로 되돌린다. 이 처리는 어느 화면에서든 같으므로 화면마다 상태를 두지 않고 전역 처리로 다룬다. 화면별 상태로 두면 아홉 곳에 같은 분기가 생긴다.

**§8.7 표의 로그인 행** →

> | 로그인 | `POST /auth/login` → 접근 토큰 · 갱신 토큰 |

**§9.2 둘째 · 셋째 항목** →

> - 권한을 받으면 Expo 푸시 토큰을 `POST /devices`로 등록하고, 응답의 `device_id`를 앱의 보안 저장소에 보관한다. 앱이 시작될 때마다 다시 등록해 토큰 교체를 따라간다. **등록은 그 요청의 로그인 세션에 묶인다**(포트폴리오 스펙 §8.8). 토큰이 이미 등록돼 있으면 지금 사용자와 지금 세션으로 옮긴다.
> - **세션이 끝나면 그 세션으로 등록한 기기로는 보내지 않는다.** 공용 기기에서 로그아웃한 사람의 알림이 오면 안 된다.
>   - 로그아웃은 `POST /auth/logout`으로 세션을 끝내고, 서버가 그 세션의 기기 등록을 함께 지운다.
>   - 유휴 만료 · 절대 상한으로 끝난 세션의 기기는 그때부터 발송에서 빠지고, 정리 작업이 지운다.
>   - 로그아웃은 서버의 답을 기다리느라 막히지 않는다. 응답이 없거나 `5xx` · `408` · `429`이거나 3초 안에 답이 없으면 앱이 OS의 푸시 등록을 끊어 이 기기가 푸시를 받지 않게 하고, 앱이 켜져 있는 동안 로그아웃을 다시 보낸다.
>   - 앱이 꺼져 다시 보내지 못해도 그 세션은 마지막 갱신 후 7일이면 끝난다.
>   - 끊은 OS 등록은 다음에 이 기기에서 누가 로그인해 등록하면 다시 켜진다.
>   - 기기 하나만 지울 때는 `DELETE /devices/{id}`를 쓴다.

## 11. 미결 · 후속

- 통합테스트 C2 묶음은 `PORTFOLIO_AUTH_TTL=PT5M`으로 만료를 만든다. 바뀐 뒤에는 접근 토큰 수명을 줄이면 앱이 조용히 갱신한다. 세션 만료를 만들려면 `PORTFOLIO_AUTH_IDLE_TTL`을 줄인다. 영향받는 케이스는 끝날 때 보고한다.
