# 데이터 계약 — 데이터팀 · 백엔드

데이터팀 표 가운데 백엔드가 읽는 것과, 백엔드 표 가운데 데이터팀이 읽는 것의 약속이다. 표마다 무엇을 · 언제까지 · 어떤 모양으로 주는지와, 약속이 지켜지지 않을 때 백엔드가 어떻게 하는지를 적는다. 화면에서 보이는 결과의 자세한 규칙은 기능 문서([포트폴리오](./portfolio.md) · [알림](./alert.md))에 있고, 여기서는 한 줄로 적고 그쪽을 가리킨다.

---

## 1. 읽는 법

### 1.1 표 블록

표 하나가 한 블록이다. 블록은 항목표와 컬럼표로 이루어진다.

| 항목 | 뜻 |
|---|---|
| 뜻 | 이 표가 무엇을 담는가 |
| 그레인 · 키 | 한 행이 무엇인가, 무엇이 유일한가 |
| 쓰는 쪽 | 그 표에 쓰는 팀과 쓰는 방식 |
| 범위 | 어느 시장 · 어느 종목 · 어느 계좌 · 어느 기간 |
| 언제까지 | 백엔드가 읽는 자리(`data` 스키마)에 언제까지 있어야 하나 |
| 완료 신호 | 적재가 끝났음을 무엇으로 아나 |
| 안 지켜질 때 | 없거나 늦거나 틀렸을 때 백엔드가 하는 일 |

컬럼표의 타입과 null 여부는 데이터팀 DDL을 따른다. null 칸의 `Y`는 비어 있을 수 있다는 뜻이다. 백엔드가 읽지 않는 컬럼은 뜻 칸에 "백엔드는 읽지 않는다"라고 적는다.

### 1.2 정본과 미러

- 데이터팀 표의 정본은 데이터팀 DDL이다. 백엔드의 미러는 같은 표를 로컬 · 테스트에서만 만드는 복제이고 운영에는 적용하지 않는다. 지금 미러가 정본과 다른 점은 [9.2](#92-미러가-데이터팀-표와-다른-점)에 있다.
- 백엔드는 데이터팀 표의 컬럼을 이름으로 읽고, 데이터팀은 백엔드 표의 컬럼을 이름으로 골라 읽는다. 상대가 읽는 컬럼의 이름 · 타입 · 뜻을 바꾸는 변경은 상대 팀과 먼저 맞춘다.

### 1.3 다루지 않는 것

- 원천 선택과 수집 방법, 레이크 구성. 데이터팀이 정한다.
- 백엔드 안에서만 쓰는 표. 각 기능 문서의 데이터 모델에 있다.

## 2. 경계와 공통 규칙

### 2.1 경계

- **증권사 · 원천마다 다른 응답을 공통 모양으로 맞추는 것까지가 데이터팀이다.** 그 위에 얹는 도메인 규칙(라인 생성 · 이월 · 평단과 등급 · 실현손익 · 지표 계산 · 평가 · 울림)은 백엔드다.
- **사용자 개념은 백엔드에만 있다.** 데이터팀 표에는 사용자 id가 없다. 계좌는 백엔드가 발급한 `account_ref`로만 식별하고, 그 계좌가 누구 것인지는 백엔드가 푼다. 알림 대상 종목 표(`alert_watchlist`)도 종목만 담는다.
- **지표는 백엔드가 계산한다.** 사용자가 기간을 고르므로(RSI 9 · 14, 이동평균 5 · 20 · 60 등) 미리 계산한 메뉴로는 조건이 성립하지 않는다. 데이터팀은 일봉 · 수급 · 장중 시세 원재료를 준다.
- **백엔드는 레이크를 읽지 않는다.** 백엔드가 읽는 데이터팀 표는 모두 앱 DB의 `data` 스키마에 있다. 레이크의 분석 산출물은 앱 화면으로 나가지 않는다 — 화면과 같은 숫자를 다른 곳에서 계산하면 둘이 어긋날 때 어느 쪽이 맞는지 가를 기준이 없다.
- **증권사 호출은 데이터팀이 한다.** 백엔드는 사용자가 넣은 인증 정보를 시크릿 저장소(SSM)에 쓰고, 수집 요청에는 그 이름(`credential_ref`)만 싣는다([7.3](#73-인증-정보-값)).

### 2.2 놓이는 곳

| 스키마 | 표를 만드는 쪽 | 쓰는 쪽 | 읽는 쪽 |
|---|---|---|---|
| `data` | 데이터팀 | 데이터팀. 백엔드는 `collection_run`의 정해진 컬럼에만 쓴다 | 백엔드 · 데이터팀 |
| `app` | 백엔드(마이그레이션) | 백엔드 | 백엔드. 데이터팀 계정은 `app_user` · `push_device`를 뺀 전부를 읽기만 한다([7.4](#74-권한-경계)) |

`data`로 오는 경로는 두 가지다. 장중 시세 · `market_data_run` · `collection_run`은 앱 DB에 직접 쓰고, 나머지는 레이크에서 되돌려 쓴다(리버스 ETL). 장중 평가는 분 단위라 레이크를 한 번 거치는 지연을 견디지 못한다.

### 2.3 키와 제약

- **종목 키는 `instrument_id`(uuid)다.** `symbol`은 표시 · 검색용이며 식별에 쓰지 않는다.
- **계좌 키는 `account_ref`(text)다.** 백엔드가 연동할 때 증권사 기관코드와 계좌번호를 HMAC으로 묶어 `ar_` + 16진 32자로 만든다. 해제했다 다시 연동해도 같은 계좌면 같은 값이고, 만든 뒤 바뀌지 않으며, 계좌번호를 역산할 수 없다.
- **다시 수집해도 같은 값이 나오는 키**: 체결 `trade_id`, 현금흐름 `cashflow_id`. 바뀌면 백엔드가 같은 체결을 두 번 센다.
- 소유 팀이 다른 표 사이에는 FK를 걸지 않는다. 두 팀의 배포 순서가 묶이기 때문이다. 백엔드는 키가 상대 표에 있는지를 쓸 때 확인하고, 없을 때의 동작을 블록마다 적는다.
- 열거형은 `text` + CHECK다.

### 2.4 시각과 날짜

- **거래일(`date`)은 그 시장의 현지 날짜다.** 미국 종목의 거래일은 뉴욕 날짜다.
- 시각은 `timestamptz`다.
- **KR 거래일**은 `dim_market_calendar`에서 `market = KR`이고 `is_trading_day`가 참인 날이다.
- 한국 날짜로 읽는 값: `collection_run.as_of`(라인 기준일), `fx_rate.as_of`(고시일), `cln_cashflow.occurred_at`(한국 시간 날짜로 자산 변화 구간에 넣는다).
- 종가의 데이터 시점은 그 거래일의 `dim_market_calendar.close_at`이다. 두 팀이 마감 시각을 따로 계산하지 않는다.

## 4. 공용 테이블

### 4.1 `instrument` — 종목 마스터

| 항목 | 내용 |
|---|---|
| 뜻 | 데이터팀이 주는 종목 목록. 라인 · 체결 · 알림 · 구성종목이 모두 `instrument_id`로 이 표를 가리킨다. 예수금도 종목처럼 다루려고 `CASH` 행 두 개(KRW 예수금 · USD 예수금)를 둔다 |
| 그레인 · 키 | 종목 1행 · PK `instrument_id` |
| 쓰는 쪽 | 데이터팀. 행을 덮어쓰기만 하고 지우지 않는다 — 지우면 그 종목의 과거 라인이 과거 총자산에서 빠진다 |
| 범위 | 국내 상장 주식과 국내 ETF, 미국 NASDAQ · NYSE · AMEX 주식과 미국 ETF, `CASH` 2행. 요구는 보유 종목 · 구성종목까지 덮는 합집합이다([8.1](#81-종목-마스터는-합집합이다)) |
| 언제까지 | 거래일마다 갱신. 국내 장 시작 전까지 — 당일 신규 상장 종목에 장중 알림을 걸 수 있어야 한다 |
| 완료 신호 | 없음. 늦으면 직전 상태로 읽는다 |
| 안 지켜질 때 | 라인을 만들 때 마스터에 없는 종목이 잔고에 있으면 그 계좌는 확정 마감까지 다시 시도하다 이월한다. 알림은 그 종목을 `종목 정보 없음`(확인 불가)으로 두고, 검색에서는 보이지 않는다 |

| 컬럼 | 타입 | null | 뜻 |
|---|---|---|---|
| `instrument_id` | uuid | N | 종목 키. 지금은 (시장, 종목코드)로 만든 값이라 종목코드가 바뀌면 새 값이 된다([9.1](#91-지금-지켜지지-않는-것)) |
| `isin` | text | Y | 국내 · 미국 공통 코드. `CASH`는 null. 백엔드는 읽지 않는다 |
| `symbol` | text | N | 종목코드 · 티커. 표시 · 검색용이며 유일하지 않다 |
| `name` | text | N | 화면 종목명이자 검색 대상. 미국 종목은 영문이 기본이고 일부만 한글명이다 |
| `asset_class` | text | N | `STOCK` · `ETF` · `CASH` |
| `market` | text | N | `KR` · `US`. `CASH` 행은 통화로 정한다(KRW → KR, USD → US) |
| `currency` | text | N | `KRW` · `USD` |
| `sector` | text | Y | 원천 업종을 공통 대분류로 묶은 값. 모르거나 ETF · 예수금이면 null이고 화면은 `미분류` |
| `sector_source` | text | Y | 분류 출처. 백엔드는 읽지 않는다 |
| `is_leveraged` | boolean | Y | 레버리지 · 인버스 종목인가. 지금은 이름으로 추정한 값이다. null이면 레버리지 축이 `미분류` |
| `delisted_on` | date | Y | 상장폐지일. null이면 상장 중. 백엔드는 이 값이 있는 종목을 검색에서 빼고 알림을 `종목 정보 없음`으로 둔다. 집계는 이 값과 무관하게 조인한다 |
| `exchange` | text | Y | 미국 주식의 거래소. 백엔드는 읽지 않는다 |

검색은 이름 · 종목코드 부분 일치다. 인덱스는 데이터팀 소유 표라 백엔드가 걸지 않는다(검색 성능은 실행 계획 미확인).

### 4.2 `dim_market_calendar` — 시장 캘린더

| 항목 | 내용 |
|---|---|
| 뜻 | 시장마다 그날이 거래일인지와 개장 · 마감 시각. 두 기능의 날짜 판정이 모두 이 표 하나에서 온다([8.2](#82-시장-캘린더는-공용이다)) |
| 그레인 · 키 | 시장 × 날짜 1행 · PK `(market, date)`. 비거래일도 행이 있다 |
| 쓰는 쪽 | 데이터팀 |
| 범위 | KR · US. 과거 300거래일 이상 ~ 앞으로 1년 |
| 언제까지 | 휴장 · 개장 시각 변경이 공표되면 그 날짜 직전 KR 거래일까지. 앞으로 1년이 늘 채워져 있어야 한다 |
| 완료 신호 | 없음 |
| 안 지켜질 때 | 포트폴리오는 그날 행이 생길 때까지 라인 생성과 확정을 기다린다(수집 안내의 연속 실패 계산만 평일로 어림한다). 알림은 행이 없는 날을 평일이면 거래일로 보고, 정규 시각(국내 09:00 ~ 15:30, 미국 09:30 ~ 16:00 현지)으로 어림한다 — 휴장일이 `거래 없음`으로 평가될 수 있다 |

| 컬럼 | 타입 | null | 뜻 |
|---|---|---|---|
| `market` | text | N | `KR` · `US` |
| `date` | date | N | 시장 현지 날짜 |
| `is_trading_day` | boolean | N | 정규장이 열리는 날 |
| `prev_trading_day` | date | N | 이 날짜 앞의 가장 가까운 거래일. 비거래일 행에도 채운다 |
| `next_trading_day` | date | N | 이 날짜 뒤의 가장 가까운 거래일 |
| `open_at` | timestamptz | Y | 정규장 개장 시각. 늦게 여는 날(수능일 등)을 반영한다. 비거래일 null |
| `close_at` | timestamptz | Y | 정규장 마감 시각. 일찍 닫는 날을 반영하고 시간외는 넣지 않는다. 비거래일 null |

### 4.3 `corporate_action` — 기업행위

| 항목 | 내용 |
|---|---|
| 뜻 | 보유 수량과 평단을 바꾸는 기업행위 원본. 포트폴리오는 이 원본으로 수량 · 평단을 고치고 종목 상세에 이력을 보인다. 알림은 이 표를 읽지 않고 이 표로 보정된 일봉을 읽는다([8.4](#84-기업행위--포트폴리오는-원본-알림은-보정-일봉)) |
| 그레인 · 키 | 종목 × 기업행위 1행 · PK `(instrument_id, ex_date, type)` |
| 쓰는 쪽 | 데이터팀. 매번 전체를 맞춘다 — 데이터팀이 틀렸다고 거둔 행은 앱 DB에서도 지운다 |
| 범위 | 국내 주식. 기간은 `ca_coverage`가 밝힌다 |
| 언제까지 | 거래일마다. 그 `ex_date`의 일봉 보정과 같은 적재 단위로, 그 거래일의 `DAILY_BAR` 완료 신호보다 늦지 않게 |
| 완료 신호 | 없음 |
| 안 지켜질 때 | 확보 구간 밖이면 백엔드가 그 종목에 "기업행위를 확인하지 못함"을 세운다. **확보 구간 안인데 행이 빠지면** 틀린 평단 · 실현손익이 경고 없이 나간다 — 백엔드가 알아챌 수단이 없다 |

| 컬럼 | 타입 | null | 뜻 |
|---|---|---|---|
| `instrument_id` | uuid | N | 기업행위가 일어난 종목. 합병이면 사라지는 종목이다 |
| `type` | text | N | `SPLIT`(무상증자 · 액면분할 · 병합 · 감자처럼 주식 수만 바꾸는 행위) · `MERGER`(합병) · `RIGHTS`(유상증자. CHECK에는 있으나 데이터팀이 만들지 않는다) |
| `ratio` | numeric(18,8) | N | 행위 후 주식 수 ÷ 행위 전 주식 수. 2:1 분할은 `2`, 5:1 병합은 `0.2` |
| `ex_date` | date | N | 새 주식 수로 거래하는 첫날(권리락일) |
| `new_instrument_id` | uuid | Y | 합병의 존속회사 종목. 백엔드는 읽지 않는다 |

백엔드는 과거 체결을 다시 쓰지 않고 `ex_date` 시점에 상태만 고친다. `SPLIT`이면 수량 × `ratio`, 평단 ÷ `ratio`로 고치고, `MERGER` · `RIGHTS`는 수량을 바꾸지 않고 그 구간을 "기업행위를 확인하지 못함"으로 둔다.

### 5.1 `adjusted_price_daily` — 수정주가 일봉

| 항목 | 내용 |
|---|---|
| 뜻 | 기업행위로 보정한 일봉. 알림의 모든 종가 평가와 장중 평가의 기준선, 포트폴리오의 보유 종목 종가 평가([6.6](#66-balance_close_valuation--종가-평가-뷰))와 ETF 분해의 구성종목 가격([8.5](#85-구성종목-가격은-일봉에서-온다)), 종목 검색의 직전 종가가 이 표에서 온다 |
| 그레인 · 키 | 종목 × 거래일 1행 · PK `(instrument_id, date)`. **그 종목이 거래된 날만 행이 있다** — 거래정지일(거래량 0)은 행을 만들지 않는다 |
| 쓰는 쪽 | 데이터팀. 기업행위가 새로 반영되면 그 종목의 과거 봉 전체를 한 트랜잭션에서 다시 쓴다 — 백엔드가 반쯤 바뀐 계열을 보지 않는다 |
| 범위 | 국내 코스피 · 코스닥 주식과 국내 ETF, 미국은 종목 마스터의 미국 종목 전체. 종목마다 최소 300거래일(상장이 그보다 짧으면 상장일부터) |
| 언제까지 | 국내: 장 마감 뒤 당일 중. 미국: 다음 미국 장 개장 전 — 국내 휴장과 무관하다. 미국 장중 알림이 직전 일봉을 기준선으로 쓴다 |
| 완료 신호 | `market_data_run`(시장, `DAILY_BAR`, 그 거래일의 `close_at`) |
| 안 지켜질 때 | 백엔드는 `DONE`이 될 때까지 그날 종가 평가를 기다리고, 다음 거래일 신호가 먼저 오면 그날 없이 평가한다(`데이터 없음`). 기대 시각이 지나면 알림 탭에 데이터 지연 안내를 띄운다. 국내는 하루 종가 변동이 ±30%를 넘는 봉이 계산 창에 있으면 `가격 보정 대기`로 평가를 미루고, 미국은 보정 누락을 알아챌 수단이 없다 |

| 컬럼 | 타입 | null | 뜻 |
|---|---|---|---|
| `instrument_id` | uuid | N | |
| `date` | date | N | 시장 현지 거래일 |
| `open` · `high` · `low` · `close` | numeric(20,4) | N | 보정 가격. 종목 통화 단위 |
| `volume` | numeric(20,4) | N | 보정 거래량(분할 비율을 곱해 소수가 생길 수 있다) |
| `adj_factor` | numeric(18,8) | N | 보정 가격 = 원래 가격 × `adj_factor`. 그 봉 뒤로 기업행위가 없으면 `1`. 포트폴리오는 이 값으로 나눠 원래 가격으로 되돌린다 |

- **왜 300거래일인가.** 알림 카탈로그 상한 안에서 평가가 읽는 봉 수의 최대가 274다(RSI 계산 창 250 + 변화량 5 + 연속 19). 백엔드는 종목마다 최근 300봉을 읽는다.
- **왜 보정 계열인가.** 보정하지 않은 계열로 지표를 계산하면 액면분할 날 그 종목의 이동평균 교차 · 거래량 급증 · RSI 알림이 한꺼번에 울린다.
- **거래정지일에 행을 만들지 않는 이유.** 알림은 그 종목이 거래된 봉으로 계열을 만든다. 거래일인데 그날 봉이 없으면 `거래 없음`으로 평가하는데, 직전 값으로 채운 행은 정지를 가린다.

### 5.3 `intraday_quote` — 장중 시세

| 항목 | 내용 |
|---|---|
| 뜻 | 장중 알림 대상 종목의 현재가와 누적 거래량. 한 번에 쓰는 묶음 하나를 "벌"이라 한다 |
| 그레인 · 키 | 종목 × 시세 시각 1행 · PK `(instrument_id, snapshot_at)` |
| 쓰는 쪽 | 데이터팀(앱 DB에 직접) |
| 범위 | `alert_watchlist`에서 `intraday`가 참인 종목. KR · US |
| 언제까지 | 장중(`open_at` ~ `close_at`) 5분 이하 간격으로 한 벌씩. 각 벌이 `snapshot_at`에서 허용 지연 안에 있어야 한다 — 국내 10분, 미국 20분(15분 지연 시세 허용). 보관은 최소 당일분(미국은 현지 거래일) |
| 완료 신호 | 벌마다 `market_data_run`(시장, `INTRADAY_QUOTE`, `snapshot_at`) |
| 안 지켜질 때 | 허용 지연을 넘은 벌은 도착해도 평가하지 않는다. 장 시간 안에 마지막 벌(없으면 개장 시각)에서 허용 지연이 지나면 데이터 지연 안내를 띄운다. 그 시각의 벌에 종목 행이 없으면 앞선 값을 쓰지 않고 `데이터 없음`이다. 아예 확보하지 못하는 동안은 운영자가 장중 데이터를 닫는다(장중 알림은 종가로 평가, N분 이상 유지 조건이 있으면 일시중지) |

| 컬럼 | 타입 | null | 뜻 |
|---|---|---|---|
| `instrument_id` | uuid | N | |
| `snapshot_at` | timestamptz | N | **그 벌이 나타내는 시세 기준 시각.** 수집 시각이 아니다 — 원천이 15분 지연 시세면 15분 이른 시각이다. 한 벌의 모든 행이 같은 값이고 그 벌의 `market_data_run.as_of`와 같다 |
| `price` | numeric(20,4) | N | 현재가. 종목 통화 단위. 원래 가격이다 — 보정 일봉은 가장 최근 주식 수 기준이라 당일 원래 가격과 같은 척도다 |
| `cum_volume` | numeric(20,0) | N | 당일 누적 거래량 |

`snapshot_at`을 시세 기준 시각으로 두는 이유: 허용 지연과 N분 이상 유지는 "그 가격이 언제의 가격인가"로 가른다. 수집 시각으로 두면 지연 시세가 방금 시세로 보인다.

> **결정 필요 — `intraday_prev_close`(전일 기준가)를 쓸지.** 데이터팀은 장중 수집과 같은 응답에서 종목별 전일 대비 기준가를 `data.intraday_prev_close`(종목당 1행, `prev_close` · `as_of`)에 쓰고, 그쪽 DDL은 "백엔드가 as_of가 지금 장 회차일 때만 쓴다"고 적는다. 백엔드는 이 표를 읽지 않고 장중 급등락 기준선을 직전 거래일 일봉 종가로 잡는다. 그래서 일봉이 아직 없는 신규 상장 종목은 급등락 조건을 평가하지 못한다. 쓸지(백엔드가 기준선 폴백으로 읽는다), 안 쓸지(데이터팀에 알려 그쪽 서술을 고친다)를 정해야 한다.

### 5.4 `market_data_run` — 시장 데이터 완료 신호

| 항목 | 내용 |
|---|---|
| 뜻 | 시장 데이터가 앱 DB에 다 들어왔다는 신호. 알림 평가는 이 행을 보고 시작한다 |
| 그레인 · 키 | 시장 × 데이터 종류 × 데이터 시점 1행 · PK `(market, kind, as_of)` |
| 쓰는 쪽 | 데이터팀. 백엔드는 읽기만 한다 |
| 범위 | KR: `INTRADAY_QUOTE` · `DAILY_BAR` · `DAILY_FLOW`. US: `INTRADAY_QUOTE` · `DAILY_BAR` |
| 언제까지 | 해당 데이터의 "언제까지"와 같다 |
| 완료 신호 | 이 표 자체 |
| 안 지켜질 때 | 신호가 없으면 그 데이터를 기다리고 평가하지 않는다. 거래일 D의 신호가 `DONE`이 되기 전에 다음 거래일의 같은 종류가 `DONE`이 되면 D는 그 데이터 없이 평가한다. **일부만 적재한 채 `DONE`을 쓰면** 빠진 종목이 `거래 없음`으로 평가되고 N일 연속 조건이 끊긴다 — 백엔드가 알아챌 수 없다 |

| 컬럼 | 타입 | null | 뜻 |
|---|---|---|---|
| `market` | text | N | `KR` · `US` |
| `kind` | text | N | `INTRADAY_QUOTE` · `DAILY_BAR` · `DAILY_FLOW` |
| `as_of` | timestamptz | N | 장중은 그 벌의 `snapshot_at`, 일별은 그 거래일의 `close_at` |
| `state` | text | N | `RUNNING` · `DONE` · `FAILED`. 백엔드는 `DONE`만 완료로 본다 |
| `finished_at` | timestamptz | Y | `DONE` · `FAILED`가 된 시각. 백엔드는 읽지 않는다 |

- **`DONE`의 뜻**: 그 시장의 대상 종목 전체가 그 시점까지 `data` 스키마에 반영됐다. 레이크 적재가 끝난 시점이 아니다. 대상에서 빠지는 것은 그날 거래가 없던 종목(거래정지)과 상장폐지 종목뿐이고, 하나라도 빠지면 `FAILED`다.
- **상태 전이**: `RUNNING → DONE`, `RUNNING → FAILED`, `FAILED → RUNNING`(재시도). `DONE`이 된 행은 바꾸지 않는다. 기업행위로 과거 봉을 다시 쓸 때 새 신호는 필요 없다 — 백엔드는 평가할 때마다 이력을 다시 읽는다.
- **누락일**: 그 시장 · 종류의 첫 `DONE` 거래일부터, 거래일인데 `DONE`이 없는 날은 그 봉이 일부 들어와 있어도 계열에서 뺀다.
- **기대 시각**(백엔드가 데이터 지연 안내를 띄우는 기준): 국내 일봉은 그 거래일 다음 날 0시(한국), 미국 일봉은 다음 미국 거래일 개장, 수급은 다음 KR 거래일 개장, 장중은 마지막 벌 + 허용 지연.

| 쓰는 쪽 | 데이터팀 |
| 범위 | 국내 ETF. 미국 ETF는 없다([9.1](#91-지금-지켜지지-않는-것)) |
| 언제까지 | 운용사 구성 파일이 바뀔 때마다. 백엔드는 조회할 때 최신을 읽으므로 정해진 마감은 없다 |
| 완료 신호 | 없음 |
| 안 지켜질 때 | 늦으면 이전 기준일의 구성비중으로 나누고 화면에 그 기준일을 알린다. `etf_coverage`가 `COVERED`가 아니면 나누지 않고 ETF 한 행으로 두며 미분해 금액을 알린다 |

| 컬럼 | 타입 | null | 뜻 |
|---|---|---|---|
| `as_of` | date | N | 구성비중 기준일 |
| `etf_instrument_id` | uuid | N | |
| `underlying_instrument_id` | uuid | N | **최종** 구성종목. 중첩 ETF는 이미 펼쳐져 있다 |
| `weight` | numeric(9,6) | N | 0 ~ 1 비율. ETF별 합이 1과 다를 수 있다 |

- **한 겹으로 준다.** 중첩 분해 · 순환 차단 · 종목 매칭은 데이터팀이 끝낸다. 끝까지 펼치지 못한 ETF는 행을 만들지 않고 `etf_coverage`를 `UNAVAILABLE`로 둔다 — 일부만 펼친 결과는 백엔드가 총합으로 검증할 수 없다.
- 종목 마스터에 없는 구성종목(채권 · 선물 · 다른 시장 종목)은 행을 만들지 않는다. 그 몫과 ETF 안 현금(`CASH` 구성종목)은 백엔드에서 `기타`가 된다.
- **비중 합은 원본 그대로 둔다.** 백엔드는 ETF마다 가장 늦은 기준일의 양수 비중만 쓰고, 합이 1 이하면 모자란 몫을 `기타`로, 1을 넘으면 합으로 나눠 전액을 배분한다.

| 쓰는 쪽 | 데이터팀 |

| 뜻 | 계좌 × 시장마다 체결을 빠짐없이 가진 기간. 등급 판정(`추정`의 근거)과 자산 변화의 투자손익 확정 · 평가 분해가 쓴다 |
| 그레인 · 키 | 계좌 × 시장 1행 · PK `(account_ref, market)`. 시장마다 그 시장 체결 조회가 성공한 창으로 만들어 한 시장의 조회 실패가 다른 시장 판정을 바꾸지 않는다 |
| 쓰는 쪽 | 데이터팀. 매번 전체를 맞추고, 거둔 구간의 행은 지운다 |
| 범위 | 수집한 계좌. 행이 없는 계좌 × 시장은 미확보다 |
| 언제까지 · 완료 신호 | `cln_trade`와 같은 적재 단위 |
| 안 지켜질 때 | 국내 확보 구간이 그날까지 오지 않으면 그 계좌의 평단 계산이 다음 확정일이 생길 때까지 기다렸다가 그날을 건너뛴다. 미국 확보 구간이 그날까지 오지 않으면 그 계좌의 미국 종목만 그날 미포함으로 계산한다. 보유한 시장 하나라도 구간을 덮지 못하면 자산 변화가 투자손익을 확정 · 평가로 나누지 않는다 |

| 컬럼 | 타입 | null | 뜻 |
|---|---|---|---|
| `account_ref` | text | N | |
| `market` | text | N | `KR` · `US`. 체결의 시장은 통화로 정한다(KRW → KR, USD → US) |
| `covered_from` · `covered_to` | date | N | 체결을 확보한 기간. 양 끝을 포함한다 |
| `is_definitive` | boolean | N | `covered_from`이 그 계좌의 최초 체결에 닿았는가. 참인데 잔고를 체결로 되감은 수량이 0이 아니면 백엔드는 그 수량을 매매 없이 들어온 것으로 보고 `추정`으로 둔다 |
| `empty_streak` | integer | N | 과거로 조회했을 때 연속 빈 응답 횟수. 백엔드는 읽지 않는다 |
| `computed_at` | timestamptz | N | 계산 시각. 백엔드는 평단 계산 뒤에 구간이 다시 계산됐는지를 이 값으로 본다 |

### 6.10 `cln_cashflow` — 배당 · 수수료 · 세금

| 항목 | 내용 |

| 뜻 | 계좌에 귀속되는 손익성 현금흐름. 자산 변화의 배당 · 수수료·세금 줄이 쓴다 |

| 범위 | 수집한 계좌. 지금 KIS 계좌는 배당만 있다(KIS에 수수료 · 세금 · 입출금 원천이 없다). 아직 지급되지 않은 배당은 넣지 않는다 |

| 컬럼 | 타입 | null | 뜻 |
|---|---|---|---|
| `cashflow_id` | text | N | `{account_ref}:{원천 키}`. 다시 수집해도 같은 값 |
| `account_ref` | text | N | |
| `type` | text | N | `DIVIDEND` · `FEE` · `TAX` — **이 셋만** |
| `amount` | numeric(20,4) | N | 계좌 현금 기준의 부호 있는 금액. 배당 · 환급은 양수, 수수료 · 세금은 음수. 배당은 원천징수 뒤 실제 입금액이다. 백엔드는 이 부호대로 더한다 |
| `currency` | text | N | `KRW` · `USD`. 백엔드는 USD를 발생일(한국 날짜) 이하 가장 늦은 `BASE` 환율로 바꾸고, 그런 행이 없으면 가장 이른 환율을 쓴다 |
| `occurred_at` | timestamptz | N | 지급 시각. 백엔드는 한국 날짜로 `(기초 기준일, 기말 기준일]`에 넣는다 |

**데이터팀이 걸러 내는 것**

| 빼는 것 | 이유 |
|---|---|
| 매매대금 입출금 · 예수금 내부 이동(RP · CMA 자동매수 · 환매) | 주식과 예수금 사이의 이동이라 총자산이 변하지 않는다 |
| 환전 | 통화 사이의 이동이라 원화 총자산이 변하지 않는다 |
| 매매 수수료 · 거래세 | 체결에 붙어 실현손익에 이미 들어간다. `FEE` · `TAX`는 계좌 관리 · 환전 수수료, 배당소득세 같은 매매 밖 비용만이다 |
| 입금 · 출금 | 사용자가 앱에서 입력한다([포트폴리오 · 4.6 입출금 입력과 미입력 판정](./portfolio.md)). `type` CHECK가 받지 않는다 |

### 6.11 `cln_cashflow_coverage` — 배당 · 수수료 · 세금 확보 구간

| 항목 | 내용 |
|---|---|
| 뜻 | 계좌 × 유형마다 원천에서 조회했는지와 그 기간. "조회했는데 0건"과 "조회하지 못함"을 가른다 |
| 그레인 · 키 | 계좌 × 유형 1행 · PK `(account_ref, type)` |
| 쓰는 쪽 | 데이터팀. 수집한 계좌마다 다섯 유형 모두 행을 만든다 |
| 범위 | 수집한 계좌. KIS 계좌는 `DIVIDEND`만 `COVERED`(모의투자 계좌는 그것도 `UNAVAILABLE`)이고 나머지는 `UNAVAILABLE`이다 |
| 언제까지 · 완료 신호 | `cln_cashflow`와 같은 적재 단위 |
| 안 지켜질 때 | 백엔드는 그 유형이 `COVERED`이고 구간이 그 계좌의 기간(기초 다음 날 ~ 기말)을 모두 덮을 때만 확보로 본다. 행이 없거나 `UNAVAILABLE`이거나 일부만 덮거나 비어 있으면 미확보로 보고 투자손익이 정확하지 않을 수 있다는 안내를 띄운다 |

| 컬럼 | 타입 | null | 뜻 |
|---|---|---|---|
| `account_ref` | text | N | |
| `type` | text | N | `DIVIDEND` · `FEE` · `TAX` · `DEPOSIT` · `WITHDRAW`. 백엔드는 `DEPOSIT` · `WITHDRAW` 행을 읽지 않는다 — 입출금은 사용자 입력으로 판정한다 |
| `state` | text | N | `COVERED`(원천에서 조회함) · `UNAVAILABLE`(원천이 없거나 조회하지 못함). 조회했는데 0건이면 `COVERED`이고 그 기간 행이 없는 것이다 |
| `covered_from` · `covered_to` | date | Y | `COVERED`가 보장하는 기간. 수집 창들을 이은 구간이다. 백엔드는 양 끝을 포함하는 날짜로 읽는다. `UNAVAILABLE`이면 null |
| `computed_at` | timestamptz | N | 계산 시각. 백엔드는 읽지 않는다 |

### 6.12 `collection_run` — 수집 실행

| 항목 | 내용 |
|---|---|
| 뜻 | 계좌 하나를 한 번 수집하는 요청과 그 진행 상태. 백엔드가 수집을 요청하는 큐이자, 데이터팀이 수집 끝을 알리는 완료 신호다 |
| 그레인 · 키 | 계좌 × 수집 실행 1행 · PK `run_id` |
| 쓰는 쪽 | **양쪽, 컬럼마다 정해져 있다**(아래 표). 같은 행을 두 팀이 쓰지만 같은 컬럼을 쓰지 않는다 |
| 범위 | 정기 수집은 데이터팀 계좌 목록([7.2](#72-계좌--라인--입출금--실현손익))에서 해제되지 않은 모든 계좌. 동기화는 사용자가 요청한 계좌 |
| 언제까지 | 정기 수집 행은 그 기준일의 확정 마감(다음 KR 거래일 08:00, 한국) 전에 `DONE`과 `silver_synced_at`까지 채워져야 한다. 동기화 행은 데이터팀 픽업 때 집힌다 |
| 완료 신호 | 이 표 자체. 백엔드는 `DONE`이고 `silver_synced_at`이 찬 행, 또는 `FAILED` · `REAUTH_REQUIRED` 행을 끝난 실행으로 처리한다 |
| 안 지켜질 때 | 그날 그 계좌의 정기 수집이 확정 마감까지 끝나지 않거나 실패하면 직전 확정 라인을 이월한다. 그날 정기 수집 행이 없는 계좌가 있으면 그날 확정이 마감까지 밀린다 |

| 컬럼 | 타입 | null | 쓰는 쪽 | 뜻 |
|---|---|---|---|---|
| `run_id` | uuid | N | 행을 만든 쪽 | |
| `account_ref` | text | N | 행을 만든 쪽 | 백엔드가 모르는 값이면 백엔드는 그 행을 처리하지 않는다 |
| `requested_by` | text | N | 행을 만든 쪽 | `SCHEDULE`(데이터팀이 만든 정기 수집) · `USER`(백엔드가 만든 동기화) |
| `as_of` | date | N | 행을 만든 쪽 | 수집 대상 기준일. 라인은 실행 시각이 아니라 이 날짜에 기록된다. 정기 수집은 KR 장 마감이 지난 가장 늦은 KR 거래일이다 |
| `requested_at` | timestamptz | N | 행을 만든 쪽 | 요청 시각. 백엔드는 계좌의 지금 인증 정보로 수집을 시작한 시각(`account.linked_at`)보다 이른 실행을 최근 수집과 수집 안내에서 뺀다 |
| `credential_ref` | text | Y | 백엔드 | 인증 정보 값의 SSM 이름([7.3](#73-인증-정보-값)). 값 자체가 아니다. 동기화 행은 넣을 때 채우고, 비어 있는 행(정기 수집 등)은 연동 중 · 연동됨 계좌에 한해 1분 간격으로 채운다 |
| `state` | text | N | 데이터팀 | `REQUESTED` · `RUNNING` · `DONE` · `FAILED` · `REAUTH_REQUIRED`. 백엔드는 동기화 행을 `REQUESTED`로 넣는다. KIS 수집은 `DONE` · `FAILED`로만 끝난다 |
| `finished_at` | timestamptz | Y | 데이터팀 | 끝난 시각. 백엔드는 이 시각 이하의 잔고를 그 실행의 것으로 읽는다 |
| `failure_reason` | text | Y | 데이터팀 | 실패 코드(화면 문구가 아니다). 백엔드는 `SOURCE_CREDENTIAL_INVALID`(앱키 · 앱 시크릿 거절)를 인증 실패로, 나머지를 일반 실패로 다룬다 |
| `warnings` | jsonb | Y | 데이터팀 | `DONE`이어도 빠진 조회. 백엔드는 읽지 않는다 |
| `silver_synced_at` | timestamptz | Y | 데이터팀 | 이 실행의 `cln_*`가 `data`에 반영된 시각 |

```
동기화        백엔드가 USER 행을 REQUESTED로 넣는다 (credential_ref 포함)
정기 수집     데이터팀이 계좌마다 SCHEDULE 행을 만든다 → 백엔드가 credential_ref를 채운다
픽업          데이터팀 워커가 credential_ref가 찬 REQUESTED 행을 RUNNING으로
수집 끝       데이터팀이 DONE / FAILED (+ failure_reason)
반영 끝       데이터팀이 cln_* 반영 뒤 silver_synced_at
라인 생성     백엔드가 끝난 실행을 계좌별로 처리
```

- **계좌 단위로 독립이다.** 한 계좌가 실패해도 나머지는 진행한다.
- **데이터팀은 다시 시도하지 않는다.** 끝난 행의 상태를 되돌리지 않고, 다시 받으려면 백엔드가 새 행을 만든다.
- 데이터팀은 지난 기준일의 정기 수집 행이 아직 `REQUESTED`면 `FAILED`(`EXPIRED`)로 닫는다 — 잔고 조회는 지금 시점만 주므로, 지난 행을 지금 수집하면 다른 날 잔고가 그 날짜로 적힌다. 동기화 행은 닫지 않으므로 백엔드가 동기화에 시한을 둔다([포트폴리오 · 5.6 수동 동기화](./portfolio.md)).
- 같은 날 같은 계좌에 정기 수집 행이 이미 있으면 데이터팀은 새로 만들지 않는다.
- 백엔드는 다음 픽업 예정 시각을 설정값으로 들고 있다가 "다음 수집(…)" 안내에 쓴다. 데이터팀 픽업 일정이 바뀌면 백엔드 설정도 함께 바꿔야 한다([9.1](#91-지금-지켜지지-않는-것)).
- 시장 데이터 완료 신호와 합치지 않는 이유는 [8.3](#83-완료-신호는-둘이다).

| 안 지켜질 때 | 데이터팀이 읽지 못하면 대상 0개로 끝나, 새 장중 알림 종목의 시세가 오지 않고 그 알림은 데이터 지연 안내 또는 `데이터 없음`이 된다. 알림이 사라진 종목을 계속 수집하는 것은 무해하다 |

|---|---|---|---|
| `instrument_id` | uuid | N | PK |
| `market` | text | N | `KR` · `US`. 종목 마스터의 시장 |

### 7.2 계좌 · 라인 · 입출금 · 실현손익

데이터팀은 백엔드 표를 하루 한 번 읽어 레이크에 남기고 세 가지에 쓴다. 읽을 컬럼은 데이터팀이 이름으로 골라 정한다.

| 표 | 데이터팀이 읽는 컬럼 | 쓰임 |
|---|---|---|
| `account` | `account_id` · `account_ref` · `broker` · `account_type` · `source` · `link_state` · `last_synced_at` | **정기 수집 대상 목록.** 정기 수집 행을 만들기 직전에 다시 읽어, `link_state`가 `DISCONNECTED`가 아닌 계좌마다 `SCHEDULE` 행을 만든다. 수집 경로는 `source`로 정한다 |
| `position_line` | 기준일 · 계좌 · 종목 · 수량 · 금액 · 환율 · `source_as_of` · 이월 · 확정 여부 | 수집한 수량과 라인 수량 대조 |
| `manual_cashflow` | `id` · `account_id` · `type` · `amount` · `currency` · `occurred_on` | 분석(레이크 전용) |
| `realized_pnl_line` | 체결 · 계좌 · 종목 · 금액 · 등급 | 분석(레이크 전용) |

데이터팀은 사용자 id · `credential_ref` · 계좌 라벨 · 입출금 메모를 가져가지 않는다.

**백엔드가 지키는 것**

- `account_ref`는 만든 뒤 바뀌지 않는다([2.3](#23-키와-제약)).
- `link_state`는 `CONNECTING`(연동 중, 첫 수집 전) · `CONNECTED`(연동됨) · `DISCONNECTED`(해제) 셋이다. 데이터팀 수집기에 남아 있는 `REAUTH_REQUIRED` 처리는 지금 쓰이지 않는다.
- `source`는 `KIS` 하나다.
- 위 컬럼의 이름 · 뜻을 바꾸려면 데이터팀과 먼저 맞춘다.

**안 지켜질 때**: 데이터팀이 계좌 목록을 읽지 못하면 그날 목록이 갱신되지 않아 새로 연동한 계좌에 정기 수집 행이 생기지 않는다(첫 수집이 밀린다). 해제한 계좌에 행이 생겨도 백엔드는 해제 계좌의 실행을 처리하지 않는다.

### 7.3 인증 정보 값

| 항목 | 내용 |
|---|---|
| 뜻 | 사용자가 넣은 KIS 앱키 · 앱 시크릿과 계좌번호. 데이터팀 워커가 증권사를 부를 때 쓴다 |
| 놓이는 곳 | SSM 파라미터 `/stock-project/accounts/<account_ref>`. 이 이름이 `collection_run.credential_ref`다. 백엔드 DB에는 값을 두지 않는다 |
| 쓰는 쪽 | 백엔드. 연동과 인증 정보 갱신 때 쓴다 |
| 읽는 쪽 | 데이터팀 워커. `credential_ref`로만 찾고 백엔드 계좌 표의 컬럼으로 찾지 않는다 |
| 안 지켜질 때 | 데이터팀이 읽지 못하거나 모양이 다르면 그 실행은 `FAILED`(`CREDENTIAL_UNREADABLE`)로 끝나고, 백엔드는 이월하며 연속 실패 안내를 띄운다 |

값은 JSON 하나다.

| 필드 | 뜻 |
|---|---|
| `app_key` · `app_secret` | KIS 앱키 · 앱 시크릿 |
| `cano` | 계좌번호 앞 8자리 |
| `acnt_prdt_cd` | 상품 코드. `01`(위탁) · `22`(연금저축) |
| `env` | `real`(실전) · `demo`(모의투자). 없으면 데이터팀 기본값을 따른다 |

### 7.4 권한 경계

| 계정 | `data` 스키마 | `app` 스키마 |
|---|---|---|
| 데이터팀 읽기(`dataeng_reader`) | 모든 표 읽기 | `app_user` · `push_device`를 뺀 모든 표 읽기 |
| 데이터팀 쓰기(`dataeng_writer`) | 모든 표 읽기 · 넣기 · 고치기 · 지우기, 표 만들기. `TRUNCATE`는 주지 않는다(도는 동안 앱 조회를 막는 배타 잠금이라) | 위와 같음(읽기만) |
| 백엔드(DB 소유 계정) | 권한으로는 모든 표에 쓸 수 있다. 계약으로 `collection_run`의 정해진 컬럼에만 쓴다 | 소유 |

- **`app` 스키마는 데이터팀 계정 모두 읽기만 한다.** 쓰기가 열리면 세션 표에 행을 넣어 남의 계정으로 로그인하거나, 앱 규칙을 거치지 않고 앱 데이터를 바꿀 수 있다.
- `app_user`는 비밀번호 해시가 있어, `push_device`는 기기에 푸시를 보낼 수 있는 자격이라 읽기도 주지 않는다.
- 그 밖의 `app` 표(계좌 · 라인 · 실현손익 · 입출금 · 알림 · 울림 · 세션 · 처리 기록 등)는 모두 읽을 수 있다. 표 단위로 좁히지 않고 데이터팀이 필요한 표 · 컬럼을 골라 읽는다. 새로 생기는 `app` 표도 같은 규칙으로 읽기가 열린다.
- 권한은 배포할 때마다 다시 적용해 따로 준 쓰기 권한이 남지 않게 한다.

## 8. 두 기능을 합쳐 정한 것

### 8.1 종목 마스터는 합집합이다

알림 범위(국내 상장 주식 · ETF 전체, 미국 상장 주식 · ETF)만으로는 포트폴리오가 필요한 종목을 다 덮지 못한다.

| 알림 범위 밖인데 포트폴리오에 필요한 종목 | 예 |
|---|---|
| 보유 중인 그 밖의 상장 증권 | ADR 등 |
| ETF 구성종목 | 국내 ETF가 담은 해외 종목 |
| 예수금 | `CASH` KRW · USD |
| 상장폐지 종목 | 과거 라인의 종목 |

그래서 범위를 "상장 종목 + 보유 종목(`cln_balance`) + 구성종목(`etf_constituent`) + 예수금 2행"으로 정한다. 데이터팀은 사용자를 몰라도 이 집합을 안다. 두 기능이 읽는 컬럼은 겹치지만 부딪히지 않는다 — 포트폴리오는 `asset_class` · `sector` · `is_leveraged`를, 알림은 `name` · `symbol` · `delisted_on`을 쓰고 `market` · `currency`는 둘 다 쓴다.

### 8.2 시장 캘린더는 공용이다

마감 시각을 두 팀 · 두 기능이 따로 계산하면 일찍 닫는 날 값이 어긋나므로, 날짜와 시각이 필요한 판정은 모두 `dim_market_calendar`에서 읽는다.

| 기능 | 판정 | 규칙 |
|---|---|---|
| 포트폴리오 | 라인을 만드는 날 | `collection_run.as_of`가 KR 거래일일 때만. 그날 캘린더 행이 없으면 생길 때까지 기다린다 |
| 포트폴리오 | 확정 마감 | 그 날짜 다음 KR 거래일 08:00(한국) |
| 포트폴리오 | 시장별 가격 기준일 | `source_as_of` 이전에 `close_at`이 지난 그 시장의 마지막 거래일. 종가 평가 뷰가 정하고 백엔드가 라인에 남긴다. ETF 분해의 구성종목 가격도 같은 규칙이다 |
| 포트폴리오 | 정기 수집 기준일 | KR 장 마감이 지난 가장 늦은 KR 거래일(데이터팀이 행을 만들 때) |
| 포트폴리오 | 연속 수집 실패 | KR 거래일로 센다. 캘린더 행이 없는 날은 평일이면 거래일로 본다 |
| 알림 | 거래일 · N일 연속 | 그 종목 시장의 `is_trading_day` |
| 알림 | 종가의 데이터 시점 | 그 거래일의 `close_at`. `market_data_run.as_of`도 같은 값 |
| 알림 | 장중 데이터 지연 | `open_at` ~ `close_at` 안에서만 본다 |
| 알림 | 캘린더 행이 없는 날 | 평일이면 거래일, 시각은 정규 시각으로 어림한다(포트폴리오의 라인 생성과 확정은 어림하지 않고 기다린다) |

### 8.3 완료 신호는 둘이다

둘 다 "데이터가 왔다"를 알리지만 하나로 합치지 않는다.

| | `collection_run` | `market_data_run` |
|---|---|---|
| 그레인 | 계좌 × 실행 | 시장 × 데이터 종류 × 데이터 시점 |
| 쓰는 쪽 | 양쪽 — 백엔드가 요청하고 데이터팀이 진행을 쓴다 | 데이터팀만 |
| 시점 타입 | date — 하루 한 벌의 기준일 | timestamptz — 장중은 분 단위 |
| `DONE`의 뜻 | 그 계좌 하나의 수집과 반영이 끝났다 | 그 시장 대상 종목 전체가 반영됐다 |
| 실패 단위 | 계좌마다 — 실패 계좌만 이월 | 시장마다 — 다음 시점이 오면 넘어감 |
| 민감 정보 | 인증 정보 참조가 실린다 | 없다 |

합치면 한 표가 두 그레인을 갖고, 상태 값의 절반이 행마다 뜻이 없으며, 인증 정보 참조가 실리는 표에 시장 데이터 신호까지 섞여 권한을 좁힐 수 없다.

### 8.4 기업행위 — 포트폴리오는 원본, 알림은 보정 일봉

같은 기업행위를 두 기능이 다른 모양으로 받는다. 둘 다 필요하다.

| | 받는 것 | 이유 |
|---|---|---|
| 포트폴리오 | `corporate_action` 원본 + `ca_coverage` | 가격이 아니라 보유 수량과 평단을 고친다. 보정 가격 계열로는 수량을 고칠 수 없다 |
| 알림 | 보정된 `adjusted_price_daily` | 지표를 가격 계열로 계산한다. 백엔드가 평가마다 기업행위를 적용하면 같은 계산이 반복된다 |

포트폴리오는 보유 종목 평가에도 일봉 종가를 쓰는데, 이때는 `adj_factor`로 되돌린 원래 가격을 그날 수량과 곱한다. 같은 사실이 두 결과로 갈라지지 않게 다음을 약속한다.

1. 일봉 보정은 `corporate_action`에 있는 행만으로 한다.
2. `corporate_action`의 새 행과 그것으로 다시 보정한 일봉은 같은 적재 단위로 반영하고, 그 뒤에 `DAILY_BAR` 완료 신호를 쓴다.
3. 일봉에 `adj_factor`를 두어 보정 결과를 `corporate_action`과 대조할 수 있게 한다.

약속을 지켜도 두 기능의 판단은 다를 수 있고 그것이 정상이다. 포트폴리오의 "기업행위를 확인하지 못함"은 "이 보유 기간의 기업행위를 확인했는가"를, 알림의 `가격 보정 대기`는 "이 계산 창에 보정 누락의 증거(국내 ±30% 초과 봉)가 있는가"를 묻는다. 미국은 가격제한폭이 없어 알림에 누락을 알아챌 수단이 없으므로 위 약속이 유일한 방어다. 지금 국내 · 미국 모두 약속이 다 지켜지지는 않는다([9.1](#91-지금-지켜지지-않는-것)).

### 8.5 구성종목 가격은 일봉에서 온다

ETF를 나누면 구성종목 행에 환산수량(안분한 원화 ÷ (구성종목 종가 × 환율))이 나간다. 그 가격을 주는 표를 따로 두지 않고 `adjusted_price_daily`의 종가를 쓴다 — 같은 가격 데이터를 한 곳에서 받으면 원천도 품질 관리도 하나다. 쓰는 종가는 시장별 가격 기준일([8.2](#82-시장-캘린더는-공용이다))의 것이고, 그날 종가나 필요한 환율이 없으면 이전 날로 대신하지 않고 환산수량을 비운다.

## 9. 알려진 한계

### 9.1 지금 지켜지지 않는 것

| 한계 | 백엔드 · 화면에 미치는 영향 | 풀리는 조건 |
|---|---|---|
| **미국 체결 확보 구간이 오지 않는다.** 데이터팀은 체결 확보 구간을 기본으로 국내만 보내고, 미국 체결은 수수료 · 세금 원천이 없어 보내지 않는다 | 미국 종목 매도는 실현손익에서 미포함이고, 미국 종목을 가진 계좌는 자산 변화가 투자손익을 확정 · 평가로 나누지 않는다. 백엔드는 국내만 와도, 둘 다 와도 동작한다 | 데이터팀이 미국 체결의 수수료 · 세금을 채우고 미국 확보 구간 행을 보낸다 |
| **종목 마스터에 맞지 않는 보유 종목은 잔고 행이 오지 않는다.** 데이터팀은 종목을 정하지 못한 잔고 행을 버린다 | 그 종목이 총자산에서 빠지고 안내도 없다. 백엔드의 "마스터에 없는 종목" 처리(재시도 후 이월)는 이 경우 걸리지 않는다 | 매칭하지 못한 종목도 자리 표시 종목으로 마스터와 잔고에 넣는다 |
| **`instrument_id`가 종목코드에 묶여 있다.** (시장, 종목코드)로 만든 값이라 종목코드가 바뀌면 새 id가 된다 | 옛 id의 라인 · 알림이 새 시세와 이어지지 않는다(옛 행은 남아 있어 과거 총자산은 유지된다) | 같은 종목이면 종목코드가 바뀌어도 id를 유지한다 |
| **`delisted_on`이 늘 비어 있다.** 데이터팀 마스터가 상장폐지를 반영하지 않는다 | 상장폐지 종목이 검색에 남고 그 종목의 알림이 상장폐지로 다뤄지지 않는다 | 상장폐지일을 채운다 |
| **국내 ETF · 미국 종목의 기업행위를 확인하지 않는다.** `ca_coverage`가 `UNAVAILABLE`이다 | 그 종목은 늘 "기업행위를 확인하지 못함" 안내가 붙는다 | 원천을 확보한다 |
| **미국 일봉이 보정되지 않는다.** 미국 `corporate_action` 행이 없다 | 미국 분할 날 이동평균 교차 · 거래량 급증 · RSI 알림이 잘못 울릴 수 있고 백엔드는 알아채지 못한다. 보유 평가는 분할 대기 가드(`SPLIT_PENDING`)로 원천 평가금액을 쓴다 | 미국 기업행위 원천을 확보해 보정한다 |
| **국내 일봉은 원천이 보정한 계열이고 `adj_factor`가 늘 1이다** | 일봉 보정이 `corporate_action`과 다른 원천에서 오고(약속 1 · 3), 보정을 `corporate_action`과 대조할 수 없다. 포트폴리오 종가 평가는 수집 직전 거래일 종가만 읽어 지금은 값이 틀리지 않는다 | 데이터팀이 국내도 원래 가격 + `corporate_action` 보정으로 바꾼다 |
| **미국 ETF 구성종목이 없다** | 미국 ETF는 ETF 분해에서 늘 미분해다 | 원천을 확보한다 |
| **KIS 계좌는 수수료 · 세금 내역이 없다** | KIS 계좌가 든 자산 변화에는 수수료·세금 내역이 확보되지 않았다는 안내가 늘 붙는다 | 원천이 생긴다(KIS에는 없다) |
| **수집은 클러스터가 켜진 시간에만 돈다** | 꺼진 시간대에 걸린 약속(예: 장중 시세, 장 마감 뒤 당일 중 일봉)은 그 시간대에 지켜지지 않고 백엔드는 위 블록의 "안 지켜질 때"대로 동작한다. 가동 시간은 이 문서에 적지 않는다 | 가동 시간이 약속 시각을 덮는다 |
| **픽업 일정을 백엔드가 설정값으로 따로 들고 있다** | 데이터팀 일정이 바뀌고 백엔드 설정이 그대로면 "다음 수집(…)" 안내 시각이 틀린다 | 일정을 바꿀 때 두 팀이 함께 바꾼다 |

### 9.2 미러가 데이터팀 표와 다른 점

백엔드 미러는 로컬 · 테스트에서만 쓴다. 아래 차이 때문에 그 경로는 백엔드 테스트가 덮지 않는다.

| 표 | 미러에 없는 것 · 다른 것 | 영향 |
|---|---|---|
| `balance_close_valuation` | 미국 분할 대기 가드(`SPLIT_PENDING`)와 그것이 읽는 `split_schedule`이 없다 | 분할 대기 행은 종가가 없는 행과 같은 모양(`close_date` 비움, `close_value` = 원천 평가금액)이라 백엔드 처리는 같지만 테스트로 확인하지 않는다 |
| `instrument` | `exchange` 컬럼이 없고, `currency`에 CHECK가 있다(정본은 없음) | 백엔드는 `exchange`를 읽지 않는다 |
| `corporate_action` | `new_instrument_id` 컬럼이 없다 | 백엔드는 읽지 않는다 |
| `collection_run` | `warnings` 컬럼과 `state` 기본값이 없다 | 백엔드는 `warnings`를 읽지 않고, 동기화 행의 `state`를 직접 넣는다 |
