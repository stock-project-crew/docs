- 주석 정리는 `comment-rules.md`를 따른다. 범위는 문서 지칭 · 히스토리 · 일회성 관찰 · 되풀이 · 검증 안 한 단정 정리와 마이그레이션 컬럼 설명 보완이다. 중요도에 따라 분량 · 깊이를 맞추는 일은 시간 관계상 뺀다(11/15 결정).
- 용어 통일은 주석 정리에서 하지 않는다. E단계 설계서 재편 때 다음 순서로 한다(11/15 결정).
  1. 설계서 세 개(common · portfolio · alert)와 계약 문서를 쓰며 용어표를 만든다. 한 개념에 한 낱말, 쓰지 않을 동의어, 코드 이름(클래스 · 컬럼)과의 대응을 적는다.
  2. 코드 주석 · 테스트 이름 · 사용자 문구에서 용어표와 다른 말을 찾아 목록으로 만든다. 사용자 문구는 화면이 바뀌므로 따로 승인받는다.
  3. 주석과 테스트 이름은 `comment-rules.md`의 형식 규칙과 함께 일괄로 고친다. 코드 식별자(클래스 · 메서드 · 컬럼 이름)는 바꾸지 않는다.

- 주석 정리 중 찾은 코드 수정 후보: 앱 `types.ts`의 계좌 `last_synced_at`이 리터럴 `null` 타입이라 서버가 채워 보내는 마지막 동기화 시각을 버린다. 계좌 화면(`AccountRow`)은 그 값이 늘 비어 있다는 전제로 마지막 동기화를 보이지 않는다. 고칠지 따로 정한다.

## 8. ADR 목록

이직용 포트폴리오로 쓴다. 결정은 이미 끝났으므로 사후에 정리했다고 밝힌다.

**고른 방법**
1. 결정 전수 목록(`decision-inventory.md`, 412건)에서 버린 대안이 원천에 있는 306건만 남겼다.
2. 고정 기준으로 채점하고 ADR 크기 주제 49개로 묶었다(`decision-scores.md`). 기준은 일반성, 놓친 역량(운영·관측, 부하, 동시성, 쿼리·인덱스) 연결, 돌아볼 결과(결함·사고·바꾼 결정)이고 각 0~2점이다.
3. 상위 주제의 근거를 원천에서 다시 확인했고, "X 대신 Y를 골랐다"는 한 문장으로 요약되는지를 더 봤다. 이 문장이 안 나오는 주제(관측·종료 처리, DB 인프라, 테스트 전략)는 ADR에서 뺐다.
4. 같은 "중복 없이 한 번" 주제를 원칙(1)과 작업별 구현(2·3)으로 나눴다. 잠금 순서는 따로 쓰면 돌아볼 거리가 얇아 2에 넣었다.

- 겹침: 1은 원칙만, 2·3은 1을 링크하고 원칙을 되풀이하지 않는다. GROUPING SETS 쿼리 설명은 4에만 두고 5는 링크한다.
- README에는 대표 3개를 앞에 둔다: 1(동시성), 6(운영), 5(쿼리 튜닝 실측). 나머지는 목록으로 연결한다.
- 쓰는 조건: 사용자가 직접 결정했고 면접에서 방어할 수 있어야 한다. 쓰다가 막히면 뺀다.
- 5의 근거 보강: E단계에서 운영 DB에 EXPLAIN을 떠서 실행 계획을 확인한다. 운영 DB 읽기라 승인이 필요하고 클러스터가 켜져 있을 때만 할 수 있다. 확인 전에는 문서에 "실행 계획 미확인"이라 쓴다.

**예비**
- 데이터팀 연동 계약(같은 Postgres + collection_run): 팀 회의록에 결정란이 비어 결정 시점·주체를 원천으로 댈 수 없다. 사용자 역할을 분명히 적을 수 있을 때만 넣는다.

**ADR이 아닌 곳으로 가는 것**
- 트러블슈팅 글: DB 역할 권한(R1, 회수 목록이 새 표를 자동으로 열었다), DB 인프라(shm 64MB로 병렬 VACUUM 실패, 테스트 DB 번호 충돌). 그 밖의 후보는 H단계에서 정한다.
- 고도화·회고: 관측·종료 처리는 D단계 과제 E, 테스트 전략은 H단계 회고.
- 설계서 본문: 확정 두 층, MyBatis, 평단 계산, 알림 평가 주기, TanStack Query, SSM·HMAC account_ref는 결론과 이유만 설계서에 둔다.
