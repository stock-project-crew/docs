# 주석 규칙

back-end · front-end의 코드 주석(Java · TS · TSX · SQL · YAML)에 적용한다. 테스트 코드도 같다.
사용자에게 보이는 문구(오류 메시지, 화면 글자)와 코드 동작은 범위 밖이다.

## 1. 남길지 판단하는 질문

> 이 줄을 바꾸거나 지우려는 사람이 이걸 모르면 틀리게 고치는가?

그렇다면 남긴다. 남기는 내용은 셋 중 하나다.

- 이유: 왜 이렇게 했나
- 제약: 바꾸면 무엇이 깨지나
- 계약: 다른 쪽(앱 · 서버 · 데이터팀 · DB · 외부 API)이 무엇을 기대하나

## 2. 지우거나 고칠 것

| 유형 | 알아보는 법 | 처리 |
|---|---|---|
| 문서 지칭 | `§`, `SG-`, `D-`, `N1`처럼 문서의 번호, 문서 경로, "스펙 · 설계 · 계획 · 결정에 따라" | 그 번호가 가리키던 근거를 그 자리에 풀어 쓴다. 이유가 주석에 이미 있으면 지칭만 지운다 |
| 히스토리 | 예전 동작, 바뀐 경위, 버그 이야기, "이번에", "새로", "~로 바꿨다", 커밋 · 브랜치 · 날짜 | 지금의 사실과 이유만 남긴다. 과거 버그에서 나온 경고는 그 위험을 현재형으로 쓴다 — "예전엔 X라 Y가 깨져 바꿨다" → "X로 하면 Y가 깨진다" |
| 일회성 관찰 | 실측 수치(ms, 건수, 크기), 특정 날의 재현, 지금만 맞는 상황(지금 계좌가 몇 개 등) | 계속 지켜지는 설계 전제면 일반화해 남긴다("사용자가 적어 잠금 대기를 감수한다"). 아니면 지운다 |
| 되풀이 | 이름 · 타입 · 코드가 이미 말하는 것 | 지운다 |
| 검증 안 한 단정 | 확인하지 않은 동작을 확정으로 씀 | 코드로 확인되면 남긴다. 안 되면 지우고 보고 목록에 올린다 |

- **부정 제약은 되풀이가 아니다.** "version은 바꾸지 않는다", "iOS에만 보낸다"처럼 하지 않는 일 · 좁힌 범위는 코드에 드러나지 않는다. 이유를 코드로 확인하면 붙이고, 못 하면 그대로 두고 보고 목록에 올린다. 지우지 않는다.
- **함수 이름을 문장으로 옮긴 첫 문장은 지운다.** `withLeft`의 "왼쪽 지표를 바꾼다." 뒤 문장만 남긴다.
- **결과는 맞고 장치가 틀리면** 코드로 확인한 장치로 고쳐 쓴다(예: "RETURNING이라 한쪽만 옮긴다" → 행 잠금 뒤 조건을 다시 보는 동작).

낱말로 판단하지 않는다. "실측"(측정된 잔고), "당시의 문구"(울린 때의 문구를 보여 주는 화면 동작)처럼 도메인 용어이거나 지금의 동작을 말하면 히스토리가 아니다.
샘플 SQL과 테스트 픽스처의 날짜 · 값은 데이터라 일회성 관찰이 아니다.

## 3. 깊이 등급

### 3.1 판정 순서

위에서부터 묻고 처음 "예"에서 멈춘다.

1. 이름 · 타입 · 바로 옆 코드만으로 다 드러나나? → **0**
2. 이 줄만 보고 고치는 사람이 틀릴 수 있나? 아니면 → **0**
3. 틀리면 이 파일 밖에서 깨지나? — 다른 트랜잭션 · 다른 복제본 · 다른 팀 · 외부 API · 배포 중 옛 코드 · 보안(남의 데이터가 새거나 바뀜) → **3**
4. 틀리면 사용자 화면의 숫자 · 문장 · 동작이 달라지나? → **2**
5. 그 밖 — 읽는 사람의 오해만 막는다(단위, 범위, null의 뜻, 반환값 0의 뜻) → **1**

"틀리면"은 **이 코드를 잘못 고쳤을 때**다. 주석이 다른 쪽(서버 · 앱 · DB)의 보장을 설명하더라도 등급은 이 코드가 깨질 때의 피해로 정한다. 예: 앱이 "서버는 남의 발화와 없는 발화를 가르지 않는다"를 적어 둔 404 분기 — 앱을 잘못 고치면 화면 문구가 틀릴 뿐 남의 데이터가 새지 않으므로 2다. 보안 3등급은 그 보장을 실제로 지키는 쪽(서버 매퍼)에 쓴다.

### 3.2 등급별로 쓰는 칸

칸에 없는 내용은 쓰지 않는다. 상한은 문장 수다.

| 등급 | 칸 (이 순서) | 상한 |
|---|---|---|
| 0 | — | 주석 없음 |
| 1 | 무엇인가(단위 · 범위 · null · 0의 뜻) | 1문장 |
| 2 | 규칙 → 어기면 사용자가 보는 것 | 2문장 |
| 3 | 보장하는 것 → 어떻게 → 깨지는 경우 → (있으면) 하지 말 것 | 4문장 |

- "어떻게"는 장치 이름까지만 쓴다(`FOR UPDATE SKIP LOCKED`, `ON CONFLICT`, 잠금 순서). 코드 줄을 문장으로 옮기지 않는다.
- 상한은 **규칙 하나당**이다. 한 주석에 규칙이 둘이면 각각의 상한을 따른다. **상한을 맞추려고 규칙을 버리지 않는다** — 줄일 것은 되풀이 · 지칭 · 히스토리 · 장치 설명이다. 규칙이 셋 이상 몰려 있으면 각 규칙을 그것을 구현한 코드 옆으로 나눈다.

### 3.3 코드 종류별 기본값

기본값보다 올리거나 내리려면 3.1의 판정이 달라야 한다.

| 종류 | 기본 | 올리는 경우 |
|---|---|---|
| 클래스 · 인터페이스 · 파일 머리 | 역할 한 문장 + 파일 안 둘 이상의 요소에 걸린 제약(각각 그 등급대로). 한 요소에만 걸린 제약은 그 요소로 내린다 | — |
| 매퍼 메서드 · SQL | 1: 스코프, 반환값 0 · null의 뜻 | 잠금 · `ON CONFLICT` · `SKIP LOCKED` · 격리 수준에 기대면 3 |
| 서비스 공개 메서드 | 2: 검사 순서, 업무 규칙 | 트랜잭션 경계 · 동시 요청 · 외부 호출이면 3 |
| 컨트롤러 메서드 | 1: 응답 코드의 뜻 | 앱과의 계약(재시도 · 멱등)이면 3 |
| DTO · record · 타입 필드 | 0 | null · 단위 · 빈 값의 뜻이 이름과 다르면 1 |
| 설정(YAML · 상수) | 1: 값의 단위와 고른 기준 | 다른 값과 맞물리면(타임아웃 · 풀 크기 · 종료 시간) 3 |
| 훅 · 쿼리 · 무효화 | 1 | 캐시 경계 · 계정 사이 누출 · 재시도면 3 |
| 화면 컴포넌트 · 표시 함수 | 2: 보이는 규칙과 그 이유 | — |
| 테스트 | 0: 이름이 시나리오를 말한다 | 이름에 없는 기대(무엇을 따로 확인하는지) · 숨은 전제(샘플 값의 출처, 순서를 고정한 방법)가 있으면 1 · 2. 테스트 이름은 바꾸지 않으므로 이름에 없는 기대를 적은 주석은 남긴다 |
| private 도우미 | 0 | 그 도우미만의 규칙이 있으면 3.1대로 |
| 구역 구분선(`// ---- 생성 ----`) | 대상 아님 | 지칭만 지운다 |
| 마이그레이션 `COMMENT ON` | 1: 상태값 · 단위 · null · 유일성의 이유 | — |

### 3.4 한 번만 쓴다

- **같은 파일 안에서만 적용한다.** 다른 파일에 같은 말이 있어도 지우지 않는다 — 파일마다 그것만 읽고 이해돼야 한다.
- 여러 메서드에 같은 제약이 걸리면 머리에 한 번 쓰고, 메서드에서는 **그 제약 문장만** 지운다. 메서드 주석에 다른 내용(그 메서드만의 규칙)이 남으면 그 부분은 둔다. 예: 잠금 순서는 매퍼 머리에, 잠금 메서드 각각은 주석 없음. `intradayAvailability`의 "저장된 평가 시점이 장중이면 닫혀도 고를 수 있다"는 그 함수만의 규칙이라 남는다.
- 같은 규칙이 서버와 앱에 다 있으면 규칙의 주인(정하는 쪽) 한 곳에 이유까지 쓰고, 다른 쪽은 "서버와 같은 순서"처럼 무엇을 맞추는지만 쓴다.
- 같은 레포 안은 `{@link}`나 이름으로 가리켜도 된다. 문서는 가리키지 않는다.

## 4. 기준 예시

이 레포의 실제 주석이다. 나쁜 예는 고친 꼴을 함께 둔다.

### 1등급

- ○ `/** 지운 행 수. 남의 행과 없는 행은 똑같이 0이다. */` — 반환값 0의 뜻 (ManualCashflowWriteMapper.deleteOwned)
- ○ `/** 열린 실행을 잠근다. 다른 트랜잭션이 잡고 있거나 이미 닫혔으면 null이다. */` — null의 뜻 (SyncMapper)
- ✗ `/** 본인 행만 찾는다. 없거나 남의 행이면 null이다. */` 뒤에 "스코프는 user_id로 건다"를 덧붙이는 것 — 그 매퍼 머리에 이미 있다(3.4)

### 2등급

- ○ `// 같은 달에 여러 건을 연달아 넣기 쉽게 계좌·유형·날짜는 남긴다.` — 규칙 + 이유 (CashflowForm)
- ○ 일간 변화 매퍼: `오늘 연동이 유효하고 두 날 모두 라인이 있는 계좌만 더한다. 한쪽에만 있는 계좌를 넣으면 그 계좌의 총자산 전체가 변화로 보인다 — 오늘 처음 잡힌 계좌는 이익으로, 해제한 계좌는 손실로.` — 규칙 → 사용자가 보는 것
- ✗ `/** 사용자가 넣는 입출금. 자산 변화의 "넣은 돈"이 여기서만 온다(스펙 §9.1). */` → `/** 사용자가 넣는 입출금. 자산 변화의 넣은 돈은 여기서만 온다 — 데이터팀이 주는 현금흐름에는 입출금이 없다. */`

### 3등급

- ○ WatchlistMapper 잠금: `같은 종목의 대상 종목 행 갱신을 한 번에 하나씩 하게 한다. 지우고 넣는 두 문장 사이에 다른 트랜잭션이 끼면 둘 다 넣다가 키가 겹친다. 잠금은 트랜잭션이 끝날 때 풀린다.` — 보장 → 깨지는 경우 → 범위, 3문장
- ○ PositionWriteMapper 머리: `잠금은 항상 날짜 → 계좌(account_id 순) 순서로 잡는다. 날짜 잠금은 실행 처리 · 계좌 확정이 공유로, 날짜 확정이 배타로 잡는다 — 확정된 날의 라인이 바뀌지 않는다.` 잠금 메서드 각각은 주석 없음(3.4). 머리의 `(설계 §7)`만 지운다
- ✗ ManualCashflowService.save — 세 문단 여섯 문장으로 상한을 넘는다. 격리 수준 이야기는 넣기 문장(매퍼 insertIfAbsent)에 몰고, 서비스는 "같은 id로 다시 받으면 새로 넣지 않고 처음 결과를 돌려준다. 이미 저장된 요청은 날짜 범위를 다시 보지 않는다 — 지금 규칙으로 거절하면 이미 들어간 입력을 앱이 실패로 안다. 넣기가 0이면 다시 찾는데, 그 사이 커밋된 행이 보여야 해서 격리 수준은 기본(READ COMMITTED)이어야 한다." 정도로 줄인다
- ✗ DeliveryMapper 머리 `(스펙 §9, 계획 ② A.9)` · `(§8.2 ④)` — 지칭만 지운다. 이유는 이미 문장에 있다

## 5. 형식

- 한국어, 현재형 평서문(`~다`). 명사로 끝내도 된다(`지운 행 수.`).
- 클래스 · 메서드 · 필드는 `/** */`, 코드 안은 `//`(SQL은 `--`). 줄 끝 주석은 상수 값의 뜻에만 쓴다(`// 'SNAP'`).
- 한 줄 120자 안팎에서 끊는다. 파일의 기존 들여쓰기를 따른다.
- 용어는 그 파일에서 이미 쓰는 말을 따른다. 용어 통일은 E단계에서 용어표를 만든 뒤 따로 한다.

## 6. 마이그레이션

- 이미 배포된 마이그레이션 파일은 고치지 않는다. 주석 한 글자도 Flyway 체크섬을 바꿔 운영 기동이 막힌다. 그 안의 문서 지칭도 그대로 둔다.
- 컬럼 설명은 새 마이그레이션 하나의 `COMMENT ON`으로 보완한다. 대상은 이름으로 뜻이 드러나지 않는 컬럼(상태값, 단위, null의 뜻, 유일성의 이유)이다. 이미 `COMMENT ON`이 있으면 두지 않는다.
- `db/external`(데이터팀 미러)은 백엔드가 소유하지 않으니 손대지 않는다.

## 7. 작업 방법

- 파일 단위로 처음부터 끝까지 읽고 적용한다. 한 파일 안에서 같은 종류의 주석은 같은 등급으로 맞춘다.
- `/* */`를 `//`로 바꾸는 것처럼 형식만 바꾸는 것도 고침(edit)이다.
- 주석이 없어서 등급보다 얕으면 채운다. 다만 1 · 0등급 자리를 새로 채우지는 않는다 — 빠져서 틀리게 고칠 수 있는 2 · 3등급만 채운다.
- 판단이 애매한 줄은 고치지 않고 보고 목록에 올린다(파일:줄, 무엇이 애매한지).
- 코드는 바꾸지 않는다. 주석만 바꾸고 테스트로 동작이 같음을 확인한다.
