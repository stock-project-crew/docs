# 산출물 계획

- 산출물은 면접관 · 리뷰어가 이 프로젝트를 빠르게 이해하고, 설계 판단을 따라 들어가 볼 수 있게 하는 독립 문서다. 이 문서는 어떤 산출물을 어떤 형식으로 만들지 정한다. 산출물 자체는 여기서 만들지 않는다.
- 산출물은 docs 레포 `yhr/deliverables/`에 둔다.
- 산출물이 기대는 문서
  - 설계서: `yhr/specs/common.md` · `portfolio.md` · `alert.md` · `data-contract.md`
  - ADR 7개: 목록은 `yhr/review/triage.md` §8
  - 용어표: `yhr/review/glossary.md`
  - 테스트 문서: `yhr/test/`

## 0. 모든 산출물이 지킬 것

| 규칙 | 뜻 |
|---|---|
| 설계서를 복사하지 않는다 | 산출물은 요약 · 그림 · 진입점이다. 규칙과 이유는 설계서 절이나 ADR로 링크한다 |
| ADR과 겹치지 않는다 | "X 대신 Y를 골랐다"는 ADR이 맡는다. 산출물은 그 결정이 시스템의 어디에 있는지 보이고 ADR로 연결한다 |
| 코드에서 나오는 것은 코드에서 뽑는다 | API 명세와 ERD는 코드 · 스키마에서 기계적으로 만들고, 다시 돌리면 갱신되게 한다. 손으로 옮겨 적은 사본은 코드와 갈라진다 |
| 그림은 이미지로 만든다 | 그림은 PNG · SVG로 만들어 어디에 붙여도 똑같이 보이게 한다. 원본(스크립트 · `.drawio`)을 이미지 옆에 둔다. Markdown 안의 Mermaid는 쓰지 않는다. 표가 많으면 자동 배치로 글자가 작아지고 묶음 · 위치를 정할 수 없으며, GitHub 밖에서는 그려지지 않는다 |
| 용어표의 말을 쓴다 | 화면 문구 외의 설명은 `glossary.md`의 쓸 말로 쓴다 |
| 잰 것만 잰 것으로 쓴다 | 성능 · 부하 · 잠금은 측정한 것만 수치로 적는다. 나머지는 "측정 안 함"으로 적고 고도화 과제(`yhr/review/upgrade-plan.md`)로 연결한다 |
| 시점 서술을 넣지 않는다 | 커밋 해시, 날짜별 진행, "작업 중" 같은 말을 쓰지 않는다. 파일 이름에도 날짜를 붙이지 않는다 |
| 실제 자산을 보이지 않는다 | 캡처와 예시 응답은 샘플 데이터로만 만든다. 실제 계좌번호 · 금액 · 이메일이 들어가지 않게 한다 |
| 한국어로 쓴다 | 레포를 공개할 계획이므로 공개해도 되는 내용만 담는다 |

## 1. 산출물 목록

| 산출물 | 무엇 | 형식 |
|---|---|---|
| 진입점 | 3분 안에 프로젝트를 파악하게 하는 첫 페이지, 다른 산출물 · 설계서 · ADR로 가는 문 | `README.md` |
| 사용자 여정 | 실제 앱 캡처를 여정 순서로 늘어놓고 화살표로 이은 이미지 5장 | Pillow 합성 스크립트 → PNG |
| 아키텍처 구성도 | 구성 · 데이터 흐름 · 복제본 런타임 · 배포 그림 4장 | drawio → PNG |
| ERD | 백엔드 표의 전체 컬럼과 관계 | 스키마를 읽는 스크립트 → Graphviz → SVG · PNG |
| API 명세 | 앱과 서버 사이의 계약 전체 | 서버 코드에서 생성한 OpenAPI → HTML · Markdown |

- **기능 명세서는 따로 두지 않는다.** 설계서 세 개(`common.md` · `portfolio.md` · `alert.md`)가 기능 명세다. 기능 목록과 각 기능의 설계서 진입점은 README의 표 하나로 보인다.
- **시나리오 문서는 따로 두지 않는다.** 시험용 시나리오(전제 · 절차 · 판정)는 테스트 설계(`yhr/test/`)에 있다. 읽는 사람을 위한 흐름은 사용자 여정 이미지가 보인다.
- **트러블슈팅 글과 회고는 산출물에 넣지 않는다.** 회고 단계에서 따로 정한다.

폴더 구성:

```
yhr/deliverables/
├─ README.md
├─ journeys.md            여정 이미지 5장 + 장마다 설계서 · ADR 링크
├─ journeys/              여정 이미지(생성물)
├─ screens/               원본 캡처
├─ architecture.md        구성도 4장 + 그림마다 설명 · 링크
├─ architecture/          .drawio 원본 + PNG
├─ erd.md                 ERD 이미지 + 표마다 한 줄 설명 · 링크
├─ erd/                   ERD 이미지(생성물)
├─ api.md                 생성한 Markdown 명세
├─ api/                   openapi.json(원본) · index.html(Redoc)
└─ src/                   생성 스크립트: journeys.py · erd.py · api.sh(OpenAPI → HTML · Markdown). 실행법은 각 파일 머리말
```

## 2. 진입점 — `README.md`

- **목적**: 면접관이 3분 안에 "무엇을 만들었고, 무엇이 어려웠고, 어디를 보면 되나"를 알게 한다.
- **담는 것**(위에서 아래로)
  1. 한 문단 소개: 무엇을 만들었나(포트폴리오 종합 관리와 매수·매도 타이밍 알림), 누구를 위한 앱인가(장기 투자자). 출시용이 아니라 역량 강화가 목적인 3인 프로젝트라는 것과 내가 맡은 범위도 적는다
  2. 대표 이미지 두 장: 여정 하나, 아키텍처 그림 1
  3. 기능 한눈에: 기능 → 화면 → 핵심 규칙 한 줄 → 설계서 절 링크
  4. 핵심 설계 판단 3개: 리더 없는 다중 복제본, 배포 중 스키마 호환, 조회 성능. ADR마다 두 줄과 링크를 단다. 나머지 ADR은 목록으로 둔다
  5. 기술 스택: Spring Boot · MyBatis · PostgreSQL 16 · 쿠버네티스 복제본 2 · ArgoCD / React Native · Expo / 데이터팀 파이프라인(외부)
  6. 하지 않은 것 · 재지 않은 것: 부하 테스트, 잠금 실측, 관측 지표. 고도화 과제로 링크한다. 면접에서 먼저 말할 수 있게 하려는 것이다
  7. 문서 지도: 산출물 · 설계서 · ADR · 테스트 문서 · 코드 레포 링크와 각 한 줄 설명
- **빼는 것**: 설치 · 실행 방법(코드 레포 README의 몫), 진행 기록
- **의존**: 다른 산출물과 ADR 파일이 있어야 완성된다. 문서 지도 같은 뼈대는 먼저 만들 수 있다
- **분량**: 100~130줄

## 3. 산출물별 계획

### 3.1 사용자 여정 — `journeys/` · `journeys.md`

- **목적**: 앱을 깔지 않고도 사용자가 무엇을 하고 무엇을 보는지 따라가게 한다. 3분 안에는 여정 이미지만 훑는다. 깊이 보는 사람은 `journeys.md`의 링크로 각 화면 뒤의 설계를 찾아간다.
- **이미지 모양**: 설계서의 와이어플로우 그림(`yhr/specs/portfolio-management/wireflow.png`)과 같은 짜임이다. 폰 틀에 넣은 캡처를 여정 순서로 놓고, 화살표 위에 누르는 것을 적고, 캡처 아래에 한 줄 설명을 단다. 와이어프레임 대신 실제 캡처를 쓴다는 점만 다르다. 여정 하나가 이미지 한 장이다.
- **여정**

  | # | 여정 | 화면 | 보여 주는 설계 |
  |---|---|---|---|
  | 1 | 처음 계좌를 연동하고 자산을 본다 | 로그인 → 요약(빈 상태) → 계좌 연동 → 한국투자증권 연동 → 계좌(동기화 카드) → 요약 | 인증 정보 보관, 동기화, 하루 한 번 수집 |
  | 2 | 어디에 쏠렸나 | 종목 → 종목(ETF 분해) → 비중(축 전환) → 종목 상세 | 그레인 하나와 가산성, ETF 분해 |
  | 3 | 번 돈인가 넣은 돈인가 | 실현손익 → 자산 변화 → 입출금 | 투자손익은 나머지, 원장 셋 |
  | 4 | 알림을 걸고 울림을 받는다 | 종목 상세 `알림 걸기` → 새 알림 단계들 → 알림 상세 → 푸시 → 울린 알림 상세 | 조건 모델, 평가, 발송 대기열 |
  | 5 | 모르면 모른다고 보인다 | 추정 등급 · 미포함 배지, 이월 안내, 인증 실패 · 수집 안내, 알림 확인 불가 | 계산할 수 없는 값을 채우지 않는다는 원칙 |

  - 여정에 들지 않는 화면(계정 시트, 인증 정보 갱신, 울린 알림 목록)은 `journeys.md` 끝에 캡처와 한 줄 설명으로 둔다. 모든 화면이 한 번은 나온다
- **`journeys.md`**: 이미지에는 링크를 걸 수 없다. 그래서 여정마다 이미지 한 장을 넣고, 그 아래 화면별로 "이 화면 뒤에 있는 것"(설계서 절 · ADR) 링크를 한 줄씩 단다. 화면 규칙은 옮기지 않는다
- **캡처**
  - 푸시 외의 화면은 Expo 웹을 브라우저에서 폰 폭으로 열어 찍는다
  - 푸시(잠금 화면 알림, 앱 안 배너)는 실기기 Expo Go에서 사용자가 찍는다
  - 데이터는 로컬 DB의 샘플 데이터다. 원천은 `back-end/src/main/resources/db/sample/`의 샘플 4개이고, 운영 DB는 쓰지 않는다
  - 샘플이 여정 5의 상태(추정 · 미포함 · 이월 · 인증 실패 · 확인 불가)를 다 만드는지 캡처 전에 확인한다. 모자라면 캡처용 샘플을 더한다(백엔드 레포 변경)
  - 원본 캡처는 `screens/<화면>.png`로 저장한다
- **생성**: `src/journeys.py`(Python + Pillow)가 여정 정의(순서 · 화살표 라벨 · 설명)와 `screens/`의 캡처를 읽어 `journeys/<번호>-<이름>.png`를 만든다. 캡처를 다시 찍으면 스크립트만 다시 돌린다
- **의존**
  - 화면 문구를 용어표에 맞춰 바꾸는 작업(`glossary.md` "E5에서 바꿀 화면 문구" 8건)이 앱 main에 들어간 뒤에 찍는다. 먼저 찍으면 다시 찍어야 한다
  - 로컬 DB · 백엔드 · Expo 웹 기동, 푸시 발송(로컬 서버가 Expo 푸시 서비스를 부름)이 필요하다
- **분량**: 이미지 5장 + 캡처 25장 안팎, `journeys.md` 120~160줄

### 3.2 아키텍처 구성도 — `architecture/` · `architecture.md`

- **목적**: 시스템이 어떤 조각으로 되어 있고, 데이터가 어떻게 흘러 화면과 푸시가 되는지 보인다. 그림 1은 3분 안에 볼 그림이다. 그림 2~4는 "두 대가 동시에 돌면?" "배포 중에는?" 같은 질문을 받을 때 펼친다.
- **그림**

  | # | 그림 | 보이는 것 | 링크 |
  |---|---|---|---|
  | 1 | 구성과 소유 경계 | 앱 · API 서버 · DB(`app`/`data` 스키마) · 데이터팀 파이프라인 · AWS SSM · Expo 푸시. 어느 팀이 무엇을 쓰고 읽는지(화살표 방향 = 권한) | `common.md` §2 · §6, `data-contract.md` §2 · §7 |
  | 2 | 데이터 흐름(계좌 연동부터 푸시까지) | 연동 → `collection_run` 요청 → 데이터팀 수집 → `cln_*` → 보유 스냅샷 생성 5단계 → 라인 · `snapshot_run` → 알림 평가 → 울림 기록 → 발송 대기열 → Expo | `portfolio.md` §5 · §6, `alert.md` §4~6 |
  | 3 | 복제본 2대의 런타임 | 주기 작업 6개 × 복제본 2. 작업마다 중복을 막는 수단(조건부 UPDATE · UNIQUE · SKIP LOCKED와 임대 · advisory 잠금 · 처리 기록 테이블) | `common.md` §7, ADR 리더 없는 다중 복제본 · 스냅샷 파이프라인 · 발송 대기열 |
  | 4 | 배포 | main 푸시 → CI 테스트 → 이미지(커밋 해시 태그) → 매니페스트 커밋 → ArgoCD 롤링 → 기동 시 Flyway. 롤링 중 옛 파드와 새 스키마가 함께 도는 구간을 표시 | `common.md` §2, ADR 배포 중 스키마 호환 |

- **`architecture.md`**: 그림마다 이미지 한 장, 설명 두세 줄, 링크를 둔다
- **빼는 것**: 클래스 · 패키지 다이어그램, 쿠버네티스 매니페스트 세부, 쿼리
- **설계서와의 차이**: `common.md` §2에 구성 그림이 하나 있다. 그림 1은 거기에 소유 경계와 권한 방향을 더한 것이다. 그림 2~4는 설계서에 없다
- **원천**: 위 설계서 절. 사실은 코드(`*Jobs` 스케줄 설정, CI 워크플로, 매니페스트)와 대조한다
- **생성**: `architecture/<번호>-<이름>.drawio`를 쓰고 drawio 데스크톱 CLI로 PNG를 내보낸다. 그림이 넷뿐이고 거의 바뀌지 않으므로, 자동 배치보다 손으로 배치하는 편이 설명이 잘 된다. 원본이 있어 diagrams.net에서 고칠 수 있다
- **의존**: 링크할 설계서 절 번호와 낱말이 확정돼야 한다. 네 설계서가 docs main에 들어간 뒤에 그린다
- **분량**: 그림 4장, `architecture.md` 40~60줄

### 3.3 ERD — `erd/` · `erd.md`

- **목적**: 백엔드 표의 전체 컬럼과 관계를 보인다. 설계서는 표를 역할 · 키 · 수명 단위로만 적으므로, 컬럼 목록은 ERD에만 있다. 깊이 보는 사람이 그레인과 멱등 키가 표 구조에 어떻게 나타나는지 확인하는 자리다.
- **그림**: 기능별 세 장
  1. 포트폴리오: `account` · `position_line` · `position_build` · `snapshot_run` · `position_basis` · `basis_build` · `realized_pnl_line` · `manual_cashflow` · `sync_run` · `sync_run_account`
  2. 알림: `alert` · `alert_state` · `alert_event` · `alert_delivery` · `push_device` · `alert_watchlist`
  3. 로그인: `app_user`와 세션 표
  - 각 표: 전체 컬럼과 타입, PK · FK · UNIQUE 표시
  - FK 없이 값으로만 가리키는 관계(데이터팀 표의 종목 id, `sync_run_account`의 수집 실행 id)는 점선으로 그린다
  - 데이터팀 표(`data` 스키마)는 이름만 있는 상자로 그린다
- **`erd.md`**: 그림 세 장과 표마다 한 줄 설명, 설계서 §7 링크를 둔다. 데이터팀 표는 `data-contract.md`로 링크한다
- **빼는 것**: 데이터팀 표의 컬럼(계약 문서가 맡는다), 인덱스, 미러 표, 표의 역할 · 수명 서술(설계서가 맡는다)
- **생성**: `src/erd.py`
  1. 일회용 Postgres 컨테이너에 백엔드 마이그레이션(`db/migration/`)을 적용한다
  2. 카탈로그(`information_schema` · `pg_catalog`)에서 컬럼 · 타입 · PK · FK · UNIQUE · 컬럼 설명을 읽는다
  3. 기능별로 묶은 Graphviz DOT를 쓴다
  4. `erd/<번호>-<이름>.svg` · `.png`를 만든다
  - FK가 없는 관계는 카탈로그에 나오지 않는다. 스크립트 안에 짧은 목록으로 둔다(손으로 고치는 유일한 부분)
  - 표를 어느 그림에 넣을지도 스크립트 안의 목록이 정한다. 목록에 없는 새 표가 생기면 스크립트가 실패해서 알린다
- **의존**: 스키마 변경은 끝났다. 지금 만들 수 있다
- **분량**: 그림 3장, `erd.md` 40~60줄

### 3.4 API 명세 — `api/` · `api.md`

- **목적**: 앱과 서버 사이의 계약 전체를 한곳에서 보인다. 3분 안에는 엔드포인트 목록을, 깊이 보는 사람은 요청 · 응답 모양과 예시를 본다.
- **담는 것**: 엔드포인트 전부(메서드 · 경로 · 파라미터 · 요청 · 응답 · 오류 코드), 인증 방식(Bearer 접근 토큰), 응답 봉투, 오류 모양, 대표 예시
- **생성**: 손으로 쓰지 않는다. 모두 서버 코드에서 나온다
  1. 백엔드에 springdoc(Spring용 OpenAPI 생성 라이브러리)을 넣는다. 컨트롤러와 DTO에서 OpenAPI 명세가 만들어진다
  2. 백엔드 테스트 하나가 명세를 받아 `openapi.json` 파일로 쓴다. 이 파일을 docs 레포 `api/openapi.json`으로 복사한다
  3. 변환 도구로 `api/index.html`(Redoc, 레포를 공개한 뒤 GitHub Pages로 연다)과 `api.md`(GitHub에서 바로 읽는 Markdown)를 만든다. `src/api.sh`가 이 단계를 한 번에 한다
- **생성기만으로는 빠지는 것과 대응**(백엔드 코드에 작게 더한다)
  - 개요 · 인증 · 봉투 · 오류 규칙 설명: OpenAPI 정보 설정(`info.description`, 보안 스킴)에 적는다. 그러면 이 설명도 생성물에 들어간다
  - 보유 화면 행의 지표 칸: `@JsonAnyGetter`로 펼쳐지는 칸이라 생성기는 "아무 속성"으로만 적는다. 지표 키 목록을 카탈로그 코드에서 읽어 명세에 넣는 설정을 더한다
  - notice 코드: 응답에서는 문자열이다. `NoticeCode` enum의 값 목록을 명세에 넣는다
  - snake_case: 서버는 Jackson 전역 SNAKE_CASE를 쓴다. 생성 명세에 이것이 반영되는지 확인하고, 안 되면 설정을 더한다
  - 예시: 명세를 쓰는 테스트가 골든 응답(`back-end/src/test/resources/golden/*.json`, 9개)을 해당 엔드포인트의 예시로 붙인다. 테스트가 검증하는 응답이라 예시가 코드와 어긋나지 않는다
- **설계서와의 차이**: 설계서는 기능별 규칙과 필드의 뜻을, 명세는 전체 목록과 모양을 맡는다. 필드 뜻은 설계서 §8로 링크한다(정보 설정의 설명에 링크를 둔다)
- **의존**
  - 엔드포인트 변경은 끝났다
  - 명세를 쓰는 테스트는 기존 백엔드 테스트처럼 서버 전체를 띄우는 테스트라 테스트 DB를 쓴다. 공유 테스트 DB와 겹치지 않게 전용 테스트 DB를 쓴다
  - 백엔드 main 푸시는 곧 운영 배포다
  - springdoc은 테스트 의존성으로만 넣는다(§6)
- **분량**: 생성물이라 분량을 정하지 않는다. 백엔드 변경은 의존성, 설정 클래스 하나, 테스트 하나

## 4. 작성 순서

| 순서 | 산출물 | 시작 조건 | 이유 |
|---|---|---|---|
| 1 | ERD | 지금 | 스키마가 끝났고 설계서 확정을 기다릴 것이 없다 |
| 2 | API 명세 | 지금 | 엔드포인트가 끝났다. 링크는 설계서 파일 경로가 정해져 있어 걸 수 있다 |
| 3 | README 뼈대 | 지금 | 문서 지도와 목차를 먼저 세우면 나머지가 걸릴 자리가 정해진다 |
| 4 | 아키텍처 구성도 | 네 설계서가 docs main에 들어간 뒤 | 링크할 절 번호와 낱말이 확정돼야 한다 |
| 5 | 사용자 여정 | 화면 문구 변경 8건이 앱 main에 들어간 뒤 | 문구가 바뀌면 다시 찍어야 한다 |
| 6 | README 완성 | ADR 파일이 생긴 뒤 | 대표 ADR 링크와 대표 이미지가 필요하다 |
| 7 | 점검 | 회고 리뷰 말단의 현행화 때 | §7 |

## 5. 승인받은 일

아래 일은 사용자 승인을 받았다.

| 일 | 무엇 때문에 |
|---|---|
| Pillow 설치(프로젝트 밖 가상환경) | 여정 이미지 합성 |
| Graphviz 설치(Homebrew) | ERD |
| drawio 데스크톱 설치(Homebrew) | 구성도 PNG 내보내기 |
| 변환 CLI 실행(npx, 설치 없이) | OpenAPI → HTML · Markdown |
| 일회용 Postgres 컨테이너 기동, 마이그레이션 · 샘플 SQL 적재 | ERD, 캡처용 로컬 DB |
| 백엔드 로컬 기동, Expo 웹 기동 | 캡처 |
| 로컬 서버의 Expo 푸시 호출 | 푸시 캡처 |
| 캡처용 샘플 추가(백엔드 레포) | 여정 5의 상태가 샘플로 안 만들어질 때 |
| springdoc 테스트 의존성 추가와 설정 · 테스트 코드(백엔드 레포) | API 명세 |
| 명세를 쓰는 테스트의 전용 테스트 DB 사용 | API 명세 |

클러스터와 운영 DB는 쓰지 않는다. 백엔드 커밋 · 푸시는 따로 확인받는다.

## 6. springdoc을 넣는 자리

springdoc은 테스트 의존성으로만 넣는다. 테스트를 돌릴 때만 명세 파일이 생기고, 운영 서버와 운영 이미지는 바뀌지 않는다. 브라우저에서 API를 눌러 보는 Swagger UI 화면은 두지 않는다. 산출물에 필요한 것은 명세 파일이다.

## 7. 말단 점검 목록

- ERD: `src/erd.py`를 다시 돌린다
- API: 명세를 쓰는 테스트를 다시 돌리고 HTML · Markdown을 다시 만든다
- 여정: 그 뒤에 바뀐 화면 문구가 있으면 해당 캡처를 다시 찍고 `src/journeys.py`를 다시 돌린다
- 구성도: 주기 작업 · 배포 흐름이 바뀌었으면 `.drawio`를 고치고 다시 내보낸다
- 링크: 설계서 · ADR · 테스트 문서 링크가 모두 열리는지 확인한다
- 개인 정보: 산출물 전체에서 계좌번호 · 이메일 · 실제 금액을 찾는다
- "측정 안 함" 문장: 고도화 과제를 실습했으면 수치로 바꾼다
